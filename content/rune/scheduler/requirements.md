# Rune 共享算力调度原始需求

本文只描述使用方要解决的问题、业务规则和产品边界，不预设 Queue、PodGroup、Volcano 或其他调度后端对象。用户如何操作见 [使用方式](usage.md)，产品抽象和后端映射见 [设计](design.md)。

## 背景

`rune` 已经通过 `Instance`、Helm chart、`Flavor`、`ResourcePool` 和租户配额管理工作负载与计算资源。随着 GPU、NPU、RDMA、NVMe 等昂贵或稀缺资源进入统一管理，使用方遇到以下问题：

- 多个租户共享集群时，已经购买或申请的资源缺少明确保障。
- 租户暂时不用资源时，集群存在空闲，但其他租户的任务仍在等待。
- 保障资源重新被需要时，平台缺少安全、可审计的收回机制。
- 紧急在线业务和普通实验任务竞争资源时，平台无法表达业务重要性。
- 分布式训练和 HPC 任务只启动部分副本时无法工作，还会浪费资源。
- 用户选择 GPU/NPU 数量后，仍可能因为 NUMA、PCIe、RDMA 或网络拓扑不匹配而无法运行。
- Instance 长时间等待或被中断时，用户不知道原因，也不知道下一步如何处理。

调度建设的目标是增强现有产品链路，不新增一套独立的 workload 入口。

## 目标

### 资源保障

- 平台能够表达租户已经获得的最低保障资源和最大可用资源。
- 租户能够知道自己当前使用了多少、临时借用了多少、还有多少任务在等待。
- 资源不足时能够区分租户权益不足、集群整体不足和设备条件不满足。

### 提高利用率

- 资源拥有方暂时不用时，平台可以按策略把空闲资源临时提供给其他任务。
- 临时使用不能破坏资源拥有方的保障承诺。
- 临时任务必须清楚知道自己可能被中断，以及中断后的恢复方式。

### 表达业务重要性

- 使用方能够表达任务是普通、重要还是关键，而不需要理解调度器数字优先级。
- 业务重要性可以影响等待顺序。
- 是否允许中断其他任务必须由独立策略控制，不能仅因为任务重要就自动获得中断权限。

### 支持协同启动

- 需要多个副本共同工作的任务，可以在所需资源全部就绪后一起启动。
- 普通服务仍可以逐个副本启动。
- 系统不能自行猜测任意 Helm chart 中哪些 Pod 属于同一次协同启动。

### 满足设备与放置要求

- 用户先选择任务运行的资源池；不了解差异时可以保留系统推荐的默认资源池。
- 选择资源池后，只展示该资源池可以提供且用户有权使用的业务规格。
- 用户通过业务规格选择设备类型、数量和能力，不需要了解节点硬件细节。
- 系统能够表达同机、同 NUMA、同 PCIe、同交换域、同 rack 等要求或偏好。
- 设备和拓扑要求不能绕过租户权益、资源范围和配额约束。

### 提供可行动的状态解释

- 用户能够知道 Instance 是等待、准备启动、运行、完成、失败还是被中断。
- 等待原因应转换为用户能理解的资源缺口和限制条件。
- 状态解释应给出可行的下一步，而不是只展示底层 Kubernetes Event。

## 用户和原始诉求

### 平台管理员

平台管理员希望：

- 配置全局资源共享和保护原则。
- 决定是否允许临时借用、资源收回和任务中断。
- 保护在线服务、关键任务和未达到最短运行时间的任务。
- 查看租户资源承诺、实际使用、借用关系和等待情况。
- 在执行可能中断任务的操作前看到影响范围。
- 对资源收回和任务中断进行审计。
- 升级或替换调度后端时，不改变普通用户的使用方式。

### 租户管理员

租户管理员希望：

- 查看本租户的保障资源、最大可用资源和当前使用量。
- 决定哪些项目或用户可以使用某组资源权益。
- 决定空闲资源是否可以临时借出。
- 定义本租户允许的运行保障等级和中断规则。
- 查看正在运行、等待、临时借用和被中断的任务。
- 判断应该调整任务还是申请更多资源。

### 普通使用者

普通使用者希望：

- 在 Chart 每个声明 Flavor 资源选择的配置位置，先按资源池筛选，再选择具体 Flavor。
- 资源池是 Flavor 选择器中的筛选步骤，并提供默认值；不是新增的 Instance 或 values 字段。
- 多个 Flavor 配置位置彼此独立，因此可以选到不同 ResourcePool 中的 Flavor。
- 用户仍然只提交 Flavor ID，系统校验后注入服务端控制的 Flavor 数据，不要求用户选择底层队列。
- 用业务语言表达任务重要性，不填写数字优先级。
- 声明任务是否允许中断、是否可以使用临时资源，以及中断后的恢复方式。
- 对分布式任务选择或继承“全部资源就绪后一起启动”的应用默认值。
- 在详情页看到等待或中断的明确原因和处理建议。

### Chart 作者

Chart 作者希望：

- 明确哪些 values 字段由平台校验和回填。
- 决定应用是否需要协同启动以及如何生成对应 workload 对象。
- 使用平台提供的资源规格、资源权益和运行策略，而不是依赖 Rune 猜测渲染结果。
- 旧 chart 不声明新能力时保持原有行为。

## 核心使用场景

### 租户资源保障

A 租户获得 128 张 GPU 的保障，B 租户获得 64 张 GPU 的保障。平台需要持续展示双方的保障量、最大可用量、实际使用量和等待需求。当某个租户无法启动任务时，系统应说明是权益已经用尽，还是集群物理资源不足。

### 空闲资源临时共享

A 租户只使用了部分保障资源，B 租户有可中断的实验任务。平台可以让 B 临时使用空闲资源；当 A 再次需要自己的保障资源时，系统按保护规则收回资源。B 的用户应事先知道任务使用的是临时资源，并在中断后看到恢复状态。

### 关键业务优先获得资源

在线推理紧急扩容与普通实验任务同时等待。系统根据管理员定义的运行保障策略调整等待顺序。如果必须中断已有任务，只有明确允许被中断且不受保护的任务才能成为候选。

### 分布式任务协同启动

训练任务需要 16 个 worker 同时工作。只有 8 个 worker 的资源可用时，任务保持等待，不应先启动 8 个并长期占用资源。该行为由应用模板明确声明，而不是 Rune 从 Pod 数量自动推导。

### 利用零散空闲资源

一个大型任务正在等待完整设备组合，集群同时存在暂时无法组成该组合的零散资源。明确允许中断的短任务可以先运行，但不能破坏大型任务所需的关键资源组合。

### 复杂设备和拓扑

用户选择“H100 × 8 高速互联”规格。平台负责保证卡数、型号、同机互联、RDMA 和拓扑条件；用户不需要逐项配置节点标签。当无法满足时，状态应区分数量不足、拓扑不满足、设备异常和资源范围不匹配。

### 缓存复用

推理任务可以优先放到已经存在模型或数据缓存的节点，以减少冷启动。缓存默认是偏好而不是硬要求；缓存节点资源不足时仍可使用其他满足资源条件的节点。缓存偏好不能绕过 Flavor、资源范围和租户权益。

### 调度状态解释

Instance 等待时，详情页应回答：

- 还缺什么资源。
- 哪些条件限制了候选节点。
- 是否在等待同组副本全部就绪。
- 是否正在使用或等待临时资源。
- 用户可以继续等待、降规格、减少副本、选择其他资源池，还是联系管理员。

## 用户可见概念判断

### 资源池

资源池是 Flavor 选择器中的一级筛选，表示当前资源配置将使用哪类算力或哪个资源范围。界面需要提供默认资源池，并解释不同资源池的硬件类型、用途、位置、成本或服务能力差异。

选择资源池后，当前选择器的 Flavor 列表必须按资源池过滤。切换资源池时，当前已经选择但不属于新资源池的 Flavor 必须清空并要求重新选择；其他 `x-resource-enum: flavors` 配置位置不受影响。

### 资源权益

资源权益说明租户在某个资源池中有多少保障和最大可用资源。系统根据 tenant + ResourcePool 自动匹配资源权益，普通用户默认不需要选择。

只有同一租户在同一资源池内确实存在多份不同预算、项目权限或服务保障时，才进一步让用户选择权益账户。用户始终不需要理解底层调度队列。

### 运行保障

用户选择业务等级，例如“尽力运行、标准、关键业务”。数字优先级和具体排序策略由管理员维护。运行保障只影响排序和保护条件，不自动代表可以中断其他任务。

### 可中断与临时资源

用户可以声明任务是否允许中断、是否可以使用临时资源以及中断后的恢复方式。界面不要求用户理解抢占、回收或回填算法。

### 协同启动

用户看到的是“全部副本资源就绪后一起启动”。PodGroup、gang 等概念只出现在技术详情中。

### 设备拓扑和缓存

普通用户先选择 ResourcePool，再选择 Flavor。拓扑条件默认由 Flavor 或应用模板管理，缓存默认由应用自动优化；专家模式可以只读展示具体限制。

## 产品约束

- 不新增独立训练任务入口，继续使用 Instance。
- 不要求普通用户直接操作调度器 CRD。
- 不从任意 Helm chart 自动推导协同启动边界。
- 不把资源权益、运行保障或调度后端放入 Flavor。
- 不允许用户通过 values 伪造平台回填的资源和保护策略。
- 不声明调度扩展的旧 chart 行为不变。
- 默认不允许跨租户中断或资源收回。
- 所有会中断运行中任务的行为都必须可解释、可审计。

## 第一阶段范围

第一阶段建立最小产品闭环：

- 集群或租户具有明确的默认资源池。
- 每个 `x-resource-enum: flavors` 选择器都可以按资源池筛选；不操作时使用默认资源池。
- 各选择器的 Flavor 列表按当前筛选的资源池过滤。
- 同一 Instance 中多个 Flavor 配置位置可以选择不同 ResourcePool 中的规格。
- 平台能够为租户在每个有配额的资源池中建立默认资源权益。
- 资源上限和保障量来自现有租户配额口径。
- 普通用户创建 Instance 时不需要手工选择底层队列。
- Chart 可以显式接收平台回填的资源权益信息。
- 示例分布式 Chart 可以声明协同启动。
- Instance 详情可以展示基础等待状态、资源缺口和 Kubernetes 事件摘要。
- 默认不启用跨租户任务中断和资源收回。
- 旧 Flavor 和旧 Chart 保持兼容。

第一阶段不要求：

- 同一资源池配置多份资源权益。
- 普通用户配置数字优先级。
- 自动推导 PodGroup。
- 完整 DRA/CDI 运行链路。
- 缓存感知调度插件。
- 插件级节点过滤、打分和 victim 解释。
- 接入多个调度后端。

## 后续能力

- 同一资源池内多权益账户及项目授权。
- 运行保障等级和显式中断策略。
- 临时资源使用和最长运行时间。
- DRA/CDI 设备申请、分配和状态展示。
- NUMA、PCIe、网络域等拓扑能力。
- 缓存感知调度。
- 完整调度解释、影响预估和审计视图。
- 更多调度后端。

## 验收标准

第一阶段从使用方验收：

- 管理员可以看到租户资源保障、最大可用量和当前使用情况。
- 租户在各资源池中的默认资源权益能随对应配额变化更新。
- 每个 Flavor 选择器先展示默认资源池，再展示该资源池中的 Flavor。
- 某个选择器切换资源池后只能选择新资源池中的 Flavor，不影响其他 Flavor 选择器。
- 用户提交的数据仍然只有 Flavor ID；服务端按当前 Flavor 注入 resources、nodeSelector 和 tolerations，新增设备字段需要扩展同一注入机制。
- 分布式示例应用能够等待全部所需副本资源就绪后再启动。
- Instance 等待时能展示基础原因和处理建议。
- 被调度后端拒绝或资源不足时，不只展示底层错误码。
- 旧 Chart 不声明新能力时行为不变。
- 默认配置不会触发跨租户中断和资源收回。
