# IAM

本目录描述晓石 AI 平台的统一身份与访问管理能力。IAM 是用户、组织、成员、角色与授权关系的权威来源；Moha、Apps、Rune 和 AIRouter 都是 IAM 能力的消费者，不应各自维护另一套可独立修改的身份主数据。

## 产品功能

| 功能 | 用户价值 |
| ---- | -------- |
| 认证 | 通过登录、Session、Token/API Key、OIDC/OAuth 和 MFA 建立可信身份 |
| 组织治理 | 管理组织、成员、用户组和租户上下文 |
| 授权 | 通过系统级与组织级 RBAC 控制资源动作 |
| 平台集成 | 通过 REST、内部 Client 和认证/授权/审计 Webhook 复用身份能力 |
| 安全运营 | 记录审计，管理头像、静态资源和用户配置等公共能力 |

## 现状判断

IAM 已经是可独立部署的完整平台服务，而不只是 Rune 的认证插件。当前实现覆盖 REST API、认证授权 Webhook、Go HTTP Client、组织与 RBAC、审计、头像、静态资源和用户配置，并通过 Casdoor、etcd 与 MongoDB 分别承载不同状态。

当前架构需要重点治理的不是“是否有 IAM”，而是以下边界：

- API Server、Moha、Apps 和 AIRouter 应通过 IAM API、Webhook 或受支持 Client 集成，不能直接读取 IAM 存储。
- 认证失败、授权拒绝和 IAM 依赖不可用是三种不同结果，调用方不能把查询失败解释为无权限或对象不存在。
- 内部路由和可信身份头必须由网络边界保护，不能因为标记为 internal 就默认安全。
- 审计写入具有独立失败语义；业务请求是否因审计不可用而失败，需要按合规等级明确配置和验证。
- IAM 仓库中的部分历史架构材料与当前 README、代码已有差异，平台文档以本文标注的实现基线和源码为准。

## 关注点

- 用户如何登录并形成可验证身份。
- 平台级与组织级权限如何计算。
- 组织、成员、角色和资源范围由谁持有。
- Webhook 和服务间 Client 如何复用 IAM 能力。
- etcd、MongoDB 与 Casdoor 分别保存什么状态。
- IAM 不可用时各条平台链路如何失败或降级。
