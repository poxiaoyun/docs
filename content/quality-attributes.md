# 质量属性与架构验收

质量属性不是抽象口号。本文使用“刺激、响应、证据”描述开发和测试能够验证的架构要求。具体数值目标应由部署环境的 SLO 和容量基线补充。

## 优先级

| 优先级 | 质量属性         | 原因                                                   |
| ------ | ---------------- | ------------------------------------------------------ |
| 最高   | 多租户隔离与安全 | 平台集中持有身份、资产和多集群访问能力                 |
| 最高   | 状态一致性与幂等 | API、Controller 和外部系统之间没有统一事务             |
| 高     | 可用性与故障隔离 | IAM、Moha、AIRouter、Kubernetes 等组件具有独立故障边界 |
| 高     | 可观测与可诊断   | 一次业务操作跨越多个组件和状态来源                     |
| 高     | 性能与伸缩       | 推理调用、控制面 API 和后台调谐的负载模型不同          |
| 高     | 资源效率与公平性 | 稀缺加速资源必须兼顾租户保障、共享利用和业务顺序       |
| 中     | 可维护与可演化   | 多仓库和领域边界需要长期保持一致                       |

## 多租户隔离

| 场景                               | 预期响应                                     | 验证证据                         |
| ---------------------------------- | -------------------------------------------- | -------------------------------- |
| 用户构造其他租户的对象路径         | 在访问存储或集群前拒绝请求                   | 403、授权日志和审计记录          |
| 用户修改 Cluster 或 Workspace 标识 | 服务端重新计算范围，不信任前端隐式边界       | API 测试与资源查询记录           |
| Controller 处理对象                | 只访问对象声明并已验证的集群和 Namespace     | reconcile 日志、Kubernetes audit |
| AIRouter 处理模型请求              | Token、tenant、workspace 和 channel 范围一致 | 网关审计和拒绝原因               |

测试应覆盖同名对象跨租户、列表过滤、直接对象访问、代理路径和缓存命中场景，防止只在页面层隔离。

## 安全

- API Server 是外部受保护请求的信任入口；Cloud 的 request-header 认证只接受受控网络来源。
- kubeconfig、上游模型凭据、Registry 凭据和 Token 不得出现在普通日志、错误正文或 status 中。
- 公开路由必须逐项声明，不能通过路径前缀意外扩大公开范围。
- 终端、WebSocket 和 service proxy 同时校验用户权限、目标集群、Namespace 和目标资源。
- [KMS](kms/design.md)当前提供数据密钥生成与解密，不应被当作通用 Secret 持久化系统。
- Apps 的受限代理不能读取普通 Secret；Installer 默认拒绝跨 Namespace 和 cluster-scoped 资源；kube-ssh 的 Access、Pod 范围和会话必须可审计。

安全变更至少需要授权单元测试、跨租户集成测试、敏感字段日志检查和入口绕过检查。

## 一致性与幂等

### 质量场景

当 API 保存 spec 后进程退出、Controller 重启、watch 重放或外部 API 超时时，系统再次处理同一 generation，最终只存在一个逻辑外部资源，status 能反映最新观察结果。

### 实现要求

- 外部资源名称或请求使用稳定幂等键。
- Controller 区分 spec generation 与 observed generation。
- 删除依赖 finalizer 完成外部清理，并允许安全重试。
- 不使用内存标志作为唯一完成证据。
- 跨组件调用超时后先查询外部事实，再决定是否重试创建。
- cache 是可重建投影；cache 未同步不能返回确定性的空结果。

## 可用性与故障隔离

| 故障                          | 允许继续工作的能力                         | 必须明确失败的能力           |
| ----------------------------- | ------------------------------------------ | ---------------------------- |
| IAM 不可用                    | 已建立的后台调谐可按本地可信状态继续时继续 | 新的受保护入口认证、成员查询 |
| Moha 不可用                   | 不依赖新资产下载的运行中工作负载           | 资产浏览、发布和新资产拉取   |
| AIRouter Control Plane 不可用 | 数据面缓存仍有效时的模型调用               | 渠道和策略管理、缓存未命中   |
| AIRouter Data Plane 不可用    | Rune 工作负载管理                          | 统一模型调用                 |
| 单个被管集群不可用            | 其他集群和中心管理能力                     | 该集群资源操作和实时查询     |
| Apps 不可用                   | 已安装工作负载与 Installer 后台调谐        | 产品浏览和新的实例操作       |
| Installer 不可用              | 已运行工作负载、Apps 产品浏览              | 新安装、升级和安装状态推进   |
| ClusterResourceQuota 不可用   | 不增加资源消耗的已运行工作负载             | 无法可靠执行的新配额准入     |
| kube-ssh 不可用               | 应用运行和其他 Rune 诊断接口               | SSH/SFTP/端口转发访问        |
| 观测后端不可用                | 工作负载调谐                               | 对应指标、日志或告警查询     |

降级必须显式：响应和 status 应指出依赖组件及失败阶段，不能用空数据伪装成功。

## 性能与伸缩

平台存在三类不同负载：同步控制面 API、异步 Controller 调谐和高频模型数据面。它们应分别容量规划和扩缩容。

- API 性能关注认证授权、列表过滤、跨集群查询和代理超时。
- Controller 性能关注队列深度、单次 reconcile 时长、失败重试和 cache 同步。
- AIRouter 数据面关注请求吞吐、首 Token 延迟、流式连接、RPM/TPM 判断和上游延迟。
- 大模型与数据集内容不应经过 Rune Cloud API 内存中转。
- 列表和观测查询必须具备范围限制、分页或时间窗口。

## 资源效率与公平性

资源利用率不能只看集群平均值，还应结合保障、借用和排队判断。最低验证指标包括：

- 按 Cluster、ResourcePool、租户和设备类型统计可分配量、已分配量和实际使用量。
- 按租户和资源池统计保障量、最大量、临时借用量、等待需求和等待时长。
- 识别“存在空闲资源但仍有任务等待”，并归因到权益、配额、拓扑、设备条件或协同启动约束。
- 统计分布式任务部分启动造成的无效占用，以及临时任务被中断后的恢复结果。
- 证明高优先级或资源收回行为受显式策略约束，不会无限期饿死普通租户或突破最大资源范围。

在资源权益和动态共享尚未完全实现时，这些指标首先用于暴露当前分配问题，不能把观测能力等同于调度策略已经闭环。

## 可观测与可诊断

每条关键链路应携带或生成可关联标识，并记录以下最小上下文：组件、操作、用户或服务身份、租户、工作空间、资源引用、结果和耗时。日志不得以牺牲敏感数据安全换取诊断便利。

| 层次       | 主要证据                                              |
| ---------- | ----------------------------------------------------- |
| 入口       | HTTP 状态、认证授权结果、审计、request/trace ID       |
| Cloud API  | 对象键、校验阶段、存储结果、外部依赖错误              |
| Apps       | ProductVersion、Instance、目标 Workspace 和请求结果   |
| Installer  | generation、artifact digest、安装阶段和受管资源       |
| Controller | generation、reconcile 结果、重试、condition           |
| Kubernetes | ResourceVersion、Event、Pod condition、调度和容器状态 |
| Moha       | 仓库、revision、LFS/Registry 操作和权限结果           |
| AIRouter   | token/channel 范围、路由、审核、限流、上游和 usage    |

## 架构验收清单

- 权威状态、写入者和可重建投影已明确。
- 同步成功与异步完成的语义没有混淆。
- 失败、超时、重试和删除路径均有测试。
- 跨租户和绕过统一入口的访问被覆盖。
- 外部依赖失败具有稳定错误分类和关联证据。
- 新链路没有让高频数据面依赖控制面数据库。
- 文档、OpenAPI、指标和告警随行为变化同步更新。
