# KMS 需求

## 背景

平台服务可能需要加密 Registry 凭据、外部服务凭据或其他敏感业务数据。调用方不应使用一个长期明文密钥直接加密全部数据，也不应把业务密文交给密钥服务持久化。

## 用户与集成方问题

### 调用方需要随机数据密钥

每个数据对象或加密范围应能够获得独立的随机数据密钥，减少长期复用同一数据密钥的影响范围。

### 调用方需要保存可恢复的密钥材料

KMS 应同时返回一次性使用的明文数据密钥和可持久化的加密数据密钥。调用方使用明文密钥完成业务数据加密后应尽快释放，只保存业务密文和加密数据密钥。

### 平台需要支持不同密码算法

当前实现需要支持 AES-256-GCM 和 SM4-GCM，并让算法作为加密数据契约的一部分保存，防止解密时产生歧义。

### 密钥能力需要独立安全边界

生成和解密接口必须由可信网络、统一入口或服务身份保护。错误响应和日志不得包含口令、明文数据密钥或完整加密数据密钥。

## 功能要求

- 生成使用密码学安全随机源的数据密钥。
- 为每次 GCM 加密生成唯一随机 nonce，并与加密数据密钥一起编码。
- 对错误算法、非法 Base64、损坏密文和错误口令返回可识别错误。
- API 契约明确算法、编码、密钥长度以及调用方保存责任。
- 服务无业务状态，可水平扩展；相同主密钥上下文下的实例应能够相互解密。

## 质量要求

- 只有被授权的内部调用方可以生成或解密数据密钥。
- 日志、指标、追踪和错误正文不泄露敏感密钥材料。
- 主密钥或口令应来自受保护配置，支持版本化、轮换和审计。
- 轮换不得使历史加密数据密钥在没有迁移方案时永久不可恢复。
- 随机源或密码算法初始化失败时必须明确失败，不能降级为弱随机或明文。

## 非目标

- 不保存业务 Secret 或业务密文。
- 不直接加密任意大小的业务数据。
- 不承担 PKI、证书签发或 SSH Key 生命周期。
- 当前实现不宣称提供云 KMS/HSM 同等级的主密钥保护和合规能力。

## 验收标准

- AES 与 SM4 数据密钥均可生成、加密和正确解密。
- 错误算法、错误口令、截断密文和非法编码均被拒绝。
- 多实例使用同一有效密钥配置时具有一致解密结果。
- API、日志和监控检查不暴露口令与明文密钥。
- 调用方能够明确保存算法标识、加密数据密钥和业务密文。
