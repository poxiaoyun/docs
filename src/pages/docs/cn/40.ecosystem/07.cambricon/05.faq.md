# FAQ

## 速查表

| 现象 | 先查什么 | 处置 |
| --- | --- | --- |
| 宿主机没有 `/dev/cambricon_dev*` | 驱动是否装上、内核模块是否加载 | 按官方文档重装驱动，装完再确认三个设备节点 |
| 升级内核后卡不见了 | 内核模块有没有跟着重装 | 重装一遍驱动 |
| 宿主机有设备节点，容器里没有 | 容器运行时工具链装没装 | 补装后重建容器 |
| 节点上没有 `cambricon.com/mlu` | 设备插件 Pod 状态与日志 | 先确认宿主机两层都好，再重启插件 |
| 设备插件 Pod 起不来、镜像拉不到 | 镜像是怎么来的 | 官方没有预编译镜像，自建后推到内网仓库 |
| 编设备插件报找不到 `cndev.h` | 构建机有没有装驱动包 | 在构建机上装与目标节点同版本的驱动包 |
| 申请了 sMLU 资源但排不上 | 节点上有没有同名资源 | 按所用 release 的 README 确认 `--mode` 与资源名 |
| 指标里没有 namespace / pod 维度 | podresources collector 开没开 | 打开后再看 `mlu_container` |
| 监控里压根没有 MLU 指标 | mlu-exporter 是否部署、30108 通不通 | 部署后用 ServiceMonitor 抓 30108 |
| 规格标签没有图标、型号名带前缀 | 平台展示层 | 属预期行为，不影响调度 |

## 为什么平台上找不到安装寒武纪组件的地方

平台的「系统应用」里只内置了 NVIDIA 与昇腾两套硬件调度组件，寒武纪、AMD、海光都不在名单里。
集群组件要按各家官方仓库手工装。这不是哪台机器配错了，是当前的产品边界，
见 [平台适配现状](/ecosystem/cambricon/platform-support)。

## 设备插件为什么要自己编译

`Cambricon/cambricon-k8s-device-plugin` 仓库里没有官方预编译镜像，只有源码，实现目录是 `device-plugin`。
构建依赖驱动包里的 `cndev.h`，所以构建机上必须先装好驱动包，否则编译阶段就过不去。

实践上分两步：在一台装好同版本驱动的机器上编，编出来的镜像推到内网仓库，节点再从内网拉。集群节点侧不需要 JDK 之类的额外环境。

## 上报的资源名有几种口径

先把官方口径和第三方口径分开看：

| 来源 | 资源名 | 性质 |
| --- | --- | --- |
| 设备插件整卡 | `cambricon.com/mlu` | 官方上报，最常用 |
| 动态 SMLU 模式 | `cambricon.com/vmlu`、`cambricon.com/mlu.smlu.vmemory`、`cambricon.com/mlu.smlu.vcore` | 三个一起用，HAMi 官方文档给的就是这一组；要开 SMLU 并把设备插件设成 `mode=dynamic-smlu` |
| DAOCloud 文档 | `cambricon.com/mlu.share`、`cambricon.com/mlu.mim-2m.8gb` | 第三方集成方口径 |

节点上出现哪一类，取决于集群里装的设备插件用的是哪个 `--mode`，或者装的是哪个第三方切分方案。
`--mode` 的取值随版本变化，各来源列举的也不一致，部署前打开所用 release 的 README 对一遍。
动态 SMLU 那一组的完整前置与申请写法见 [HAMi](/ecosystem/hami)。

```bash
kubectl describe node <mlu-node> | grep -A 5 "Allocatable" | grep cambricon.com
```

这一条打出来什么资源名，平台侧就按什么资源名建规格。

## 平台型号枚举里有 MLU590，官网产品页查不到

模型元数据里的加速卡型号枚举有 MLU220 / MLU270 / MLU370 / MLU590 四个。其中 MLU590 在寒武纪官网的产品页上没有核实到，
只出现在第三方资料里，本分区不把它当事实用。枚举里能选到，只说明平台登记过这个名字，不代表型号的规格与供货状态。

选型时以官网产品页和整机厂商的兼容列表为准，别拿模型卡片的下拉项当型号清单。
