# Kubernetes 组件

集群侧要装的是两件事：设备插件把卡注册成可调度资源，监控导出器把卡的指标暴露出来。寒武纪没有把它们打成一个 Operator 包，两个组件各自从开源仓库取。

| 组件 | 作用 | 不装的后果 |
| --- | --- | --- |
| 设备插件（cambricon-k8s-device-plugin） | 把 MLU 注册成 Kubernetes 扩展资源 | 节点上没有 `cambricon.com/mlu`，任务申请不到卡 |
| mlu-exporter | 暴露 MLU 的利用率、显存、温度等指标 | 平台监控里看不到卡的状态，只能看任务日志 |
| 容器运行时工具链 | 让容器内可见 MLU 设备节点 | 设备插件能起，但任务容器里用不到卡（属宿主机层，见 [驱动与容器运行时](/ecosystem/cambricon/driver-runtime)） |

## 获取渠道

| 组件 | 渠道 |
| --- | --- |
| 设备插件 | `https://github.com/Cambricon/cambricon-k8s-device-plugin`，实现目录 `device-plugin`，README 自述为官方实现 |
| 设备插件镜像 | 官方不提供预编译镜像，要自己构建 |
| mlu-exporter | `https://github.com/Cambricon/mlu-exporter`，仓库内含 DaemonSet、ConfigMap、ServiceMonitor 与 Helm 几种部署形态 |
| 国内镜像 | Gitee 上的组织页 `https://gitee.com/organizations/cambricon/projects` |

设备插件的构建依赖驱动包里的 `cndev.h`，所以构建机上要先装好与目标节点同版本的驱动包，否则编译过不去。

## 设备插件上报的资源名

整卡上报的名字是：

```
cambricon.com/mlu
```

资源名可以当成卡的身份证号，平台建规格、建配额、任务申请都认这一串字符。申请的方式和 NVIDIA 那边一个套路，**申请几张就写几**：

```yaml
resources:
  limits:
    cambricon.com/mlu: 1
```

设备插件的 `--mode` 开关决定上报哪一种资源名，取值随版本变化，不同来源列举的也不一致，见过这些：`default`、`sriov`、`env-share`、`mlu-share`、`dynamic-smlu`、`mim`、`topology-aware`。

:::warning mode 取值以所用 release 的 README 为准
上面这一串是各来源列举的并集，不等于某个版本的完整取值，也不保证每个版本都支持。
部署前打开所用 release 的 README 对一遍，按里面写的取值配。
:::

:::info 版本
仓库能看到的最新 tag 是 v2.3.0（2026-08-07）。本分区不锁版本，现场按目标集群选。
:::

## 一卡多用

一张卡切给多个任务用，官方给的术语有五种，粒度和隔离程度都不同：

| 术语 | 含义 | 资源名 |
| --- | --- | --- |
| vMLU | 虚拟化，把一张卡切出虚拟实例 | 官方术语，具体资源名以所用 release 的 README 为准 |
| sMLU | 时分复用的软切分 | `cambricon.com/mlu.smlu.vcore` 与 `cambricon.com/mlu.smlu.vmemory`，Koordinator 官方文档确认为设备插件上报 |
| dynamic-smlu | 动态 sMLU | 以所用 release 的 README 为准 |
| MIM | 物理划分，对标 NVIDIA MIG | 以所用 release 的 README 为准 |
| env-share | 用环境变量方式共享一张卡 | 以所用 release 的 README 为准 |

sMLU 的两个资源名分开报算力与显存，申请时要一起写，数值口径由设备插件版本决定：

```yaml
resources:
  limits:
    cambricon.com/mlu.smlu.vcore: <按所用 release 的 README 口径填>
    cambricon.com/mlu.smlu.vmemory: <按所用 release 的 README 口径填>
```

SR-IOV 是另一条路，靠设备插件的两个参数开启，`--virtualization-num` 指定要切出的 VF 数量：

```bash
--mode=sriov --virtualization-num=<VF 数量>
```

### 第三方集成方的资源名

下面这些名字来自第三方项目与集成方的文档，不是寒武纪官方的上报口径。看到节点上出现这类资源名，说明集群里装的是第三方切分方案：

| 来源 | 资源名 | 性质 |
| --- | --- | --- |
| HAMi 的动态 SMLU 模式 | `cambricon.com/vmlu`、`cambricon.com/mlu.smlu.vmemory`、`cambricon.com/mlu.smlu.vcore`，三个一起用 | [HAMi 官方文档](https://project-hami.io/docs/userguide/cambricon-device/enable-cambricon-mlu-sharing) 给出的口径 |
| DAOCloud 文档 | `cambricon.com/mlu.share`、`cambricon.com/mlu.mim-2m.8gb` | 第三方集成方口径 |

走前一条路线时，卡上要先用 `cnmon set -c <id> -smlu on` 打开 SMLU，设备插件要以
`mode=dynamic-smlu` 运行并把最小分配单位设成 256 MB（`min-dsmlu-unit=256`）。
这两步不满足，`vmlu` 那几个资源名不会被上报。

这些方案与平台内置的 Volcano vGPU 是两套东西，建规格前先确认集群里到底装的是哪一套。
HAMi 覆盖的厂商与资源名对照见 [HAMi](/ecosystem/hami)。

## 监控

指标由 **mlu-exporter** 提供，Prometheus 格式：

| 项 | 值 |
| --- | --- |
| 监听端口 | 30108 |
| 指标路径 | `/metrics` |
| 指标前缀 | `mlu` |
| 容器维度指标 | `mlu_container`，可关联 namespace / pod / container |
| 前置条件 | 需要启用 podresources collector，否则拿不到容器维度的标签 |
| 部署形态 | DaemonSet、ConfigMap、ServiceMonitor、Helm |
| 接入平台监控 | 用 ServiceMonitor 交给 Prometheus Operator 抓取 |

这个端口和 NVIDIA 那边的 9400、AMD 的 5000 都不一样，做统一看板时别按同一个端口写。

## 与 Volcano 的关系

平台的多卡任务交给 Volcano 排。寒武纪的官方文档里没有列出 Volcano 专用插件，所以走通用路径：设备插件把卡报成标准扩展资源，Volcano 按资源名和数量排。

- 多卡任务能排，靠的是 Kubernetes 标准的扩展资源机制，不需要额外插件。
- 卡内切分后按份调度、显存按比例分配这类能力，不在官方插件支持范围内。要做得上第三方方案，那是另一条路线。
- 队列、gang 调度这些 Volcano 自带能力与厂商无关，装不装插件都一样用。

## 装完怎么验证

```bash
# 节点上出现了可分配的 MLU 资源
kubectl describe node <mlu-node> | grep -A 5 "Allocatable" | grep cambricon.com

# 设备插件与监控组件起来了
kubectl get pods -A | grep -i cambricon
kubectl get pods -A | grep -i mlu-exporter

# 监控端口能通，能看到以 mlu 开头的指标
kubectl port-forward -n <namespace> <mlu-exporter-pod> 30108:30108
curl -s http://127.0.0.1:30108/metrics | grep '^mlu'
```

再交一个最小任务，申请 1 张卡，容器里能看到设备节点就算通了。
