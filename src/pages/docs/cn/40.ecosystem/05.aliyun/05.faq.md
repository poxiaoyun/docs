# FAQ

## 先分层，再定位

PPU 的问题基本逃不出三层，按顺序查比到处试要快：

| 层 | 怎么看 | 卡在哪里 |
| --- | --- | --- |
| 节点层 | `kubectl get nodes -l aliyun.accelerator/xpu_type=ppu` | 看不到节点，是节点池或组建的问题，与调度无关 |
| 资源层 | `kubectl describe node <NODE_NAME> \| grep -i ppu` | 有节点但没资源，是设备插件的问题 |
| 调度层 | `kubectl describe pod <POD_NAME>` 看 Events | 资源有、Pod 不 Running，看污点、节点选择、配额 |

先确定停在哪一层，再去翻对应的页面。绕开这一步直接改配置，通常会把问题搞得更乱。

## 速查表

| 现象 | 可能原因 | 怎么办 |
| --- | --- | --- |
| 灵骏节点池里看不到 PPU 节点 | 节点未加入节点池，或节点未就绪 | 控制台确认节点池成员与节点状态 |
| 节点在集群里，但没有 PPU 标签 | 设备插件未安装或未在目标节点运行 | 检查 `ack-ppu-device-plugin` 的 Pod 与日志；节点带灵骏污点时留意组件自身的容忍 |
| `Allocatable` 里没有 `alibabacloud.com/ppu` | 设备插件没跑在 PPU 节点上 | 同上 |
| Pod 一直 Pending，事件里提到 taint | 漏了灵骏节点污点的容忍 | 补 `node-role.alibabacloud.com/lingjun` 的容忍 |
| Pod 起了，但容器里用不了卡 | 镜像里缺 PPU SDK 与运行时 | 换成 PPU 版的业务镜像，先跑 `ppu-smi` 确认 |
| 申请 `rdma/hca` 失败 | 未安装 `ack-rdma-device-plugin` | 安装后重试 |
| 多卡任务通信慢 | 装机时没勾 `Enable PPU Topology`，或申请卡数与互联域不对齐 | 重配组件勾上拓扑；按 1/2/4/8/16 的粒度申请 |
| 卡分散、大任务排不进来 | 没开 Binpack，或 `binpackResourceWeight` 里没加 `alibabacloud.com/ppu` | 按[调度策略](/ecosystem/aliyun/device-plugin/scheduling)配置 |
| 平台里厂商标签不是 PPU | 规格的资源键写错了 | 核对资源键是否为 `alibabacloud.com/ppu` |
| 平台里看不到 PPU 算力 | 资源池未纳管该集群，或规格未分配卡数 | 在资源池里确认集群已接入，并检查规格的可用数量 |
| 实例被驱逐后没自动恢复 | 节点被判异常，副本数只有 1 | 把副本数调到 2 以上，或让实例带重调度策略 |

## 几条落地经验

1. **先跑通一整卡，再考虑切分。** 拿一个最小任务验证节点、插件、镜像、框架四件事都通了，
   再去开 MIG。顺序反了，出问题时你分不清是切分配置错了还是镜像本身有问题。
2. **Binpack 与隔离性要一起看。** 集中放置能减少碎片，也会把故障影响面收窄到一个节点上。
   训练集群适合开，线上推理服务要谨慎，必要时把权重调低。
3. **卡数与互联域对齐。** 用 8 卡就申请 8 卡，别申请 6 卡或 7 卡，插件凑不出好的拓扑组合。
4. **多机任务一次把 RDMA 申请上。** 忘记申请 `rdma/hca` 的后果是多机通信退化成普通网络，
   而且现象是「能跑但很慢」，很容易被当成模型本身慢。
5. **存储和算力的网络分区在规划阶段对齐。** CPFS 智算版要求两者处在同一高性能网络分区，
   事后调整要动节点池，代价不小。
6. **别把参数当固定接口。** PPU SDK 与 `ppu-smi` 还在演进，切换之前先跑一遍
   `ppu-smi -h`，以当前版本的支持范围为准。同一代芯片也有不同固件版本，参数与精度支持
   可能不一致。
