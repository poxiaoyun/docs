# 在平台上使用

前面几页都在阿里云侧，这一页回到平台：把 PPU 变成能分配给用户、能被点开看的算力。

## 平台怎么认这张卡

平台按**资源键**识别加速卡，不看卡插在哪台机器上。PPU 对应的键是：

```
alibabacloud.com/ppu
```

切分过的实例写成 `alibabacloud.com/ppu-4u.4g48gb` 这类形式，同样会被识别为 PPU。

识别到之后，界面上的表现是：

| 位置 | 显示 |
| --- | --- |
| 规格名称 | `PPU*1` 这种形式，星号后面是卡数 |
| 卡片图标 | PPU 的厂商图标 |
| 厂商标签 | `PPU` |
| 实例列表 | 资源名带 `ppu` 或 `alibabacloud.com/ppu` 的实例归到 PPU 一类 |
| 资源总览 | 计入加速卡用量，按 PPU 分类展示利用率 |

如果在界面上看到的厂商标签不是 PPU，八成是规格里的资源键写错了，先去核对规格定义。

## 建一条算力规格

一条 PPU 规格需要三样东西：

| 配置项 | 填什么 |
| --- | --- |
| 资源键 | `alibabacloud.com/ppu`（切分实例填对应档位） |
| 卡数 | 1、2、4、8、16；切分实例填份数 |
| 节点选择 | `aliyun.accelerator/xpu_type: ppu`，需要限定型号时再加 `ppu_name` |

配套的 CPU 与内存按业务实测值给。PPU 机器 CPU 核数普遍不少，但推理服务的瓶颈通常在显存带宽和
并行策略上，CPU 给多了是浪费。

规格建好后，用户侧的用法和 GPU 规格没有区别：选规格、选镜像、起实例。

## 一个实例的完整链路

从资源识别到业务跑起来，平台的流程是这样的：

1. **资源识别**：节点上的 PPU 被集群纳管后，资源池里出现 PPU 算力。
2. **规格划分**：管理员按交付口径拆成若干算力规格，分配可用卡数。
3. **创建实例**：用户按规格申请，平台生成带资源声明和污点容忍的负载。
4. **运行与访问**：容器起来后可以直接进终端，也可以对外发布推理服务。
5. **观测**：在实例详情看资源占用，在监控里看卡级指标。

平台侧不参与卡的管理，做的是「谁能用、用多少、跑在哪」这三件事。

## 看哪些监控指标

阿里云为 PPU 提供了 Prometheus 格式的指标体系，覆盖利用率、互联、显存、温度功率、错误健康几类。
指标命名与主流的 PPU 监控生态兼容，已有的 Prometheus + Grafana 大盘可以直接复用。

日常最值得盯的几项：

| 指标类别 | 看什么 | 什么时候该警觉 |
| --- | --- | --- |
| 利用率 | PPU Util（时间利用率）、SM Active（空间利用率） | 长期低于 30% 通常不是卡的问题，是并行策略或批大小的问题 |
| 精度管线 | Tensor / FP32 / FP16 / FP8 等管线活跃率 | 与业务实际精度不一致，说明镜像里的精度配置没生效 |
| 互联带宽 | ICN Link TX/RX、PCIe TX/RX | 多卡任务里 ICN Link 远低于峰值，说明通信被卡住或并行度开得不够 |
| 显存 | Framebuffer Used / Free / Total | 各卡显存占用严重不均，多半是负载均衡没做好 |
| 温度与功率 | PPU Temp、Power Usage、Clock Throttle Reasons | 出现节流原因就说明已经降频，训练速度会被拖慢 |
| 错误与健康 | XID Errors、Retired Pages | 有任何一条非零，先隔离节点再排查 |

多业务共用一个节点时，指标要按容器维度归因，否则会出现「整机利用率看着挺高，某个业务其实在空转」
这种误判。

## 性能剖析

监控能回答「卡忙不忙」，回答不了「为什么慢」。阿里云在 ACK 上提供了基于 eBPF 的按需剖析能力：
不改业务代码、不用在镜像里埋探针、也不用重启服务，直接对运行中的 Pod 采集。

对训练任务尤其有用：不可能为了做一次剖析就把跑了几小时的任务停掉。采集维度通常包含算子耗时、
显存分配与碎片、通信带宽与重传、调用栈等，输出的是瓶颈归因结论而不只是几张曲线。

平台侧目前通过阿里云的控制台能力查看，暂不在平台内做二次呈现。

## 故障与自愈

PPU 节点出问题时，链路是这样的：卡级错误先由 XID 检测捕获并上报，阿里云把灵骏平台的硬件运维事件
（风扇异常、电源降级、链路闪断等）转成 Kubernetes 的节点状态，平台按节点状态规避调度、迁移负载。

用平台的时候不需要关心这些机制，但要知道两件事：

- 节点被判定异常后，上面正在跑的实例不会自己长回来，需要重新调度，做推理服务时建议副本数大于 1。
- 超节点形态下故障影响面更大：一张卡异常可能让同域内所有依赖它的任务一起停住。

## 一个容易踩的口径问题

阿里云不同产品线给 PPU 的资源键不一定相同。ACK 灵骏节点池里是 `alibabacloud.com/ppu`，
部分产品（例如 RDS Custom 的灵骏节点）用的是 `aliyun/ppu`。填规格前先在目标集群上确认一次：

```bash
kubectl describe node <NODE_NAME> | grep -i "ppu"
```

以集群实际上报的资源名为准，不要照抄别的环境的文档。
