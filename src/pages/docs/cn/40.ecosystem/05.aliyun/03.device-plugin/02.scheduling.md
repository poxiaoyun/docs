# 调度策略

PPU 的调度有两层：卡在节点内怎么选，任务在节点之间怎么放。前者由设备插件负责，后者由 kube-scheduler
配合拓扑信息决定。默认配置能跑，但多卡多机任务会吃性能亏，所以这一页值得花十分钟配完。

## 卡怎么选：设备拓扑感知

Pod 申请多张 PPU 时，设备插件不是随便抓几张卡给它，而是按卡间的物理拓扑挑互联带宽最高的组合。
这件事不需要你配置，装组件时勾了 `Enable PPU Topology` 就已经生效。

需要你做的只有一件事：**申请数量按互联域对齐**。支持申请的粒度是 1、2、4、8、16 卡，
在超节点形态下机内 8 卡是高速互联的，跨机则靠 ICN Link。如果业务本身需要 8 卡做张量并行，
却只申请 6 张，插件也只能凑给你，拓扑优势剩不下多少。

## 任务怎么放：Binpack

默认调度倾向于把 Pod 摊开到不同节点。对 PPU 来说这不是好事：卡分散之后，集群里到处是缺口，
大任务排不进来，小任务也未必更省。

开 Binpack 让 PPU 任务优先往同一节点上堆，做法是改 kube-scheduler 的参数：

1. 阿里云容器服务控制台，进入目标集群的**组件管理**。
2. 在**核心组件**区域找到 `kube-scheduler`，点**配置**。
3. 勾选**启用 Pod 调度优先集中放置**。
4. 在 `binpackResourceWeight` 里点**添加**，`resourceName` 填 `alibabacloud.com/ppu`。

第 4 步是关键，只勾第 3 步对 PPU 不起作用：权重列表里没有这个资源名，调度器不会专门为它做集中放置。

:::warning Binpack 是双刃剑
集中放置减少碎片，但同一节点上堆得越满，单机故障的影响面也越大，散热压力同样集中。
如果集群里跑的是大量小推理实例、且服务等级要求高可用，可以把权重调低或只对特定队列启用，
不必一刀切。
:::

## 多机与超节点

多机多卡任务里，Worker 落在哪个节点决定了它们之间的通信走哪条路：落进同一个高速互联域，
走 ICN Link；落到域外，就退化成普通 RDMA 甚至 TCP。带宽差一个量级，训练时间差得更不止一个量级。

阿里云在 ACK 上提供了超节点维度的网络拓扑感知调度，按机架 → 交换域 → 超节点 → 节点四层来放置任务：

| 策略 | 适用场景 | 效果 |
| --- | --- | --- |
| Binpack | 训练任务 | 尽量把所有 Worker 聚到同一个超节点 |
| 均衡 | 多个任务并行 | 把副本摊到不同超节点，避免互相抢资源 |
| 成组调度 | 强耦合的多副本任务 | 一组 Pod 要么都拿到资源，要么都不启动 |

成组调度值得单独说一句。几十卡的训练任务如果不成组，会出现「前几个 Worker 起来了、占着卡等后面的」
这种局面：卡被占住但算不出东西，集群看着很忙，实际吞吐为零。

配套还有两个约束参数：`maxSplits` 限制一个任务最多被打散到几个超节点，
`whenNotSatisfied: DoNotSchedule` 表示拓扑约束不满足时宁可排队也不降级调度。
具体字段名和取值以你所用 ACK 版本的组件参数说明为准。

设备插件与调度器是协同工作的：调度器先决定 Worker 落在哪些子节点上，设备插件再在每个子节点内
挑最优的卡组合，同时自动把跨机互联需要的 channel 设备与环境变量注入容器。业务侧提交一个标准的多机任务
就能享受这套组合，不需要手工配置互联参数。

## 平台侧怎么接

平台的算力规格里声明的是资源键与节点约束，例如：

```yaml
resources:
  limits:
    alibabacloud.com/ppu: "8"
nodeSelector:
  aliyun.accelerator/xpu_type: ppu
```

创建实例时平台生成这段配置，ACK 那边按上面这些策略落地。所以调度策略只在阿里云侧调一次，
平台里所有用 PPU 规格的实例都会跟着变。反过来，改平台的规格定义不会影响 ACK 的调度器参数。
