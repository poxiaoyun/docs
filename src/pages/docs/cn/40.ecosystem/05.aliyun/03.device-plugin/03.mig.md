# MIG 切分

一张 PPU 只跑一个小模型有点浪费。MIG 把卡按硬件切成若干**互相隔离**的实例，
每个实例有独立的 CU 和显存，一个任务崩了不会牵连别人。

要澄清一个常见误解：MIG 做的是**隔离**，不是**超卖**。切出去的算力和显存加起来不会超过这张卡的总量，
只是把整卡拆成几份，让多个任务各用一份。

## 几个概念

| 概念 | 含义 |
| --- | --- |
| GPU instance | PPU 硬件资源切分后的实例，实例之间隔离运行 |
| GPU instance profile | 一次切分能提供的能力，例如可独占多少 CU、多少显存 |
| Compute instance | GPU instance 再细分出的实例，独占 CU、复用其他资源 |
| Compute instance profile | Compute instance 的切分方案 |

多数情况下你只跟第一层打交道：切出 GPU instance，把资源名写进 Pod 的 `resources.limits`。
需要把算力再细分时才会用到 Compute instance。

## 开启 MIG 模式

在 PPU 节点上执行：

```bash
ppu-smi -mig 1
```

`ppu-smi` 也用来查询 MIG 模式下各实例的信息，以及创建、删除实例。具体子命令与参数随 SDK 版本变化，
以官方《多设备实例管理（MIG）》文档和当前节点上 `ppu-smi -h` 的输出为准。

:::warning 开 MIG 会打断正在跑的任务
切换 MIG 模式要重建设备配置，节点上正在使用 PPU 的容器会受影响。生产节点上操作前先确认可以停机，
或者把该节点从调度中摘出来再做。
:::

## 能申请哪些档位

切分后的资源名形如 `alibabacloud.com/ppu-<算力份数>u.<显存份数>g<显存容量>gb`：

| 显存规格 | 可选算力份数 |
| --- | --- |
| `1g12gb`（12GB） | `4u`、`8u` |
| `2g24gb`（24GB） | `1u`、`12u`、`16u` |
| `4g48gb`（48GB） | `1u`、`2u`、`3u`、`4u`、`8u`、`16u`、`24u`、`32u`、`64u` |

算力与显存分开切，所以档位组合比看上去多。落在哪个档位由设备插件按卡的实际切分能力上报决定，
以节点上的 `Allocatable` 为准。

## 申请示例

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: ppu-mig-test
spec:
  containers:
    - name: app
      image: <业务镜像>
      resources:
        limits:
          alibabacloud.com/ppu-4u.4g48gb: "1"
  tolerations:
    - key: node-role.alibabacloud.com/lingjun
      operator: Exists
      effect: NoSchedule
```

验证方式和整卡一样：

```bash
kubectl get pod ppu-mig-test -o wide
kubectl describe node <NODE_NAME> | grep -A 20 "Allocated resources"
```

`Allocated resources` 里出现对应的 `ppu-4u.4g48gb` 即生效。

## 什么时候用

**适合**：模型小到 24GB 显存就装得下，而且希望多个实例互不干扰。比如一组小参数模型做在线分类、
embedding 服务，或者给多个项目各分一块。

**不适合**：需要多卡并行的任务。切分后的实例之间没有卡间互联可言，张量并行这类策略根本跑不起来。
另外，卡被切成多份后，平台里会看到一堆小规格，碎片管理比整卡麻烦，Binpack 的集中效果也会打折。

## 平台侧看到什么

平台按资源键识别加速卡。写成 `alibabacloud.com/ppu` 时，规格名显示为 `PPU*1` 这类形式，
厂商标为 PPU；写成切分资源名时同样会被识别为 PPU，规格里的卡数就是申请份数。
在实例详情和规格列表里核对一眼，能确认自己拿到的是整卡还是一份切分实例。
