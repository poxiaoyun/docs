# Ascend Device Plugin

Ascend Device Plugin 负责**把节点上的 NPU 注册成 Kubernetes 的资源**：它会发现卡、做健康检查，
然后告诉集群「这台机器有几张卡可用」。只有注册成功，Pod 才能通过声明资源的方式用上卡。

可以把它理解成**给卡上户口**：卡本来只是插在机器上的硬件，注册之后才有集群认可的「身份」，
调度器才知道哪台机器还有卡空着。

## 什么情况下必须装

- **整卡调度**：一个 Pod 独占一张卡。
- **静态 / 动态虚拟化调度**：把一张卡切分给多个 Pod。
- **断点续训、弹性训练**。
- **推理卡故障恢复 / 重调度**。

只在集群里跑容器化业务、不需要调度卡时可以跳过，但那样平台就看不到 NPU 资源。

## 开始之前

- 每台 NPU 节点已装好驱动，且 `/usr/local/Ascend/driver` 存在。
- [Ascend Docker Runtime](/ecosystem/huawei/mindcluster/ascend-docker-runtime) **已安装并重启过容器引擎**。
- 组件镜像已放到集群能拉取的位置。
- 想好 YAML 选型：按处理器型号、是否使用 Volcano，选择对应的那一份。

## 操作步骤

### 1. 给 NPU 节点打标签

组件按标签选择要部署到哪些节点，先给节点打上：

```bash
kubectl label node <npu-node> accelerator=huawei-Ascend910
```

### 2. 确认镜像存在

```bash
docker images | grep k8sdeviceplugin
```

containerd 场景可用：

```bash
ctr -n k8s.io c ls | grep k8sdeviceplugin
```

### 3. 选择对应的 YAML

把软件包解压目录里的 YAML 拷贝到 Kubernetes 管理节点，按型号和场景挑文件，例如训练 / 推理、
是否使用 Volcano、是否特定开发板。

:::warning 不要改 DaemonSet 的名称
组件内部有自动识别运行时的逻辑，依赖固定的 DaemonSet 名称。随意改名字可能导致识别异常。
:::

### 4. 部署

```bash
kubectl apply -f device-plugin-910-v<version>.yaml
```

使用 Volcano 的场景：

```bash
kubectl apply -f device-plugin-volcano-v<version>.yaml
```

:::tip 集群里有多种型号怎么办
如果集群里同时存在多种昇腾 AI 处理器，需要**为每种型号分别部署对应的 YAML**。
:::

### 5. 检查

```bash
kubectl get pod -n kube-system | grep -i device-plugin
```

## 装完之后，集群里能看到什么变化

这是判断「卡是否真的接进集群」的关键，逐条确认：

| 看什么 | 命令 | 期望结果 |
| --- | --- | --- |
| 插件 Pod 状态 | `kubectl get pod -n kube-system \| grep -i device-plugin` | 每台 NPU 节点上各有一个 Pod，状态 `Running` |
| 节点新增资源名 | `kubectl get node <npu-node> -o jsonpath='{.status.allocatable}'` | 输出中出现 `huawei.com/Ascend910` |
| 卡的数量 | `kubectl describe node <npu-node> \| grep -A 2 huawei.com` | 数量与节点上实际可用的卡数一致 |

资源名出现之后，业务 Pod 就可以这样申请卡（片段）：

```yaml
resources:
  limits:
    huawei.com/Ascend910: 1
```

只要节点上还有空闲的卡，这类 Pod 就能被调度成功——这就是接收集群成功的最终标志。

## 常见问题

| 现象 | 可能原因 | 怎么办 |
| --- | --- | --- |
| Pod 起来了，但节点上没有出现资源名 | Ascend Docker Runtime 没装好或没重启容器引擎 | 先装好运行时并重启容器引擎，再重启本组件 |
| 只有部分节点出现资源 | 节点没打标签，或标签值与 YAML 里的选择器不一致 | 给缺卡的节点补打 `accelerator=huawei-Ascend910` |
| 卡数量对，但业务 Pod 仍调度失败 | 集群里没有可用的卡，或申请的资源名写错 | 确认资源名与节点上报的一致，用 `kubectl describe node` 看剩余量 |
| device IP 等基础信息变化后识别异常 | 插件缓存了旧的设备信息 | 重启 Device Plugin 让它重新识别 |

## 平台默认参数

通过平台安装时这几个值已经设好，手改 YAML 或排查时对照它来看：

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| 节点标签选择器 | `accelerator=huawei-Ascend910` | 组件只部署到带这个标签的节点 |
| `deviceType` | `Ascend910` | 上报的资源名对应 `huawei.com/Ascend910` |
| `useAscendDocker` | `true` | 与 Ascend Docker Runtime 配合，把驱动与设备挂进容器 |
| `volcanoType` | `true` | 以 Volcano 模式上报设备，多卡任务成组调度依赖它 |
| `presetVirtualDevice` | `true` | 静态虚拟化：按预切分的 vNPU 规格上报资源 |
| `autoStowing` | `true` | 自动整理可用设备信息，避免把不可用卡上报给调度器 |
| `listWatchPeriod` | `5` | 设备信息刷新周期（秒） |
| `containerRuntime` | `containerd` | 按节点实际运行时填（Docker / containerd / iSulad） |

:::warning 容器运行时填错会怎样
填错时插件 Pod 能起来，但拿不到设备 —— 现象是「节点上没有 `huawei.com/Ascend910`」。
排查时先核对节点运行时类型与这里的取值是否一致，再看日志。
:::

## 组件挂载了哪些路径

26.0.0 起，设备插件除了驱动与 kubelet 目录，还额外挂载了几处配置与状态目录。
排查「某个能力为什么没生效」时，对照这张表看容器里到底有没有这个路径：

| 挂载路径 | 用途 |
| --- | --- |
| `/usr/local/Ascend/driver` | 驱动与设备接口，插件的核心依赖 |
| `/var/lib/kubelet/device-plugins` | 向 kubelet 注册设备 |
| `/var/lib/kubelet/pod-resources` | 读取 Pod 的资源分配结果 |
| `/etc/vnpu.cfg` | 静态虚拟化（vNPU）的规格配置 |
| `/user/restore/reset` | 卡复位，故障恢复流程使用 |
| `/user/cluster-info/datatrace-config` | DataTrace 配置，按业务需要开关驱动侧的调试数据落盘 |
| `/user/mindx-dl/dpu-config` | DPU 相关配置 |
| `/run/containerd`、`/run/docker.sock`、`/run/docker` | 与容器运行时交互 |

## 落地注意

- **驱动升级顺序**：升级驱动前先停业务，再停 Device Plugin。
- **重启场景**：NPU 基础信息发生变化（例如 device IP 变更）后，需要重启插件重新识别。
- **动态库权限**：DCMI 动态库及其父目录建议由 root 管控，不要给 group / other 写权限。
