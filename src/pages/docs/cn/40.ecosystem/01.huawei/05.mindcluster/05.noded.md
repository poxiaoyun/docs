# NodeD

NodeD 是集群里的**节点状态监测组件**。它常驻在每台节点上，定期把节点本身和 NPU 的健康状况上报给集群，
让平台能识别出「这台机器 / 这张卡坏了」，进而触发故障重调度、断点续训这类动作。

可以把它理解成**每个机房角落里的巡检员**：他每天走一圈，把哪儿灯不亮、哪台设备发烫记下来报给中控室。

## 什么情况下必须装

- 需要**整卡调度或虚拟化调度**。
- 需要**断点续训、弹性训练**：节点挂掉时任务要能接续。
- 需要**推理卡故障恢复 / 重调度**。

如果只是想让集群能调度卡、不关心故障上报，可以暂不安装。

## 开始之前

- 每台 NPU 节点已装好驱动，`npu-smi info` 正常。
- 组件镜像已放到集群能拉取的位置，且版本与 Ascend Device Plugin 等组件配套。
- 节点已打过标签（与设备插件使用同一套标签）：

  ```bash
  kubectl label node <npu-node> accelerator=huawei-Ascend910
  ```

## 操作步骤

### 1. 确认镜像存在

```bash
docker images | grep noded
```

### 2. 准备 YAML

把软件包解压目录里的 NodeD YAML 拷贝到 Kubernetes 管理节点。

### 3.（可选）调整上报间隔

断点续训、弹性训练等场景可能需要修改节点状态上报周期，在 YAML 的启动参数里调整：

```yaml
args: ["/usr/local/bin/noded -logFile=/var/log/mindx-dl/noded/noded.log -logLevel=0 -reportInterval=5"]
```

`-reportInterval` 是上报间隔（秒）。Kubernetes 默认在一段时间收不到节点响应时会把节点置为 `NotReady`；
当 API Server 压力较大时，可以适当调大这个值来减轻压力，但需要先评估稳定性影响。

### 4. 部署

不使用 DPC 故障检测时：

```bash
kubectl apply -f noded-v<version>.yaml
```

使用 DPC 故障检测、且环境满足版本要求时：

```bash
kubectl apply -f noded-dpc-v<version>.yaml
```

### 5. 检查

```bash
kubectl get pod -n <noded-命名空间> | grep noded
```

官方安装包的命名空间通常为 `mindx-dl`，请以你实际使用的 YAML 为准。

## 装完之后，集群里能看到什么变化

| 看什么 | 命令 | 期望结果 |
| --- | --- | --- |
| 组件 Pod 状态 | `kubectl get pod -n <noded-命名空间> \| grep noded` | 每台节点上各有一个 Pod，状态 `Running` |
| 是否在周期上报 | `kubectl logs -n <noded-命名空间> <noded-pod> -f` | 日志持续输出，能看到周期性上报的记录 |
| 节点状态信息 | `kubectl describe node <npu-node>` | 节点对象上带有 NodeD 维护的节点与设备状态信息，字段名以组件版本为准 |

上报生效后，节点或卡出现故障时，平台侧能够识别并触发相应的重调度动作。

:::warning 调大上报间隔是双刃剑
把 `-reportInterval` 调大能减轻 API Server 压力，但也会**推迟故障被发现的时间**。
调整前先做稳定性评估，不要为了压负载把间隔调到过大。
:::

## 常见问题

| 现象 | 可能原因 | 怎么办 |
| --- | --- | --- |
| Pod 一直 `Pending` | 节点没有匹配的标签，或节点资源不足 | 确认节点标签，检查节点可分配资源 |
| Pod 反复 `CrashLoopBackOff` | 日志目录权限不对，或版本与设备插件不配套 | 先看 Pod 日志，再确认日志目录权限与组件版本配套关系 |
| 日志里没有上报记录 | 上报间隔设置过大，或组件未真正开始工作 | 确认 `-reportInterval` 取值，并确认 Pod 状态为 `Running` |
| 节点被置为 `NotReady` | API Server 压力大，上报间隔偏小 | 结合稳定性评估适当调大 `-reportInterval` |
