# FAQ

## 速查表

| 现象 | 先查什么 | 处置 |
| --- | --- | --- |
| `rocminfo` 报找不到设备 | 当前账号在不在 `render`、`video` 组 | 加组或改用 udev 规则，然后重启 |
| `rocminfo` 报模块没加载 | 内核驱动是否装上 | 按 Instinct 数据中心的驱动文档重装 |
| 宿主机能看到卡，容器里看不到 | 走的哪条容器工具链路线 | 集群是 containerd 就用 CDI 生成 `/etc/cdi/amd.json` |
| 设置了 `--runtime=amd` 但容器起不来 | 容器运行时是不是 Docker | 这个运行时只在 Docker 下有效，containerd 走 CDI |
| 节点上没有 `amd.com/gpu` | 设备插件 Pod 状态与日志 | 先确认驱动与容器工具链都好，再重启插件 |
| 任务申请到卡但一跑就报库缺失 | 镜像里的 ROCm 版本 | 换与宿主机驱动配套的镜像 |
| 节点上出现多个 `amd.com/...` 资源名 | 设备插件的命名策略 | 用了 `mixed` 策略，规格与配额要按对应资源名建 |
| 规格标签显示成 `GPU` 而不是 AMD | 平台展示逻辑 | 属预期行为，不影响调度 |
| 多卡任务排队很久 | 有没有资源被整卡占住 | 平台没有卡内切分，按卡数量排 |
| 想按显存比例切卡 | 有没有引入 HAMi | 走 [HAMi](/ecosystem/hami)，资源名 `amd.com/gpumem` 与 `amd.com/gpucores`，设备插件换成 HAMi 的 `amd-device-plugin` |
| 想按型号挑节点 | 节点标签有没有打上 | 装 Node Labeller，再按型号标签调度 |

## 为什么平台上找不到安装 AMD 组件的地方

平台的「系统应用」里只内置了 NVIDIA 与昇腾两套硬件调度组件，
AMD 的集群组件要按官方 GPU Operator 手工装。这不是配置问题，是当前的产品边界，
见 [平台适配现状](/ecosystem/amd/platform-support)。

## 容器里看不到卡，但宿主机正常

九成是容器工具链路线选错。AMD 给了两条路：

- **CDI**：`amd-ctk cdi generate` 生成设备规格文件，运行时自己读。Docker、Podman、containerd 都支持。
- **AMD 容器运行时**：注册 `--runtime=amd`，**只有 Docker 认这个参数**。

集群节点通常跑 containerd，所以必须走 CDI。判断方法很简单：看 `docker info` 里
默认运行时是不是 `runc`，以及集群的 `RuntimeClass` 里有没有 AMD。都没有就走 CDI。

生成完可以用官方命令验一遍规格文件：

```bash
sudo amd-ctk cdi validate --path=/etc/cdi/amd.json
```

## 驱动版本和 ROCm 版本怎么看

```bash
amd-smi version
```

这一条一次打印三行：工具版本、ROCm 版本、`amdgpu` 驱动版本。从 ROCm 7.0 起驱动与用户态是两条独立的
版本序列，**所以不要用 ROCm 版本去反推驱动版本**，查兼容性要看 AMD 官方的兼容性矩阵。

## 升级驱动要不要先停组件

要。先停业务，再停集群侧的设备插件与监控导出器，最后动驱动。设备插件会周期性调用驱动接口，
带着它升驱动容易留下「插件在跑但上报的设备数不对」的状态，只能靠重启插件恢复。

## 卡内切分和 MIG 是一回事吗

不是。AMD 的计算分区是把一张卡按物理分区拆开并行使用，颗粒度与模式名（SPX / DPX / QPX / CPX）
由卡型决定；NVIDIA MIG 是另一种实现。两者都不做跨分区的故障隔离。
需要按显存比例精细切分、且允许共享故障域的场景，走 [HAMi](/ecosystem/hami)：HAMi 从 v2.10.0 起
把 AMD Instinct / ROCm 列入稳定支持，显存 1 MiB 一档、算力 1% 一档，前提是换成 HAMi 的设备插件，
并把 AMD GPU Operator 自带的设备插件关掉。共享故障域这一点在 HAMi 上也一样成立。
