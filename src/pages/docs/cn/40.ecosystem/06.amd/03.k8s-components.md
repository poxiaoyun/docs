# Kubernetes 组件

集群侧要装的东西打成一个包，叫 **AMD GPU Operator**。它和 NVIDIA 那边的 GPU Operator 是同一类东西：
把设备插件、节点标签、监控导出器、驱动管理打包到一起，用一个 Helm chart 装。

| 组件 | 作用 | 不装的后果 |
| --- | --- | --- |
| Device Plugin | 把卡注册成 Kubernetes 资源 | 节点上没有 `amd.com/gpu`，任务申请不到卡 |
| Node Labeller | 给节点打上卡型号、显存等标签 | 想按型号挑节点时没有依据 |
| Metrics Exporter | 暴露 GPU 指标 | 平台监控里看不到卡的利用率与温度 |
| DCM（device-config-manager） | 下发计算分区 profile | 卡只能按出厂分区模式用 |
| NFD / KMM | 节点特征发现与内核模块管理 | 是上面几个的底座，一般跟着一起装 |

## 安装

官方仓库带 Helm chart，CRD 是 `DeviceConfig`（`amd.com/v1alpha1`）：

```bash
helm repo add rocm https://rocm.github.io/gpu-operator
helm repo update
```

:::warning chart 名与可配置项以仓库 README 为准
AMD GPU Operator 的 chart 名称在仓库 README 里出现过简写，命名空间与 values 结构也随版本调整。
装之前先打开仓库页面对一遍，不要把别处的示例直接抄进来。
:::

## 设备插件上报的资源名

默认只上报一个整卡资源：

```
amd.com/gpu
```

这跟 NVIDIA 的 `nvidia.com/gpu` 是同一个套路，**申请几张卡就写几**：

```yaml
resources:
  limits:
    amd.com/gpu: 2
```

设备插件有一个 `--resource_naming_strategy` 开关，值不同上报出来的资源名不同：

| 取值 | 上报的资源名 | 什么时候用 |
| --- | --- | --- |
| `single`（默认） | 只有 `amd.com/gpu` | 只按整卡调度，最简单 |
| `mixed` | 按分区模式分别上报，例如 `amd.com/spx_nps1`、`amd.com/cpx_nps4` | 同一个集群里要按不同分区模式分别排任务 |

改成 `mixed` 之后，节点上会出现多个资源名，**规格与配额也要跟着按对应资源名建**，否则任务申请不到。

## 监控

指标由 **AMD Device Metrics Exporter** 提供，Prometheus 格式：

| 项 | 值 |
| --- | --- |
| Exporter 监听端口 | 5000 |
| 指标路径 | `/metrics` |
| GPU Agent 端口 | 50061 |
| 接入平台监控的方式 | 建 ServiceMonitor，由 Prometheus Operator 抓取 |

这个端口和 NVIDIA 那边的 9400 不一样，做统一监控看板时别按同一个端口写。

## 计算分区

AMD 这一代卡的分区叫 **Compute Partitioning（算力分区）** 加 **Memory Partitioning（NPS，显存分区）**，
组合成若干模式：

| 模式 | 含义 |
| --- | --- |
| SPX | 整卡一份，不切 |
| DPX | 切成两份 |
| QPX | 切成四份 |
| CPX | 切成八份（按型号而定） |

MI300A 因为是 APU，模式集合不一样，是 SPX / TPX / CPX 三个。

实际操作不是手工改卡，而是**由 GPU Operator 的 DCM 下发 profile**，节点上打对应标签：

```bash
kubectl label node <gpu-node> dcm.amd.com/gpu-config-profile=<profile>
```

:::warning 分区不等于硬隔离
AMD 的计算分区是让同一张卡的不同分区并行跑不同任务，**不等于 NVIDIA MIG 那种带独立显存与故障隔离的实例**。
需要强隔离的场景要先确认业务是否接受共享故障域。
:::

## 和调度器的关系

平台的多卡任务交给 Volcano 排。AMD **没有官方的 Volcano 插件**，所以走的是通用路径：
设备插件把卡报成标准扩展资源，Volcano 按资源名和数量排。由此有两个结果：

- 多卡任务能排，靠的是标准的扩展资源机制。
- 卡内切分后按份调度、显存按比例分配这类能力，**不在 Volcano 官方支持范围内**，要引入 HAMi。
  HAMi 从 v2.10.0 起把 AMD Instinct / ROCm 列入稳定支持，用的资源名是 `amd.com/gpumem`
  （MiB）与 `amd.com/gpucores`（百分比），设备插件换成 HAMi 的 `amd-device-plugin`。
  这是与平台内置 Volcano vGPU 并列的另一条路线，细节见 [HAMi](/ecosystem/hami)。

## 装完怎么验证

```bash
# 节点上出现了可分配的 AMD 资源
kubectl describe node <gpu-node> | grep -A 5 "Allocatable" | grep amd.com

# 设备插件 Pod 起来了
kubectl get pods -A | grep -i amd

# 监控端口能通
kubectl get svc -A | grep -i metrics-exporter
```

再交一个最小任务，申请 1 张卡，容器里跑 `amd-smi` 能打出卡就算通了。
