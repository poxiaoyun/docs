# Volcano 与 vGPU 切分

Volcano 负责多卡任务的调度，vGPU 负责让多个任务共用一张卡。平台上的多卡任务不走 Kubernetes 默认调度器，
而是交给 Volcano；一张卡要分给多个任务时，用的是 Volcano 的 vGPU 能力。

打个比方：Volcano 像分配办公室的物业，vGPU 像用活动隔断把一间大办公室分成几个工位，任务走了工位就还回池子。

## Volcano 解决什么问题

Kubernetes 默认调度器一次只看一个任务，遇到「4 张卡必须同时拿到、否则一起等」这类需求会卡住。
Volcano 补上了这些能力：

| 能力 | 解决什么 |
| --- | --- |
| 成组调度（gang） | 多卡任务要么全部拿到卡、要么都不启动，避免拿一半卡干等 |
| 队列与公平共享 | 多个团队共用集群时按队列分额度，不会互相饿死 |
| 抢占 | 高优先级任务来了，能让低优先级的先让位 |
| 装箱（binpack） | 尽量把任务挤到少数节点上，空出整机给大任务 |
| NUMA 亲和 | 多卡任务尽量落在同一 NUMA 域内，减少跨 CPU 访存开销 |
| 设备共享（deviceshare） | 支持 vGPU 资源，让一张卡分给多个任务 |

## vGPU 怎么切

vGPU 由**调度器侧（deviceshare 插件）+ 节点侧设备插件**配合完成：节点侧把每张卡虚拟出若干份额并上报，
调度器按份额分配。默认每张卡切 **10 份**，显存按 **128 MiB** 为一个折算单位。

| 资源名 | 含义 |
| --- | --- |
| `volcano.sh/vgpu-number` | 申请几个 vGPU 份额 |
| `volcano.sh/vgpu-memory` | 申请的显存额度（MiB） |
| `volcano.sh/vgpu-memory-percentage` | 按整卡显存百分比申请 |
| `volcano.sh/vgpu-cores` | 申请的算力（百分比） |

## 平台默认参数

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| Volcano 版本 | `1.12.1` | 命名空间 `volcano-system` |
| 每卡份额数 | `10` | 一张卡最多同时分给 10 个任务 |
| 显存折算因子 | `128` | 单位 MiB |
| 节点专属配置 | 空 | 需要给个别节点单独设切分数或 MIG 策略时再填 |
| vGPU 监控 | 开启 | 设备插件内 `9394` 端口暴露指标，抓取间隔 `30s` |
| 调度动作 | 入队、分配、回填、回收、抢占 | 调度器启动即生效 |

设备插件以 DaemonSet 形式跑在 GPU 节点上，并把切分参数作为启动参数传入
（`--device-split-count` 与 `--gpu-memory-factor`），因此**改份额数要重新下发 DaemonSet**。

## 怎么申请共享卡

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: vgpu-demo
spec:
  containers:
    - name: cuda
      image: nvidia/cuda:12.2.0-base-ubi8
      command: ["nvidia-smi"]
      resources:
        limits:
          volcano.sh/vgpu-number: 1      # 要一个份额
          volcano.sh/vgpu-memory: 3000   # 显存 3000 MiB
          volcano.sh/vgpu-cores: 50      # 算力 50%
```

只写 `volcano.sh/vgpu-number` 也能跑，显存和算力按默认值折算；想控制得更细就三项都写。

## 节点专属配置

某些节点需要单独设份额数、显存折算比或 MIG 策略时，在安装配置的「节点专属配置」里加条目：

```yaml
nodeConfig:
  - name: gpu-node-01
    operatingmode: hami-core      # 共享模式
    devicememoryscaling: 1.8      # 显存折算比：上报值 = 实际显存 × 该系数
    devicesplitcount: 10          # 该节点每卡切几份
    migstrategy: none             # 该节点的 MIG 策略
```

- `devicememoryscaling` 大于 1 相当于**超分显存**（上报得比实际多），适合显存利用率低的任务，
  但要留意真实显存被多个任务用满时的风险。
- `migstrategy` 与 [MIG 实例划分](/ecosystem/nvidia/gpu-operator/mig-manager) 是同一件事，
  **两处只能开一处**。

## 验证

```bash
# 设备插件与监控
kubectl get pod -n volcano-system -o wide | grep volcano-device-plugin
# 节点上的 vGPU 资源
kubectl get node <gpu-node> -o jsonpath='{.status.allocatable}' | tr ',' '\n' | grep vgpu
```

节点上出现 `volcano.sh/vgpu-number` 就说明切分已经上报成功。

## 常见问题

| 现象 | 可能原因 | 怎么办 |
| --- | --- | --- |
| 节点上只有 `nvidia.com/gpu`，没有 `volcano.sh/vgpu-*` | vGPU 没开，或设备插件没起来 | 在调度组件配置里开启 GPU 虚拟化；查 `volcano-system` 下设备插件 Pod 状态 |
| 申请 `volcano.sh/vgpu-number` 的 Pod 一直 Pending | 份额用完了，或申请的算力/显存超过单份上限 | `kubectl describe node <gpu-node>` 看剩余份额；调小 `vgpu-memory` / `vgpu-cores` |
| 任务里 `nvidia-smi` 看到的显存比申请的大 | 这是软件级隔离的固有特性：限制由注入的共享库实施 | 属预期现象；需要硬件级隔离改用 [MIG](/ecosystem/nvidia/gpu-operator/mig-manager) |
| 换了份额数但节点上没变化 | 参数写进了 DaemonSet，需要重新下发 | 重新下发组件；确认设备插件 Pod 已被重建 |
| 调度器与昇腾的 Volcano 版本不一致 | 两个集群或两套组件各自的版本不同 | 同一集群只保留一套调度组件，不要混装 |
| CPU 利用率上不去、多卡任务变慢 | 卡跨 NUMA 分布 | 保持 numa-aware 插件开启（平台默认已开） |

:::warning 共享份额不是硬隔离
vGPU 的算力与显存限制是**软件层**实施的，隔离强度不如 MIG。跑对隔离敏感的生产任务时，
优先考虑 [MIG 实例划分](/ecosystem/nvidia/gpu-operator/mig-manager)。
:::
