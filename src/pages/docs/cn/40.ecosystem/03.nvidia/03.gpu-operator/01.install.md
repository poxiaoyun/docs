# 安装与验证

装组件只是第一步，确认装对了才是重点。系统应用显示「已部署」，不等于卡已经可以被调度；
真正的判据是节点上出现了可分配的资源名。

## 开始之前

- 每台 GPU 节点已装好驱动，`nvidia-smi` 能看到卡。
- 集群 Kubernetes 与容器运行时版本受支持；运行时类型记下来（默认按 `containerd` 装）。
- 需要监控数据时，集群里已装 Prometheus Operator；没有的话安装时关掉 ServiceMonitor 选项。
- **离线环境**：先把下表的镜像同步到集群能拉取的位置。在线环境可跳过。

### 需要准备的镜像

| 用途 | 镜像 |
| --- | --- |
| GPU Operator 本体 | `nvcr.io/nvidia/gpu-operator:v23.6.0` |
| 节点特征发现 | `registry.k8s.io/nfd/node-feature-discovery:v0.13.1` |
| 容器工具链 | `nvcr.io/nvidia/k8s/container-toolkit:v1.13.4-ubuntu20.04` |
| 设备插件 | `nvcr.io/nvidia/k8s-device-plugin:v0.14.1-ubi8` |
| 节点 GPU 标签 | `nvcr.io/nvidia/gpu-feature-discovery:v0.8.1-ubi8` |
| 监控采集 | `nvcr.io/nvidia/k8s/dcgm-exporter:3.1.8-3.1.5-ubuntu20.04` |
| MIG 划分 | `nvcr.io/nvidia/cloud-native/k8s-mig-manager:v0.5.3-ubuntu20.04` |
| Volcano 调度器与控制器 | `vc-scheduler` / `vc-controller-manager` / `vc-webhook-manager` / `vc-agent`，标签均为 `v1.12.1` |
| Volcano vGPU 设备插件 | `volcano-vgpu-device-plugin:v1.11.1` |

## 操作步骤

### 1. 选择安装入口

进入 **集群管理 → 选择目标集群 → 运维管理 → 系统应用**，点**创建系统应用**，
在模板里选 **NVIDIA 调度组件**（对应本节列出的 GPU Operator + Volcano + Volcano vGPU 一整套）。

如果这个集群之前已经装过昇腾调度组件，**不要重复装调度器**：一个集群只保留一套调度组件。

### 2. 确认关键配置

| 配置项 | 建议值 | 说明 |
| --- | --- | --- |
| 集群硬件类型 | NVIDIA | 决定装哪一套调度组件 |
| 容器运行时 | 与节点实际一致（默认 `containerd`） | 填错会出现设备插件找不到容器运行时 |
| 由 GPU Operator 安装驱动 | 保持关闭 | 节点已装驱动时不要打开，避免动到宿主机内核模块 |
| DCGM Exporter | 开启 | 平台监控面板依赖它的指标 |
| 创建 ServiceMonitor | 集群有 Prometheus Operator 时开启 | 否则安装会卡在 CRD 不存在 |
| GPU 虚拟化（vGPU） | 需要多任务共享一张卡时开启 | 详细配置见 [Volcano 与 vGPU 切分](/ecosystem/nvidia/volcano-vgpu) |
| 镜像仓库 | 离线环境填企业仓库地址 | 平台会自动改写所有组件的镜像前缀，不必逐个填 |

### 3. 等组件就绪

安装过程会依次创建两个命名空间并拉起组件：

```bash
kubectl get pod -n gpu-operator
kubectl get pod -n volcano-system
```

`gpu-operator` 里会多出 GPU Operator 自身、节点特征发现、容器工具链、设备插件、
监控导出器这一批 Pod；`volcano-system` 里是调度器、控制器和（开启 vGPU 时的）设备插件。
它们都是 DaemonSet 或 Deployment，**每个 GPU 节点上各有一份设备插件 Pod**。

## 装完之后，集群里能看到什么变化

这是判断「卡是否真的接进集群」的关键，逐条确认：

| 看什么 | 命令 | 期望结果 |
| --- | --- | --- |
| 设备插件 Pod | `kubectl get pod -n gpu-operator -o wide \| grep device-plugin` | 每台 GPU 节点各一个，状态 `Running` |
| 节点新增资源名 | `kubectl get node <gpu-node> -o jsonpath='{.status.allocatable}'` | 输出中出现 `nvidia.com/gpu` |
| 卡的数量 | `kubectl describe node <gpu-node> \| grep nvidia.com/gpu` | 数量与节点上实际可用的卡数一致 |
| 节点 GPU 标签 | `kubectl describe node <gpu-node> \| grep nvidia.com/gpu.product` | 能看到具体型号 |

资源名出现之后，业务 Pod 就可以这样申请卡（片段）：

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

只要节点上还有空闲的卡，这类 Pod 就能被调度成功 —— 这就是接入成功的最终标志。

## 常见问题

| 现象 | 可能原因 | 怎么办 |
| --- | --- | --- |
| 设备插件 Pod 一直 `CrashLoopBackOff` | 容器工具链没就绪，或容器运行时类型填错 | 看 `kubectl logs -n gpu-operator <device-plugin-pod>`；确认运行时类型与该节点实际一致 |
| 节点上没有出现 `nvidia.com/gpu` | 宿主机驱动没装好，或被 `nouveau` 占用 | 在节点上执行 `nvidia-smi` 与 `lsmod \| grep nouveau` 确认 |
| 有资源名，但 Pod 调度到该节点后起不来 | 业务镜像里的 CUDA 版本高于驱动支持的上限 | 降低镜像 CUDA 版本，或升级宿主机驱动 |
| Validator Pod 报失败 | 某个子组件没就位 | `kubectl logs -n gpu-operator <validator-pod>` 看它指出的是哪一步 |
| 监控面板没有 GPU 数据 | DCGM Exporter 未启用，或 ServiceMonitor 没建 | 检查 `kubectl get svc -n gpu-operator \| grep dcgm`，以及集群里是否有 Prometheus Operator |
| 卸载后重装，设备插件起不来 | 节点上残留的 `nvidia` 相关挂载与目录未清理 | 按官方卸载说明清理节点残留后再重装 |

:::warning 驱动升级时的停机顺序
升级宿主机驱动前，先停业务，**再按相反顺序停组件**：先停设备插件与 vGPU 设备插件，
再停监控导出器，最后才动驱动。带着它们在跑容易踩到「读到一半旧驱动」的坑。
:::
