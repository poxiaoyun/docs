# Kubernetes 组件

集群侧要装的东西打成两个包：**GPU Operator**（chart 名 `metax-operator`）和
GPU Extensions（chart 名 `metax-gpu-extensions`）。前者是完整的一套，后者是精简版。

| 组件 | 作用 | 不装的后果 |
| --- | --- | --- |
| operator-controller | 编排下面这些组件的生命周期 | 整套装不起来 |
| gpu-device | 设备插件，把卡注册成 Kubernetes 资源 | 节点上没有 `metax-tech.com/gpu`，任务申请不到卡 |
| gpu-label | 给节点打上卡型号等标签 | 想按型号挑节点时没有依据 |
| driver-manager | 管理驱动的下发与版本对齐 | 驱动要每台机器手工对齐 |
| vfio-manager | 管 SR-IOV 的 VF 直通 | 走不了 KubeVirt 直通那条路 |
| container-runtime | 配置沐曦容器运行时 | 容器里看不到卡 |

`gpu-device` 基于 Device Plugin Framework 实现，带拓扑感知分配与健康检查；**它没有开源**，
没有独立的公开 GitHub 仓库，通过沐曦软件中心或商务途径分发，镜像地址是
`cr.metax-tech.com/cloud/gpu-device`。

## 两套 chart 的取舍

| chart | 包含的组件 | 什么时候选 |
| --- | --- | --- |
| `metax-operator`（GPU Operator） | operator-controller、gpu-device、gpu-label、driver-manager、vfio-manager、container-runtime | 要驱动托管、要 SR-IOV、要容器运行时一起配 |
| `metax-gpu-extensions`（GPU Extensions） | gpu-device、gpu-label | 驱动与容器运行时已在节点上装好，只要按**整卡**调度 |

两个 chart 都放在沐曦自己的 OCI 仓库：

```
oci://cr.metax-tech.com/cloud/metax-operator
oci://cr.metax-tech.com/cloud/metax-gpu-extensions
```

:::warning 拉 chart 需要商务授权
这两个 OCI 地址不是公开仓库，需要先拿到商务授权才能拉取，`gpu-device` 本身也不开源。
装之前先把授权和镜像拉取凭据准备好，否则 `helm install` 会卡在拉包这一步。
:::

版本要求：Kubernetes ≥ 1.23；节点上 docker ≥ 18.09.3 或 containerd ≥ 1.5.0。

## 设备插件上报的资源名

`gpu-device` 上报的资源名只有一个，**整卡与 SR-IOV 的 VF 都用它**：

```
metax-tech.com/gpu
```

申请几张卡就写几：

```yaml
resources:
  limits:
    metax-tech.com/gpu: 1
```

:::warning `metax-tech.com/vgpu` 不是沐曦的资源名
官方文档里没有出现过 `metax-tech.com/vgpu` 这个资源名，它来自其它厂商的命名习惯。
写规格或配额时以节点上实际报出来的 `metax-tech.com/gpu` 为准。
:::

## 监控

指标由 **mx-exporter** 提供，它是基于 MXSML 的 Python 程序：

| 项 | 值 |
| --- | --- |
| 组件 | mx-exporter（Python，基于 MXSML） |
| 默认端口 | 8000 |
| 采集间隔 | 10000 ms |
| 指标前缀 | `mx_`，例如 `mx_device_type`、`mx_driver_ver`、`mx_chip_hotspot_temp` |
| 安装方式 | Helm chart，落到 `metax-monitor` 命名空间 |
| 仓库 | `https://github.com/MetaX-MACA/mxExporter` |

平台的统一监控看板按端口对接，沐曦这一档是 8000，别按别的厂商的端口号写。
`mx-smi` 只是命令行工具，不能当 exporter 用。

## 一卡多用

沐曦有三条切分路线，资源名各不相同：

| 方式 | 资源名 | 说明 |
| --- | --- | --- |
| 软件切分 sGPU | `metax-tech.com/sgpu`、`metax-tech.com/vcore`、`metax-tech.com/vmemory` | 一张卡最多 16 个实例；`vcore` 是百分比，`vmemory` 单位 GiB；需要 HAMi ≥ 2.6.0 或沐曦自己的 gpu-scheduler，HAMi 侧的前置见 [HAMi](/ecosystem/hami) |
| 硬件虚拟化 SR-IOV | `metax-tech.com/gpu` | 在 `driver-config`（v1 / v2）里配 `vfNum`，节点上可分配数量等于物理卡数 × `vfNum` |
| KubeVirt 直通 | `metax-tech.com/vfio-gpu` | 虚拟机直接接管一张卡 |

SR-IOV 这条要注意：配了 `vfNum` 之后节点上出现的还是 `metax-tech.com/gpu`，但数量会翻倍，
**平台侧按卡数建的规格和配额要跟着改**，否则会出现「资源明明有、任务排不上去」。

## 和 Volcano 的关系

沐曦这边**有官方的 Volcano 插件**，跟 AMD 那种只能走通用扩展资源的情况不一样。
沐曦基于 Volcano 的扩展机制开发了 `gpu-aware` 调度插件，参数是 `weight` 与 `loss.weight`，
支持拓扑感知与超节点调度。它不做共享：按卡切分的活交给 HAMi 或沐曦自己的 gpu-scheduler，
和 `gpu-aware` 是两条并行的路线。

## 装完怎么验证

```bash
# 节点上出现了可分配的沐曦资源
kubectl describe node <gpu-node> | grep metax-tech.com

# 设备插件相关 Pod 起来了
kubectl get pods -A | grep -i metax

# 监控导出器在跑
kubectl get pods -n metax-monitor
```

再交一个最小任务，申请 1 张卡，容器里跑 `mx-smi` 能打出卡就算通了。
