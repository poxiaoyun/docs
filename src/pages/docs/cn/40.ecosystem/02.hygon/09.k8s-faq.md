# FAQ

海光 DCU 集群组件的常见故障都在这张表里：先按现象找到最像的一行，再照「怎么办」里的命令排查。
表里放不下的长命令，统一放在后面的「完整命令」一节。

## 常见故障速查表

:::tip 先分清是驱动问题还是集群问题
下面这些问题大多**根子在宿主机驱动**，集群侧只是症状。判断方法：在节点上跑
`lsmod | grep -E "hydcu|hycu"` 和 `hy-smi`，**这两个不通就先回
[DCU 驱动安装](/ecosystem/hygon/driver-runtime) 处理，不要动集群组件。**
:::

| 现象 | 可能原因 | 怎么办 |
| --- | --- | --- |
| `lspci` 里看不到 DCU，或看到设备 `rev` 为 `rev ff` | 卡没插好 / 设备已处于异常状态 | 见 [DCU 驱动安装](/ecosystem/hygon/driver-runtime) 的「先确认硬件在场」：`rev ff` 需硬重启（DC）或掉电重启（AC）恢复 |
| 驱动装不上，或装完卡仍不可用 | BIOS 里 BAR 地址超出 44 bit | 用 `lspci -vvv` 看 `Region` 段地址，超限时调低 BIOS 的 MMIO High Base，以整机手册为准 |
| 升级驱动后 `lsmod` 里的模块名从 `hydcu` 变成 `hycu` | 驱动 6.3.x 起改了模块名 | 正常现象，按新模块名排查即可（6.2.x 及以下为 `hydcu`） |
| DCU-Label-Node 给 DCU 节点添加标签失败 | 组件版本偏旧，与当前驱动不兼容 | 升级到 V2.2.0 及以上版本后重新部署，升级前先确认当前版本（见「确认组件当前版本」） |
| 申请 DCU 资源后，Pod 内容器没有 `/opt/hyhal` 目录 | 设备插件版本偏旧 | 升级到 V2.1.0 及以上版本，该版本起会自动挂载 `/opt/hyhal`，升级前先确认当前版本（见「确认组件当前版本」） |
| Exporter 指标里 K8s 相关标签始终为空 | 没有使用卡的工作负载 / kubelet 工作目录不对 / 环境变量与集群不一致 | 见下方「排查 Exporter 标签为空」 |
| Exporter 在跑，但 Prometheus 里查不到 DCU 指标 | 没建 ServiceMonitor，采集器没发现这个服务 | 见 [DCU-Exporter](/ecosystem/hygon/k8s-exporter) 的「在 Prometheus 里确认」，按实际 Service 标签补 ServiceMonitor |
| containerd 容器内运行 `hy-smi` 报 `Failed to connect service!` | 特定驱动版本（6.3.13）的问题 | 升级或降级驱动；无法升降级时，启动工作负载时指定 `hostNetwork` 作为临时规避 |
| 6.2.* 驱动升级到 6.3.* 后，容器内 `hy-smi` 报 `RSMI_NOT_SUPPORTED` | 容器内环境变量未加载 | 在容器内执行 `source /opt/hyhal/env.sh && hy-smi` |
| Docker 容器内要把应用跑到指定 DCU 上 | 没有指定卡号 | 用环境变量 `HIP_VISIBLE_DEVICES` 指定（`0,1,2...` 选卡，`-1` 表示用 CPU），写法见「完整命令」 |
| vDCU 组件部署后 Pod 启动失败 | 组件未就绪 / 节点缺标签 / webhook 服务找不到 / 有遗留资源 | 见下方「排查 vDCU Pod 启动失败」 |
| 想在 Docker 环境下单独启动 DCU-Exporter | 不走 Kubernetes，直接跑容器 | 用下方「在 Docker 中启动 DCU-Exporter」里的命令 |

## 排查 Exporter 标签为空

1. 检查集群中是否存在使用 DCU 设备的工作负载：

   ```bash
   kubectl get pod -A -o wide
   ```

2. 检查节点 `/var/lib/kubelet` 是否为 kubelet 的实际工作目录：

   ```bash
   ls -d /var/lib/kubelet
   ```

3. 检查容器中 `KUBERNETES_SERVICE_HOST` 与 `KUBERNETES_SERVICE_PORT` 两个环境变量是否与集群实际配置一致：

   ```bash
   kubectl exec -n kube-system <dcu-exporter-pod> -- env | grep KUBERNETES
   ```

## 排查 vDCU Pod 启动失败

1. 检查组件 Pod 状态是否正常，并确认设备插件所在节点带有标签 `dcu=on`：

   ```bash
   kubectl get pod -n kube-system -owide | grep -E "dcu-device-plugin|vdcu"
   kubectl get node <node-name> --show-labels | grep dcu
   ```

2. 若报错包含 `service "admission-webhook-dcu-svc" not found`：
   - 检查 `vdcu-admission-webhook` 是否与宿主机共用网络，以及宿主机 `443` 端口是否被占用；
   - 删除遗留资源后重新部署：

   ```bash
   kubectl delete secrets -n kube-system admission-webhook-dcu-certs
   kubectl delete mutatingwebhookconfigurations mutating-webhook-dcu-cfg
   ```

3. V2.1.0 及之前版本还需检查：
   - `k8s-vdcu-scheduler` 版本是否与 k8s 集群版本匹配；
   - `k8s-vdcu-scheduler` 是否被调度到了非 DCU 节点；
   - 低版本 k8s 可能需要把 scheduler 部署文件里的 `kubescheduler.config.k8s.io/v1` 改为 `kubescheduler.config.k8s.io/v1beta2`。

## 完整命令

### 确认组件当前版本

查看各组件 Pod 正在使用的镜像（镜像标签即为版本）：

```bash
kubectl get pod -n kube-system -o jsonpath='{range .items[*]}{.metadata.name}{"  "}{.spec.containers[*].image}{"\n"}{end}' | grep -E "dcu-|vdcu"
```

### 在 Docker 中启动 DCU-Exporter

```bash
docker run --name dcu-exporter-v2 -d --privileged \
  --device=/dev/kfd \
  --device=/dev/mkfd \
  --device=/dev/dri \
  -v /etc/vdev:/etc/vdev \
  -v /etc/hostname:/etc/hostname \
  -v /opt/hyhal:/opt/hyhal \
  -p 16080:16080 image.sourcefind.cn:5000/dcu/admin/base/dcu-exporter:v2.2.0
```

### 指定应用使用的 DCU 卡号

在工作负载的环境变量里指定 `HIP_VISIBLE_DEVICES`：

```yaml
env:
  - name: HIP_VISIBLE_DEVICES
    value: "0" # 0,1,2,...,n 选择 DCU；填 -1 表示使用 CPU
```
