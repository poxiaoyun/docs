# DCU-Device-Plugin（标准模式）

DCU-Device-Plugin 负责**把节点上的 DCU 注册成 Kubernetes 的资源**：它发现卡、做健康检查，
然后告诉集群「这台机器有几张卡、每张能怎么用」。注册成功后，业务 Pod 才能通过声明资源的方式用上卡。

可以把它理解成**给卡上户口**：卡本来只是插在机器上的硬件，注册之后才有集群认可的「身份」，
调度器才知道哪台机器还有卡空着。

## 什么情况下必须装

- 需要在集群里调度**物理 DCU**（一个任务独占一张卡）。
- 需要在集群里调度**预切分 vDCU**（提前把卡切成固定规格，给多个任务使用）。

不用卡、或只在机器上直接跑程序，可以跳过本页。

## 组件有哪几种工作模式

组件通过启动参数 `RESOURCE_REGISTER_STRATEGY` 区分场景。**本页讲的是标准模式**，其余模式的部署见对应页面：

| 参数值 | 含义 | 暴露的资源名 |
| --- | --- | --- |
| `dcu` | 仅管控 DCU 物理设备 | hygon.com/dcu |
| `vdcu` | 仅管控预切分 vDCU | hygon.com/dcu-share-* |
| `mixed`（默认） | **标准模式**：物理设备与预切分 vDCU 协同管控 | hygon.com/dcu、hygon.com/dcu-share-* |
| `hami` | 动态切分 vDCU 设备 | hygon.com/dcunum |
| `mig` | MIG 虚拟化设备管控 | hygon.com/dcu-mig-* |

### 标准模式的规则

- 支持物理 DCU 卡与预切分 vDCU 的管控。
- 通过资源名称区分物理卡和不同规格的 vDCU，例如：
  - `hygon.com/dcu`：整卡调度；
  - `hygon.com/dcu-share-40c-30g`：40 CU / 30G 显存的 vDCU；
  - `hygon.com/dcu-share-20c-40g`：20 CU / 40G 显存的 vDCU。
- 存在预切分 vDCU 的卡**不再参与整卡调度**；有 vDCU 的卡必须通过 vDCU 规格的资源名调度。

## 开始之前

- 每台有卡的机器已装好驱动。
- 建议先部署 [DCU-Label-Node](/ecosystem/hygon/k8s-label-node)，给节点补齐 DCU 标签。
- 组件镜像已放到集群能拉取的位置。
- 准备好部署文件 `k8s-dcu-plugin.yaml`。

## 操作步骤

### 1. 部署

```bash
kubectl apply -f k8s-dcu-plugin.yaml
```

### 2. 查看 Pod

```bash
kubectl get pod -n kube-system -owide | grep dcu-device-plugin
```

每个有卡节点上各有一个 Pod，状态为 `Running`。

## 装完之后，集群里能看到什么变化

这是判断「卡是否真的接进集群」的关键，逐条确认：

```bash
kubectl describe node <node-name>
```

在输出的 `Capacity` 字段里看到 `hygon.com/dcu: 2`，就表示这个节点有两块 DCU 可被集群分配。

只要节点上还有空闲的卡，下面这类 Pod 就能被调度成功——这是接入成功的最终标志。

## 怎么申请卡

### 申请整卡 DCU

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: dcu-pytorch-demo
spec:
  containers:
    - name: dcu-pytorch-demo
      image: image.sourcefind.cn:5000/dcu/admin/base/pytorch:2.1.0-ubuntu22.04-dtk24.04.2-py3.10
      command: ["/bin/bash", "-c", "--"]
      args: ["sleep infinity & wait"]
      resources:
        limits:
          hygon.com/dcu: 1
```

### 申请预切分 vDCU

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: dcu-share-pytorch-demo
spec:
  containers:
    - name: dcu-share-pytorch-demo
      image: image.sourcefind.cn:5000/dcu/admin/base/pytorch:2.1.0-ubuntu22.04-dtk24.04.2-py3.10
      command: ["/bin/bash", "-c", "--"]
      args: ["sleep infinity & wait"]
      resources:
        limits:
          hygon.com/dcu-share-15c-8g: 1
```

## 容器里能看到什么

设备插件分配卡的时候，会顺带把宿主机上的设备和目录挂进容器，业务代码用到的就是它们：

| 容器内路径 | 是什么 | 缺了会怎样 |
| --- | --- | --- |
| `/dev/kfd` | DCU 的计算设备节点 | 容器内看不到卡，`hy-smi` 报连不上服务 |
| `/dev/mkfd` | 计算设备的辅助节点 | 同上 |
| `/dev/dri` | 图形/渲染设备节点 | 部分依赖 DRM 的库初始化失败 |
| `/opt/hyhal` | 海光 HAL 运行时库 | 容器内找不到运行时，框架加载失败 |

在 Kubernetes 里这一步由设备插件自动完成，**不需要业务自己配**；
自己用 `docker run` 手跑容器时要手工加这些参数（见 [FAQ](/ecosystem/hygon/k8s-faq) 里的 Docker 示例）。

:::warning 设备插件版本低于 V2.1.0 不会挂 `/opt/hyhal`
这一版起才自动挂载 `/opt/hyhal`。老版本装上去，现象是「Pod 正常调度、容器里却没这个目录」。
:::

## 使用限制

- 每个容器最多申请 **1 张 vDCU**。申请多于 1 张时，集群会把申请数量削减为 1 张，只有 1 张生效。

:::warning 别把整卡和 vDCU 混着调度
一张卡上已经切出 vDCU 后，就不能再按整卡 `hygon.com/dcu` 申请它。**混用会导致显存超分配（OOM）。**
有 vDCU 的卡，一律用对应的 vDCU 规格资源名申请。
:::

## 常见问题

| 现象 | 可能原因 | 怎么办 |
| --- | --- | --- |
| Pod 起来了，但节点上没出现资源名 | 驱动没装好，或节点标签缺失 | 先确认驱动模块已加载，再确认节点已由 DCU-Label-Node 打过标签 |
| 只有部分节点有资源 | 这些节点没打标签，或没装驱动 | 对有卡节点补装驱动与标签，然后重启设备插件 |
| 卡数量对，但业务 Pod 仍调度失败 | 没有空闲卡，或资源名写错 | `kubectl describe node <node-name>` 看剩余量，核对资源名拼写 |
| Pod 内容器没有 `/opt/hyhal` 目录 | 设备插件版本偏旧 | 升级到 V2.1.0 及以上版本（该版本起会自动挂载 `/opt/hyhal`） |
