# 安装与参数

HAMi 本体用 Helm 装，命令只有一条，麻烦的部分在前面：驱动、容器工具链、厂商设备插件都要先到位，
而且不同厂商的到位标准不一样。

## 集群与工具前置

| 项 | 要求 |
| --- | --- |
| Kubernetes | 1.23 及以上，容器运行时正常 |
| Helm / kubectl | 已安装，账号有装集群级资源的权限 |
| 节点 | 满足各家驱动的操作系统与内核要求 |

装之前先确认一件事：**这个集群有没有在用平台内置的 NVIDIA 调度组件**。用了的话，集群里已经有一个
`volcano-vgpu-device-plugin` 在跑，它和 HAMi 的设备插件会抢同一份 `nvidia.com/gpu`，不能并存。
两者的取舍见[平台侧现状与接入路径](/ecosystem/hami/platform-support)。

## 各厂商的额外前置

驱动和工具包的版本是硬门槛，版本不够插件起不来。

| 厂商 | 额外前置 |
| --- | --- |
| NVIDIA | 驱动版本与卡的型号、业务的 CUDA 版本匹配；容器运行时配好 NVIDIA Container Toolkit |
| 华为昇腾 | 按卡型准备，最小粒度取决于卡类型模板 |
| 海光 DCU | `dtk` 驱动 ≥ 24.04，`hy-smi` v1.6.0 |
| 寒武纪 MLU | `neuware-mlu370-driver` > 5.10，`cntoolkit` > 2.5.3，且每张卡要开 SMLU 模式 |
| 天数智芯 | 驱动版本 > 3.1.0，节点上装 `gpu-manager`（不要装 `gpu-admission`） |
| 摩尔线程 | MT CloudNative Toolkits > 1.9.0，驱动 ≥ 1.2.0 |
| 沐曦 | MetaX Driver ≥ 2.32.0，MetaX GPU Operator ≥ 0.10.2 |
| 昆仑芯 | 驱动 ≥ v5.0.21.16，`xpu-container-toolkit` ≥ `xpu_container_1.0.2-1`，卡型限 P800-OAM |
| 壁仞 | 节点打标签 `biren=on`，部署 HAMi 侧的设备插件 |
| AMD | ROCm 环境（按 ROCm 7.0.2 验证过），`amd-smi static --gpu 0` 能看到型号、显存与 CU 数；用 HAMi 的 `amd-device-plugin`，不要用 ROCm 上游的 `k8s-device-plugin` |

AMD 有一条额外的限制要提前看：显存隔离是通过 glibc 的 `LD_AUDIT` 加载 `libamvgpu.so` 实现的，
需要 `GLIBC_2.34` 以上的符号。基于更老 glibc 的镜像（比如 Ubuntu 20.04、RHEL 8）以及 musl、Alpine 镜像目前用不了。
国产厂商里海光和寒武纪反而省事，它们的设备插件自带设备发现与挂载，不需要额外的运行时组件。

## 装 HAMi

```bash
# 给要管理的节点打标签，NVIDIA 的设备插件默认认 gpu=on
kubectl label nodes <node-name> gpu=on

# 加仓库
helm repo add hami-charts https://project-hami.github.io/HAMi/
helm repo update

# 安装。NVIDIA 用默认值即可；其他厂商加对应的设备开关
helm install hami hami-charts/hami -n kube-system
```

非 NVIDIA 厂商要把对应开关打开，同时指定调度器镜像的 K8s 版本：

```bash
helm install hami hami-charts/hami -n kube-system \
  --set scheduler.kubeScheduler.image.tag=<你的 Kubernetes 版本> \
  --set devices.mthreads.enabled=true
```

Chart 会按集群的 Kubernetes 版本自动挑调度器镜像。想知道本机版本：

```bash
kubectl version -o jsonpath='{.serverVersion.gitVersion}'
```

## 决定切分行为的参数

这些参数在 `hami-scheduler-device` 这个 ConfigMap 里，可以在 Helm 里给，也可以装完直接改 ConfigMap
然后重启相关组件。

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `nvidia.deviceSplitCount` | `10` | 一张卡最多同时分给几个任务 |
| `nvidia.deviceMemoryScaling` | `1` | 显存折算比。大于 1 就是超分，上报值 = 物理显存 × 该系数 |
| `nvidia.deviceCoreScaling` | `1` | 算力折算比，用法同上 |
| `nvidia.memoryFactor` | `1` | 申请时 `nvidia.com/gpumem` 的数值会乘以它。大显存卡上这个参数必须调，见下面的说明 |
| `nvidia.defaultMemory` | `0` | 不写显存时用多少，`0` 表示用满整卡显存 |
| `nvidia.defaultCores` | `0` | 不写算力时用多少百分比，`100` 表示独占 |
| `nvidia.defaultGPUNum` | `1` | 只写了显存或算力、没写 `nvidia.com/gpu` 时自动补几 |
| `nvidia.migstrategy` | `none` | `none` 忽略 MIG，`mixed` 按独立资源分配 MIG 设备 |
| `nvidia.disablecorelimit` | `false` | 置 `true` 关掉算力限制 |

资源名本身也能改，`nvidia.resourceCountName`、`resourceMemoryName`、`resourceMemoryPercentageName`、
`resourceCoreName` 分别对应卡数、显存、显存百分比、算力四个名字。

:::warning memoryFactor 在大显存卡上不是可选项
Kubernetes 的扩展资源数量上限是 32767。`volcano.sh/vgpu-memory` 这类资源按整数上报，
A100 80GB 这种卡不折算就会顶到上限，节点上的显存资源直接算错。平台内置的 Volcano vGPU 默认把
显存折算因子设成 128 MiB 就是这个原因。
:::

## 节点级配置

个别节点需要单独设切分数或工作模式时，改 `hami-device-plugin` 这个 ConfigMap，给节点加条目：

| 字段 | 含义 |
| --- | --- |
| `name` | 节点名 |
| `operatingmode` | `hami-core` 或 `mig`，默认 `hami-core` |
| `devicememoryscaling` | 该节点的显存超分比 |
| `devicecorescaling` | 该节点的算力超分比 |
| `devicesplitcount` | 该节点每卡允许几个任务共享 |
| `filterdevices` | 不注册给 HAMi 的设备类型 |
| `uuid` / `index` | 要忽略的设备 UUID 或序号 |

`operatingmode` 与 MIG 是同一件事的两种说法：节点上已经用 MIG 划好了实例，就让 HAMi 按 MIG 模式工作。
两边都开会出现同一张卡被两套逻辑分别分配的情况。

## 装完怎么确认

```bash
# 调度器与设备插件是否就绪
kubectl get pods -n kube-system | grep -E 'hami-scheduler|hami-device-plugin'

# 节点上有没有出现可分配资源
kubectl get node <node-name> -o jsonpath='{.status.allocatable}' | tr ',' '\n' | grep -E 'nvidia.com|sh/vgpu'

# 设备余量写在节点注解里
kubectl get node <node-name> -o jsonpath='{.metadata.annotations.hami\.io/node-nvidia-register}'
```

三条都对上了，再跑一个只申请显存的小 Pod，进容器看 `nvidia-smi` 的总量是不是等于申请值。
容器里看到的总量的确应该比宿主机小，这是预期行为。

## 升级与卸载

- 升级用 `helm upgrade hami hami-charts/hami -n kube-system`，起不来的话优先怀疑设备插件镜像版本，
  官方历史上有过环境变量改名导致老镜像启动失败的情况。
- 卸载前先把在跑的共享卡 Pod 清掉，否则设备插件走了、容器里的库还挂着，重启会异常。
- 昆仑芯的 vXPU 在 v2.8.0 之前有已知问题，P800 节点上不要停在老版本。
