# 平台侧现状与接入路径

平台里的 HAMi 成分只有一个：NVIDIA 调度组件（`scheduler-nvidia`）打包的
`volcano-vgpu-device-plugin` `v1.11.1`。它不是 HAMi 的残件，而是 HAMi 官方列为「四条到达设备的路径」
之一的 Volcano vGPU 路径的完整实现。差的不是这条路径的完成度，而是**只有这一条路径**。

## 平台上已经有什么

| 项 | 值 |
| --- | --- |
| 组件包 | `plugins/system/scheduler-nvidia`，chart 版本 `1.0.0`，appVersion `1.12.1` |
| 里面的 HAMi 成分 | `volcano-vgpu-device-plugin`，镜像 tag `v1.11.1` |
| 一起装的还有 | NVIDIA GPU Operator `v23.6.0`、Volcano `1.12.1` |
| 覆盖硬件 | 只有 NVIDIA |
| 与厂商的关系 | 源头是 HAMi 的 `Project-HAMi/volcano-vgpu-device-plugin`，隔离靠 HAMi-core |

平台在这个组件里暴露的每一项配置，名字都能在 HAMi 的节点级配置里找到对应：

| 平台侧配置 | 对应 HAMi 的 | 平台默认值 |
| --- | --- | --- |
| 每卡份额数 | `deviceSplitCount` | `10` |
| 显存折算因子 | `memoryFactor` / `gpuMemoryFactor` | `128` MiB |
| 节点专属配置的 `operatingmode` | `operatingmode` | `hami-core` |
| 节点专属配置的 `devicememoryscaling` | `deviceMemoryScaling` | `1` |
| 节点专属配置的 `migstrategy` | `migstrategy` | `none` |

平台侧的调度也接上了：Volcano 的调度器配置里开了 `deviceshare` 插件并置
`deviceshare.VGPUEnable: true`，装箱插件把 `volcano.sh/vgpu-number` 也算进资源权重。
另外 vGPU 开关依赖 Volcano，关掉 Volcano 而留着 vGPU，组件会直接拒绝安装。

## 平台内置路径能做什么

| 能力 | 说明 |
| --- | --- |
| 一张卡分给多个任务 | 默认最多 10 份，可调 |
| 按份额、按显存、按显存百分比、按算力申请 | 四个资源名都可用 |
| 显存超分 | `devicememoryscaling` 大于 1 时上报得比物理显存多 |
| 节点级覆盖 | 个别节点单独设切份数、折算比或 MIG 策略 |
| 指标采集 | 设备插件里的监控容器在 `9394` 端口暴露指标，PodMonitor 默认开启，间隔 30 秒 |
| 按资源名与数量排队、装箱、抢占 | 由 Volcano 负责，账单与配额跟着资源走 |

## 平台内置路径不能做什么

下面这些都要装了完整的 HAMi 才有。

| 缺的能力 | 影响 |
| --- | --- |
| 非 NVIDIA 卡的卡内共享 | AMD、寒武纪、摩尔线程、沐曦、壁仞、天数智芯、昆仑芯在平台上都只能整卡调度 |
| `nvidia.com/gpumem` / `gpucores` 这套资源名 | 业务侧照着 HAMi 文档写的清单在平台上申请不到资源 |
| 卡 UUID、卡型号级别的过滤 | 不能把任务钉在某几张卡或排除某型号 |
| 节点级与卡级的 binpack / spread / mutex 策略 | 平台的装箱由 Volcano 的 binpack 插件管，粒度到不了卡这一层 |
| 运行时优先级抢占 | `nvidia.com/priority` 这类卡内抢占没有 |
| HAMi WebUI | 没有图形界面看每张卡的份额占用 |

## 两套路径的资源名不一样，这是重点

在平台上，同一张 NVIDIA 卡有两套申请口径，因为上报的资源名不同：

| 上报方 | 资源名 | 含义 |
| --- | --- | --- |
| GPU Operator 的设备插件 | `nvidia.com/gpu` | 整卡，一张算一张 |
| `volcano-vgpu-device-plugin` | `volcano.sh/vgpu-number`、`-memory`、`-memory-percentage`、`-cores` | 份额 |

两套名字不重叠，所以它们能在同一个节点上共存，这也是平台默认就能同时用整卡和份额两种模式的原因。

完整 HAMi 的情况不一样：`hami-device-plugin` 上报的正是 `nvidia.com/gpu`，和 GPU Operator 的设备插件撞名。
HAMi 官方给的做法是把 GPU Operator 的设备插件关掉：

```yaml
devicePlugin:
  enabled: false
```

所以往平台上装完整 HAMi 时，要在两件事里选一件：保留 `nvidia.com/gpu` 的整卡口径（那就不能走 HAMi 的
`gpumem` / `gpucores`），或者把整卡口径让给 HAMi（那就关掉 GPU Operator 的设备插件）。
想两套都留，只有在两者资源名不重叠时才成立。

:::warning 别把两套切分逻辑叠在同一个节点上
平台的 `vGPU.enabled` 与完整 HAMi 是两套按份额切分的实现。同一个节点上两套都开，
会有两份设备插件各自维护卡的状态，份额算不准，排障时也很难看出是谁分的。
要换路径就把原先那套关掉。
:::

## 手工接入完整 HAMi 的顺序

1. **先定路线**。只做 NVIDIA 卡的份额共享，用平台内置的就行，不要另装。
   需要非 NVIDIA 卡共享，或者需要按显存精确切 NVIDIA 卡，才装完整 HAMi。
2. **清场**。在平台的 NVIDIA 调度组件配置里把 GPU 虚拟化关掉，避免和 HAMi 争同一张卡。
3. **让出资源名**。关掉 GPU Operator 的设备插件，把 `nvidia.com/gpu` 交给 HAMi。
   DCGM Exporter 不受影响，物理级指标继续上报。
4. **装厂商设备插件**。部分厂商由 HAMi 侧提供插件，部分要用厂商自己的工具包：

   | 厂商 | 设备插件来源 |
   | --- | --- |
   | AMD | HAMi 的 `amd-device-plugin` |
   | 昇腾 | HAMi 的 `ascend-device-plugin` |
   | 昆仑芯 | HAMi 的 `vxpu-device-plugin`（限 P800-OAM） |
   | 壁仞 | HAMi 的 `biren-device-plugin`，节点标签 `biren=on` |
   | 海光 | `dcu-vgpu-device-plugin` |
   | 寒武纪 | 厂商的 `cambricon-device-plugin`，要配 `mode=dynamic-smlu` |
   | 摩尔线程 | 厂商的 MT CloudNative Toolkits |
   | 沐曦 | 厂商的 MetaX GPU Operator 或 GPU Extensions |
   | 天数智芯 | 厂商的 `gpu-manager`，注意不要装成 `gpu-admission` |

5. **装 HAMi**。Helm 一条命令，按厂商打开设备开关。
6. **平台侧建资源规格**。资源名按 HAMi 上报的名字填，不要按平台原来那套填。

原来那套规格不用删。两套资源名不冲突的话可以并存，业务按需要选一种口径提交。

## 怎么核对装对了

```bash
# 平台内置那套的设备插件
kubectl get pod -n volcano-system | grep volcano-device-plugin

# 完整 HAMi 的调度器与设备插件
kubectl get pod -n kube-system | grep -E 'hami-scheduler|hami-device-plugin'

# 两套资源名各自的余量
kubectl get node <node-name> -o jsonpath='{.status.allocatable}' | tr ',' '\n' \
  | grep -E 'nvidia.com|volcano.sh/vgpu'
```

节点上同时出现 `nvidia.com/gpu` 和 `volcano.sh/vgpu-number`，说明两套都在跑，
这正是平台内置路径的默认状态。如果装完整 HAMi 时节点上的 `nvidia.com/gpu` 数量没变，说明 GPU Operator
的设备插件没关掉，HAMi 的设备插件没有真正接上。
