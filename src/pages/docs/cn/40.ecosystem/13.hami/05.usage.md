# 申请与运维

申请共享卡的写法是标准的 Kubernetes 资源申请，只是把资源名换成 HAMi 的那套。写法本身没有平台专有的语法，
难点在于各家资源名不同、单位不同，以及几条只在本厂商成立的限制。

## 各厂商最小写法

只列 `resources.limits` 这一部分，单位与粒度按各家来的。

| 厂商 | 写法 |
| --- | --- |
| NVIDIA | `nvidia.com/gpu: 1`、`nvidia.com/gpumem: 10240`（MiB）、`nvidia.com/gpucores: 50` |
| 华为昇腾 | `huawei.com/Ascend910B: 1`、`huawei.com/Ascend910B-memory: 16384` |
| 海光 | `hygon.com/dcunum: 1`、`hygon.com/dcumem: 2000`、`hygon.com/dcucores: 60` |
| 寒武纪 | `cambricon.com/vmlu: 1`、`cambricon.com/mlu.smlu.vmemory: 20`、`cambricon.com/mlu.smlu.vcore: 10` |
| 天数智芯 | `iluvatar.ai/BI-V150-vgpu: 1`、`iluvatar.ai/BI-V150.vCore: 50`、`iluvatar.ai/BI-V150.vMem: 64` |
| 摩尔线程 | `mthreads.com/vgpu: 1`、`mthreads.com/sgpu-memory: 32`、`mthreads.com/sgpu-core: 8` |
| 沐曦 | `metax-tech.com/sgpu: 1`、`metax-tech.com/vcore: 60`、`metax-tech.com/vmemory: 4` |
| 昆仑芯 | `kunlunxin.com/vxpu: 1`、`kunlunxin.com/vxpu-memory: 24576`；整卡用 `kunlunxin.com/xpu: 1` |
| 壁仞 | `birentech.com/gpu: 1` |
| AMD | `amd.com/gpu: 1`、`amd.com/gpumem: 8192`、`amd.com/gpucores: 25` |

寒武纪、海光、摩尔线程三家有一条共同规则：显存和算力**只在整卡数写 1 的时候生效**，
写 `2` 就是两张整卡，显存和算力会被忽略。昆仑芯反过来，按份切走 `vxpu`、整卡走 `xpu`，两个名字分开。
壁仞只能申请整卡或 SVI 预划好的分片，没法指定显存。

## 一个完整的例子

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: vgpu-demo
spec:
  containers:
    - name: cuda
      image: ubuntu:22.04
      command: ["nvidia-smi"]
      resources:
        limits:
          nvidia.com/gpu: 1            # 一个 vGPU
          nvidia.com/gpumem: 10240     # 显存 10240 MiB
          nvidia.com/gpucores: 50      # 算力 50%
```

沐曦的 sGPU 写法一样，只是换成自己的资源名和单位：

```yaml
      resources:
        limits:
          metax-tech.com/sgpu: 1       # 一个 sGPU
          metax-tech.com/vcore: 60     # 60% 算力
          metax-tech.com/vmemory: 4    # 4 GiB 显存
```

不写显存或算力时按该家的默认值走，通常是「用满」。显存也可以用百分比的形式给，
NVIDIA 上是 `nvidia.com/gpumem-percentage`，平台内置的 Volcano vGPU 上也有一项
`volcano.sh/vgpu-memory-percentage`，两边名字不同、不能互换。

## 注解

注解控制的是**挑哪张卡**和**怎么排**，跟申请多少资源是两件事。

| 注解 | 作用 |
| --- | --- |
| `nvidia.com/use-gpuuuid` | 只能用列出的这几张卡 |
| `nvidia.com/nouse-gpuuuid` | 排除列出的这几张卡 |
| `nvidia.com/use-gputype` | 只能用列出的型号 |
| `nvidia.com/nouse-gputype` | 排除列出的型号 |
| `hami.io/node-scheduler-policy` | 节点层策略，`binpack` 或 `spread` |
| `hami.io/gpu-scheduler-policy` | 卡层策略，`binpack`、`spread` 或 `mutex`。`mutex` 表示只放到完全没有负载的卡上 |
| `hami.io/device-scoring-weights` | 设备打分的权重，形如 `slot=1,core=1,memory=3`，三项都要写 |
| `nvidia.com/vgpu-mode` | 这个 Pod 用 `hami-core` 还是 `mig` |

海光与寒武纪各有一套自己的型号过滤注解：`hygon.com/use-dcutype`、`hygon.com/nouse-dcutype`、
`cambricon.com/use-mlutype`、`cambricon.com/nouse-mlutype`。名字带厂商前缀的注解只对那一家生效。

## 优先级只有两级

`nvidia.com/priority` 的取值是 `0` 和 `1`，`0` 是高、`1` 是低。它的作用范围是**同一张卡内的运行时抢占**：
低优先级任务在跑，来了一个高优先级的，高优先级的会把低优先级的暂停、占用资源、跑完再让低优先级的恢复。

它不解决排队问题。多个任务在等资源、要按提交优先级决定谁先拿到，HAMi 自己不做这件事，
要交给 Volcano 的队列：Volcano 定义不同优先级的队列并负责抢占，HAMi 负责卡内的共享与运行时抢占。
两个机制叠在一起才凑出完整的多级优先级。

## 容器里的环境变量

| 变量 | 取值 | 作用 |
| --- | --- | --- |
| `GPU_CORE_UTILIZATION_POLICY` | `default` / `force` / `disable` | `force` 把算力严格压在申请的百分比以内；`disable` 不限制 |
| `CUDA_DISABLE_CONTROL` | `true` / `false` | 置 `true` 时 HAMi-Core 在容器里完全不生效，隔离与限制都没了，只用于排障 |
| `LIBCUDA_LOG_LEVEL` | `0` | 关掉容器输出里的 `[HAMI-core ...]` 日志 |

`CUDA_DISABLE_CONTROL=true` 这条特别要留意，它常被用来绕过启动报错，然后忘了删，导致限制事实上失效。

## 指标从哪看

| 来源 | 端口 | 内容 |
| --- | --- | --- |
| `hami-device-plugin` | `31992` | 每个容器的 vGPU 指标，端口可用 `devicePlugin.service.httpPort` 改 |
| `hami-scheduler` 的 Webhook | `31998` | 调度器 Webhook 的服务端口 |
| 平台内置的 `volcano-device-plugin` | `9394` | 走的是内置那条路径时的 vGPU 指标 |

两个端口是两个来源，别对着 `9394` 找 HAMi 的容器级指标。官方提供 Grafana 看板模板，
覆盖设备分配情况与实时用量。

## 跑大模型推理要注意

- 单卡跑 vLLM 并申请 `nvidia.com/gpumem`，不需要额外配置。
- **多卡张量并行**要求 HAMi `v2.9.0` 及以上。更低版本会因为多个进程共享同一份 CUDA 显存状态文件导致
  NCCL 初始化失败。这条在 vLLM 0.18 以上版本上才会碰到。
- 在 Volcano 环境里跑，`tensor_parallel_size` 要按 Pod 单独设，不要设成所有 Pod 共用。
- 如果启动时报 CUDA graph 捕获相关的错误，加 `--enforce-eager` 试。

另外，按上报显存大小来决定用多少显存的框架（vLLM 就是这一类）会老老实实只用配额。
所以给推理服务分显存时不用留太多余量，但也不能给到装不下模型。
