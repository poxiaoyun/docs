# 架构与调度链路

HAMi 本身不重写 Kubernetes 的调度器，而是往原有的调度流程里插两个环节：一个准入 Webhook 改 Pod 的调度器名字，
一个调度扩展在打分阶段补上设备维度的判断。设备分配的结果最后由节点侧的设备插件和容器内的库落实。

## 四个组件

| 组件 | 跑在哪 | 干什么 |
| --- | --- | --- |
| HAMi MutatingWebhook | 控制面 | 扫 Pod 的 `resources` 字段。如果每个资源项都属于 CPU、内存或 HAMi 认识的资源，就把这个 Pod 的 `schedulerName` 改成 `hami-scheduler` |
| HAMi Scheduler | 控制面 | 承担调度扩展角色：选节点、选设备槽，并维护一份全局的异构设备视图 |
| `hami-device-plugin` | 每个设备节点 | 从 Pod 的注解里读出调度结果，把对应的设备映射进容器；周期性把设备余量写回节点 |
| HAMi-Core | 容器内 | 执行显存与算力的硬限制，是「限制真的生效」的那一层 |

Webhook 只对**资源里出现 HAMi 资源**的 Pod 动手，其余 Pod 照旧走默认调度器。也就是说装完 HAMi 不会把整个集群的
调度行为改变，只有真正申请共享卡的 Pod 换了一条路径。

## 一个 Pod 的完整链路

1. Pod 提交，HAMi 的准入 Webhook 拦住它，判断资源项、改 `schedulerName`，必要时补默认值。
2. `hami-scheduler` 接管，先按节点策略挑节点，再按设备策略挑具体的卡和份额。
3. 调度结果写进 Pod 的注解。
4. 目标节点上的设备插件读到注解，把设备挂进容器，并在启动阶段挂上资源控制库。
5. 容器启动时控制库生效，超出申请的显存分配会被拒，超出的算力被节流。

节点策略和设备策略是两层，各自可以选集中或分散：

| 配置 | 可选值 | 含义 |
| --- | --- | --- |
| `scheduler.defaultSchedulerPolicy.nodeSchedulerPolicy` | `binpack`（默认）/ `spread` | 尽量把任务塞到已经用过的节点，还是分散到不同节点 |
| `scheduler.defaultSchedulerPolicy.gpuSchedulerPolicy` | `binpack` / `spread`（默认）/ `mutex` | 尽量共用同一张卡、分散到不同卡，还是只用完全空闲的卡 |

单个 Pod 可以在注解里覆盖这两项，不改全局配置。

## 设备信息怎么到调度器手里

Kubernetes 的 Device Plugin 接口一次只能上报一种资源，所以显存和算力没法跟卡数一起写进 `capacity`。
HAMi 的做法是把这几类信息分开送：

| 信息 | 走哪条路 | 表现 |
| --- | --- | --- |
| 卡数 | 标准 Device Plugin 上报 | 节点 `capacity` 与 `allocatable` 里出现 `nvidia.com/gpu` |
| 显存、算力、型号、NUMA、健康状态 | 写进节点注解 | 注解 `hami.io/node-nvidia-register`，值是 JSON 数组，每个元素含 `id`、`count`、`devmem`、`devcore`、`type`、`numa`、`mode`、`health` |
| 设备独占与过滤 | 注解配合 | `nvidia.com/use-gpuuuid`、`nvidia.com/nouse-gputype` 这类注解由 Webhook 落到调度判断里 |

所以在节点上看到 `capacity` 里只有 `nvidia.com/gpu`、没有 `nvidia.com/gpumem`，是设计如此，不是没装好。
想知道某个节点还剩多少显存，看注解而不是看 `capacity`。

## 限制是在哪一层落实的

NVIDIA 卡上的实现方式是把一个库注入到容器里：

- 宿主机的 `/usr/local/vgpu/libvgpu.so` 通过 `/etc/ld.so.preload` 进容器，覆盖 CUDA 的相关调用。
- 显存：拦截显存分配调用，超过 `nvidia.com/gpumem` 就返回分配失败，应用侧看到的是一次 OOM。
- 算力：对 kernel launch 走令牌桶节流，让实际占用不超过 `nvidia.com/gpucores`。
- 监控：库同时接管显存查询类调用，所以容器里 `nvidia-smi` 看到的总量是配额值，不是物理值。

这套做法有两个明确的边界，选型时要认：

- **绕过 CUDA 库的负载不受管控。** 直接调驱动 API、或者跑在 Docker-in-Docker 里的进程，都不经过被拦截的那一层。
- **隔离强度低于 MIG。** 它是用户态拦截，不是硬件分区，多租户噪声隔离是尽力而为。

如果容器里设了 `CUDA_DISABLE_CONTROL=true`，控制库会整体不生效，这条是留给排障用的，别留在生产配置里。

## vGPU 与 MIG 怎么选

| 对比项 | HAMi vGPU | NVIDIA MIG |
| --- | --- | --- |
| 硬件要求 | 任意 NVIDIA 卡，驱动 v440 以上 | Ampere 及更新的架构，如 A100、H100、A30 |
| 隔离机制 | 用户态库拦截 | 硬件引擎分区 |
| 显存限制 | 软限制，在 CUDA API 层 | 硬限制，硬件强制 |
| 算力限制 | 软限制，库内节流 | 硬限制，独立 SM 分区 |
| 切分粒度 | 1 MiB 显存、1% 算力 | 固定的 MIG 配置档，如 1g.10gb |
| 动态调整 | 支持，不用清空节点 | 要重配 MIG 配置文件 |
| 噪声隔离 | 尽力而为 | 强隔离 |

卡本身不支持 MIG、或者需要灵活指定显存大小时选 vGPU；硬隔离是合规或 SLA 硬要求时选 MIG。
HAMi 也支持通过 `mig-parted` 做动态 MIG，`hami.io/vgpu-mode` 注解可以让单个 Pod 指定用 `hami-core` 还是 `mig`。

## 和其他调度器的关系

HAMi 可以和几种调度体系配合，但关系不一样：

| 对象 | 关系 |
| --- | --- |
| `kube-scheduler` | 并行共存。HAMi 是调度扩展，只接管被 Webhook 改过名字的 Pod |
| Volcano | 两种配合方式。用 `volcano-vgpu-device-plugin` 走 Volcano 的 `deviceshare`；或者用 HAMi 主路径、由 Volcano 负责队列与抢占，HAMi 负责卡内共享 |
| Koordinator | 节点上装 HAMi-Core，Pod 侧按 HAMi 的资源名申请，由 Koordinator 调度 |
| Kueue、KAI Scheduler | 由对方负责排队或调度，复用 HAMi-Core 做隔离 |

官方把到达设备的路径拆成四条：HAMi、HAMi-DRA、Volcano vGPU、KAI Scheduler。后三条自己调度，
但隔离仍然依赖 HAMi-Core。

KubeVirt 与 Kata Containers 目前不兼容，原因是它们依赖虚拟机做隔离，而 HAMi 的设备插件走的是设备直挂。
这类场景不要按普通容器的经验套。
