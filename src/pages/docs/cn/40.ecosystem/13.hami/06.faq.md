# FAQ

## 速查

| 现象 | 可能原因 | 怎么办 |
| --- | --- | --- |
| 节点上显示 10 个 vGPU，一个 Pod 却拿不到同一张卡的两个 | vGPU 是任务视图，不是可累加的资源 | 属设计如此。要更多算力就调大显存与算力份额，或申请两张整卡 |
| 节点 `capacity` 里只有 `nvidia.com/gpu`，没有 `gpumem` | Device Plugin 一次只能上报一种资源 | 属预期。显存与算力写在节点注解里，看 `hami.io/node-*-register` |
| 容器里 `nvidia-smi` 的显存比宿主机少 | 控制库接管了显存查询 | 属预期。按配额上报，宿主机上看到的才是物理值 |
| 申请了 `nvidia.com/gpumem` 但没被限制住 | 限制被绕过了 | 按下面「限制为什么没生效」逐条排查 |
| 容器日志一直刷 `[HAMI-core Warn(...)]` | 控制库的正常日志 | 不用管；要静默就设 `LIBCUDA_LOG_LEVEL=0` |
| 装完 HAMi 后节点上的卡数不对 | 两套设备插件都在上报同一份资源 | 关掉 GPU Operator 的设备插件，或停掉另一套切分实现 |
| 换了切份数但节点上没变化 | 参数在设备插件的启动参数里 | 重新下发设备插件，确认 Pod 被重建 |
| 卡里看不到自己要的资源名 | 资源名抄的是另一家的口径 | 用节点上实际出现的资源名，见[支持的设备与资源名](/ecosystem/hami/device-matrix) |
| 昇腾、海光节点上还要不要装额外运行时 | 看厂商插件有没有内置 | 海光与寒武纪的插件自带设备发现与挂载，不需要 |
| KubeVirt、Kata 容器里拿不到卡 | 与设备直挂方案不兼容 | 当前不支持，需要另找方案 |
| 大模型多卡推理起不来 | HAMi 版本低 | 张量并行要 `v2.9.0` 及以上 |

## 10 个 vGPU 和一张卡上要两个，是两回事

`deviceSplitCount: 10` 的含义是「这张卡最多同时服务 10 个任务」，不是「这张卡被切成了 10 份可累加的资源」。

- vGPU 是同一张物理卡在不同任务里的**视图**，划分的是可见性，不增加物理资源。
- 申请 `nvidia.com/gpu: 2` 表示要两张**物理卡**，不是同一张卡上的两个 vGPU。
- 容器里看到的 GPU UUID 与节点上物理卡的 UUID 一致，也印证了这一点。

要提高单个任务的算力，办法是把 `nvidia.com/gpucores` 和 `nvidia.com/gpumem` 调到需要的值，
而不是多申请几个 vGPU。

## 限制为什么没生效

按常见程度排：

1. 容器里设了 `CUDA_DISABLE_CONTROL=true`。这条最容易被漏掉，因为它常用于绕过启动报错。
2. 负载跑在 Docker-in-Docker 里，进程不经过被注入的那一层。
3. 应用直接调用 GPU 驱动 API，绕过了 CUDA 库。
4. 节点上 `nvidia-container-runtime` 不是默认运行时，控制库没有被挂进容器。

判定方法很直接：进容器看 `nvidia-smi` 报的显存总量。等于配额说明控制库生效了；等于物理显存说明没生效。

## HAMi、Volcano vGPU、厂商官方插件三者的关系

三种东西都在管 GPU 资源，但资源名和适用场景不一样。

| | 资源名 | 谁来调度 | 适合 |
| --- | --- | --- | --- |
| HAMi 主路径 | `nvidia.com/gpu`、`nvidia.com/gpumem`、`nvidia.com/gpucores` | HAMi 调度扩展 | 要按显存和算力精细切、要卡与型号级别的过滤 |
| Volcano vGPU | `volcano.sh/vgpu-number`、`-memory`、`-cores` | Volcano 的 `deviceshare` 插件 | 集群本来就用 Volcano，只要按份额共享 |
| 厂商官方插件 | 各家自己的扩展资源名 | 看集群配置 | 整卡分配、不需要共享 |

共存规则：

- HAMi 与 NVIDIA 官方设备插件**不建议共存**，两者都上报 `nvidia.com/gpu`，会冲突。
- HAMi 与 Volcano vGPU **理论上可以共存**，但推荐只开一个。
- Volcano vGPU 与 NVIDIA 官方设备插件**理论上可以共存**，因为资源名不重叠。平台内置的 NVIDIA
  调度组件就是这一种组合。

## 多节点多卡分布式训练

支持，但边界要清楚：

- 一个 Pod 可以同时使用**同一个节点上**的多张卡。
- 一个 Pod **不能跨节点**。
- 跨节点靠多个 Pod 配合分布式框架（PyTorch、TensorFlow、Horovod 等）实现，进程间通过 NCCL、RDMA 通信。

所以「多机多卡」在 Kubernetes 里的形态是一组 Pod，不是一个大 Pod。多卡任务还需要成组调度
（gang scheduling）保证要么全拿到卡、要么都不启动，这一层由 Volcano 的 gang 插件负责，HAMi 不管。

## 和平台内置的那套怎么配合

平台的 NVIDIA 调度组件里已经带了 Volcano vGPU 的设备插件，走的是 `volcano.sh/vgpu-*` 这套资源名。
它和 HAMi 主路径是两条并列的路线，不是上下游关系。要点有三个：

1. 只做 NVIDIA 卡的份额共享，用平台内置的就够了，不用另装。
2. 要非 NVIDIA 卡的共享，或者要按显存精确切 NVIDIA 卡，才装完整 HAMi。
3. 装完整 HAMi 时，把平台组件里的 GPU 虚拟化开关关掉，并处理好 `nvidia.com/gpu` 的归属。

逐项对照和完整顺序见[平台侧现状与接入路径](/ecosystem/hami/platform-support)。
