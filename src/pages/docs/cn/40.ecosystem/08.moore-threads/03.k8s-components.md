# Kubernetes 组件

集群侧的东西打成一个包，叫 **MT GPU Operator**，当前版本 v2.1.0，Helm chart 文件名是 `mt-gpu-operator-2.1.0.tgz`，支持 Kubernetes 1.19 到 1.32，安装时可选 full 与 core 两种模式。装完集群里会多出两个 CRD：`ClusterConfig`（`mthreads.com/v1alpha4`）与 `ClusterPolicy`（`mthreads.com/v1beta2`），组件的开关和资源名这类设置走这两个对象。

| 组件 | 作用 | 不装的后果 |
| --- | --- | --- |
| `mt-device-plugin` | 把卡注册成 Kubernetes 资源 | 节点上没有 `mthreads.com/gpu`，任务申请不到卡 |
| `mt-universal-gpu-device-controller` | 设备分配与准入控制 | 需要按策略分配设备的场景走不通 |
| `mt-gpu-feature-discovery` | 给节点打上卡型号、驱动版本这类标签 | 想按型号挑节点时没有依据 |
| `mt-container-toolkit-daemonset` | 在节点上铺开容器工具链 | 容器里看不到卡 |
| `mt-operator-validator` | 装完自检 | 出问题要自己一项一项查 |
| `mt-gpu-webhook` | sGPU 场景的准入与设备注入 | 申请 sGPU 切分资源时进不来 |
| `mt-gpushare-scheduler` | 卡内共享调度 | 一张卡分给多个任务的能力不可用 |

## 从哪拿组件包

组件不开源。MooreThreads 的 GitHub 组织下没有 device-plugin 和 operator 仓库，组件包随 KUAE 云原生套件发布，**没有公开的 Helm repo**。

:::warning 装之前先向厂商要包
`helm repo add` 那一套在这里用不上。组件包和 chart 要向厂商获取，顺带拿到与驱动、Kubernetes 版本对应的配套说明。别去第三方镜像站找同名 chart，版本对不上很难查。
:::

## 设备插件上报的资源名

默认只上报一个整卡资源：

```
mthreads.com/gpu
```

申请几张卡就写几：

```yaml
resources:
  limits:
    mthreads.com/gpu: 2
```

要改名就动 `ClusterPolicy` 的 `gpuResourceName` 字段，比如写成 `example.com/MTT-S5000-80G`。改完之后节点上报的资源名跟着变，平台侧的规格与配额要按新名字重建，已经建好的规格不会自动跟着改。

## 监控

| 组件 | 端口 / 路径 | 说明 |
| --- | --- | --- |
| `mt-dcgm` | hostPort 5555 | hostengine，采集侧的服务 |
| `mt-dcgm-exporter` | `/metrics`，端口 9400 | 对外暴露指标，默认采集间隔 10s |

指标名沿用 `DCGM_FI_*` 前缀，另外还有 MTLink 相关的专属指标。9400 这个端口和 NVIDIA DCGM Exporter 的默认端口是同一个，同一个集群里两家都有的时候，得把其中一个改掉，不然后面接监控看板时数据会串。

:::warning 老文档里的 mt-gpu-exporter
`mt-gpu-exporter` 已经不再产品化支持，新集群直接用 `mt-dcgm` 加 `mt-dcgm-exporter` 这一套。
:::

## 一卡多用

有两条路，给出的东西不一样，别混着规划：

| 路线 | 怎么切 | 资源名 / 形态 | 适用 |
| --- | --- | --- | --- |
| sGPU | Kubernetes 内切分，算力按时间片权重，显存按 512MiB 为单位 | `mthreads.com/sgpu-core`、`mthreads.com/sgpu-memory` | 集群里多个任务共享一张卡 |
| MT vGPU | 宿主侧硬件切分，mdev / SR-IOV，类型名 `mtgpu-1101` | 设备节点，**不是 Kubernetes 资源名** | 需要硬件级隔离的场景，S4000 与 S5000 标称支持 |

sGPU 需要启用 GPU scheduler 与 webhook（对应上面表里的 `mt-gpushare-scheduler` 和 `mt-gpu-webhook`），两个资源要一起申请：

```yaml
resources:
  limits:
    mthreads.com/sgpu-core: <时间片权重>
    mthreads.com/sgpu-memory: <按 512MiB 为单位>
```

sGPU 是显存独占、算力按权重分时，**不是强隔离**，需要独立显存与故障隔离的场景不要按它规划。

另外 `mthreads.com/vgpu` 这个资源名出现在 HAMi 的场景里，HAMi 官方文档给摩尔线程配的还有
`mthreads.com/sgpu-memory`（1 个单位 512MB）与 `mthreads.com/sgpu-core`，并注明只在 MTT S4000 上验证过，
其他型号上不要照搬。这条路线也不支持多卡共享，一个 Pod 里只能共享一张卡。见 [HAMi](/ecosystem/hami)。

## 和 Volcano 的关系

没有找到官方针对摩尔线程的 Volcano 插件。MT 自带的 `mt-gpu-scheduler` 与 `mt-gpushare-scheduler` 是厂商自研的调度组件，**它们与 Volcano 的关系未确认**。

:::info 这条要问厂商
要在一个集群里同时用 Volcano 和摩尔线程的调度组件，先找厂商确认两者是否冲突、谁负责卡内切分。这里给不出结论，也不建议按「设备插件报标准扩展资源、Volcano 按资源名排」的通用路径直接推。
:::

## 装完怎么验证

```bash
# 节点上出现了可分配的摩尔线程资源
kubectl describe node <gpu-node> | grep -A 5 "Allocatable" | grep mthreads.com

# 组件 Pod 起来了
kubectl get pods -A | grep -i mt-

# 监控组件在跑
kubectl get pods -A | grep -i dcgm

# 两个 CRD 都在
kubectl get crd | grep mthreads.com
```

再交一个最小任务，申请 1 张卡，容器里跑 `mthreads-gmi` 能打出卡就算通了。
