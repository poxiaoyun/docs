# Build & Environment

This page is for people who want to **run the console locally** or **deploy it into their own environment**. After reading it you can do all of this on your own: install the environment, start the dev server, build both outputs, and understand what each environment variable does.

## Get it running with one block of commands

```bash
# Install dependencies (first time only)
pnpm install

# Start the local development server
pnpm dev
```

Then open `http://localhost:8000`. The dev server does not include a back end itself; it **proxies** requests such as `/api` and `/airouter-data` to a back-end address — see "Local development proxy" below.

## Before you start

| Requirement | Version | Notes |
| --- | --- | --- |
| Node.js | `>= 20` | Below this, installing dependencies or starting will fail |
| pnpm | `10.15.0` | The project pins this package-manager version |
| A reachable back end | — | Locally it points at a development back end by default, and you need an account for it |

## Common commands

| Command | What it does |
| --- | --- |
| `pnpm install` | Install dependencies |
| `pnpm dev` | Start the dev server on port `8000` |
| `pnpm build` | Type-check, then build; produces the regular-user interface |
| `pnpm build:boss` | Build the BOSS interface |
| `pnpm preview` / `pnpm start` | Preview the build output |
| `pnpm test` | Run unit tests |
| `pnpm lint` | Check code standards |
| `pnpm fm:check` | Check code formatting |
| `make build` | Build both outputs in turn, injecting build information and raising Node's memory limit |

## Two build outputs

The same codebase can build **two interfaces**, switched by one environment variable. This is the easiest thing to get confused about:

| `VITE_PLATFORM` | Output directory | Path | Interface |
| --- | --- | --- | --- |
| `console` (default) | `dist/console` | `/console` | The regular-user AI Platform, Chat App and Moha Hub |
| `boss` | `dist/boss` | `/boss` | The BOSS portal for platform admins |

`VITE_ASSETS_DIR` can set the static asset directory separately; when it is not set, it follows the path.

:::warning Change these two variables and the URL changes with them

`VITE_PLATFORM` decides both the output directory and the page's base path. If you change the output directory but forget the path mapping in the gateway, the page goes blank or assets return 404. Before changing it, confirm that the routing on the deployment side changes too.

:::

## Local development proxy

The dev server listens on port `8000`, and the preview server for the build output listens on port `3080`. Because the back end is not on the same port, the dev server forwards these paths:

| Front-end path | Forwarded to | Purpose |
| --- | --- | --- |
| `/api` | `PROXY_TARGET` | All management-plane APIs |
| `/moha` | `PROXY_TARGET` | Moha Hub requests |
| `/airouter-data` | `PROXY_TARGET` | The model-conversation data plane |
| `/console/airouter-data` | `PROXY_TARGET` (with the `/console` prefix stripped) | The data plane when written with a prefix |
| `/avatars` | `PROXY_TARGET` + `/api/iam/avatars` | Avatars and other static resources |

When `PROXY_TARGET` is not set it defaults to the development back end `https://rune.develop.xiaoshiai.cn`.

## Environment variables at a glance

| Variable | Stage | What it controls | What changes if you get it wrong |
| --- | --- | --- | --- |
| `VITE_PLATFORM` | Build | Whether to build `console` or `boss` | Both the output directory and the path change |
| `VITE_ASSETS_DIR` | Build | The static asset directory | A wrong value makes images, icons and other assets 404 |
| `PROXY_TARGET` | Local dev | The back end the dev server proxies to | All local APIs point at the new back end; a wrong value breaks every call |
| `BUILD_DATE` | Build | The build time shown in the interface | Only affects the displayed build information |
| `GIT_VERSION` | Build | The version number shown in the interface | Only affects the displayed build information |
| `GIT_COMMIT` | Build | The commit shown in the interface | Only affects the displayed build information |
| `GIT_BRANCH` | Build | The branch shown in the interface | Only affects the displayed build information |
| `NODE_OPTIONS` | Build | The memory limit available to Node | Too small, and the build can run out of memory halfway |
| `LISTEN_PORT` | Runtime | The port nginx listens on inside the container | The container port changes; keep it in step with the Service |
| `API_SERVER` | Runtime | The back-end API service address | The deployment template injects it into the container; a wrong address means the page cannot call the APIs |
| `LLM_ROUTER_SERVER` | Runtime | The model data-plane service address | Injected by the deployment template; a wrong address makes conversation features unavailable |

:::tip Which variables are for whom

- Local development only: the only one you really care about is `PROXY_TARGET`.
- Producing a build: care about `VITE_PLATFORM`, and add `GIT_*` and `BUILD_DATE` when you want version information.
- Deploying to a cluster: care about `LISTEN_PORT`, `API_SERVER` and `LLM_ROUTER_SERVER`; the deployment template injects them.

:::

## How build information gets in

At build time the following values are written into the page so the interface can show version information. The fallbacks are:

| Displayed item | Source variable | Shown when not provided |
| --- | --- | --- |
| Build time | `BUILD_DATE` | The current time |
| Version | `GIT_VERSION` | `development` |
| Commit | `GIT_COMMIT` | `unknown` |
| Branch | `GIT_BRANCH` | `unknown` |
| Node version | Read automatically at build time | — |

## Containerisation and deployment

### Image

The image is based on `nginx:alpine`. It copies the built `dist` directory in, configures nginx from a template, and listens on `8080` inside the container by default.

### What nginx inside the container does

| Responsibility | Behaviour |
| --- | --- |
| Health check | `/healthz` returns `{"status":"ok"}` |
| Serve the pages | `/console/` points at `dist/console/`, `/boss/` at `dist/boss/` |
| Single-page-app fallback | When a requested file does not exist, fall back to the matching `index.html`, so refreshing never 404s |
| Caching | Hashed js, css, images and fonts are cached long-term |
| Redirect | `/` redirects to `/console/` |

### Helm deployment

The deployment package lives under `deploy/console`. Its `apiServer`, `llmRouterServer` and `containerPorts.http` values are injected as the container's `API_SERVER`, `LLM_ROUTER_SERVER` and `LISTEN_PORT` environment variables, and the container gets liveness and readiness probes against `/healthz`. In other words: **to change the back-end address you do not repackage the image — you change the value in the deployment package.**

### Continuous integration

When code is pushed or a merge request is opened, the pipeline runs in order: code-standard check → format check → unit tests → build both outputs → build and push the image. When you push a tag it additionally publishes the Helm chart.

## Common problems

| Symptom | Possible cause | What to do |
| --- | --- | --- |
| Installing or starting reports a Node version error | Node is below 20 | Upgrade Node and install dependencies with pnpm |
| The build runs out of memory halfway | Node's memory limit is too low | Raise the value of `NODE_OPTIONS` |
| The local page opens but every API errors | The back end behind `PROXY_TARGET` is unreachable | Point it at a back end you can reach |
| After deployment the page is blank and assets 404 | The build-time path and the gateway mapping disagree | Confirm `VITE_PLATFORM` matches the path configured in the gateway |
| The container starts but probes fail | `LISTEN_PORT` does not match the probe or Service port | Make all three agree |
