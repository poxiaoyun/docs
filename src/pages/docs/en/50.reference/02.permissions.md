This page explains the permission model used by the console front end: what permission strings look like, which roles produce them, and what each scope can see.

> ⚠️ **Note**: In the current version, front-end permissions are **derived from roles on the front end** rather than fetched as a permission list from the back end. The comment at `src/auth/authz/context.tsx:28-31` states: "generate a permission list from roles as a simulation; used while the back end has no `/permissions` API, and can later be replaced by an API call." This page therefore describes **UI-level** access control; whether the server enforces the same checks is out of scope here.

---

## Permission string format

A permission is written `resource:action`, for example `instance:create` or `workspace:list`. The check is implemented at `src/auth/authz/context.tsx:153-167`:

1. If the user has `*:*`, allow immediately (system administrator);
2. If the user has `${resource}:*`, allow any action on that resource;
3. Otherwise match `${resource}:${action}` exactly;
4. When `can()` is called with a `service`, match the three-part form `${service}:${resource}:${action}`.

> 💡 **Tip**: Business code commonly calls `can('create', 'instance')` or `can('list', 'workspace')` — the argument order is **action first, resource second** (`src/auth/authz/types.ts:18-24`).

## Scope model

A role record uses the `UserRole` structure (`src/types/member.ts:22-29`): a user name plus optional `tenant`, `workspace` and `cluster` fields and a `roles` array. These combine into three scopes:

| Scope | Condition (`roles` contains `admin`) | Management UI |
|-------|--------------------------------------|---------------|
| **System** | No `tenant` and no `workspace` | BOSS |
| **Tenant** | Has `tenant`, no `workspace` | Console |
| **Workspace** | Has `tenant` and `workspace` | Console |

The role enum is defined at `src/types/tenant.ts:18-22` and only has three values: `admin`, `member`, `developer`. "Tenant administrator" is not a separate enum value — it is a record whose role is `admin` **with a `tenant` scope**; a system administrator is an `admin` **without** `tenant`/`workspace`.

> ⚠️ **Note**: The derivation logic has no branch for a workspace-scoped `admin` — an `admin` record that carries a `workspace` produces no permissions. Whether that is intended is not confirmed.

## Permissions produced by each role

The table mirrors `generatePermissionsFromRoles()` (`src/auth/authz/context.tsx:32-85`); the final list is de-duplicated:

| Role record | Generated permissions |
|-------------|-----------------------|
| `admin`, no `tenant`, no `workspace` (system administrator) | `*:*` |
| `admin` + `tenant` (tenant administrator) | `workspace:*`, `member:*`, `quota:*`, `instance:*`, `image:*`, `template:*`, `volume:*` |
| `developer` + `tenant` | `workspace:list`, `workspace:get`, `instance:*`, `image:list`, `image:get`, `template:list`, `template:get` |
| `member` + `tenant` | `workspace:list`, `workspace:get`, `instance:list`, `instance:get`, `image:list`, `image:get` |

This yields the following UI differences:

| Capability | System admin | Tenant admin | Developer | Member |
|------------|:---:|:---:|:---:|:---:|
| View workspaces | ✅ | ✅ | ✅ | ✅ |
| Create/edit/delete workspaces | ✅ | ✅ | ❌ | ❌ |
| Full instance operations | ✅ | ✅ | ✅ | ❌ |
| View instances | ✅ | ✅ | ✅ | ✅ |
| View images | ✅ | ✅ | ✅ | ✅ |
| Create/edit/delete images | ✅ | ✅ | ❌ | ❌ |
| View templates | ✅ | ✅ | ✅ | ❌ |
| Create/edit/delete templates | ✅ | ✅ | ❌ | ❌ |
| Member management | ✅ | ✅ | ❌ | ❌ |
| Quota management | ✅ | ✅ | ❌ | ❌ |
| Storage volume management | ✅ | ✅ | ❌ | ❌ |
| Access BOSS | ✅ | ❌ | ❌ | ❌ |

> 💡 **Tip**: The system administrator's `*:*` makes `can()` return `true` for any resource and action — equivalent to holding every permission.

## Fetching and refreshing roles

- Role data comes from `GET /api/iam/current/roles` (`src/services/account.ts:98-101`) and is fetched automatically after authentication succeeds (`src/auth/authz/context.tsx:109-123`).
- When not authenticated the permission list is cleared (`src/auth/authz/context.tsx:113-116`); a failed fetch clears it too and ends loading (`:139-143`).
- `refresh()` re-requests the roles endpoint (`src/auth/authz/context.tsx:210`) and can be used after sign-in or after switching tenant/workspace.
- `hasRole(role, scope?)` is a simple role check: if the current user is a system administrator it returns `true` for any role query (`src/auth/authz/context.tsx:182-200`).

## FAQ

### Why is a button missing?

The UI hides entries and action buttons based on `can()`. If you need more permissions, ask a tenant administrator to adjust your role.

### Permissions did not change after switching tenant

Permissions are tied to role records, so the role list must be re-fetched after switching tenant. The console triggers this automatically when the authentication state changes (`src/auth/authz/context.tsx:109-123`); if it still does not take effect, refresh the page.
