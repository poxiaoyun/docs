# Permission Model

Some buttons you can see and some you cannot; a colleague has a menu item that you do not. This is not the page failing — it is a **difference in roles**. This page covers three things: which roles the platform has, what each one can do, and why your buttons disappear.

## The conclusion in one line

The platform has only **three roles**: `admin`, `developer` and `member`. One role combined with different scopes is what produces the familiar identities "platform admin / tenant admin / developer / member".

## What each role can do

| Capability | Platform admin | Tenant admin | Developer | Member |
| --- | :---: | :---: | :---: | :---: |
| View workspaces | Yes | Yes | Yes | Yes |
| Create / edit / delete workspaces | Yes | Yes | No | No |
| View instances (inference, fine-tuning, dev environments, …) | Yes | Yes | Yes | Yes |
| Create / edit / delete / start / stop instances | Yes | Yes | Yes | No |
| View images | Yes | Yes | Yes | Yes |
| Create / edit / delete images | Yes | Yes | No | No |
| View templates | Yes | Yes | Yes | No |
| Create / edit / delete templates | Yes | Yes | No | No |
| Manage members | Yes | Yes | No | No |
| Manage quota | Yes | Yes | No | No |
| Create / delete storage volumes | Yes | Yes | No | No |
| Access the BOSS admin portal | Yes | No | No | No |

:::tip Four sentences to remember the difference

- **Platform admin**: can do anything, including entering BOSS.
- **Tenant admin**: can do anything inside their own tenant, but cannot enter BOSS.
- **Developer**: can build everything that "runs" except workspaces — instances can be created and deleted freely, but people, quota and storage volumes belong to admins.
- **Member**: read only, no changes.

:::

## How roles combine with scope

You will hear four names, but there are still only three roles. The difference is **which scope** the role is assigned at:

| Name you hear | What it actually is | Which interface it sees |
| --- | --- | --- |
| **Platform admin** | An `admin` with no tenant and no workspace | BOSS |
| **Tenant admin** | An `admin` scoped to a particular tenant | The AI Platform |
| **Developer** | A `developer` scoped to a particular tenant | The AI Platform |
| **Member** | A `member` scoped to a particular tenant | The AI Platform |

It follows that **the same person can be an admin of several tenants at once** — an admin in tenant A and an ordinary member in tenant B. Your permissions right now depend on **the tenant you are currently in**.

## How permissions are decided

The platform translates your roles into a list of permission entries, each written as "resource:action", for example:

| Permission entry | Meaning |
| --- | --- |
| `instance:create` | Can create instances |
| `instance:list` | Can view the instance list |
| `workspace:get` | Can view one workspace's details |
| `member:*` | Can do anything with that resource |
| `*:*` | Can do anything (platform admins only) |

Checks run in this order:

1. If you have `*:*`, you are allowed immediately.
2. If you have "this resource:*", any action on that resource is allowed.
3. Otherwise, match "resource:action" exactly.

That is why a platform admin can do everything: they are given `*:*`.

:::info This applies inside the page

Before rendering menus and buttons, the page checks permissions, and entries you do not have are **simply not shown**. The point is to keep you out of dead ends, not to hide information. In the current version, roles and permissions are derived by the page from your roles, and are fetched automatically after you sign in.

:::

## What you see without permission

| Symptom | Cause | What to do |
| --- | --- | --- |
| The left menu is missing the **Workbench** and **Observability** groups | You are a **Member** | Go through the request process if you need to work |
| A button such as **Create Inference** is gone | You do not have the matching create permission | See how to request it below |
| You cannot see **Members** or **Quota** | Only admins manage members and quota | Ask a tenant admin |
| The page returns `403` | The current role lacks that permission | Ask an administrator to change your role |
| The page returns `401` | The sign-in state expired — not a permission problem | Sign in again |
| Buttons did not change after switching tenant | Permissions refresh only when the sign-in state changes | Refresh the page once |

:::warning Do not retry when you lack permission

`403` is the permission verdict; refreshing or retrying will not change it. The right move is to work out which role you need, then ask someone who can grant it.

:::

## Which role do I need for a given task

| I want to | Role needed |
| --- | --- |
| Deploy inference services, run fine-tuning, open dev environments | Developer or above |
| Just view instance status and logs | Member or above |
| Create a workspace | Tenant admin or above |
| Create workspace members, assign roles | Tenant admin or above |
| Adjust workspace quota | Tenant admin or above |
| Create / delete storage volumes | Tenant admin or above |
| Onboard clusters, divide resource pools, define flavors, allocate quota to tenants | Platform admin |
| Configure gateway channels and content moderation, view global call logs | Platform admin |

## How to request access

1. First work out exactly which task you need to do, then look up the role it needs in the table above.
2. Contact the **tenant admin** of your current tenant (they manage the workspace's members, quota and storage volumes).
3. For platform-level operations (clusters, resource pools, platform settings), contact a **platform admin**.
4. Once you have the new role, **refresh the page** for it to take effect.
