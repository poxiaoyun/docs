This page describes the back-end API surfaces the console front end **actually calls**, covering their path prefixes, authentication and typical endpoints.

> 💡 **Tip**: The console is a single-page application. Every request targets `window.location.origin` (`src/global-config.ts:48`); a reverse proxy on the same origin dispatches requests to different back-end services by path prefix.

---

## Two surfaces: management plane and data plane

| Item | Management plane | Data plane |
|------|------------------|------------|
| Path prefix | `/api/...` | `/airouter-data/v1/...` |
| Typical use | Manage tokens, query usage, read/write platform configuration, and operate IAM / Cloud / Moha resources | Call large models (OpenAI-compatible Chat Completions) |
| Authentication | `user_session` browser cookie (sent automatically) | `Authorization: Bearer <API Key>` header |
| Caller | The console's internal axios instance | Console pages and external programs |

> ⚠️ **Note**: Older documentation wrote the LLM `base_url` as `/api/airouter/v1`. That is the **management-plane** prefix, not the chat endpoint. Chat completions live under `/airouter-data/v1`.

## Management-plane API

### Authentication

- After a successful sign-in the session token is stored in a cookie named `user_session` (`src/auth/authn/token.ts:3`); signing out clears it through `Cookies.remove('user_session', { path: '/' })` (same file, `:9-11`).
- The global axios instance only sets `Content-Type: application/json` and uses the current site origin as its `baseURL` (`src/lib/axios.ts:10-15`).
- The request interceptor does **not** inject an `Authorization` header — that logic is commented out (`src/lib/axios.ts:21-28`). Management-plane authentication relies entirely on the cookie the browser sends automatically.
- As a result, management-plane endpoints are not suitable for out-of-browser calls with a Bearer token. To call LLMs programmatically, use the data plane below.

### Service domains (by path prefix)

| Prefix | Service | Typical endpoint | Code location |
|--------|---------|------------------|---------------|
| `/api/iam` | IAM: sign-in/registration, users, tenants, members and roles, SSH keys, captcha, MFA | `POST /api/iam/login`, `GET /api/iam/current/roles`, `GET /api/iam/captcha` | `src/services/iam.ts`, `src/services/account.ts` |
| `/api/cloud` | Cloud: clusters, workspaces, instances, flavors, quotas, scheduling, logs | `GET /api/cloud/tenants/{tenant}/clusters/{cluster}/workspaces` | `src/services/workspace.ts`, `src/services/instance.ts`, `src/services/flavor.ts` |
| `/api/ai` | AI: instance runtime metrics | `GET /api/ai/tenants/{tenant}/.../instances/{instance}/metrics/{metrics}` | `src/services/instance.ts` |
| `/api/moha` | Moha: models, datasets, images, organizations | `GET /api/moha/organizations/{org}/images` | `src/services/image.ts`, `src/services/tenant-config.ts` |
| `/api/airouter/v1` | LLM gateway management plane: tokens, call logs, usage, global settings | `GET /api/airouter/v1/me/tokens`, `GET /api/airouter/v1/me/usage/dashboard` | `src/services/api-key.ts`, `src/services/usage.ts`, `src/services/runtime-config.ts` |
| `/api/license` | License records | `GET /api/license/records` | `src/services/license.ts` |

> ⚠️ **Note**: The table only covers endpoints the console front end has called. The full back-end API contract (field definitions, error codes, server-side authorization) is not in the front-end code and is not confirmed here.

## Data-plane API (LLM gateway)

### Address

The Chat Completions endpoint is `{origin}/airouter-data/v1/chat/completions` (`src/pages/chatapp/chat.tsx:159`, `src/pages/chatapp/docs.tsx:38-41`). The API docs inside the Model Marketplace use the same address (`src/pages/chatapp/components/model-docs-content.tsx:39-40`).

### Headers

| Header | Required | Description |
|--------|----------|-------------|
| `Authorization` | Yes | `Bearer <API Key>`, created under ChatApp → My Tokens |
| `Content-Type` | Yes | `application/json` |
| `Accept` | For streaming | `text/event-stream` |
| `X-Tenant` | As needed | Tenant that owns the model; the value must be URL-encoded |
| `X-Workspace` | As needed | Workspace that owns the model; URL-encoded |
| `X-Channel` | As needed | Channel to use; URL-encoded |

When a user opens the Experience page, the console first reads the account's API keys (`GET /api/airouter/v1/me/profile`, `src/services/api-key.ts:182-184`) and uses the first one as the Bearer token (`src/pages/chatapp/chat.tsx:114-117`). `X-Tenant` / `X-Workspace` / `X-Channel` come from the selected model and are written after `encodeURIComponent` (`src/pages/chatapp/chat.tsx:141-157`).

### Compatibility and samples

The data plane is compatible with OpenAI Chat Completions, so any official SDK works — point `base_url` at `{origin}/airouter-data/v1`. The console ships cURL, Python (`requests`) and Go samples (`src/pages/chatapp/docs.tsx:43-111`).

```bash
curl --request POST '{origin}/airouter-data/v1/chat/completions' \
  --header 'Authorization: Bearer YOUR_TOKEN' \
  --header 'Content-Type: application/json' \
  --data '{
    "model": "YOUR_MODEL",
    "stream": false,
    "messages": [{"role": "user", "content": "Hello, introduce yourself"}]
  }'
```

See [Model Playground](/rune/chatapp/experience) and [Parameter Tuning](/rune/chatapp/debug) for request-body fields and parameter defaults.

## Status codes and rate limits

| Status code | Meaning |
|-------------|---------|
| `200` | Success |
| `400` | Invalid request parameters |
| `401` | Unauthenticated or session expired |
| `403` | No permission |
| `404` | Resource not found |
| `429` | Rate limited; retry after lowering the request rate |
| `5xx` | Server error |

Rate limits are configured **per API key** through `rateLimitRPM` (requests per minute) and `rateLimitTPM` (tokens per minute, entered in the form in units of K) — see [My Tokens](/rune/chatapp/token).

> ⚠️ **Note**: Whether the sign-in endpoint or captcha has its own separate rate limit is not visible in the front-end code and is not confirmed.
