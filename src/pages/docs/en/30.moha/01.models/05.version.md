# Model Versions

A model keeps improving: new weights, another config file, a fixed description. Moha gives you two tools to manage these changes — **branches** and **snapshots**.

| Term | What it means |
| --- | --- |
| Branch | One timeline of the repository; the default is `main`. Open a new branch to try out changes |
| Snapshot | A photo of the current state, saved so you can return to it later |
| Rollback | Reset a branch to the state of a snapshot |

:::tip A snapshot is a save point
In a game you save manually, and if things go wrong you just load that save. A snapshot is that save point:
taking a snapshot freezes all the files as they are right now, and if you break something later, one rollback takes you back to that moment.
:::

## How to switch versions

A model repository has no separate "version" tab. You switch versions at the top left of the **File** tab:

1. Open the model repository and click the **File** tab.
2. Click the **Branch: main** button at the top left to open the menu.
3. The menu has two groups:
   - **Branch**: all branches in the repository; choosing one shows the file list for that branch.
   - **Snapshot**: all snapshots; choosing one shows the file list as it was in that snapshot.

The chosen version appears on the button, and both the file list and the preview follow it.

## How to create a new version

A version is really a new commit or a new branch. Make your changes locally and push them:

```bash
cd my-model

# Start a new branch from the current one (skip this if you want to change main directly)
git checkout -b feature/v2

# Change files, then commit and push
git add .
git commit -m "Update model weights"
git push origin feature/v2
```

You can also create a branch with the SDK:

```bash
moha branch-create ai-lab/my-model v2 --from main
```

## How to create a snapshot

Take a snapshot when you need to pin a stable release.

1. On the **File** page, switch to the branch you want to pin and confirm the content is correct.
2. Click the **Snapshot** tab.
3. Click the **Freeze** button.
4. Fill in:
   | Field | How to fill it | Notes |
   | --- | --- | --- |
   | Title | For example `v1.0.0` | At most 32 characters; a version number is the clearest |
   | Reason | For example `First public release` | Can be left empty; a clear reason helps you find it later |
5. Click **Confirm**. The page shows **Snapshot created**.

The snapshot list shows each snapshot's **Title**, **Branch**, **Commit Message**, **Creator** and **Created At**.

:::tip
Name snapshots with semantic versions such as `v1.0.0` or `v1.1.0`, so you can tell a bug fix from a new feature at a glance.
:::

## Diff, rollback and delete

On the **Snapshot** tab, every row has three actions on the right:

| Action | What it does |
| --- | --- |
| **Diff** | Compare this snapshot with the current state, file by file |
| **Rollback** | Reset the snapshot's branch to the state of this snapshot |
| **Delete Snapshot** | Remove this snapshot record |

:::warning Rollback and delete cannot be undone

- **Rollback** resets the target branch to the snapshot's commit, and **the commit history may be rewritten**. Before rolling back, make sure nobody else is working on that branch.
- **Delete Snapshot** cannot be recovered. Make sure nothing else still references it first.

:::

## Common problems

| What you see | Likely cause | What to do |
| --- | --- | --- |
| A branch is missing from the menu | It is a branch used internally by the platform | Such branches only appear in the list as a **Snapshot** |
| The diff is incomplete | The diff content is too large | Compare the specific files locally with Git |
| A push to a snapshot-related reference is rejected | Snapshot references are protected | Snapshots are managed on the page only and cannot be overwritten by a push |
