# Publishing, Stopping and Republishing

A Space is not running until you **publish** it, even after the code is in. This page covers taking it online, taking it down, restarting it, and where to look when the status label gets stuck.

## Concepts

| Term | Plain explanation |
| --- | --- |
| Publish | Start the app instances and assign an access address — "opening the shop" |
| Stop | Take the app offline and release compute; the address stops working, and you can publish again later |
| Republish | Restart the instances with the current configuration, used after changing config or code |
| Log | Output from the instances during start-up and runtime; the first place to look when something breaks |

### Reading the status label

The Space detail page shows a status label at the top:

| Status | Meaning |
| --- | --- |
| **Unknown** | The platform has not received a runtime status yet |
| **Deploying** | Creating instances, pulling images, starting processes |
| **Installed** | Dependencies or the app are installed but not yet serving |
| **Running** | The app is ready, and the Overview tab shows the app interface |
| **Syncing status** | The platform is reconciling the real state; just wait |
| **Processing failed** | Deployment or start-up failed; check the log |
| **Completed with failures** | Some steps succeeded and some failed; also check the log |
| **Paused** | Stopped on purpose; instances released |
| **Scaled to zero** | Scheduled running scaled replicas to 0 outside the window; it recovers automatically |
| **Terminating** | The Space is being deleted |

## Where the Operations button is

The **Operations** button is not in the top right of the page — it sits at the **right end of the tab row** (the row with **Overview**, **File**, **Snapshot**, **Discussion & Feedback** and **Settings**), and opens a dropdown menu.

:::warning Only Space administrators see it
The button only appears for administrators of the Space (the **Admin** repository role). The owner, organization administrators and system administrators see it too. Members with the **Read/Write** role do not, which means they cannot publish or stop the Space.
:::

## Publish: get the Space running

A newly created Space with no instances only offers **Publish** in the menu.

1. Open the Space detail page and click **Operations** → **Publish**.
2. The dialog title is "Publish space XXX" and explains that publishing starts the app instances and applies the saved deploy configuration.
3. Click **Confirm**.

The status label shows **Deploying** first, then **Running** once it is ready, and the Overview tab shows the app interface.

:::info "Submitted" does not mean "running"
The dialog notes that a successful request only means the platform accepted it; the runtime status updates afterwards. Do not click again repeatedly — just watch the status label.
:::

## Stop: go offline and release resources

A Space with instances offers **Stop**, **Republish** and **Log**.

1. Click **Operations** → **Stop**.
2. The dialog explains that stopping pauses the app instances and releases compute, and that you can publish again to resume.
3. Click **Confirm**.

After stopping, the status becomes **Paused** and the access address stops working. Click **Republish** when you need it again.

:::warning Stopping disconnects everyone using it
Stopping releases compute immediately, and anyone currently using the Space is disconnected. Make sure nobody is using it first.
:::

## Republish: apply your changes

Republish after changing the deploy config, environment variables, or after pushing new code.

1. Click **Operations** → **Republish**.
2. The dialog explains that republishing restarts the app instances and reapplies the current deploy configuration.
3. Click **Confirm**.

:::tip Saving the deploy config republishes for you
Saving the flavor or environment variables under **Settings** → **Deploy Config** triggers a republish automatically, so you do not need to click here. You only need a manual republish after pushing code.
:::

## Reading the log

1. Click **Operations** → **Log** to open the log panel.
2. The panel shows instance output in chronological order, which is where you diagnose image pull failures, dependency install errors and start-up exceptions.
3. When the status is **Processing failed** or **Completed with failures**, the log is the only place that explains why.

Before the Space is ready, the Overview tab also offers a **Log** entry that does the same thing.

## Scheduled running: automatic start and stop

Scheduled running and manual operations are two separate mechanisms: manual **Stop** pauses the Space, while scheduled running flips the replica count between "some" and "0" on a timetable.

1. Go to the **Settings** tab and find the **Scheduled running** card.
2. Turn on **Enable scheduled running**, pick a **Schedule mode** (Every day / Selected weekdays / Run once), and fill in the window and **Time zone**.
3. Save to apply. Outside the window the status shows **Scaled to zero**, and it recovers when the window starts.

For a Space that has never been deployed, this configuration applies on the next deployment.

## Changing the flavor and environment variables

1. Go to **Settings** → **Deploy Config**.
2. Change the **Flavor** or **Environment Variables** and click **Update**.
3. Saving triggers an automatic republish; wait for the status to return to **Running**.

**Product SDK** and **Deploy Workspace** are fixed at creation time and are read-only here.

## Confirming the result

- After publishing the status moves from **Deploying** to **Running**, and the Overview tab shows the app interface.
- After stopping the status becomes **Paused**, the Overview no longer shows the app, and the getting-started guide returns instead.
- After republishing the status briefly returns to **Deploying** and then recovers.
- After saving the deploy config the status label goes through "Deploying → Running" on its own, confirming the automatic republish.
