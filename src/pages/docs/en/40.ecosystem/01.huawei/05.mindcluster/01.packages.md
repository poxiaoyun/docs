# Get the package

Before installing the cluster components, get everything you need in one go and verify it. MindCluster components are
usually delivered as **"component binary + Dockerfile / YAML + configuration files"**, and a few of them need a matching
image as well. Getting this step right gives every later step a stable input.

:::tip Why do this first
It is like checking all the materials before starting a renovation: if the model is wrong or the box has been opened,
you only find out halfway through and have to redo the work. Software packages are the same — **version mismatch** and
**a tampered package** are two problems you must rule out up front.
:::

## Before you start

- Confirm the target version: this section uses **MindCluster 26.0.0**, and each component's image tag must match it. Do not mix in other versions.
- Confirm the node CPU architecture: `x86_64` or `aarch64`. The downloaded packages and the plugin library must both match it.
- Have permission to download the official packages, and be able to reach the location where they are stored.

## Steps

### 1. Confirm the version and architecture

On each target node, check the architecture:

```bash
uname -m
```

`x86_64` means x86, `aarch64` means ARM. The binaries and the Ascend NPU plugin library you download later must match this result.

### 2. Download the deliverables by component

| Component | Deliverables to prepare |
| --- | --- |
| Ascend Docker Runtime | The `.run` package used for installation |
| NPU Exporter | Binary, Dockerfile, and the YAML for the DaemonSet |
| Ascend Device Plugin | Binary, Dockerfile, and several YAML files split by processor model / whether Volcano is used |
| NodeD | The YAML for the DaemonSet, configuration files, and a Dockerfile |
| Volcano (Ascend-customized, optional) | The Volcano component package and the architecture-matching Ascend NPU plugin library |

### 3. Prepare the images

If a component is deployed as a container, the image must also be placed where the cluster can pull it (for example an
enterprise registry). These are the images and tags that match MindCluster 26.0.0:

| Image | Tag |
| --- | --- |
| `ascend-k8sdeviceplugin` | `v26.0.0` |
| `npu-exporter` | `v26.0.0` |
| `vc-scheduler` | `v1.9.0-v26.0.0` |
| `vc-controller-manager` | `v1.9.0-v26.0.0` |
| `vc-webhook-manager` | `v1.9.0` |

:::warning The scheduler images cannot be replaced with upstream versions
Volcano's `vc-scheduler` and `vc-controller-manager` must use the **tags that include the Ascend plugin** (of the form
`v1.9.0-v26.0.0`). If you swap in the upstream Volcano `v1.9.0` image with the same tag, scheduling will lack the Ascend
NPU plugin and the cards cannot be scheduled correctly.
:::

### 4. Verify the package signature

Download the corresponding signature file together with the package, and complete OpenPGP verification before installing
or upgrading. For how to obtain the public key and the exact verification command, follow the official signature
verification guide.

:::warning Stop if verification fails
A failed signature check means the package may have been altered in transit or in storage. **Do not continue installing** —
download it again first; if it still fails, contact technical support.
:::

### 5. Extract and check the directory contents

Extract the package and confirm that each component directory contains the file types listed in step 2 (binary, Dockerfile,
YAML). Missing files mean the download was incomplete — download again.

### 6. Record the delivery information

Record these four items in the delivery note, so you can compare against them directly when troubleshooting later:

- Each component version
- Each image tag
- Container runtime type (Docker / containerd)
- The Kubernetes version range of the cluster

## Confirm the result

- Each component's extracted directory contains its binary, Dockerfile, and YAML.
- All signature verifications pass.
- The delivery note records the versions, image tags, runtime type, and Kubernetes version.

## FAQ

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| A YAML or binary is missing after extraction | Incomplete download | Download the full package for that component again |
| Signature verification fails | The package was tampered with, or the signature file does not match | Stop installing and download again; if it still fails, contact technical support |
| A binary reports an architecture error on the node | The wrong CPU architecture was downloaded | Confirm with `uname -m`, then download the package for the matching architecture |
| The scheduler Pod fails to start and logs say a plugin is missing | An upstream Volcano image was used | Switch to the matching tag that includes the Ascend plugin |
