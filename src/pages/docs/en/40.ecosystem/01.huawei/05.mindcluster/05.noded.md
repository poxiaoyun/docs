# NodeD

NodeD is the **node status monitoring component** in the cluster. It runs on every node and periodically reports the health
of the node itself and of the NPUs to the cluster, so the platform can identify "this machine / this card is broken" and
then trigger actions such as fault rescheduling and resumable training.

Think of it as **an inspector patrolling every corner of the machine room**: every day he walks his round, notes which
lights are out and which machine is running hot, and reports to the control room.

## When you must install it

- You need **whole-card or virtualized scheduling**.
- You need **resumable or elastic training**: when a node dies, the job must be able to continue.
- You need **inference card failure recovery / rescheduling**.

If you only want the cluster to be able to schedule cards and do not care about fault reporting, you can leave it out for now.

## Before you start

- Every NPU node already has the driver installed and `npu-smi info` is normal.
- The component image is already placed where the cluster can pull it, and its version matches components such as Ascend Device Plugin.
- The nodes are labeled (the same label set used by the device plugin):

  ```bash
  kubectl label node <npu-node> accelerator=huawei-Ascend910
  ```

## Steps

### 1. Confirm the image exists

```bash
docker images | grep noded
```

### 2. Prepare the YAML

Copy the NodeD YAML from the extracted package directory to the Kubernetes management node.

### 3. (Optional) Adjust the reporting interval

Scenarios such as resumable or elastic training may require changing the node status reporting period. Adjust it in the
startup parameters of the YAML:

```yaml
args: ["/usr/local/bin/noded -logFile=/var/log/mindx-dl/noded/noded.log -logLevel=0 -reportInterval=5"]
```

`-reportInterval` is the reporting interval in seconds. By default Kubernetes marks a node `NotReady` when it receives no
node response for a while; when the API Server is under heavy load, you can increase this value to reduce the pressure, but
assess the stability impact first.

### 4. Deploy

Without DPC fault detection:

```bash
kubectl apply -f noded-v<version>.yaml
```

With DPC fault detection, when the environment meets the version requirements:

```bash
kubectl apply -f noded-dpc-v<version>.yaml
```

### 5. Check

```bash
kubectl get pod -n <noded-namespace> | grep noded
```

The official package's namespace is usually `mindx-dl`; take the YAML you actually use as the source of truth.

## What changes in the cluster after installation

| What to look at | Command | Expected result |
| --- | --- | --- |
| Component Pod status | `kubectl get pod -n <noded-namespace> \| grep noded` | One Pod on every node, status `Running` |
| Whether it is reporting periodically | `kubectl logs -n <noded-namespace> <noded-pod> -f` | Log output keeps flowing, with periodic reporting entries |
| Node status information | `kubectl describe node <npu-node>` | The node object carries node and device status information maintained by NodeD; field names depend on the component version |

Once reporting is in effect, when a node or card fails, the platform can identify it and trigger the corresponding
rescheduling action.

:::warning A larger reporting interval cuts both ways
Increasing `-reportInterval` reduces API Server pressure but also **delays when a fault is discovered**. Assess stability
before changing it, and do not set the interval too large just to shed load.
:::

## FAQ

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| The Pod stays `Pending` | No node matches the label, or the node lacks resources | Confirm the node labels and check the node's allocatable resources |
| The Pod keeps going `CrashLoopBackOff` | Wrong log directory permissions, or the version does not match the device plugin | Read the Pod logs first, then confirm the log directory permissions and version compatibility |
| No reporting entries in the logs | The reporting interval is too large, or the component never really started working | Confirm the `-reportInterval` value and that the Pod is `Running` |
| The node is marked `NotReady` | Heavy API Server pressure, or the reporting interval is too small | Increase `-reportInterval` appropriately after a stability assessment |
