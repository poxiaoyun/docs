# NPU Exporter

NPU Exporter **collects NPU runtime metrics on a schedule** — utilization, HBM usage, temperature, power, health status,
and more — and exposes them on `/metrics` at port `8082` for a monitoring system such as Prometheus to scrape.

Think of it as **an electricity meter installed on every card**: the card does not report its own power draw and
temperature, so someone has to read the meter periodically.

## When you must install it

- You need to view NPU utilization, HBM, or temperature curves in the console, or autoscale by accelerator utilization.
- You need alerting and capacity statistics for the NPUs.

If you only need resource scheduling and no monitoring data, you can skip this page.

## Before you start

- Every NPU node already has the driver installed (`npu-smi info` shows the cards).
- The component image is already placed where the cluster can pull it.
- If you enable the ServiceMonitor integration, the cluster must already have the Prometheus Operator custom resources installed.

## Deployment method 1: containerized (DaemonSet, recommended)

### 1. Confirm the image exists

On a compute node, check (Docker scenario):

```bash
docker images | grep npu-exporter
```

containerd scenario:

```bash
ctr -n k8s.io c ls | grep npu-exporter
```

### 2. Copy the YAML to the management node

Copy the NPU Exporter YAML from the extracted package directory to the Kubernetes management node.

### 3. Pick the YAML for your runtime type and adjust the parameters

Docker and containerd mainly differ in the `-containerMode` startup parameter and the mount path of the runtime socket,
so pick the one that matches your nodes. When you need to adjust it, change these startup parameters:

| Parameter | Purpose | Default |
| --- | --- | --- |
| `-port` | Port that exposes the metrics | `8082` |
| `-updateTime` | Collection interval (seconds) | `5` |
| `-containerMode` | Container runtime type | Fill in the node's actual Docker / containerd |
| `-logFile` | Log file path | The YAML default |
| `-logLevel` | Log level | `0` |

### 4. Deploy

```bash
kubectl apply -f npu-exporter-v<version>.yaml
```

### 5. Check

```bash
kubectl get pod -n npu-exporter
```

## Deployment method 2: binary (when security requirements are high)

If the cluster does not allow containers to run in privileged mode, switch to a binary deployment: place `npu-exporter`
in a fixed directory and start it with a systemd service / timer so it starts late enough that the device is ready.

- Configure the correct owner and permissions for the log directory.
- If the component needs to read container information, you may have to grant the binary the relevant capability, then restart the service.

## Confirm the result

1. The Pod is `Running`:

   ```bash
   kubectl get pod -n npu-exporter
   ```

2. Forward the port and look at the metrics directly; if it prints content, collection works:

   ```bash
   kubectl port-forward -n npu-exporter <npu-exporter-pod> 8082:8082
   ```

   In another terminal:

   ```bash
   curl -s http://127.0.0.1:8082/metrics | head
   ```

3. If ServiceMonitor is enabled, the platform monitoring should show this metrics endpoint being scraped successfully.

## FAQ

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| The Pod keeps going `CrashLoopBackOff` | Wrong log directory permissions, insufficient permissions on the DCMI dynamic library, or a wrong runtime socket mount path | Read the Pod logs first, then check the log directory owner, the DCMI dynamic library and its parent directory permissions, and the socket mount path in turn |
| `/metrics` has no NPU-related metrics | The driver on the node is unhealthy, or the mount path is wrong | Run `npu-smi info` on the node to confirm the driver is healthy |
| The component misbehaves after a driver upgrade | The component is still calling the old driver interface | Stop the workload, then stop the Exporter before upgrading the driver, and bring them back in the reverse order afterward |

## Operational notes

- **Kubernetes version**: whether K8s 1.24 and later need an extra `cri-dockerd` depends on the cluster's runtime and deployment method.
- **Dynamic library permissions**: it is best to manage the DCMI dynamic library and its parent directory as root, without group / other write permission.
- **Container deployment risk**: containerized operation needs privileged mode and socket mounts; when security requirements are high, switch to the binary method.

:::warning Stop the Exporter before upgrading the driver
The Exporter calls driver interfaces periodically. Before upgrading the driver, stop the workload, then stop the Exporter;
after the upgrade, bring them back in the reverse order. Otherwise the component may read a half-upgraded driver and report
abnormal metrics.
:::
