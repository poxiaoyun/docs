# Ascend Device Plugin

Ascend Device Plugin **registers the NPUs on a node as Kubernetes resources**: it discovers the cards, runs health checks,
and then tells the cluster "this machine has this many usable cards". Only after registration succeeds can a Pod use a
card by requesting that resource.

Think of it as **giving each card an identity**: the card is just hardware plugged into a machine, and only after
registration does it get an identity the cluster recognizes, so the scheduler knows which machine still has a free card.

## When you must install it

- **Whole-card scheduling**: one Pod takes an entire card.
- **Static / dynamic virtualized scheduling**: one card is split across several Pods.
- **Resumable and elastic training**.
- **Inference card failure recovery / rescheduling**.

If you only run containerized workloads in the cluster and do not need to schedule cards, you can skip it — but then the
platform will not see the NPU resources.

## Before you start

- Every NPU node already has the driver installed, and `/usr/local/Ascend/driver` exists.
- [Ascend Docker Runtime](/ecosystem/huawei/mindcluster/ascend-docker-runtime) **is installed and the container engine has been restarted**.
- The component image is already placed where the cluster can pull it.
- Decide on the YAML: choose the one matching the processor model and whether Volcano is used.

## Steps

### 1. Label the NPU nodes

The component selects nodes by label, so label them first:

```bash
kubectl label node <npu-node> accelerator=huawei-Ascend910
```

### 2. Confirm the image exists

```bash
docker images | grep k8sdeviceplugin
```

For the containerd scenario:

```bash
ctr -n k8s.io c ls | grep k8sdeviceplugin
```

### 3. Choose the matching YAML

Copy the YAML from the extracted package directory to the Kubernetes management node, and pick the file by model and
scenario — for example training / inference, whether Volcano is used, or a specific development board.

:::warning Do not rename the DaemonSet
The component has built-in logic to detect the runtime, and it depends on a fixed DaemonSet name. Renaming it at will can
break that detection.
:::

### 4. Deploy

```bash
kubectl apply -f device-plugin-910-v<version>.yaml
```

For a Volcano scenario:

```bash
kubectl apply -f device-plugin-volcano-v<version>.yaml
```

:::tip What if the cluster has several models
If several types of Ascend AI processors exist in the cluster, you must **deploy the matching YAML separately for each model**.
:::

### 5. Check

```bash
kubectl get pod -n kube-system | grep -i device-plugin
```

## What changes in the cluster after installation

This is the key check for "is the card really connected to the cluster". Confirm each item:

| What to look at | Command | Expected result |
| --- | --- | --- |
| Plugin Pod status | `kubectl get pod -n kube-system \| grep -i device-plugin` | One Pod on every NPU node, status `Running` |
| New resource name on the node | `kubectl get node <npu-node> -o jsonpath='{.status.allocatable}'` | `huawei.com/Ascend910` appears in the output |
| Number of cards | `kubectl describe node <npu-node> \| grep -A 2 huawei.com` | Matches the number of cards actually available on the node |

Once the resource name appears, a workload Pod can request a card like this (fragment):

```yaml
resources:
  limits:
    huawei.com/Ascend910: 1
```

As long as the node still has a free card, this kind of Pod schedules successfully — that is the final sign that the
cluster integration worked.

## FAQ

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| The Pod is up but no resource name appears on the node | Ascend Docker Runtime was not installed properly, or the container engine was not restarted | Install the runtime and restart the container engine first, then restart this component |
| The resource appears only on some nodes | The node was not labeled, or the label value does not match the selector in the YAML | Add `accelerator=huawei-Ascend910` to the nodes that are missing it |
| The card count is right but workload Pods still fail to schedule | The cluster has no free cards, or the requested resource name is wrong | Confirm the resource name matches what the node reports, and check the remaining amount with `kubectl describe node` |
| Recognition breaks after basic information such as the device IP changes | The plugin cached the old device information | Restart the Device Plugin so it re-detects the cards |

## Platform defaults

When installed from the platform these values are already set. Use the table when editing the YAML by hand or
troubleshooting:

| Parameter | Default | Purpose |
| --- | --- | --- |
| Node label selector | `accelerator=huawei-Ascend910` | The plugin is deployed only to nodes carrying this label |
| `deviceType` | `Ascend910` | Maps to the reported resource name `huawei.com/Ascend910` |
| `useAscendDocker` | `true` | Works with Ascend Docker Runtime to mount the driver and devices into containers |
| `volcanoType` | `true` | Reports devices in Volcano mode; gang scheduling of multi-card jobs depends on it |
| `presetVirtualDevice` | `true` | Static virtualisation: reports pre-partitioned vNPU profiles |
| `autoStowing` | `true` | Tidies the available device information so unusable cards are not reported to the scheduler |
| `listWatchPeriod` | `5` | Device information refresh period (seconds) |
| `containerRuntime` | `containerd` | Set it to what the node actually uses (Docker / containerd / iSulad) |

:::warning What happens when the container runtime is wrong
The plugin Pod starts but cannot reach the devices — the symptom is **no `huawei.com/Ascend910` on the node**.
Check that the node's runtime matches this setting first, then read the logs.
:::

## What the component mounts

From 26.0.0 onwards the device plugin mounts a few extra configuration and state directories besides the driver
and kubelet paths. When investigating "why is this capability not taking effect", use this table to see whether
the path even exists inside the container:

| Mount path | Purpose |
| --- | --- |
| `/usr/local/Ascend/driver` | Driver and device interfaces — the plugin's core dependency |
| `/var/lib/kubelet/device-plugins` | Registering devices with kubelet |
| `/var/lib/kubelet/pod-resources` | Reading the resource allocations of Pods |
| `/etc/vnpu.cfg` | Profile configuration for static virtualisation (vNPU) |
| `/user/restore/reset` | Card reset, used by the recovery flow |
| `/user/cluster-info/datatrace-config` | DataTrace configuration, to switch the driver's debugging data writes on or off per workload |
| `/user/mindx-dl/dpu-config` | DPU-related configuration |
| `/run/containerd`, `/run/docker.sock`, `/run/docker` | Interacting with the container runtime |

## Operational notes

- **Driver upgrade order**: before upgrading the driver, stop the workload, then stop the Device Plugin.
- **Restart scenario**: after the basic NPU information changes (for example a device IP change), restart the plugin to re-detect.
- **Dynamic library permissions**: it is best to manage the DCMI dynamic library and its parent directory as root, without group / other write permission.
