# Platform support status

Recognising a card on the platform takes several independent pieces of logic: image registration, model metadata,
flavor display and cluster components. The same vendor is often in different states across them, so when something
is missing in the UI, first work out whether it was never configured or simply does not exist yet.

For Cambricon, the first half is mostly there and the second half is missing two pieces.

## Layer-by-layer check

| Layer | Where | Status for Cambricon |
| --- | --- | --- |
| Image accelerator type | The accelerator option when registering an image | **Registered**: `Neuware(寒武纪)` |
| Model metadata model | The accelerator card model selectable on a model card | **4 registered**: MLU220 / MLU270 / MLU370 / MLU590 |
| Model metadata backend enum | `hardware_backends` in model metadata | **Included**: `mlu` |
| Flavor accelerator label | The GPU / NPU / MLU wording on a flavor label | **Supported**: shows `MLU` |
| Flavor model name | The flavor name assembled from resource name and model | **Prefix is not stripped.** Only nvidia / amd / intel / huawei are on the strip list; other vendors' model names are concatenated as-is |
| Flavor vendor icon | The small icon on a flavor label | **Absent**, Cambricon has no dedicated icon |
| Cluster scheduling components | Cluster Management → Operations → System Apps | **Absent**, the platform bundles only NVIDIA and Ascend |

The model enum contains MLU590, which does not match what the official product pages show. The nature of that source
is flagged in [Products & software stack](/ecosystem/cambricon/products); treat it as a third-party lead.

## What works today

- **Image metadata**: pick `Neuware(寒武纪)` as the accelerator type when registering an image, and search and filtering pick it up.
- **Model metadata**: the model card offers MLU220 / MLU270 / MLU370 / MLU590, and `hardware_backends` carries `mlu`, so a cross-vendor model list can be filtered by backend.
- **Flavor label**: the accelerator label reads `MLU`, which distinguishes it from GPU and NPU flavors in a list.
- **Compute scheduling**: as soon as the device plugin on the node reports `cambricon.com/mlu`, quotas, flavors and job requests all work against that resource name, with Volcano scheduling multi-card jobs.

## What does not work yet

| Missing capability | Impact | How to fill the gap |
| --- | --- | --- |
| One-step cluster component install | Nothing to click in System Apps, so bringing up a node takes a few commands | Deploy the device plugin and mlu-exporter by hand, see [Kubernetes components](/ecosystem/cambricon/k8s-components) |
| Dedicated vendor icon | The flavor label has the text `MLU` but no icon | A display-layer choice, with no effect on scheduling |
| Model name prefix handling | A prefix in the model field is not stripped, so the flavor name looks different from the NVIDIA and AMD ones | Fill the model field with the wording you want displayed |
| Prebuilt monitoring dashboard | MLU metrics must be wired into Prometheus by hand | Deploy mlu-exporter and add a ServiceMonitor scraping port 30108 |
| Partitioning templates | The platform only has Ascend NPU slicing templates, none for MLU | Partitioning happens in the driver and device plugin, not through the platform |

## Full manual path

System Apps has no Cambricon entry, so the first four steps happen outside the platform:

1. Install the Neuware driver on every machine with a card and confirm `/dev/cambricon_devX`, `/dev/cambricon_ctl` and `/dev/cambricon_ipcmY` appear.
2. Install the container runtime toolkit on the same machines, and confirm the same device nodes inside a container.
3. Build and deploy the device plugin. There is no prebuilt official image and the build needs `cndev.h` from the driver package; confirm `cambricon.com/mlu` appears on the node.
4. Deploy mlu-exporter and confirm `/metrics` answers on port 30108.
5. Back on the platform, create a flavor and quota against `cambricon.com/mlu`, then submit a job asking for one card to confirm.

Step 5 is the only one that touches the platform UI; the first four are all on the cluster side.
