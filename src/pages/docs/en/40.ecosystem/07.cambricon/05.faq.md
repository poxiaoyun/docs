# FAQ

## Quick reference

| Symptom | Check first | What to do |
| --- | --- | --- |
| No `/dev/cambricon_dev*` on the host | Whether the driver installed and the kernel module loaded | Reinstall the driver per the official notes, then confirm the three device nodes |
| Cards gone after a kernel upgrade | Whether the kernel module was reinstalled | Reinstall the driver |
| Host has device nodes, container does not | Whether the container runtime toolkit is installed | Install it, then recreate the container |
| No `cambricon.com/mlu` on the node | Device plugin pod status and logs | Confirm both host layers first, then restart the plugin |
| Device plugin pod will not start, image cannot be pulled | Where the image came from | There is no prebuilt official image; build it and push to your internal registry |
| Building the plugin fails on `cndev.h` | Whether the build machine has the driver package | Install the same driver version as the target nodes on the build machine |
| An sMLU request never schedules | Whether the node carries that resource name | Check `--mode` and the resource name against the README of the release in use |
| Metrics lack namespace / pod dimensions | Whether the podresources collector is enabled | Enable it and look at `mlu_container` again |
| No MLU metrics at all | Whether mlu-exporter is deployed and 30108 answers | Deploy it, then scrape with a ServiceMonitor |
| Flavor has no icon, model name keeps its prefix | Platform display layer | Expected behaviour, no effect on scheduling |

## Why is there nowhere in the platform to install Cambricon components

System Apps bundles only NVIDIA and Ascend hardware scheduling components. Cambricon, AMD and Hygon are not on that
list, and their cluster components are installed by hand from each vendor's repositories. This is a current product
boundary rather than a misconfigured machine; see [Platform support status](/ecosystem/cambricon/platform-support).

## Why do I have to build the device plugin myself

The `Cambricon/cambricon-k8s-device-plugin` repository ships source only, no prebuilt image, with the implementation
in the `device-plugin` directory. The build depends on `cndev.h` from the driver package, so the build machine needs
the driver installed or the compile stage fails.

In practice it is a two-step job: build on a machine with the matching driver, push the resulting image to your
internal registry, and let the nodes pull from there. The nodes themselves need nothing extra.

## How many resource name variants are there

Separate the official names from the third-party ones first:

| Source | Resource name | Nature |
| --- | --- | --- |
| Device plugin, whole card | `cambricon.com/mlu` | Official, and the one you will use most |
| Dynamic SMLU mode | `cambricon.com/vmlu`, `cambricon.com/mlu.smlu.vmemory`, `cambricon.com/mlu.smlu.vcore` | Used together; this is the group HAMi's official documentation gives. Needs SMLU enabled and the device plugin set to `mode=dynamic-smlu` |
| DAOCloud documentation | `cambricon.com/mlu.share`, `cambricon.com/mlu.mim-2m.8gb` | Third-party integrator |

Which of these appears on a node depends on the `--mode` the installed device plugin runs with, or on which
third-party slicing scheme is in place. The `--mode` values change between versions and sources disagree, so check
the README of the release you deploy. The prerequisites and request syntax for the dynamic SMLU group are under
[HAMi](/ecosystem/hami).

```bash
kubectl describe node <mlu-node> | grep -A 5 "Allocatable" | grep cambricon.com
```

Whatever this prints is what the platform-side flavor should be built against.

## The platform offers MLU590 but the official product page does not

Model metadata's card model enum has four entries: MLU220 / MLU270 / MLU370 / MLU590. Of those, MLU590 could not be
verified on Cambricon's product pages and appears only in third-party material, so this section does not treat it as
fact. Being selectable in the enum only means the platform has that name registered, not that the model's specs or
availability are known.

Take the model from the official product pages and the server vendor's compatibility list, not from a dropdown in a
model card.
