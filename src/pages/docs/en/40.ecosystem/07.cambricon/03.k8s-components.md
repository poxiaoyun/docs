# Kubernetes components

Two things go on the cluster side: the device plugin registers the card as a schedulable resource, and the exporter
exposes card metrics. Cambricon does not wrap them in an operator package; each comes from its own open-source
repository.

| Component | What it does | What breaks without it |
| --- | --- | --- |
| Device plugin (cambricon-k8s-device-plugin) | Registers MLU as a Kubernetes extended resource | No `cambricon.com/mlu` on the node, so jobs cannot request a card |
| mlu-exporter | Exposes MLU utilisation, memory, temperature and other metrics | The platform has no card-level view, only job logs |
| Container runtime toolkit | Makes MLU device nodes visible inside containers | The plugin starts, but workloads in containers cannot use the card (host layer, see [Drivers & container runtime](/ecosystem/cambricon/driver-runtime)) |

## Where to get them

| Component | Source |
| --- | --- |
| Device plugin | `https://github.com/Cambricon/cambricon-k8s-device-plugin`, implementation directory `device-plugin`, README describes it as the official implementation |
| Device plugin image | No prebuilt official image; you build it yourself |
| mlu-exporter | `https://github.com/Cambricon/mlu-exporter`, with DaemonSet, ConfigMap, ServiceMonitor and Helm deployment forms in the repository |
| Domestic mirror | The organisation page on Gitee, `https://gitee.com/organizations/cambricon/projects` |

Building the device plugin depends on `cndev.h` from the driver package, so the build machine needs the same driver
version as the target nodes or the compile will fail.

## Resource names the device plugin reports

The whole-card resource is:

```
cambricon.com/mlu
```

Think of the resource name as the card's ID number: flavors, quotas and job requests on the platform all key off that
string. Requesting it works the same way as on the NVIDIA side, **one per card you want**:

```yaml
resources:
  limits:
    cambricon.com/mlu: 1
```

The plugin's `--mode` switch decides which resource names get reported. Its values change between versions and the
sources do not agree with each other; these have all been seen: `default`, `sriov`, `env-share`, `mlu-share`,
`dynamic-smlu`, `mim`, `topology-aware`.

:::warning Read the README of the release you deploy
That list is the union of what the various sources mention. It is neither the complete set for any one version nor a
promise that every version supports all of them. Open the README of the release you are deploying and use the values
written there.
:::

:::info Version
The newest tag visible in the repository is v2.3.0 (2026-08-07). This section does not pin a version; pick one for
the target cluster.
:::

## Sharing one card

Cambricon names five ways of giving one card to more than one job, with different granularity and isolation:

| Term | Meaning | Resource name |
| --- | --- | --- |
| vMLU | Virtualisation, cutting virtual instances out of one card | An official term; the exact resource name follows the README of the release in use |
| sMLU | Time-division software slicing | `cambricon.com/mlu.smlu.vcore` and `cambricon.com/mlu.smlu.vmemory`; Koordinator's official documentation confirms the device plugin reports these |
| dynamic-smlu | Dynamic sMLU | Follows the README of the release in use |
| MIM | Physical partitioning, the counterpart of NVIDIA MIG | Follows the README of the release in use |
| env-share | Sharing a card through environment variables | Follows the README of the release in use |

The two sMLU resource names split compute and memory, so request them together. The value scale comes from the
device plugin version:

```yaml
resources:
  limits:
    cambricon.com/mlu.smlu.vcore: <per the README of the release in use>
    cambricon.com/mlu.smlu.vmemory: <per the README of the release in use>
```

SR-IOV is a separate route, switched on with two device plugin parameters, where `--virtualization-num` sets the
number of VFs to carve out:

```bash
--mode=sriov --virtualization-num=<VF count>
```

### Resource names from third-party integrators

The names below come from third-party projects and integrator documentation, not from Cambricon's own reporting.
Seeing them on a node means the cluster runs a third-party slicing scheme:

| Source | Resource name | Nature |
| --- | --- | --- |
| HAMi's dynamic SMLU mode | `cambricon.com/vmlu`, `cambricon.com/mlu.smlu.vmemory`, `cambricon.com/mlu.smlu.vcore`, used together | The set [HAMi's official documentation](https://project-hami.io/docs/userguide/cambricon-device/enable-cambricon-mlu-sharing) gives |
| DAOCloud documentation | `cambricon.com/mlu.share`, `cambricon.com/mlu.mim-2m.8gb` | Third-party integrator |

On the first route, SMLU has to be enabled on each card first with `cnmon set -c <id> -smlu on`, and the device
plugin has to run with `mode=dynamic-smlu` and a minimum allocation unit of 256 MB (`min-dsmlu-unit=256`).
Without those two, none of the `vmlu` keys are reported.

These schemes and the platform's built-in Volcano vGPU are two different things. Check which one the cluster actually
has before creating a flavor. The vendors and resource keys HAMi covers are compared under
[HAMi](/ecosystem/hami).

## Monitoring

Metrics come from **mlu-exporter**, in Prometheus format:

| Item | Value |
| --- | --- |
| Listen port | 30108 |
| Metrics path | `/metrics` |
| Metric prefix | `mlu` |
| Container-level metric | `mlu_container`, correlating namespace / pod / container |
| Prerequisite | The podresources collector must be enabled, otherwise the container labels are absent |
| Deployment forms | DaemonSet, ConfigMap, ServiceMonitor, Helm |
| Platform monitoring | A ServiceMonitor, scraped by the Prometheus Operator |

This port is not the 9400 used on the NVIDIA side or the 5000 used for AMD, so do not reuse one port number across a
shared dashboard.

## Relationship with Volcano

The platform schedules multi-card jobs with Volcano. Cambricon's official documentation lists no dedicated Volcano
plugin, so the generic path applies: the device plugin reports the card as a standard extended resource, and Volcano
schedules by resource name and count.

- Multi-card jobs schedule fine, because that is the standard Kubernetes extended resource mechanism and needs no extra plugin.
- Per-share scheduling of a sliced card, and proportional memory allocation, are outside the official plugin's scope. Doing so means a third-party scheme, which is a different route.
- Queueing and gang scheduling are Volcano features independent of the vendor, and work the same either way.

## Verifying the install

```bash
# The node now offers a schedulable MLU resource
kubectl describe node <mlu-node> | grep -A 5 "Allocatable" | grep cambricon.com

# Device plugin and monitoring pods are up
kubectl get pods -A | grep -i cambricon
kubectl get pods -A | grep -i mlu-exporter

# The monitoring port answers and exposes mlu-prefixed metrics
kubectl port-forward -n <namespace> <mlu-exporter-pod> 30108:30108
curl -s http://127.0.0.1:30108/metrics | grep '^mlu'
```

Then submit a minimal job asking for one card and check that the container sees the device nodes.
