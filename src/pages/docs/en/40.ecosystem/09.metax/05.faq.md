# FAQ

## Quick reference

| Symptom | Check first | Action |
| --- | --- | --- |
| `mx-smi` lists no cards | Whether `metax.ko` is loaded | Reinstall KMD / UMD from the matching Software Center package |
| The host sees the card, containers do not | Whether containerd is configured for the MetaX runtime | Install `metax-container-runtime`; registration follows the official notes |
| No `metax-tech.com/gpu` on the node | `gpu-device` pod status and logs | Confirm the driver and container runtime are healthy, then restart the plugin |
| `helm install` stalls pulling the chart | Authorisation and credentials for the OCI registry | Both charts need commercial authorisation; get it first |
| A job requesting `metax-tech.com/vgpu` gets no card | The resource name is wrong | MetaX has no such name; whole cards and VFs both use `metax-tech.com/gpu` |
| Quotas run short after setting `vfNum` | How many cards the flavours and quotas were built for | The schedulable count equals physical cards × `vfNum` |
| You want to split a card by memory share | Whether HAMi or MetaX's gpu-scheduler is installed | sGPU uses `metax-tech.com/sgpu` and needs HAMi ≥ 2.6.0, see [HAMi](/ecosystem/hami) |
| MetaX metrics are absent from monitoring | Whether `mx-exporter` is installed and on which port | Install mx-exporter and scrape port 8000 |
| C500 or N260 cannot be selected on a model card | Whether the platform has MetaX models registered | It does not; use a placeholder for now |
| The flavor name keeps a prefix and has no MetaX icon | Platform display layer | A current product boundary, it does not affect scheduling |

## Why is there no place to install MetaX components on the platform

System Apps bundles only two hardware scheduling component sets, NVIDIA and Ascend. MetaX cluster components have to
be installed by hand from the official charts. This is not a configuration problem but the current product boundary;
see [Platform support status](/ecosystem/metax/platform-support).

## Containers cannot see the card while the host can

Start by ruling out two wrong assumptions: this layer is not CDI, and it is not the standard toolkit. MetaX uses its
own container runtime:

- **containerd nodes**: install `metax-container-runtime`. containerd itself keeps running as usual; registration follows the official notes.
- **Docker nodes**: use `metax-docker`.

The check is direct: whether either component is installed on the node, and whether the containerd configuration
points at the MetaX runtime. If neither is true, it is simply not installed.

## Can I use `metax-tech.com/vgpu`

No. That resource name never appears in MetaX's official documentation; it is a habit carried over from other
vendors. The MetaX device plugin reports exactly one resource name:

```
metax-tech.com/gpu
```

Whole cards and the VFs produced by SR-IOV both use it. Resource requests, flavors and quotas all go by this name.

## Why does the flavor name keep a prefix and carry no icon

The platform strips the model prefix from flavor names for nvidia / amd / intel / huawei only. MetaX is not on that
list, so the flavor name keeps its prefix. The vendor icon works the same way: MetaX has no dedicated icon, and the
flavor label only shows the generic `GPU`.

Neither affects scheduling; both reflect the current display layer. Making the display cleaner requires the platform
to add MetaX to those lists.
