# Platform Support Status

Recognising an accelerator on the platform runs through four places in the code, each handling one thing. This page
lists the actual state of each for MetaX, so that a missing item in the UI does not send you hunting for a
configuration mistake that is not there.

What the platform has given MetaX so far is half an ID card: the accelerator type is registered, the model names,
icons and scheduling components are not.

## Layer-by-layer check

| Layer | Location | State for MetaX |
| --- | --- | --- |
| Image accelerator type | The accelerator option when registering an image | **Registered**: `MACA(沐曦)` |
| Model metadata model name | The accelerator model selectable on a model card | **Missing**: not one MetaX model is registered |
| Model metadata backend enum | `hardware_backends` in model metadata | **No** `maca`; the current enum is cpu / cuda / rocm / ascend / mlu / musa / metal |
| Flavor accelerator label | The wording on the flavor label | **Generic path**: shows `GPU`, no MetaX-specific label |
| Flavor model name | How the flavor name is assembled | **The prefix is not stripped**: the platform's strip list only covers nvidia / amd / intel / huawei |
| Flavor vendor icon | The small icon on the flavor label | **Missing**: MetaX has no dedicated icon |
| Cluster scheduling components | Cluster Management → Operations → System Apps | **Missing**: the platform bundles only NVIDIA and Ascend |

## What works today

- **Image metadata**: tag an image as `MACA(沐曦)` when uploading or registering it, and search and filtering pick it up.
- **Compute scheduling**: once `gpu-device` reports `metax-tech.com/gpu` on a node, quotas, flavors and job requests built on that resource name all work on the platform side.
- **Resource flavors**: you can create a flavor by resource name by hand. It works; it just carries no MetaX-specific information in the display layer.

## What does not work yet

| Missing capability | Impact | Workaround |
| --- | --- | --- |
| MetaX models in model metadata | You cannot pick C500 or N260 when creating a model card | Use a placeholder model for now and switch back once the platform registers them |
| A `maca` value in the backend enum | `hardware_backends` has no `maca` | Leave the field empty or pick the closest existing value; scheduling does not read it |
| A MetaX accelerator label on flavors | The flavor label shows generic `GPU` instead of MetaX | A display-layer design decision, it does not affect scheduling |
| Prefix stripping for the flavor model name | The flavor name carries a prefix and reads less cleanly | Wait for the platform to add `metax` to the strip list |
| A vendor icon on flavors | No MetaX icon on the flavor label | Same as above, display layer only |
| One-click install for cluster scheduling components | You cannot install it from System Apps | Install the official charts by hand, see [Kubernetes components](/ecosystem/metax/k8s-components) |

## Full manual procedure

The platform's System Apps has nothing for MetaX, so all four steps happen outside the platform:

1. Install KMD / UMD and the MXMACA user space on every machine with a card; `mx-smi` should list the cards.
2. Install `metax-container-runtime` (or `metax-docker`) on the same machines so containers can see the devices.
3. Install the cluster components in the cluster with `metax-operator` or `metax-gpu-extensions`, and confirm `metax-tech.com/gpu` appears on the nodes.
4. Back on the platform, create resource flavors and quotas for that resource name, then submit a job requesting one card to verify.

Step 4 is the only one that touches the platform UI; the first three all happen on the cluster side.
