# Drivers & Container Runtime

This page stays on the host layer and does not touch Kubernetes. Cluster-side components are covered in
[Kubernetes components](/ecosystem/metax/k8s-components).

Two checks mark the install as done: `mx-smi` lists the cards, and it reports a driver version. Fail either one and
every cluster component installed afterwards is wasted.

## Prerequisites

| Item | Requirement |
| --- | --- |
| Operating system | A distribution matched to the target MXMACA version; the exact list is in the MetaX Software Center |
| Kernel driver | KMD / UMD, kernel module `metax.ko`, shipped with `k8s-driver-image` |
| User space | MXMACA® SDK, providing `macaRT`, `mxcc` and the operator libraries |
| Container runtime | docker ≥ 18.09.3 or containerd ≥ 1.5.0, the minimum the cluster components require |
| Package source | MetaX Software Center, `https://developer.metax-tech.com/softnova/index` |

## Installing the driver

The driver splits into kernel-mode KMD and user-mode UMD, and MetaX ships it as `k8s-driver-image`, the same package
used for both host installs and cluster distribution. Work through the steps in this order:

1. In the Software Center, find the package matching **model + operating system + MACA version**.
2. Install KMD / UMD, then confirm `metax.ko` is loaded.
3. Install the MXMACA user space, then confirm `mxcc` and `macaRT` are available.
4. Verify the cards and driver version with `mx-smi`.

:::warning Commands follow the current official release
MetaX install commands change with the package version and the distribution, and every package in the Software Center
carries its own install notes. The steps above describe the flow; before touching a machine, open the note for that
package and follow it line by line.
:::

## Container runtime

MetaX uses its own implementation on this layer, not CDI and not the standard toolkit. The two names MetaX publishes
map to two environments:

| Component | Environment | Notes |
| --- | --- | --- |
| `metax-container-runtime` | containerd | MetaX's container runtime; once configured, containerd uses it to mount devices into containers |
| `metax-docker` | Docker | The corresponding runtime on the Docker side |

The relationship with standard containerd needs to be explicit: **containerd itself is untouched, what you add is the
MetaX runtime**. The node's containerd keeps running as usual and workloads reach the devices through the MetaX
runtime, so a node must have both a working containerd service and the MetaX runtime registered. Official base images
are named like `maca-c500` and `mxc500-maca`, and workload images build on top of them.

The commands for installing and registering the runtime likewise follow the notes for the relevant Software Center
package.

## Verification

```bash
mx-smi
```

If this lists the cards and a driver version on the host, the driver layer is in place.

`mx-smi` is a command-line tool, **not a monitoring exporter**. Collecting metrics on a cluster requires installing
`mx-exporter` separately. They are two different things, so do not confuse them while troubleshooting.

## Uninstall and upgrade

Stop workloads first, then stop `gpu-device` and `mx-exporter` on the cluster side, and only then touch the driver.
`gpu-device` reads driver interfaces on a timer, so upgrading underneath it tends to leave the plugin running while
reporting the wrong device count, which only a plugin restart clears.

When swapping driver or container runtime versions, re-check the `driver-config` on the nodes as well; that is where
the SR-IOV `vfNum` setting lives.
