# Kubernetes Components

The cluster side ships as two packages: **GPU Operator** (chart `metax-operator`) and GPU Extensions
(chart `metax-gpu-extensions`). The first is the full set, the second a trimmed-down one.

| Component | Purpose | What breaks without it |
| --- | --- | --- |
| operator-controller | Manages the lifecycle of the components below | The whole set cannot be installed |
| gpu-device | Device plugin; registers the cards as Kubernetes resources | No `metax-tech.com/gpu` on the node, so workloads cannot request a card |
| gpu-label | Labels nodes with card model and similar | No basis for picking nodes by model |
| driver-manager | Manages driver distribution and version alignment | Drivers must be aligned by hand on every machine |
| vfio-manager | Manages SR-IOV VF passthrough | The KubeVirt passthrough path is unavailable |
| container-runtime | Configures the MetaX container runtime | Containers cannot see the cards |

`gpu-device` is built on the Device Plugin Framework and includes topology-aware allocation and health checks.
**It is not open source**: there is no standalone public GitHub repository, it is distributed through the MetaX
Software Center or commercial channels, and its image is `cr.metax-tech.com/cloud/gpu-device`.

## Choosing between the two charts

| Chart | Components included | When to pick it |
| --- | --- | --- |
| `metax-operator` (GPU Operator) | operator-controller, gpu-device, gpu-label, driver-manager, vfio-manager, container-runtime | You want driver management, SR-IOV, and the container runtime configured together |
| `metax-gpu-extensions` (GPU Extensions) | gpu-device, gpu-label | Driver and container runtime are already on the nodes and you only schedule **whole cards** |

Both charts live in MetaX's own OCI registry:

```
oci://cr.metax-tech.com/cloud/metax-operator
oci://cr.metax-tech.com/cloud/metax-gpu-extensions
```

:::warning Pulling the charts needs commercial authorisation
These two OCI addresses are not a public registry; you need commercial authorisation before you can pull from them,
and `gpu-device` itself is not open source either. Get the authorisation and registry credentials ready first,
otherwise `helm install` stops at the pull step.
:::

Version requirements: Kubernetes ≥ 1.23; docker ≥ 18.09.3 or containerd ≥ 1.5.0 on the nodes.

## Resource name reported by the device plugin

`gpu-device` reports a single resource name, and **whole cards and SR-IOV VFs both use it**:

```
metax-tech.com/gpu
```

Request as many as you need cards:

```yaml
resources:
  limits:
    metax-tech.com/gpu: 1
```

:::warning `metax-tech.com/vgpu` is not a MetaX resource name
`metax-tech.com/vgpu` does not appear anywhere in MetaX's official documentation; it comes from other vendors'
naming habits. When writing flavors or quotas, go by what the node actually reports: `metax-tech.com/gpu`.
:::

## Monitoring

Metrics come from **mx-exporter**, a Python program built on MXSML:

| Item | Value |
| --- | --- |
| Component | mx-exporter (Python, built on MXSML) |
| Default port | 8000 |
| Scrape interval | 10000 ms |
| Metric prefix | `mx_`, for example `mx_device_type`, `mx_driver_ver`, `mx_chip_hotspot_temp` |
| Installation | Helm chart, landing in the `metax-monitor` namespace |
| Repository | `https://github.com/MetaX-MACA/mxExporter` |

A shared monitoring dashboard hooks up by port, and the MetaX one is 8000, so do not reuse another vendor's port
number. `mx-smi` is only a command-line tool and cannot serve as an exporter.

## Sharing one card

MetaX has three partitioning paths, each with its own resource names:

| Method | Resource names | Notes |
| --- | --- | --- |
| Software partitioning, sGPU | `metax-tech.com/sgpu`, `metax-tech.com/vcore`, `metax-tech.com/vmemory` | Up to 16 instances per card; `vcore` is a percentage and `vmemory` is in GiB; requires HAMi ≥ 2.6.0 or MetaX's own gpu-scheduler. HAMi's prerequisites are under [HAMi](/ecosystem/hami) |
| Hardware virtualisation, SR-IOV | `metax-tech.com/gpu` | Set `vfNum` in `driver-config` (v1 / v2); the schedulable count on a node equals physical cards × `vfNum` |
| KubeVirt passthrough | `metax-tech.com/vfio-gpu` | A virtual machine takes over one card directly |

Watch the SR-IOV path: after setting `vfNum` the node still reports `metax-tech.com/gpu`, but the count multiplies.
**Flavors and quotas built by card count must be updated to match**, or jobs will refuse to schedule while the
resources look available.

## Relationship with Volcano

MetaX **does have an official Volcano plugin**, unlike AMD, which can only go through generic extended resources.
MetaX built a `gpu-aware` scheduling plugin on Volcano's extension mechanism, with the parameters `weight` and
`loss.weight`, supporting topology-aware and supernode scheduling. It does not do sharing: splitting a card is
left to HAMi or MetaX's own gpu-scheduler, which runs alongside `gpu-aware` rather than inside it.

## Verifying the install

```bash
# The node reports schedulable MetaX resources
kubectl describe node <gpu-node> | grep metax-tech.com

# Device plugin pods are up
kubectl get pods -A | grep -i metax

# The monitoring exporter is running
kubectl get pods -n metax-monitor
```

Then submit a minimal job requesting one card; if `mx-smi` prints the card inside the container, the path is good.
