# Observability and operation and maintenance

This page covers **how to see what the cluster is doing and how to let it improve itself**: metrics, logs and traces help you locate a problem, while autoscaling and rescheduling components adjust things when nobody is watching.
You turn to this layer when you troubleshoot, watch resource trends, or want a service to scale with traffic.

:::tip Three words to tell apart first
**Metrics** are like a thermometer: one number recorded at intervals, to watch a trend.
**Logs** are like a medical chart: every event written down in time order, to read back when something goes wrong.
**Tracing** is like a parcel tracking number: which stages a single request passed through and how long each one took.
:::

## What this category solves

| Problem | Who handles it |
| --- | --- |
| See CPU, memory and accelerator utilization trends | kube-prometheus-stack or VictoriaMetrics |
| Alert when a service has a problem | Alertmanager (installed with the monitoring component) |
| Query a container's past logs | Loki + Logging Operator |
| Trace a request across services and find where it stalls | OpenTelemetry Collector + Jaeger |
| Let a large model help analyze a failure | Holmes |
| Add replicas when traffic rises and remove them when it falls | KEDA |
| Pod CPU and memory requests are always off | VPA |
| Nodes run hot and cold and resources are fragmented | Descheduler |
| Drive autoscaling with Prometheus metrics | Prometheus Adapter |

## Which components are included

| Component | Purpose | Key traits | How the platform uses it |
| --- | --- | --- | --- |
| kube-prometheus-stack (Prometheus monitoring stack) | Collects and stores metrics and fires alerts | Ships Prometheus, Alertmanager and Grafana, plus node and cluster state collection | Operations Management → System Apps; once installed, view through the monitoring component's dashboards |
| metrics-server (basic metrics service, 3.13.0) | Provides basic resource usage for nodes and Pods | Resource-usage metrics are only complete once it is installed; optional | Operations Management → System Apps (monitoring) |
| Loki + Logging Operator (container log solution) | Collects, aggregates and queries container logs | Fluent Bit collects, SyslogNG aggregates, Loki stores; pick single / simple scalable / distributed by log volume | Operations Management → System Apps; query logs on the Log Management page |
| VictoriaMetrics (time-series database and alerting stack) | Prometheus-compatible metric storage, query and alerting | Provides collection, alerting and dashboards as one set; supports cluster mode and multiple replicas | Operations Management → System Apps |
| VictoriaLogs (log storage and query) | Lightweight log storage and query | Supports single and cluster modes, with configurable retention and capacity | Operations Management → System Apps |
| OpenTelemetry Collector + Jaeger (tracing) | Collects and stores request trace data | The Collector supports multiple replicas and can connect to a Jaeger backend | Operations Management → System Apps |
| Holmes (intelligent diagnostics service, 0.34.0) | Uses a large model to analyze resource problems automatically | Multi-tenant isolation; it can only diagnose resources you are authorized for | Install under System Apps, then configure under System Settings → AI Assistant Settings |
| KEDA (event-driven autoscaling, 2.20.2) | Autoscales on external events or metrics | Turns message queues, databases and monitoring metrics into scaling triggers | Operations Management → System Apps |
| VPA (vertical autoscaling, 1.6.0) | Recommends and adjusts Pod CPU and memory requests automatically | Makes a recommendation first, then recreates the Pod to apply it by policy; does not manage replica counts | Operations Management → System Apps |
| Descheduler (rescheduling and defragmentation) | Moves load from hot nodes to idle ones | Supports scheduled and fixed-interval triggers and can skip Pods with mounted storage volumes | Operations Management → System Apps |
| Prometheus Adapter (metrics adapter, 4.14.1) | Turns Prometheus metrics into metrics Kubernetes can use | Lets autoscaling react to business metrics instead of only CPU | Installed with the monitoring and scheduling components |

## When you need to care about it

- **You want to query logs**: first confirm **Loki + Logging Operator** is installed, then go to **Operations Management → Log Management** and use the **All Logs** and **Node Logs** tabs.
- **You want monitoring and alerting**: install **kube-prometheus-stack** or **VictoriaMetrics**. The two overlap, so **pick one per cluster** rather than installing two collection stacks.
- **You want to trace calls across services**: install **OpenTelemetry Collector + Jaeger** and add the matching reporting to your business code.
- **Service load fluctuates a lot**: use **KEDA** to scale on events or metrics; if only CPU and memory requests are off, use **VPA**.
- **You want autoscaling on business metrics**: install **Prometheus Adapter** to bring Prometheus metrics in.
- **Nodes are unevenly busy**: enable **Descheduler** to move load by CPU and memory waterlines.
- **You want a large model to help troubleshoot**: install **Holmes**, then fill in the model and access key under **System Settings → AI Assistant Settings**.

:::warning Do not mix the two observability stacks
The Prometheus stack (kube-prometheus-stack) and the VictoriaMetrics stack (VictoriaMetrics) overlap. Install only one per cluster, or you will collect and alert twice and compete for storage and CPU.
:::

## Before you start

- Installing these components needs **platform administrator** rights, and you go to **Operations Management → System Apps** inside a specific cluster.
- A storage class must be ready in advance; the monitoring and logging components need persistent storage for historical data, or the data is lost on restart.
