# Kubernetes Components

Two components go on the cluster side: the device plugin registers the card as a schedulable resource, and the
exporter exposes card metrics to Prometheus.

| Component | Purpose | Notes |
| --- | --- | --- |
| `xpu-device-plugin` | Registers the card as a Kubernetes resource | No confirmed official GitHub repository; the plugin appears to be distributed with the driver package or through an account on the official site |
| `xpu-exporter` | Exposes Prometheus metrics | DaemonSet, default port 9507 |
| `xpushare-device-plugin` | Related to splitting a card | Images exist under the Docker Hub organisation `kunlunxpu`, last updated 2022 to 2023 |
| `cxpu-device-plugin` | Related to splitting a card | Same as above |

The images can be pulled, but everything under `kunlunxpu` dates from 2022 to 2023, so check it against the driver
you are running before use.

In Tencent Cloud TKE this component set is identified as `xpu-gpu`, with the DaemonSet named
`xpu-device-plugin-daemonset` and image tag `v5.0.2-alpha.3`. Installing it yourself does not have to match that
tag, but comparing against it tells you whether you are looking at the same generation.

## The resource key the device plugin reports

The current convention is a single key for a whole card:

```
kunlunxin.com/xpu
```

Request as many cards as you need by number:

```yaml
resources:
  limits:
    kunlunxin.com/xpu: 1
```

## The legacy resource key

In the README of older device plugin versions the key is `baidu.com/xpu`, the splitting parameter is
`--sriov-num-vfs`, and the node label is `baidu.com/sriov-num-vfs=x`. Older clusters may still be on that set.

:::warning Check what the node actually reports before defining a flavor
Both conventions are out there, and there is no way to tell which one your cluster uses without looking. Run
`kubectl describe node <node> | grep -iE "kunlunxin.com|baidu.com"` and define the flavor against whatever comes
back. Get it wrong and the flavor exists while jobs keep failing to acquire a card.
:::

## Monitoring

Metrics come from `xpu-exporter`, in Prometheus format:

| Item | Value |
| --- | --- |
| Component | `xpu-exporter` |
| Form | DaemonSet |
| Metric format | Prometheus |
| Default port | 9507 |
| Wiring into platform monitoring | Create a ServiceMonitor scraping 9507 |

This port differs from NVIDIA's 9400 and AMD's 5000, so do not reuse the same port number in a shared dashboard.

## Where vXPU splitting stands

Kunlunxin calls card sharing vXPU, built on SR-IOV. There are three paths, each asking for more than the last:

| Path | Status | Resource key |
| --- | --- | --- |
| Official vXPU (TKE chart parameters) | The parameters are placeholders and are not in effect | None |
| HAMi's `vxpu-device-plugin` | Usable, limited to P800-OAM and to memory slicing | `kunlunxin.com/vxpu`, `kunlunxin.com/vxpu-memory` |
| The legacy `--sriov-num-vfs` | Older convention | Paired with the node label `baidu.com/sriov-num-vfs=x` |

:::warning The splitting parameters are inert on the platform and cloud vendor sides
`devicePlugin.enableSriov`, `sriovNumVfs` and `enableXpuShare` in the TKE chart are placeholders; turning them on
does not actually split the card. To schedule by share on the platform, the only route is HAMi, which is outside
the platform's built-in path.
:::

## Relationship to Volcano

The platform's scheduling backend is Volcano, and Volcano's device backends are only nvidia and ascend. There is
no official Kunlunxin plugin. So Kunlunxin takes the generic path: the device plugin reports the card as a standard
extended resource, and Volcano schedules by resource key and count.

- Multi-card jobs can be scheduled, on the strength of the standard extended resource mechanism.
- Scheduling split shares of a card, and allocating memory by ratio, are outside what Volcano supports officially
  and need HAMi. HAMi has supported Kunlunxin since v2.7.0, and v2.8.0 fixed vXPU occasionally not working on P800
  nodes. Its support matrix ticks memory isolation for Kunlunxin but not compute isolation, so slicing by memory
  works while slicing by compute does not. This is a separate route from the platform's built-in path; the
  prerequisites and resource keys are under [HAMi](/ecosystem/hami).

## Verifying an install

```bash
# Kunlunxin resources reported by the node
kubectl describe node <node> | grep -iE "kunlunxin.com|baidu.com"

# Plugin and exporter pods
kubectl get pods -A | grep -i xpu

# Metrics port
kubectl get svc -A | grep -i xpu-exporter
```

Then submit a minimal job requesting one card and run `xpu-smi` inside the container.
