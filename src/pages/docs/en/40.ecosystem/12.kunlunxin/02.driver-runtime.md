# Drivers & Container Runtime

On the host, there is one sign that this layer is done: `xpu-smi` runs and shows a device. The cluster-side
components are covered in [Kubernetes components](/ecosystem/kunlunxin/k8s-components).

If that one check fails, every cluster component installed afterwards is wasted.

## Prerequisites

| Item | Requirement |
| --- | --- |
| Operating system | No complete supported list is public; follow the distribution notes in the driver package shipped with the card |
| Kernel driver | kmd inside XRE, shipped with the driver package |
| User-space runtime | The user-space part of XRE; `xpu-smi` only exists once it is installed |
| Container runtime | Cluster nodes usually run containerd; how the card is made visible follows the driver package notes |
| Compilable driver | XDR, shipped as source, only needed when a specific kernel version must be supported |

## Driver and software stack

Kunlunxin packages the kernel driver, the user-space runtime and the device management tools together under the
name XRE.

The kmd in the kernel lets the operating system see the card, and the user-space part provides the runtime and
`xpu-smi`. Operator libraries, communication libraries and framework integration above that live in the workload
image, covered in [Products & software stack](/ecosystem/kunlunxin/products).

XDR is a separate line, shipped as source for cases that compile their own driver. Unless there is a concrete
kernel support requirement, leave it alone.

:::warning Where the layering detail comes from
The layering on this page comes mostly from the Tencent Cloud TKE Kunlunxin component documentation. That is a
third-party write-up quoting official wording. It is fine for understanding the structure, and not fine as an
installation manual.
:::

## Verifying the driver

```bash
xpu-smi
```

If it lists a device, the layer is in place. Which subcommands `xpu-smi` takes, and how to select a single card,
are not documented publicly; follow the notes shipped with the driver package. Keep the full output of this command
when filing an issue, because the first question will be about the driver version.

## Seeing the card inside a container

The host recognising the card is not enough; the container has to see it too. Configuration differs per container
runtime and follows the driver package, so it is not spelled out here. Once configured, verify with a minimal job:
request one card and run `xpu-smi` inside the container. The resource request syntax is in
[Kubernetes components](/ecosystem/kunlunxin/k8s-components).

## Upgrades

Stop the workload first, then stop `xpu-device-plugin` and `xpu-exporter` on the cluster side before touching the
driver. The device plugin polls the driver interface, so upgrading underneath it tends to leave a state where the
plugin runs but reports the wrong device count, recoverable only by restarting the plugin.

:::warning Install commands are not on the web
Kunlunxin has no developer documentation site that can be cited publicly, and the package names, repository addresses
and install parameters ship inside the driver package. Get the package first, or request it through the official
channel at `https://www.kunlunxin.com`, rather than copying commands out of third-party documentation.
:::
