# FAQ

## Quick reference

| Symptom | Check first | Action |
| --- | --- | --- |
| `xpu-smi` reports no device | Whether the driver package is installed, and the account's permissions | Reinstall following the driver package shipped with the card |
| The host sees the card but a container does not | Whether the container runtime was configured | Configure it following the container runtime notes in the driver package |
| The node has no `kunlunxin.com/xpu` | Device plugin pod state and logs | Confirm the driver is in place, then restart the plugin |
| The node reports `baidu.com/xpu` | Device plugin version | Legacy convention; define the flavor against the actual key, or replace the plugin |
| The flavor does not look like an accelerator | The flavor's type field | Set it to GPU |
| The flavor tag says `GPU` rather than Kunlunxin | Platform display logic | Expected, no effect on scheduling |
| The flavor name carries the `kunlunxin.com/` prefix | The strip list covers only four vendors | Expected |
| Turning on the vXPU parameters changes nothing | Whether they are placeholders | Not in effect; use HAMi for per-share scheduling |
| Multi-card jobs queue for a long time | Whether whole cards are held by idle jobs | No built-in splitting, scheduling is by card count |
| Prometheus cannot scrape card metrics | The `xpu-exporter` port | Default 9507; check the ServiceMonitor points there |

## Why a flavor is not recognised as an accelerator

The platform decides whether a resource is an accelerator from keywords in the resource key: gpu, npu, mlu, dcu
and ascend, any one of which is enough. `kunlunxin.com/xpu` contains none of them, so automatic recognition does
not happen.

There is one fix: set the flavor's type field to `GPU` by hand when defining it. After that the flavor is handled
as an accelerator and quota, flavors and job requests work normally. The full comparison is on
[Platform support](/ecosystem/kunlunxin/platform-support).

## Which resource key does the node report

Both conventions exist, so look at the node:

```bash
kubectl describe node <node> | grep -iE "kunlunxin.com|baidu.com"
```

`kunlunxin.com/xpu` is the current convention, and `baidu.com/xpu` comes from the README of older device plugin
versions. Fill in the flavor with whatever the node reports rather than guessing from documentation.

## Why turning on the vXPU parameters changes nothing

The Tencent Cloud TKE chart has `devicePlugin.enableSriov`, `sriovNumVfs` and `enableXpuShare`, which look like
splitting switches but are placeholders that do not split the card today. The official vXPU is an SR-IOV route
that has not yet landed as a working configuration.

To schedule by share on the platform, the route is HAMi's `vxpu-device-plugin`, with the resource keys
`kunlunxin.com/vxpu` and `kunlunxin.com/vxpu-memory`, currently covering only P800-OAM and only memory slicing.
HAMi is outside the platform's built-in path, as described in
[Kubernetes components](/ecosystem/kunlunxin/k8s-components).

## Why there is no official installation documentation

Kunlunxin has no standalone developer documentation site: neither `developer.kunlunxin.com` nor
`docs.kunlunxin.com` resolves, the `kunlunxin` organisation does not exist on GitHub, and
`github.com/kunlunxin/xpu-device-plugin` returns 404. What can be found publicly on the software stack comes
mostly from the Tencent Cloud TKE component documentation, which is a third-party write-up.

That is why this section states the layering and the verification method without giving install commands. Driver
packages, package names and install parameters come from the driver package shipped with the card, or from the
official channel at `https://www.kunlunxin.com`.

:::warning Do not paste versioned commands from third-party documentation
Package names and repository addresses in third-party documentation go stale, and the images under the
`kunlunxpu` organisation in particular stop at 2022 to 2023. Confirm it matches the driver you are running before
pasting anything.
:::
