# Platform Support

"Recognising a card" on the platform runs through four pieces of code, each responsible for one thing. The list
below gives the actual state of each for Kunlunxin, so that a missing item in the UI can be told apart from a
misconfiguration.

## Layer-by-layer comparison

| Layer | Location | State for Kunlunxin |
| --- | --- | --- |
| Image accelerator type | The accelerator option when registering an image | **Absent**. The options are CUDA / ROCm / CANN / DKT / MACA / CoreX / Musa / Neuware / CPU |
| Model metadata model | The accelerator model selectable on a model card | **No Kunlunxin model is registered** |
| Model metadata backend enum | `hardware_backends` in model metadata | **Absent**. The list is cpu / cuda / rocm / ascend / mlu / musa / metal, with no xpu |
| Resource-key recognition for flavors | How the platform decides whether a resource is an accelerator | **A problem unique to this vendor**: the resource key alone is not enough, and the flavor's type field has to be set to GPU |
| Accelerator label on a flavor | The wording shown on the flavor tag | Generic path, shown as `GPU` |
| Model name on a flavor | Flavor name assembly | The prefix is not stripped. The list of prefixes the platform strips is only nvidia / amd / intel / huawei |
| Vendor icon on a flavor | The small icon on the flavor tag | **Absent** |
| Cluster scheduling component | Cluster Management → Operations → System Apps | **Absent**. The platform bundles only NVIDIA and Ascend |

## The resource-key trap

The platform decides whether a resource is an accelerator by looking for keywords in the resource key: a hit on
gpu, npu, mlu, dcu or ascend is enough. `kunlunxin.com/xpu` contains none of them, so the platform is given a name
that is not on the list and will not treat it as an accelerator.

The consequence is straightforward: with only the resource key filled in, the flavor is not recognised as an
accelerator and both quota and scheduling treat it as an ordinary resource.

The way around it is to specify the type by hand. When defining a flavor, set the **type** field to `GPU`. After
that the platform handles the flavor as an accelerator and quota and job requests work normally. This is the one
place in a Kunlunxin deployment that requires manual intervention; the symptom of forgetting is a flavor that
looks like an ordinary resource in the list and cannot be selected when requesting a job.

## What works today

- **Flavors**: define a flavor against the resource key the node reports, set its type field to GPU, and quota, flavors and job requests all follow the accelerator path.
- **Both resource keys**: `kunlunxin.com/xpu` and the legacy `baidu.com/xpu` are handled as standard extended resources, so fill in whichever the node reports.
- **Scheduling**: once `xpu-device-plugin` runs on the node and reports the resource, multi-card jobs schedule from the platform side.

## What does not work yet

| Missing capability | Effect | Workaround |
| --- | --- | --- |
| Image accelerator type | No Kunlunxin entry when registering an image, so pick the closest option | A gap in the platform enum, no effect on running |
| Model metadata model | No P800 or other model to select on a model card | Put the model in the model description or the flavor name |
| xpu in `hardware_backends` | Model metadata cannot mark an XPU backend | Map to the closest backend |
| Keyword recognition of the resource key | Nothing is recognised if the type field is left empty | Set the flavor's type field to GPU by hand |
| Vendor icon on a flavor | No Kunlunxin icon on the flavor tag | A display-layer gap, no effect on scheduling |
| Prefix stripping in flavor names | The flavor name carries the whole `kunlunxin.com/` prefix instead of a clean model name | Expected, since the strip list only covers four vendors |
| One-click install of cluster components | Nothing to click for Kunlunxin in System Apps | Install by hand, see [Kubernetes components](/ecosystem/kunlunxin/k8s-components) |
| vXPU splitting | The official splitting parameters are not in effect | Use HAMi, see [Kubernetes components](/ecosystem/kunlunxin/k8s-components) |

## The full manual sequence

System Apps has no Kunlunxin entry, so the cluster side is done by hand:

1. Install the driver package on every machine that has a card, until `xpu-smi` shows it.
2. Configure the container runtime on the same machines so containers can see the card.
3. Install `xpu-device-plugin` and `xpu-exporter` on the cluster and confirm the node reports `kunlunxin.com/xpu` or `baidu.com/xpu`, with metrics on port 9507.
4. Back on the platform, define a flavor, set the type field to GPU, then create the quota.
5. Submit a job requesting one card and run `xpu-smi` inside the container.

Step 4 is the only one that touches the platform UI; everything else happens on the cluster side.
