# Products & Software Stack

## Product lines

The data centre line splits in two: training cards are called TianGai and their model names start with `BI`;
inference cards are called ZhiKai and start with `MR`. The Chinese product name and the model name are two
different strings, so match on the model name when you read a spec.

| Line | Product name | Model | Key specs | Role |
| --- | --- | --- | --- | --- |
| TianGai | TianGai 100 | BI-V100 | 32 GB HBM2, 250 W | Training card |
| ZhiKai | ZhiKai 100 | MR-V100 | Not found on a first-party page | Inference card |

The official Kubernetes vGPU documentation declares support for a wider set of models than those two lines cover:

| Model | Status in the vGPU documentation |
| --- | --- |
| BI-V100 | Declared supported |
| BI-V150S | Declared supported |
| BI-V150 | Declared supported |
| MR-V100 | Declared supported |
| MR-V100-DUO | Declared supported |

:::warning Do not extrapolate from the models above
MR-V50 and TianGai 150 / 200 / 300 could not be found on a first-party product page, so their specs and support
status are **unconfirmed**. Do not infer a generation or a spec sheet from the model number; use the current
product pages in the vendor documentation centre.
:::

## The stack has four layers

The vendor calls the whole thing the CoreX SDK, installed under `/usr/local/corex` by default.
Four layers have to be separated, because a missing layer breaks everything above it:

| Layer | Components | Installed on | Role |
| --- | --- | --- | --- |
| Kernel driver | CoreX driver | Host | Lets the operating system recognise the card and exposes the device nodes |
| Runtime and tools | The CoreX SDK itself, with the commands `ixSMI`, `ixPROF`, `ixKN`, `ixSYS`, `ixGDB` | Host | Device management, profiling, system information and debugging |
| Compiler and libraries | Compiler and function libraries | Host or workload image | Build and runtime dependencies for workload images |
| Containers and frameworks | ix-Container-Toolkit plus the inference and operator libraries | Host and workload image | Lets containers reach the card and frameworks run on CoreX |

The operator and inference libraries turn up under the names ixDNN, ixBLAS, ixCCL, ixRT, IGIE, IxFormer and ixTE.
Most of those names come from third-party write-ups and only some can be matched against first-party
documentation, so **confirm the spelling and the version in the vendor documentation centre before quoting them**
in anything you deliver.

## The resource-name change

This has nothing to do with the hardware, but getting it wrong means jobs never get a card.
The device plugin used to report `iluvatar.ai/gpu`; the current official name is `iluvatar.com/gpu`.

:::warning SDK newer than 3.4 must use iluvatar.com
The old name still works, but the vendor marks it deprecated and states that with an SDK version greater than 3.4
it must be changed to `iluvatar.com`. When you upgrade the SDK, change the specs, quotas and job templates together;
change only one of them and you get a quota that exists but a job that cannot be scheduled.
:::

Note that this is not the same domain as the vGPU resources. The difference between the two sets is covered in
[Kubernetes Components](/ecosystem/iluvatar/k8s-components).

:::tip Search the documentation centre and the knowledge base
The documentation centre holds the released installation and user manuals, while the knowledge base is better for
looking up a specific entry by keyword. Details such as the supported model list, the resource-name spelling and
vGPU splitting often appear in only one of the two. Search both before you conclude.
:::
