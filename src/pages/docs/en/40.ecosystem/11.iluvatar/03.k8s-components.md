# Kubernetes Components

The cluster side needs very little: one device plugin and one metrics exporter are enough to use the cards and
see them. If you would rather not manage both by hand, the vendor Operator takes care of them.

| Component | Form | Role | Source |
| --- | --- | --- | --- |
| ix-device-plugin | A DaemonSet named `iluvatar-device-plugin` | Registers the cards as a Kubernetes extended resource | `https://github.com/Deep-Spark/ix-device-plugin` (Apache-2.0) |
| ix-config | A ConfigMap | Device plugin configuration; the reported resource name is its `resourceName` field | Ships with the device plugin |
| ix-exporter | Metrics exporter | Publishes card utilisation and memory metrics | `https://github.com/Deep-Spark` |
| ix-GPU-Operator | An Operator written with kubebuilder | Creates and manages ix-exporter and ix-device-plugin | `https://github.com/Deep-Spark/ix-GPU-Operator` |
| ix-volcano-plugin | Volcano scheduling plugin | Teaches Volcano about the vGPU resources | `https://github.com/Deep-Spark/ix-volcano-plugin` |

## Installation methods

| Method | Notes |
| --- | --- |
| The chart bundled with the device plugin | The ix-device-plugin repository carries its own Helm chart; installing it gives you the DaemonSet and the ConfigMap |
| `iluvatar-vgpu-manager-3.0.8.tgz` | The vGPU manager, installed into the `iluvatar-vgpu` namespace; requires Helm ≥ 3.2.0 and Kubernetes ≥ 1.20 |
| ix-GPU-Operator | Installing it creates ix-exporter and ix-device-plugin as well |
| The Operator's own chart | **Unconfirmed**: whether the ix-gpu-operator repository publishes a Helm chart has not been verified, so read the repository README before installing |

## The resource name the device plugin reports

By default it reports one whole-card resource:

```
iluvatar.com/gpu
```

Ask for as many cards as you need:

```yaml
resources:
  limits:
    iluvatar.com/gpu: 1
```

The name is not baked into the image; it comes from the `resourceName` field of the `ix-config` ConfigMap.
Changing that field changes the name across the whole cluster, so specs and quotas have to change with it.

:::warning The old iluvatar.ai/gpu name is deprecated
`iluvatar.ai/gpu` still works, but the vendor has marked it deprecated and states that with an SDK version greater
than 3.4 it must be changed to `iluvatar.com`. When an existing cluster upgrades its SDK, change the specs, quotas
and job templates together; change one and you get a quota that exists but a job that cannot be scheduled.
:::

Three node labels are set:

| Label | Meaning |
| --- | --- |
| `iluvatar.com/gpu.present` | Whether the node has a card |
| `iluvatar.com/gpu.memory` | Card memory capacity |
| `iluvatar.com/gpu.product` | Card model |

The value formats follow the vendor documentation, and these labels **must not be edited by hand** because the next
reporting cycle overwrites them.

## Monitoring

Metrics come from **ix-exporter**. The name does not contain `iluvatar`, so do not search for `iluvatar-exporter`
when you look for the image or the Pod.

| Item | Value |
| --- | --- |
| Listening port | 32021 |
| Metrics path | `/metrics` |
| Common metric names | `ix_gpu_utilization`, plus a group prefixed `ix_mem_*` |

On the collection side there are also two components, go-ixDCGM and go-ixml.

:::info The port differs from other vendors
NVIDIA's DCGM Exporter uses 9400, while Iluvatar uses 32021. Do not reuse the same port template for a shared
monitoring dashboard, or you will scrape empty data.
:::

## vGPU splitting and two sets of resource names

Sharing one card is officially called **vGPU (iluvatar VGPU)**. Compute can be split down to 1% and memory down to
256MB. The shares are not requested with the whole-card resource name, but with a different set:

| Purpose | Resource name | Example |
| --- | --- | --- |
| Whole card | `iluvatar.com/gpu` | Ask for one card by writing `1` |
| Split card count | `iluvatar.ai/<model>-vgpu` | `iluvatar.ai/BI-V150-vgpu: 1` |
| Split compute | `iluvatar.ai/<model>.vCore` | `iluvatar.ai/BI-V150.vCore: 50` |
| Split memory | `iluvatar.ai/<model>.vMem` | `iluvatar.ai/BI-V150.vMem: 64` |

One unit of `.vCore` is 1% of compute and one unit of `.vMem` is 256MB; omitting memory means using it all. The
model is spelled out, such as `MR-V100`, `MR-V50`, `BI-V150` or `BI-V100`. When several cards are requested the
compute share is scaled by the card count.

The whole-card names use the `iluvatar.com` domain, the split ones use `iluvatar.ai`. One vendor with two sets of
house numbers: remember a single rule and you are fine. **`iluvatar.com` is a whole card, `iluvatar.ai` is a
split share**.

Two device plugin settings relate to splitting: `flags.splitboard` and `sharing.timeSlicing.replicas`.

:::warning Several naming schemes share the iluvatar.ai domain; check the node first
HAMi's [official documentation](https://project-hami.io/docs/userguide/device-supported) lists exactly the set
above for Iluvatar: `<model>-vgpu`, `<model>.vCore` and `<model>.vMem`. See
[HAMi](/ecosystem/hami/device-matrix) for how this set is used. The names `iluvatar.ai/vgpu`,
`iluvatar.ai/vcuda-core` and `iluvatar.ai/vcuda-memory` also circulate online and come from an earlier scheme.
Because several schemes coexist under the same `iluvatar.ai` domain, **check what the node actually reports
before defining a flavor**:

```bash
kubectl get node <gpu-node> -o jsonpath='{.status.allocatable}' | tr ',' '\n' | grep iluvatar
```

Do not paste names from any single document straight into a spec.
:::

## How it relates to Volcano

Iluvatar **ships an official Volcano plugin** at `https://github.com/Deep-Spark/ix-volcano-plugin`.
That is where it differs from AMD, which can only go through the generic extended-resource route.

| Item | Requirement |
| --- | --- |
| Volcano version | 1.7.0 / 1.9.0 / 1.11.0 |
| Device plugin setting | `usevolcano=true` must be set |

The plugin does not work when the versions do not match. Confirm the actual Volcano version in the cluster before
enabling the switch on the device plugin; do it the other way round and the plugin comes up while the resources
stay out of scheduling.

## How to verify after installing

```bash
# The node reports allocatable Iluvatar resources
kubectl describe node <gpu-node> | grep -A 5 "Allocatable" | grep iluvatar

# The device plugin DaemonSet is running
kubectl get ds -A | grep iluvatar-device-plugin

# Which resource name is actually reported
kubectl get cm ix-config -n <namespace> -o yaml | grep -i resourceName

# The extra resource names that only appear with splitting enabled
kubectl get node <gpu-node> -o jsonpath='{.status.allocatable}' | tr ',' '\n' | grep iluvatar.ai

# The monitoring service is there
kubectl get svc -A | grep -i ix-exporter
```

Then submit a minimal job asking for one `iluvatar.com/gpu`. If `ixsmi` prints the card inside the container,
the path is complete.
