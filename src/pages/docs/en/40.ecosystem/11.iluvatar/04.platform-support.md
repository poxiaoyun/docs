# Platform Support

Recognising a card on the platform takes several code paths, each responsible for one thing. This page lists the
actual state of each of them for Iluvatar CoreX, so you can tell a configuration gap from a missing feature instead
of guessing when something is not where you expect it in the UI.

## Layer-by-layer check

| Layer | Location | Current state for this vendor |
| --- | --- | --- |
| Image accelerator type | The accelerator option when registering an image | **Registered**: `CoreX(天数智芯)` |
| Model metadata model name | The accelerator model selectable on a model card | **No Iluvatar model is registered** |
| Model metadata backend enum | `hardware_backends` in the model metadata | **Missing**: the list is cpu / cuda / rocm / ascend / mlu / musa / metal |
| Spec accelerator label | The wording shown on the spec label | **Generic path**: shows `GPU`, with no vendor-specific label |
| Spec model name | How the spec name is assembled | **The prefix is not stripped**: only nvidia / amd / intel / huawei are on the platform's strip list |
| Spec vendor icon | The small icon on the spec label | **Missing**: there is no Iluvatar icon |
| Cluster scheduling components | Cluster Management → Operations → System Apps | **Missing**: only the NVIDIA and Ascend packages are bundled |

## What works today

- **Image metadata**: `CoreX(天数智芯)` is selectable as the accelerator when registering an image, so search and filtering work.
- **Resource specs**: build specs and quotas against the `iluvatar.com/gpu` the node reports, and platform-side scheduling follows that resource name.
- **Scheduling**: once the device plugin is installed on the node, multi-card jobs are requested and queued through the same flow as any other hardware.

## What does not work yet

| Missing capability | Impact | How to work around it |
| --- | --- | --- |
| No Iluvatar models in the model metadata | BI-V100, MR-V100 and others cannot be selected on a model card | This is platform metadata maintenance; for now leave the model blank |
| No matching backend enum | Model metadata cannot state that it runs on CoreX | No platform-side workaround; note it in the model description |
| Spec label does not show the vendor | The label reads the generic `GPU` instead of Iluvatar | A display-layer design decision, it does not affect scheduling |
| Spec name keeps the model prefix | The model prefix stays in the spec name as-is | Name the spec by hand if you need a clean string |
| No vendor icon | There is no small icon on the spec label | The platform assets do not include one |
| No one-click cluster components | System Apps only bundles NVIDIA and Ascend | Install the official components by hand, in the order below |

## The full manual sequence

System Apps has no Iluvatar package, so the cluster-side work happens outside the platform:

1. Install the CoreX SDK on every machine that has a card, until `ixsmi` lists the cards; the default directory is `/usr/local/corex`.
2. Install ix-Container-Toolkit on the same machines and register the runtime as `iluvatar`.
3. Install ix-device-plugin in the cluster, or install ix-GPU-Operator and let it manage the device plugin and the exporter.
4. Confirm the node reports `iluvatar.com/gpu`; if you need metrics, confirm ix-exporter is running on port 32021.
5. If you need card splitting, install the vGPU components and build specs against `iluvatar.ai/<model>.vCore`.
6. Back on the platform, create the resource spec and quota for that resource name, then submit a job asking for one card to verify.

Only step 6 happens in the platform UI; the first five are cluster-side. The most common rework point in this
sequence is a step 4 resource that does not match the step 6 spec name.
