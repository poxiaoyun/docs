# Drivers & Container Runtime

This page covers the host layer only and does not touch Kubernetes. Cluster components are covered in
[Kubernetes Components](/ecosystem/iluvatar/k8s-components).

The sign that you are done is `ixsmi` listing the cards. If that does not work, every cluster component
installed afterwards is wasted effort.

## Before you start

| Item | Requirement |
| --- | --- |
| Operating system | A server distribution; the supported list is the current version in the vendor documentation centre |
| Hardware | The card is installed; `lspci` shows an Iluvatar device |
| Permissions | root or sudo, since installing the driver reloads kernel modules |
| Installation media | The CoreX SDK package for your operating system, from the vendor documentation centre |
| Optional | Compiled workload images need the compiler toolchain shipped with the matching SDK |

## Install the CoreX SDK

The vendor calls the whole thing the CoreX SDK, and it **installs under `/usr/local/corex`** by default.
The driver, the function libraries, the compiler and the command line tools all come with it, so one install
is enough.

Four steps:

1. Get the package for your server operating system from the vendor documentation centre.
2. Stop the workloads using the cards, so nothing holds the device while the driver is updated.
3. Run the installation as described in the vendor manual, keeping the default `/usr/local/corex` directory.
4. Put the SDK tools on `PATH`, or call them by absolute path.

:::warning Commands are governed by the current vendor version
The package name, the installation arguments and the exact path of each tool under `/usr/local/corex` all change
between SDK versions. The steps above explain the flow; copy the commands from the current installation manual in
the vendor documentation centre rather than from an example found elsewhere.
:::

## Install the container runtime toolkit

Recognising the card on the host is not enough, because workloads run in containers. This layer is
**ix-Container-Toolkit**, from `https://github.com/Deep-Spark/ix-container-toolkit`. Installing it gives you two
things: the `ix-ctk` command line, and a runtime registered with the container engine.

The configuration steps:

1. Fetch and install ix-Container-Toolkit following the repository README.
2. Use `ix-ctk` to register the runtime with the container runtime the node actually uses (on platform cluster nodes this is usually containerd).
3. Restart the container runtime process so the configuration takes effect.

:::info The runtime name is always iluvatar
Whether the node runs containerd or Docker, the runtime is registered under the name `iluvatar`.
Look for that name when writing a RuntimeClass or checking the configuration, not for the tool name `ix-ctk`.
:::

Restarting the container runtime restarts every container on the node, so **confirm the node can be taken out of
service**, or do it in a maintenance window.

## Verify

On the host:

```bash
ixsmi
```

Seeing card model, memory capacity and current utilisation means the driver is in place. If no device shows up,
check whether the SDK finished installing and whether the kernel module is loaded before suspecting the card.

The command line tools that come with the SDK are `ixSMI`, `ixPROF`, `ixKN`, `ixSYS` and `ixGDB`.
`ixSMI` is the everyday device tool, the counterpart of `nvidia-smi` on the NVIDIA side; for the others, follow the
matching manual in the vendor documentation centre.

In a container:

Start a container from a workload image that carries the CoreX SDK and run `ixsmi` inside it. Getting the same card
list as the host means the container runtime layer works. Inside a cluster the device plugin injects the devices,
so you do not pass device paths on the container command line by hand.

## Upgrade and removal

Stop workloads before upgrading the SDK, then stop the cluster-side device plugin and metrics exporter.
The device plugin polls the driver interface, so upgrading with it running tends to leave a plugin that is up but
reports the wrong device count, and only a restart clears that.

Remove the SDK as described in the vendor manual, then confirm `/usr/local/corex` is empty before installing the new
version, so files from two releases do not end up in the same directory. Do not skip that check on a major upgrade.
