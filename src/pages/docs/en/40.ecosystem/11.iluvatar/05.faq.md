# FAQ

## Quick troubleshooting table

| Symptom | Check first | What to do |
| --- | --- | --- |
| `ixsmi` reports no device | Whether the CoreX SDK finished installing, whether the kernel module is loaded | Reinstall per the vendor manual and confirm it landed in `/usr/local/corex` |
| The host sees the card, a container does not | Whether ix-Container-Toolkit is installed, whether the runtime is registered | Configure it per the vendor repository and confirm the registered name is `iluvatar` |
| The node has no `iluvatar.com/gpu` | The device plugin Pod status and the `resourceName` in `ix-config` | Confirm the host and the container toolkit first, then restart the plugin |
| An old node reports `iluvatar.ai/gpu` | The SDK version | With an SDK newer than 3.4 change it to `iluvatar.com`, and change the specs and quotas too |
| A vGPU request fails with an unknown resource name | Which key the node actually reports | Write the name the node reports, not the older `vcuda-*` scheme |
| Extra `iluvatar.ai` resources appear on the node | Whether splitting or time slicing is enabled | Build specs for the set you actually use rather than mixing the two |
| Multi-card jobs will not schedule under Volcano | The Volcano version and the device plugin switch | Volcano must be 1.7.0 / 1.9.0 / 1.11.0 and the device plugin needs `usevolcano=true` |
| No card metrics in monitoring | Whether ix-exporter is running and which port is scraped | Scrape `/metrics` on 32021 rather than writing 9400 |
| The spec label shows `GPU`, not Iluvatar | Platform display logic | Expected behaviour, it does not affect scheduling |
| No Iluvatar model on the model card | Whether the platform metadata has one | None is registered; see Platform Support |

## Why the resource names use two domains

Iluvatar uses two sets of resource names in Kubernetes, with different domains and different purposes:

| Purpose | Resource name |
| --- | --- |
| Whole card | `iluvatar.com/gpu` |
| Split shares | `iluvatar.ai/<model>-vgpu`, `iluvatar.ai/<model>.vCore`, `iluvatar.ai/<model>.vMem` |

The whole-card set is the current official name; it used to be written `iluvatar.ai/gpu` and that form is
deprecated. The split set still uses the `iluvatar.ai` domain. **When you see a resource name starting with
`iluvatar.ai`, work out which set it belongs to first**. It may be a share, or it may be an old cluster that has
not moved to the new whole-card name.

## Which vGPU resource name should I use

The split path has three names, all under `iluvatar.ai`: `iluvatar.ai/<model>-vgpu` for the card count,
`iluvatar.ai/<model>.vCore` for compute (one unit per 1%) and `iluvatar.ai/<model>.vMem` for memory (one unit per
256MB). This is the set [HAMi's official documentation](https://project-hami.io/docs/userguide/device-supported)
lists for Iluvatar, with the model written as MR-V100, MR-V50, BI-V150 or BI-V100. See
[HAMi](/ecosystem/hami/device-matrix) for how to request it. The vendor's own vGPU
documentation carries a separate list of supported models.

The names `iluvatar.ai/vgpu`, `iluvatar.ai/vcuda-core` and `iluvatar.ai/vcuda-memory` also circulate and come
from an earlier scheme. They are not the same set, and mixing them means the request will not schedule.

Since several schemes coexist under the same `iluvatar.ai` domain, the way to tell is to read what the node
actually reports:

```bash
kubectl get node <gpu-node> -o jsonpath='{.status.allocatable}' | tr ',' '\n' | grep iluvatar
```

The name that appears on the node is the name this cluster accepts.

## The container cannot see the card

First confirm the host layer is fine: `ixsmi` should list the cards on the host. If the host fails too, fix the
driver and leave containers alone for now. When the host is fine, the problem is in the container runtime toolkit:

- **Is ix-Container-Toolkit installed**: without it there is no `ix-ctk`.
- **Is the runtime registered**: the name it registers is `iluvatar`, and the container runtime has to be restarted afterwards.
- **Did the restart happen**: a changed runtime configuration does nothing until the process restarts.

Inside a cluster the device plugin injects the devices, so you do not pass device paths on the container command
line. That also means a Pod with no card should be checked for a `iluvatar.com/gpu` request of its own.

## Should I install the device plugin or the Operator

It depends on how much you want to manage by hand. Installing ix-device-plugin alone works, but you then have to
install ix-exporter separately. Installing ix-GPU-Operator creates and manages both components for you, putting
upgrades and status checks in one place.

If you pick the Operator, note that whether it publishes a Helm chart of its own has not been verified, so read the
repository README for the installation method first. Either way the reported resource name comes from the
`resourceName` field of `ix-config`, and that does not change.
