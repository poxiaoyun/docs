# Lingjun node pool

PPU cards are not installed on general-purpose ECS instances; they live in Lingjun machines. To let the cluster see
those machines, you create a **Lingjun node pool** and add them to it.

The node pool follows the standard ACK node pool model: create it, resize it, manage add-ons, upgrade it, all from the
console or the API. Existing clusters do not need to be rebuilt — add a Lingjun node pool alongside what you have, and
the ECS and GPU nodes are unaffected. General-purpose, GPU, and PPU capacity can coexist in one cluster, and workloads
pick between them with `nodeSelector`.

## Before you start

| Item | Requirement |
| --- | --- |
| Cluster | ACK managed cluster, **Pro edition** |
| Cluster add-ons | `ack-rdma-device-plugin` and `ack-ppu-device-plugin` installed |
| Nodes | Lingjun (PPU) nodes already delivered on the Alibaba Cloud side and available |
| Permissions | Able to manage the node pools and add-ons of the target cluster |

Add-on installation is covered in [Device plugin · Install and verify](/ecosystem/aliyun/device-plugin/install).
Creating the pool before installing the add-ons is fine; the node labels simply appear once the add-ons come up.

## Steps

### 1. Create a Lingjun node pool

In the Container Service console, open the target cluster and create a node pool with the **node type set to Lingjun**.
Fill in the rest according to your needs. Every machine in this pool becomes a PPU node.

### 2. Add existing Lingjun nodes

Add the Lingjun nodes already delivered on the Alibaba Cloud side to this pool. Once added, ACK takes over scheduling,
but the driver, firmware, and hardware maintenance stay on Alibaba Cloud's side. You should not install drivers by hand,
and you cannot.

### 3. Confirm the nodes are ready

```bash
kubectl get nodes -l aliyun.accelerator/xpu_type=ppu
```

A node in `Ready` state means it is connected. If the command returns nothing, the nodes are missing their PPU labels —
go back and check the add-ons rather than hunting for a network problem.

### 4. Check the node labels

A ready node carries these labels:

| Label | Meaning | Example |
| --- | --- | --- |
| `aliyun.accelerator/xpu_type` | Accelerator type | `ppu` |
| `aliyun.accelerator/ppu_name` | PPU model | `PPU-ZW810E` |
| `aliyun.accelerator/ppu_count` | PPUs per node | `16` |
| `aliyun.accelerator/ppu_mem` | Memory per PPU | `98304MiB` |

To read them:

```bash
kubectl get node <NODE_NAME> -o jsonpath='{.metadata.labels}' \
  | jq 'to_entries[ ] | select(.key | startswith("aliyun.accelerator"))'
```

`ppu_count` and `ppu_mem` double as an acceptance check: the card count is right, the memory is 96GB, and you can see
both at a glance.

## Taints and tolerations

Lingjun nodes carry a taint by default:

```yaml
key: node-role.alibabacloud.com/lingjun
effect: NoSchedule
```

**A pod without the matching toleration will never land there**, no matter how many spare cards the node has. This is
the most common first-time mistake. The toleration looks like this:

```yaml
tolerations:
  - key: node-role.alibabacloud.com/lingjun
    operator: Exists
    effect: NoSchedule
```

When you create an instance from a platform flavor, the platform generates this block from the scheduling constraints
declared in the flavor, so you do not write it by hand.

## Selecting nodes

With ECS, GPU, and PPU nodes in one cluster, pick with labels:

```yaml
nodeSelector:
  aliyun.accelerator/xpu_type: ppu
```

Add `aliyun.accelerator/ppu_name: PPU-ZW810E` if you need a specific model.

Hypernode deployments carry two more labels that identify the interconnect domain, used by multi-node jobs:

| Label | Meaning |
| --- | --- |
| `alibabacloud.com/lingjun-hypernode-id` | Shared by all child nodes inside the same hypernode |
| `alibabacloud.com/hypernode-link.version` | Protocol version of the cross-machine interconnect |

## RDMA and storage

- **RDMA**: `ack-rdma-device-plugin` reports the node's RDMA NICs as `rdma/hca`. Multi-node training and multi-node
  inference need to request it; without it, traffic falls back to ordinary networking, which is an order of magnitude slower.
- **Storage**: high-performance storage such as CPFS intelligent computing requires the compute and storage instances to
  sit in the **same high-performance network partition**. Align the node pool and the storage network partition during
  planning; changing it later is expensive.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| No PPU node in the node list | Node not added to the Lingjun pool, or not ready | Confirm pool membership in the console, then check node state and events |
| Node listed but without PPU labels | Device plugin missing or not running | Check the `ack-ppu-device-plugin` pod state and logs |
| Pod stuck Pending, complaining about a taint | Lingjun taint toleration not set | Add the `tolerations` block above |
| Pod cannot get `rdma/hca` | `ack-rdma-device-plugin` not installed | Install it, then confirm `rdma/hca` appears on the node |
