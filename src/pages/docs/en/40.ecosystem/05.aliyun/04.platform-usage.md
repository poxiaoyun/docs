# Using PPU on the platform

The previous pages stay on the Alibaba Cloud side. This one comes back to the platform: turning PPU into capacity that
can be handed to users and inspected on screen.

## How the platform recognises the card

The platform identifies accelerators by **resource key**, not by which machine the card sits in. The key for PPU is:

```
alibabacloud.com/ppu
```

Partitioned instances are written as `alibabacloud.com/ppu-4u.4g48gb` and similar, and are recognised as PPU too.

Once recognised, the UI looks like this:

| Where | What shows |
| --- | --- |
| Flavor name | Something like `PPU*1`, the number after the asterisk being card count |
| Card icon | The PPU vendor icon |
| Vendor label | `PPU` |
| Instance list | Instances whose resource name contains `ppu` or `alibabacloud.com/ppu` are grouped as PPU |
| Resource overview | Counted as accelerator usage and shown as a PPU utilisation series |

If the vendor label is something other than PPU, the resource key in the flavor is almost certainly wrong — go check the
flavor definition before anything else.

## Defining a flavor

A PPU flavor needs three things:

| Setting | Value |
| --- | --- |
| Resource key | `alibabacloud.com/ppu`, or a partition tier for split instances |
| Card count | 1, 2, 4, 8, 16; share count for partitioned instances |
| Node selection | `aliyun.accelerator/xpu_type: ppu`, plus `ppu_name` when a model must be pinned |

Set CPU and memory from measured workload numbers. PPU machines tend to come with plenty of cores, but inference
throughput usually bottlenecks on memory bandwidth and parallel strategy, so extra CPU is mostly wasted.

Once the flavor exists, users work with it exactly as they do a GPU flavor: pick the flavor, pick an image, start an
instance.

## The full path for one instance

From resource discovery to a running service:

1. **Resource discovery**: once the PPU on the nodes is managed by the cluster, PPU capacity appears in the resource pool.
2. **Flavor definition**: an administrator splits it into flavors by delivery agreement and assigns available cards.
3. **Instance creation**: a user requests by flavor; the platform generates the workload with its resource requests and
   taint toleration.
4. **Run and access**: the container comes up, reachable from a terminal or published as an inference service.
5. **Observation**: resource usage in instance details, card-level metrics in monitoring.

The platform does not manage the cards themselves. Its job is who can use them, how much, and where they run.

## Which metrics to watch

Alibaba Cloud exposes a Prometheus-format metric set for PPU, covering utilisation, interconnect, memory, temperature and
power, and error health. Naming follows the wider PPU monitoring ecosystem, so an existing Prometheus plus Grafana
dashboard can be reused directly.

The ones worth watching day to day:

| Category | What to look at | When to worry |
| --- | --- | --- |
| Utilisation | PPU Util (time), SM Active (space) | Sustained below 30% is rarely a card problem — look at parallel strategy and batch size |
| Precision pipelines | Activity of the Tensor / FP32 / FP16 / FP8 pipelines | Mismatch with what the workload should use means the image's precision settings did not take effect |
| Interconnect | ICN Link TX/RX, PCIe TX/RX | On multi-card jobs, ICN Link far below peak means traffic is blocked or parallelism is too low |
| Memory | Framebuffer Used / Free / Total | Badly uneven memory across cards usually means load balancing is off |
| Temperature and power | PPU Temp, Power Usage, Clock Throttle Reasons | Any throttle reason means the card is already downclocking and training will slow |
| Errors and health | XID Errors, Retired Pages | Any non-zero value: isolate the node first, investigate second |

When several workloads share a node, attribute metrics per container. Otherwise you get the classic misread: overall
utilisation looks healthy while one tenant is idling.

## Profiling

Monitoring answers "is the card busy". It does not answer "why is it slow". Alibaba Cloud offers on-demand profiling on
ACK based on eBPF: no code changes, no probes baked into images, no service restart — it attaches to a running pod.

That matters most for training. Nobody is going to stop a job that has been running for hours just to take a profile.
Typical collection covers operator timings, memory allocation and fragmentation, communication bandwidth and retransmits,
and call stacks, and the output is bottleneck attribution rather than a few more curves.

Today this is reached through the Alibaba Cloud console; the platform does not re-present it.

## Failures and self-healing

When a PPU node goes wrong, the chain runs like this: card-level errors are caught and reported by XID detection;
Alibaba Cloud converts Lingjun hardware operations events — fan faults, power supply degradation, link flaps — into
Kubernetes node states; the platform then steers scheduling away and migrates workloads.

You do not need to know these mechanisms to use the platform, but two consequences matter:

- Once a node is judged unhealthy, the instances on it do not come back by themselves. They need rescheduling, so run
  inference services with more than one replica.
- On hypernode instances the blast radius is larger: one bad card can stall every job in the same domain that depends on it.

## One inconsistency to watch for

Different Alibaba Cloud product lines do not necessarily use the same resource key for PPU. In ACK Lingjun node pools it
is `alibabacloud.com/ppu`; some products, such as Lingjun nodes under RDS Custom, use `aliyun/ppu`. Check the target
cluster before filling in a flavor:

```bash
kubectl describe node <NODE_NAME> | grep -i "ppu"
```

Trust what the cluster reports, not what another environment's documentation says.
