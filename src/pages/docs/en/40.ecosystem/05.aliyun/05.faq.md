# FAQ

## Split by layer, then locate

PPU problems almost always fall into one of three layers. Checking in order beats trying things at random:

| Layer | How to check | What it tells you |
| --- | --- | --- |
| Node | `kubectl get nodes -l aliyun.accelerator/xpu_type=ppu` | No node means a node pool or add-on problem, unrelated to scheduling |
| Resource | `kubectl describe node <NODE_NAME> \| grep -i ppu` | Node present but no resources means a device plugin problem |
| Scheduling | `kubectl describe pod <POD_NAME>` and read Events | Resources present but pod not Running means taints, node selection, or quota |

Decide which layer you are stuck at, then open the matching page. Skipping this step and changing configuration
usually makes things messier.

## Quick reference

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| No PPU node in the Lingjun node pool | Node not added to the pool, or not ready | Confirm pool membership and node state in the console |
| Node in the cluster but without PPU labels | Device plugin not installed, or not running on that node | Check the `ack-ppu-device-plugin` pod and logs; when the node carries a Lingjun taint, check the add-on's own toleration |
| `Allocatable` has no `alibabacloud.com/ppu` | Device plugin not running on the PPU node | Same as above |
| Pod stuck Pending with a taint event | Lingjun taint toleration missing | Add the toleration for `node-role.alibabacloud.com/lingjun` |
| Pod runs but cannot use the card | Image lacks the PPU SDK and runtime | Switch to a PPU build of the workload image and confirm with `ppu-smi` |
| Requesting `rdma/hca` fails | `ack-rdma-device-plugin` not installed | Install it and retry |
| Multi-card jobs are slow | `Enable PPU Topology` not ticked, or request size not aligned with the interconnect domain | Reconfigure the add-on with topology on; request in 1/2/4/8/16 granularity |
| Cards get scattered and large jobs never fit | Binpack off, or `alibabacloud.com/ppu` missing from `binpackResourceWeight` | Configure as described in [Scheduling policies](/ecosystem/aliyun/device-plugin/scheduling) |
| Platform labels the vendor as something other than PPU | Wrong resource key in the flavor | Check that the key is `alibabacloud.com/ppu` |
| No PPU capacity visible on the platform | Cluster not onboarded to the resource pool, or flavor has no cards assigned | Confirm the cluster is connected and check the flavor's available count |
| Instances do not recover after eviction | Node judged unhealthy, replica count is 1 | Raise replicas to 2 or more, or use an instance with a rescheduling policy |

## Field notes

1. **Get a whole card working before partitioning.** Prove node, plugin, image, and framework with one minimal job, then
   move to MIG. Do it the other way round and you will not be able to tell a partitioning mistake from a broken image.
2. **Weigh binpack against isolation.** Consolidation reduces fragmentation and concentrates failure impact onto one node.
   Good for training clusters, riskier for online inference — lower the weight when in doubt.
3. **Align card count with the interconnect domain.** Ask for eight cards if you need eight; the plugin cannot assemble a
   good topology out of six or seven.
4. **Request RDMA up front on multi-node jobs.** Forgetting `rdma/hca` degrades multi-node traffic to ordinary networking,
   and the symptom is "it works but it is slow" — easily misread as a slow model.
5. **Align storage and compute network partitions during planning.** CPFS intelligent computing requires both in the same
   high-performance network partition, and fixing it later means touching the node pool.
6. **Do not treat parameters as a frozen interface.** The PPU SDK and `ppu-smi` are still evolving. Run `ppu-smi -h`
   before switching versions and take the current release's supported range as the truth. The same chip generation also
   ships with different firmware revisions, which can differ in flags and precision support.
