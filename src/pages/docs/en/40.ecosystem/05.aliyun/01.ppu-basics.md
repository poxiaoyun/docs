# PPU basics

PPU is not a GPU under a different name. T-Head designed its own parallel-computing architecture, instruction set,
compiler, and operator libraries; the whole stack is called the **PPU SDK**. Most of the time you will not notice:
same images, same frameworks. The moment an operator is missing or a precision does not line up, you are back to the
question of how far that stack actually reaches.

Today PPU is only offered on Alibaba Cloud. The cards sit in Lingjun machines and are scheduled through ACK.

## Models

| Model | Form factor | What public material says |
| --- | --- | --- |
| PPU-ZW810E | Single card, typically 16 per Lingjun node | The first public model; node labels carry the value `PPU-ZW810E` |
| ZW-M890 | Hypernode instance (GP9A), sold in units of 64 cards | 800GB/s inter-card interconnect, 9,216GB memory pool, MXFP4 support |
| M890P | Same family as M890 | Fully supported from device plugin 1.4.0 (2026-08) |

To find out what a node actually has, skip the paperwork and read the labels:

```bash
kubectl get node <NODE_NAME> -o jsonpath='{.metadata.labels}' \
  | jq 'to_entries[ ] | select(.key | startswith("aliyun.accelerator"))'
```

The value of `aliyun.accelerator/ppu_name` is the model.

## Key specs (ZW810E)

| Item | Value | Notes |
| --- | --- | --- |
| Memory | 96GB HBM2e | Per card; the node label `ppu_mem` reports `98304MiB` |
| Inter-card interconnect | 700GB/s | In-house ICN link; this sets the communication cost of multi-card parallelism |
| Host interface | PCIe 5.0 x16 | Bandwidth between card and host |
| Power | 400W | Per card |

These numbers are for deciding whether a model fits and how wide you can set parallelism. A single 96GB card holds a
32B-class model in BF16 (roughly 64GB of weights); anything larger needs tensor parallelism or quantisation — the same
arithmetic as any card with the same memory.

:::info Specs follow the console and the delivery sheet
The figures above are public-material numbers, good enough for early sizing. When you order or expand, take the flavor,
memory, and card count from the Alibaba Cloud console and the actual delivery sheet. The same chip generation can ship
with different firmware revisions.
:::

## Software stack

| Layer | What it contains | Who manages it |
| --- | --- | --- |
| Driver and firmware | Makes the system see the card | Alibaba Cloud; the customer stays out of it |
| PPU SDK | Compiler, operator libraries, `ppu-smi` and friends | Inside workload images; the platform does not install it |
| Frameworks | Megatron, DeepSpeed, vLLM, SGLang, and so on | Officially "migrates without changes"; verify against your framework version anyway |

`ppu-smi` is the tool you will reach for most often. It plays the role `nvidia-smi` plays elsewhere: list cards,
check memory, switch MIG mode.

On the model side, public material mentions compatibility with common open models such as Qwen and LLaMA.
**Compatible is not the same as zero changes.** If your workload uses an uncommon operator or a hand-written CUDA
extension, get a minimal job running on PPU before promising a fleet-wide rollout.

## How a card gets split

There are two routes: whole card, or partitioned instances.

| Route | Resource name | Characteristics |
| --- | --- | --- |
| Whole card | `alibabacloud.com/ppu` | One container owns one card. Simplest, most predictable performance |
| MIG | `alibabacloud.com/ppu-4u.4g48gb` and similar | Hardware-level isolation; compute and memory are split independently |

The MIG concepts are close to NVIDIA's, with different vocabulary. Hardware resources are first cut into several
**GPU instances** that run isolated from each other; a **GPU instance profile** describes how many CUs and how much
memory one cut can provide. If you need finer granularity, a GPU instance can be cut further into **compute
instances**, which own CUs exclusively and share everything else. MIG mode is switched with:

```bash
ppu-smi -mig 1
```

For the available tiers and a request example, see [Device plugin · MIG](/ecosystem/aliyun/device-plugin/mig).

## What it suits

- **LLM inference services**: online chat, RAG, agents. vLLM and SGLang both run, and this is the most common PPU workload.
- **Training and fine-tuning**: pre-training and post-training are both in scope. The M890 hypernode form targets
  trillion-parameter scale.
- **Autonomous driving and multimodal**: Alibaba Cloud pushes this hard in the automotive industry, with ready-made
  pieces across data labelling, model training, and cloud-based simulation.
- **Multi-tenant compute pooling**: once connected to the platform, capacity is split by project or tenant, which suits
  several internal teams sharing one pool.

Going the other way: **small single-machine jobs with narrow operator needs** are not worth rushing onto PPU.
The migration and tuning cost never gets amortised, and an existing GPU pool is less trouble.
