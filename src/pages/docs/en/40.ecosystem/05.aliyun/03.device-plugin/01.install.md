# Install and verify

Add-ons are installed from the **Alibaba Cloud Container Service console**: Clusters → target cluster → Components and
Add-ons → search the add-on name → install.

## Before you start

- The cluster is an ACK managed cluster, **Pro edition**.
- The Lingjun node pool exists and the PPU nodes are already members. See
  [Lingjun node pool](/ecosystem/aliyun/lingjun-nodepool).

## 1. Install ack-rdma-device-plugin

Default parameters are fine. It reports the node's RDMA NICs as `rdma/hca`, which multi-node jobs need.

If this phase is single-node verification only, you can defer it — but multi-node training and multi-node inference
will require it.

## 2. Install ack-ppu-device-plugin

One option matters here: **tick `Enable PPU Topology`**.

With it enabled, the add-on reports the physical topology of the PPUs and the scheduler assigns the best combination,
supporting requests for 1, 2, 4, 8, or 16 cards. It works without the option too, but you get an arbitrary set of cards
and multi-card jobs lose a noticeable amount of communication performance.

## 3. Confirm the add-ons are running

```bash
kubectl get pods -A | grep -E "ppu|rdma"
```

The device plugin runs as a DaemonSet: as many pods as there are PPU nodes. If a pod is not `Running`, read its logs
first:

```bash
kubectl logs -n kube-system <POD_NAME> --tail=100
```

## 4. Confirm resources are reported

```bash
kubectl describe node <NODE_NAME> | grep -A 20 "Allocatable"
```

You expect to see `alibabacloud.com/ppu` plus the `alibabacloud.com/ppu-*u.*g*g` tiers this card supports. Once this
passes, the path from node to scheduler is working and everything after it is downhill.

## 5. Run a smoke test

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: ppu
  name: ppu-test
  namespace: default
spec:
  selector:
    matchLabels:
      app: ppu
  template:
    metadata:
      labels:
        app: ppu
    spec:
      containers:
        - image: anolis-registry.cn-zhangjiakou.cr.aliyuncs.com/openanolis/nginx:1.14.1-8.6
          imagePullPolicy: IfNotPresent
          name: ppu
          ports:
            - containerPort: 80
              protocol: TCP
          resources:
            limits:
              alibabacloud.com/ppu: "1"
      dnsPolicy: ClusterFirst
      restartPolicy: Always
      schedulerName: default-scheduler
      tolerations:
        - key: node-role.alibabacloud.com/lingjun
          operator: Exists
          effect: NoSchedule
```

Two settings are worth a second look:

- `resources.limits.alibabacloud.com/ppu`: how many cards to request, valid values 1, 2, 4, 8, 16.
- `tolerations`: the Lingjun taint must be tolerated, or the pod stays Pending forever.

Verify:

```bash
kubectl get pod -l app=ppu -o wide
kubectl describe node <NODE_NAME> | grep -A 5 "Allocated resources"
```

The pod is `Running`, the `NODE` column shows a PPU node, and `Allocated resources` lists a consumed
`alibabacloud.com/ppu`. That is the whole install.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| No PPU labels on the node after installing | The add-on pod is not running | Check pod state and logs; confirm it was scheduled onto the Lingjun node |
| `Allocatable` has no `alibabacloud.com/ppu` | The device plugin is not running on the target node | Check DaemonSet coverage; a Lingjun taint can keep the add-on itself off the node |
| Pod Pending with a taint event | Missing Lingjun toleration | Add `tolerations` as in step 5 |
| Requesting `rdma/hca` fails | RDMA device plugin not installed | Install `ack-rdma-device-plugin` and retry |
| Multi-card jobs are slow | `Enable PPU Topology` was not ticked at install time | Reconfigure the add-on with topology reporting on |
