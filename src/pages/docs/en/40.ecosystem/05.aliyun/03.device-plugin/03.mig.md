# MIG partitioning

Running one small model on a whole PPU wastes most of the card. MIG cuts a card in hardware into several
**isolated** instances, each with its own CUs and memory, so one job crashing does not take its neighbours down.

One misunderstanding worth clearing up first: MIG is about **isolation**, not oversubscription. The compute and memory
handed out never exceed what the card physically has; the card is simply divided so several jobs can each hold a share.

## Concepts

| Concept | Meaning |
| --- | --- |
| GPU instance | An instance produced by partitioning PPU hardware; instances run isolated from each other |
| GPU instance profile | What one partition can offer, such as how many CUs and how much memory it owns exclusively |
| Compute instance | A further split of a GPU instance; it owns CUs exclusively and shares everything else |
| Compute instance profile | The splitting scheme for a compute instance |

Most of the time you only touch the first layer: create GPU instances and put the resource names into a pod's
`resources.limits`. Compute instances come up only when you need finer compute granularity.

## Enabling MIG mode

On a PPU node:

```bash
ppu-smi -mig 1
```

`ppu-smi` is also how you list instances in MIG mode and create or delete them. Subcommands and flags move with the SDK
version, so check the official "GPU instance management (MIG)" documentation and the output of `ppu-smi -h` on the node
you are working on.

:::warning Switching MIG interrupts running jobs
Changing MIG mode reconfigures the device, and containers using the PPU on that node are affected. Confirm the node can
be taken offline before doing it in production, or drain it from scheduling first.
:::

## Available tiers

Partitioned resource names look like `alibabacloud.com/ppu-<compute>u.<memory shares>g<memory>gb`:

| Memory tier | Available compute sizes |
| --- | --- |
| `1g12gb` (12GB) | `4u`, `8u` |
| `2g24gb` (24GB) | `1u`, `12u`, `16u` |
| `4g48gb` (48GB) | `1u`, `2u`, `3u`, `4u`, `8u`, `16u`, `24u`, `32u`, `64u` |

Because compute and memory are split independently, there are more combinations than the table suggests. Which tiers
appear is decided by what the device plugin reports for that card — the node's `Allocatable` is the source of truth.

## Request example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: ppu-mig-test
spec:
  containers:
    - name: app
      image: <workload image>
      resources:
        limits:
          alibabacloud.com/ppu-4u.4g48gb: "1"
  tolerations:
    - key: node-role.alibabacloud.com/lingjun
      operator: Exists
      effect: NoSchedule
```

Verification works the same as for whole cards:

```bash
kubectl get pod ppu-mig-test -o wide
kubectl describe node <NODE_NAME> | grep -A 20 "Allocated resources"
```

Seeing the matching `ppu-4u.4g48gb` under `Allocated resources` means it took effect.

## When to use it

**Good fit**: the model fits in 24GB and you want instances that cannot disturb each other — a set of small models
serving online classification or embedding, or a card carved up for several projects.

**Bad fit**: anything needing multi-card parallelism. Partitioned instances have no meaningful inter-card interconnect,
so tensor parallelism cannot run at all. Partitioning also leaves the platform looking at a pile of small flavors;
fragmentation is harder to manage and binpack consolidation loses much of its value.

## What the platform sees

The platform identifies accelerators by resource key. Written as `alibabacloud.com/ppu`, a flavor shows up as `PPU*1` and
is labelled with the PPU vendor; partitioned resource names are recognised as PPU as well, with the card count being the
number of shares requested. A glance at the instance details or the flavor list tells you whether you got a whole card or
a share.
