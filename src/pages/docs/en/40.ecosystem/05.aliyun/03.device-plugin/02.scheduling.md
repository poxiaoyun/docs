# Scheduling policies

PPU scheduling has two layers: which card inside a node, and where the job goes across nodes. The device plugin handles
the first; kube-scheduler, informed by topology data, handles the second. Defaults will run your workload, but
multi-card and multi-node jobs pay a performance tax, so this page is worth ten minutes.

## Which cards: device topology awareness

When a pod asks for several PPUs, the device plugin does not grab an arbitrary handful. It picks the combination with
the highest interconnect bandwidth according to the physical topology. Nothing to configure — if you ticked
`Enable PPU Topology` during installation, this is already active.

The only thing you control is **aligning the request size with the interconnect domain**. Requests are supported in
granularity of 1, 2, 4, 8, and 16 cards. On hypernode instances the eight cards inside a machine are on a high-speed
fabric, while cross-machine traffic goes over ICN Link. If a job wants eight cards for tensor parallelism but asks for
six, the plugin gives you six and most of the topology advantage evaporates.

## Where the job goes: binpack

Default scheduling spreads pods across nodes, which is the wrong instinct for PPU. Once cards are scattered, gaps appear
everywhere: big jobs cannot fit, and small jobs are not necessarily better off either.

Binpack puts PPU workloads on the same node first. To turn it on, change the kube-scheduler parameters:

1. In the Alibaba Cloud Container Service console, open the target cluster's **Components and Add-ons**.
2. Find `kube-scheduler` under the core components and click **Configuration**.
3. Tick **Pod scheduling prioritizes consolidating Pods on fewer nodes**.
4. Under `binpackResourceWeight`, click **Add** and set `resourceName` to `alibabacloud.com/ppu`.

Step 4 is the one that does the work. With only step 3 ticked, the scheduler has no weight entry for this resource name
and will not consolidate PPU workloads specifically.

:::warning Binpack cuts both ways
Consolidation reduces fragmentation, but the fuller a node gets, the larger the blast radius of a single node failure —
and the more concentrated the thermal load. If the cluster runs many small inference instances with strict availability
requirements, lower the weight or enable it only for selected queues rather than across the board.
:::

## Multi-node and hypernodes

For multi-node, multi-card jobs, where a worker lands decides which path its traffic takes: inside the same
high-speed interconnect domain it uses ICN Link, outside it degrades to ordinary RDMA or even TCP. That is an order of
magnitude in bandwidth, and much more in training time.

Alibaba Cloud provides hypernode-level network topology-aware scheduling on ACK, placing jobs across four levels:
rack → switch domain → hypernode → node.

| Policy | Fits | Effect |
| --- | --- | --- |
| Binpack | Training jobs | Pulls all workers into the same hypernode |
| Balanced | Many concurrent jobs | Spreads replicas across hypernodes so they do not compete |
| Gang scheduling | Tightly coupled multi-replica jobs | All pods get resources, or none start |

Gang scheduling deserves its own paragraph. Without it, a job of several dozen cards can end up with the first few
workers running and holding cards while waiting for the rest: cards are occupied but produce nothing, the cluster looks
busy, and throughput is zero.

Two related constraints come with it: `maxSplits` caps how many hypernodes one job may be split across, and
`whenNotSatisfied: DoNotSchedule` means the job waits rather than being scheduled in a degraded placement when the
topology constraint cannot be met. Field names and accepted values depend on your ACK version — check the component's
parameter documentation.

The device plugin and the scheduler work as a pair: the scheduler decides which child nodes host the workers, then the
device plugin picks the best card combination inside each child node and injects the channel devices and environment
variables that cross-machine interconnect needs. You submit a standard multi-node job and get the whole arrangement;
there are no interconnect parameters to set by hand.

## How the platform fits in

A platform flavor declares a resource key and node constraints, for example:

```yaml
resources:
  limits:
    alibabacloud.com/ppu: "8"
nodeSelector:
  aliyun.accelerator/xpu_type: ppu
```

When you create an instance, the platform generates this block and ACK applies the policies above. So the scheduling
policies are configured once on the Alibaba Cloud side, and every instance using a PPU flavor follows. The reverse is
not true: editing a flavor definition on the platform does not change any ACK scheduler parameter.
