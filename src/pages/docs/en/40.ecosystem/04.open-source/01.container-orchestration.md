# Containers and Orchestration

This page covers the platform's **scheduling and network base**: which machine a job lands on, how containers talk to each other, and how outside access reaches the cluster.
You turn to this layer when you connect new hardware, give an instance a fixed IP or domain, or work out why jobs keep queueing.

A **scheduler** is the component that decides which machine each job runs on; it watches how much CPU, memory and card capacity each machine has left before picking a spot.
The default scheduler that ships with Kubernetes looks at one job at a time and does not suit multi-card jobs, so the platform uses Volcano to handle this kind of scheduling.

:::tip Understand this layer in one line
Picture the cluster as an office building: the **scheduler** is the property manager assigning offices, the **network components** are the roads and door numbers, and the **ingress gateway** is the front desk.
The foundation (Kubernetes) is already laid; this page is about the "building facilities" on top of it.
:::

## What this category solves

| Problem | Who handles it |
| --- | --- |
| Which machine a job lands on, and how multi-card jobs run as a group | Scheduling component (Volcano) |
| How one card is shared by several jobs | GPU virtualization (Volcano vGPU) |
| A container needs a fixed IP or a second network card | Multus-CNI |
| How the outside reaches a service by domain | ingress-nginx / Higress |
| How you get into an instance to operate it | kube-ssh / sshpiper |
| Where images are pulled from and which storage class is default | Global configuration (global) |

## Which components are included

| Component | Purpose | Key traits | How the platform uses it |
| --- | --- | --- | --- |
| Kubernetes (container orchestration base) | Combines many servers into one cluster and schedules containers across them | Declarative management, self-healing, extensible | The running base of the whole platform; the Cluster Status page shows the cluster overview |
| Volcano (batch and AI-training scheduler) | Queues batch and training jobs and schedules them as a group | Queues, co-scheduling, fair sharing, preemption, bin packing | Operations Management → Scheduler Management; once installed the platform dispatches jobs according to the scheduler configuration |
| Volcano vGPU (GPU virtualization) | Splits one GPU into shares that several jobs can share | Each card is split into 10 shares by default and each share's memory is counted in 128 MiB units | Turn on **GPU virtualization** in the scheduling component, then request vGPU shares when creating an instance (NVIDIA only) |
| GPU Operator / Ascend scheduling components | Registers accelerator cards as schedulable resources and hands them to Volcano | The NVIDIA side integrates GPU Operator and Volcano vGPU; the Ascend side integrates the Device Plugin, NPU Exporter and Volcano | Operations Management → System Apps; choose the scheduling component that matches the cluster hardware (see [NVIDIA](/ecosystem/nvidia) and [Huawei](/ecosystem/huawei)) |
| Multus-CNI (multi-NIC fixed IP) | Attaches an extra virtual network card to a container and assigns a fixed IP | Based on IPvlan / Macvlan, gives containers a fixed IP | Operations Management → System Apps; use it for instances that need a fixed IP or two isolated networks |
| ingress-nginx (NGINX ingress controller) | Routes HTTP traffic from outside the cluster by domain to services inside | Uses NGINX for reverse proxy and load balancing; the default ingress implementation | Operations Management → System Apps; instance access domains are handled by it |
| Higress (unified ingress gateway) | Another ingress gateway implementation that can replace nginx-ingress | You choose the gateway implementation at install time and fill in the host names used for routing | Operations Management → System Apps; switch implementations in the ingress gateway component |
| kube-ssh (SSH access gateway) | Provides one SSH entry point for the cluster | Used together with the SSH gateway service endpoint in the global configuration | Operations Management → System Apps; exposed to the outside through the endpoint set in the global configuration |
| sshpiper (SSH reverse proxy) | Forwards SSH connections to different backends based on the login user name | Supports both password and public-key forwarding | Operations Management → System Apps; use it when one jump host must reach several targets |
| Global configuration (global) | One central place for defaults shared by all system applications | Image registry, image pull secret, default storage class, scheduler list, service endpoints | Operations Management → System Apps; other components read defaults from here at install time |

## When you need to care about it

- **Jobs keep queueing and cards stay idle**: look at **Scheduler Management** first and confirm Volcano is installed and no queue is holding jobs back.
- **You are adding new machines (especially with cards)**: install the matching **hardware scheduling component** first ([NVIDIA](/ecosystem/nvidia) or [Huawei](/ecosystem/huawei)), then go back to Scheduler Management and confirm the scheduler took effect.
- **An instance needs a fixed IP or internal/external network isolation**: install **Multus-CNI** and attach a second network card when creating the instance.
- **Domain access does not work**: confirm **ingress-nginx** or **Higress** is installed, then check that the gateway host name list contains your domain.
- **Images will not pull**: add the image registry address and pull secret under **Global configuration**; other components then read them automatically.

:::warning Do not install scheduling components twice
Keep exactly one set of scheduling components per cluster. Do not switch or reinstall the scheduler on a cluster that is already in use, or queued jobs may be interrupted.
:::
