# DCU-Device-Plugin (standard mode)

DCU-Device-Plugin **registers the DCUs on a node as Kubernetes resources**: it discovers the cards, runs health checks,
and then tells the cluster "this machine has this many cards, and here is how each of them can be used". Only after registration
can workload Pods use a card by declaring a resource.

Think of it as **registering the card's residence**: the card is just hardware plugged into a machine, and only after registration
does it have an identity the cluster recognizes, so the scheduler knows which machine still has a free card.

## When you must install it

- When you need to schedule **physical DCUs** in the cluster (one task taking a whole card).
- When you need to schedule **pre-segmented vDCUs** in the cluster (the card is split into fixed sizes in advance for several tasks).

If you do not use cards, or only run programs directly on the machine, you can skip this page.

## Working modes of the component

The component distinguishes scenarios with the startup parameter `RESOURCE_REGISTER_STRATEGY`. **This page covers standard mode**; other modes are deployed on their own pages:

| Parameter value | Meaning | Resource name exposed |
| --- | --- | --- |
| `dcu` | Manages physical DCU devices only | hygon.com/dcu |
| `vdcu` | Manages pre-segmented vDCUs only | hygon.com/dcu-share-* |
| `mixed` (default) | **Standard mode**: manages physical devices and pre-segmented vDCUs together | hygon.com/dcu, hygon.com/dcu-share-* |
| `hami` | Dynamically segmented vDCU devices | hygon.com/dcunum |
| `mig` | MIG virtualization device management | hygon.com/dcu-mig-* |

### Rules of standard mode

- Supports physical DCU cards and pre-segmented vDCUs.
- Distinguishes physical cards and different vDCU sizes by resource name, for example:
  - `hygon.com/dcu`: schedule the whole card;
  - `hygon.com/dcu-share-40c-30g`: a vDCU with 40 CU / 30G memory;
  - `hygon.com/dcu-share-20c-40g`: a vDCU with 20 CU / 40G memory.
- A card that already has a pre-segmented vDCU **no longer takes part in whole-card scheduling**; a card with vDCUs must be scheduled through the vDCU size resource name.

## Before you start

- The driver is installed on every machine that has a card.
- It is recommended to deploy [DCU-Label-Node](/ecosystem/hygon/k8s-label-node) first, to fill in the DCU labels on the nodes.
- The component image is already available somewhere the cluster can pull from.
- You have the deployment file `k8s-dcu-plugin.yaml`.

## Steps

### 1. Deploy

```bash
kubectl apply -f k8s-dcu-plugin.yaml
```

### 2. Check the Pods

```bash
kubectl get pod -n kube-system -owide | grep dcu-device-plugin
```

There should be one Pod per node that has a card, in `Running` state.

## What changes in the cluster afterwards

This is how you tell whether the card really joined the cluster. Check it step by step:

```bash
kubectl describe node <node-name>
```

Seeing `hygon.com/dcu: 2` in the `Capacity` field of the output means the node has two DCUs the cluster can allocate.

As long as the node still has a free card, a Pod like the ones below can be scheduled — this is the final sign of a successful setup.

## How to request a card

### Request a whole DCU card

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: dcu-pytorch-demo
spec:
  containers:
    - name: dcu-pytorch-demo
      image: image.sourcefind.cn:5000/dcu/admin/base/pytorch:2.1.0-ubuntu22.04-dtk24.04.2-py3.10
      command: ["/bin/bash", "-c", "--"]
      args: ["sleep infinity & wait"]
      resources:
        limits:
          hygon.com/dcu: 1
```

### Request a pre-segmented vDCU

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: dcu-share-pytorch-demo
spec:
  containers:
    - name: dcu-share-pytorch-demo
      image: image.sourcefind.cn:5000/dcu/admin/base/pytorch:2.1.0-ubuntu22.04-dtk24.04.2-py3.10
      command: ["/bin/bash", "-c", "--"]
      args: ["sleep infinity & wait"]
      resources:
        limits:
          hygon.com/dcu-share-15c-8g: 1
```

## Usage limits

- Each container can request **at most 1 vDCU**. If you request more than 1, the cluster reduces the request to 1 and only 1 takes effect.

:::warning Do not mix whole-card and vDCU scheduling

Once a card has vDCUs segmented on it, it can no longer be requested as a whole card with `hygon.com/dcu`.
**Mixing the two leads to memory over-allocation (OOM).** For a card that has vDCUs, always request it by its vDCU size resource name.

:::

## Common problems

| Symptom | Possible cause | What to do |
| --- | --- | --- |
| The Pod starts, but the resource name does not appear on the node | The driver is not installed correctly, or node labels are missing | First confirm the driver modules are loaded, then confirm the node was labeled by DCU-Label-Node |
| Only some nodes have the resource | Those nodes are not labeled, or the driver is not installed | Install the driver and labels on the nodes that have cards, then restart the device plugin |
| The card count is right, but workload Pods still fail to schedule | No free card, or the resource name is misspelled | Check the remaining amount with `kubectl describe node <node-name>` and verify the resource name spelling |
| The container has no `/opt/hyhal` directory | The device plugin version is too old | Upgrade to V2.1.0 or above, which mounts `/opt/hyhal` automatically |
