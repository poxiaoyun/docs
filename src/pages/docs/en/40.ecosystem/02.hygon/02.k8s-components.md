# DCU Kubernetes Component User Guide

Once the host driver is installed the machine itself can use the card, but the cluster still does not know a card exists.
This group of components runs on Kubernetes. It registers card information into the cluster, reports card state to
monitoring, and publishes the card as a schedulable resource. After all of them are installed, workload Pods can request
a DCU by declaring a resource.

One way to remember the group: think of it as the card's three-piece set inside the cluster — a name plate (node labels),
a power meter (monitoring probe), and a residence permit (resource registration).

:::info How this group of pages is organized

The directory splits the components across several pages. For a first-time installation, start from **Overview** in the table below and work down in order;
if you only need to add one component or are troubleshooting, jump straight to the matching page.

:::

:::warning Hygon components are deployed by hand

**Cluster Management → Operations → System Apps** currently offers only the two bundled scheduling stacks,
NVIDIA and Ascend. **There is no one-click entry for Hygon.** Every component below is installed by hand with
`kubectl apply` as described in this chapter, pulling images from the Hygon registry
(`image.sourcefind.cn:5000/...`).

:::

## Before you start

- The driver is installed on every machine that has a card, and `lsmod | grep -E "hydcu|hycu"` shows the driver modules.
- The cluster's Kubernetes version meets the system requirements in [Overview](/ecosystem/hygon/k8s-overview).
- The images for each component are already available somewhere the cluster can pull from.
- You have permission to run `kubectl apply` against the cluster.

## Component summary

| Component | What it does | Prerequisite | How to verify after installing |
| --- | --- | --- | --- |
| [Overview](/ecosystem/hygon/k8s-overview) | Component descriptions, image list, system requirements | None | Check that the hardware, driver, and OS versions meet the requirements |
| [DCU-Label-Node](/ecosystem/hygon/k8s-label-node) | Label the node to state which card this machine has | Driver installed on the host | Labels such as `hygon.com/dcu` appear on the node |
| [DCU-Exporter](/ecosystem/hygon/k8s-exporter) | Collect card state metrics for monitoring to scrape | Driver installed on the host | `/metrics` on port `16080` returns data |
| [DCU-Device-Plugin (standard mode)](/ecosystem/hygon/k8s-device-plugin-standard) | Register physical cards and pre-segmented vDCUs as schedulable resources | Driver installed; node already labeled | `hygon.com/dcu` appears in the node's allocatable resources |
| [DCU-Device-Plugin (MIG mode)](/ecosystem/hygon/k8s-device-plugin-mig) | Register already-created MIG instances as resources | MIG enabled and instances created on the host | `hygon.com/dcu-mig-*` appears in the node's allocatable resources |
| [vDCU dynamic segmentation mode](/ecosystem/hygon/k8s-vdcu-dynamic-splitting) | Split a card on demand at submit time and reclaim it automatically | Device plugin installed (HAMi mode) | `hygon.com/dcunum` appears in the node's allocatable resources |
| [FAQ](/ecosystem/hygon/k8s-faq) | Common problems and troubleshooting | None | Look up a symptom and get the matching troubleshooting commands |

## Why this order is required

1. **Install the driver first**: every component below reads driver interfaces. Without the driver they cannot start.
2. **Then install DCU-Label-Node**: it puts the DCU labels on the nodes, and the device plugin uses those labels to choose which nodes to manage.
3. **DCU-Exporter can go before or after**: it only collects monitoring data. It does not take part in resource registration and does not affect scheduling.
4. **Install DCU-Device-Plugin last**: it registers the card into the cluster. Only after this step does the cluster see the card.
5. **Install the vDCU components only if you need segmentation**: dynamic segmentation additionally needs vDCU-Scheduler, and the device plugin must run in HAMi mode.

:::warning Pick exactly one segmentation approach

Standard mode (physical cards plus pre-segmented vDCU), MIG mode, and vDCU dynamic segmentation are three different routes.
Do not mix them in the same environment: once MIG is enabled, vDCU virtualization is not available. To choose one, see
[MIG mode](/ecosystem/hygon/k8s-device-plugin-mig) and [vDCU dynamic segmentation mode](/ecosystem/hygon/k8s-vdcu-dynamic-splitting).

:::
