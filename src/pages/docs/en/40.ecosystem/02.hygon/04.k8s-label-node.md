# DCU-Label-Node

DCU-Label-Node is a small program that runs on every node. It checks whether this machine has a DCU and, if so, **labels** the node
with the card model, the number of compute units, and the memory size. These labels are what the device plugin and the scheduler later use
to decide "which machine has a card, and which card it is".

Think of it as **hanging a name plate on the machine**: the scheduler stands in the corridor and can only read name plates — it cannot see what is actually installed in the room.

## When you must install it

If you want to schedule DCU in the cluster at all, install this first so the nodes carry DCU labels. The device plugin uses these labels
to choose which nodes to manage; if you skip it, the labels are missing and the device plugin may not cover this machine.

## Before you start

- The driver is installed on every machine that has a card (`lsmod | grep -E "hydcu|hycu"` shows the driver modules).
- The component image is already available somewhere the cluster can pull from.
- You have the deployment file `k8s-dcu-label-node.yaml`.
- You have permission to run `kubectl apply` against the cluster.

## Steps

### 1. Deploy

Deploy it to the cluster as a DaemonSet (the default namespace is `kube-system`):

```bash
kubectl apply -f k8s-dcu-label-node.yaml
```

### 2. Check the Pods

```bash
kubectl get pod -n kube-system -owide | grep dcu-label-node
```

There should be one Pod per machine that has a card, in `Running` state.

## Labels added to the node afterwards

The component creates the following labels on nodes where a DCU is confirmed:

| Label | Meaning | Example |
| --- | --- | --- |
| `hygon.com/dcu` | Whether the node has a DCU device: `true` if it does | `hygon.com/dcu=true` |
| `hygon.com/dcu.name` | DCU model | `hygon.com/dcu.name=K100_AI` |
| `hygon.com/dcu.cu-count` | Number of compute units (CUs) on the DCU | `hygon.com/dcu.cu-count=120` |
| `hygon.com/dcu.vram` | DCU memory capacity | `hygon.com/dcu.vram=64G` |

Notes:

- On a node without a DCU, none of the labels prefixed with `hygon.com/dcu` are created.
- The model, CU count, and memory labels are generated automatically by default, and can be switched on or off with startup parameters in the deployment file.

## Using the labels

Once the labels are in place, workloads can use `nodeSelector` to **pin a job to machines of a particular
model** — something you often need in a cluster with mixed models (say, pinning large-model training to the
cards with the most memory):

```yaml
spec:
  nodeSelector:
    hygon.com/dcu.name: K100_AI   # schedule only onto K100-AI machines
  containers:
    - name: dcu-job
      resources:
        limits:
          hygon.com/dcu: 1
```

To simply require "a machine with a card", write `hygon.com/dcu: "true"`; to pick by memory, use
`hygon.com/dcu.vram`.

## Verify

Check the node description to confirm the labels were set:

```bash
kubectl describe node <node-name>
```

If you can see the labels from the table above in the `Labels` section of the output, the labeling worked.

## Common problems

| Symptom | Possible cause | What to do |
| --- | --- | --- |
| No labels are created on a node that has a card | The component version is too old and is incompatible with the current driver | Upgrade to V2.2.0 or above and redeploy |
| Only some nodes have labels | Those nodes have no card, or the driver is not installed correctly | On each of those machines, run `lsmod \| grep -E "hydcu\|hycu"` to confirm the driver is loaded |
| The Pod does not start | The image cannot be pulled, or the deployment file has wrong parameters | Run `kubectl describe pod -n kube-system <dcu-label-node-pod>` and read the events |

:::warning Re-check the labels after a driver upgrade

After you upgrade the host driver, the DCU information on the node may change. Run `kubectl describe node <node-name>` again
and confirm the labels still match reality.

:::
