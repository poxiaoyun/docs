# DCU driver installation

This step installs the driver on every machine that has a DCU, so the host itself recognizes the card.
There are two signs of success: the driver service `hymgr` is running, and `lsmod` shows the driver modules.
If the driver is not installed, none of the cluster components that follow can work.

The driver is the base software the operating system needs in order to use the card; without it the system only knows
that a piece of hardware is plugged in.

:::info This page covers the host layer only

No Kubernetes is involved here: for the cluster-side components, see [Kubernetes components](/ecosystem/hygon/k8s-components).
Nor does it cover DTK / DAS and the layers above; those belong to the workload environment and are not needed to attach
a card to the platform. For what the three software layers are, see [Hygon (DCU)](/ecosystem/hygon).

:::

## Before you start

- Confirm the operating system and the hardware model of the machine, then find the matching driver version in the compatibility list below.
- Get the driver package (the `.run` file) from the vendor channel and upload it to a directory the target machine can reach.
- You need **root** permission and the ability to install build tools and kernel headers.

## Driver compatibility list

Check this table when you pick a driver. Different hardware models need different drivers and DTK (development toolkit) versions:

| Driver version | Supported hardware | Recommended DTK version |
| --- | --- | --- |
| rock-4.0-23-5.6.25 | Z100/Z100L | 21.04/21.10/22.04 |
| rock-4.5.2-5.11.40 | Z100/Z100L | 22.04/22.10/23.04 |
| rock-5.2.0-5.16.18 | Z100/Z100L | 22.10/23.04 |
| rock-5.2.0-5.16.29 | Z100/Z100L/K100 | 23.04/23.10 |
| rock-5.7.1-6.2.35-V1.6.7d | Z100/Z100L/K100/K100-AI | DTK 24.04.* |
| rock-6.3.8+ | BW1000/K100-AI/K100/Z100L/Z100 | DTK 25.04.* |
| rock-6.3.28-V1.3.0b and later | BW series (BW1000/BW1100/BW150/BW100/BW10) | DTK 25.04.* |
| rock-6.3.30-V1.4.1a and later | K100-AI/K100/Z100L/Z100; BW series | DTK 26.04.* |

### How to read a driver package name

Driver packages come in two naming generations. Decide which one you are looking at first:

| Form | Example | Meaning |
| --- | --- | --- |
| Older: `rock-<ROCm version>-<driver version>-V<package version>.run` | `rock-5.7.1-6.2.35-V1.6.7d.run` | `5.7.1` is the compatible ROCm version, `6.2.35` is the driver version |
| Newer: `rock-<driver version>-V<package version>.run` | `rock-6.3.30-V1.4.1a.run` | Only the driver version and package version remain |
| Some BW-series packages: `z-rock-...` | `z-rock-6.3.28-1.3.0b.run` | A dedicated package for the BW series (including BW1100) |

**The DTK version must match the driver version**: DTK 24.04.* with 6.2.x drivers, 25.04.* with early 6.3.x
drivers, and 26.04.* with 6.3.30 and later. When DTK and driver do not match, the usual symptom is
"`hy-smi` sees the card, but any framework run fails".

:::info Driver and framework versions are two separate mappings

Driver ↔ DTK is one mapping; the AI framework packages (PyTorch / vLLM wheels) ↔ DTK is another.
Both must line up before a job can actually run. Confirm both before you install.

:::

### Picking the driver and firmware by DTK generation

If the DTK version is already fixed for the site (workload images depend on it), work backwards from the DTK
generation to pick the driver and VBIOS — do not go by card model alone:

| Product / DTK generation | Driver version | VBIOS version |
| --- | --- | --- |
| BW1000 / BW1100 / BW150 / BW100 / BW10 | `z-rock-6.3.28-1.3.0b` | `z.6.312.002400Q.998006` |
| K100-AI / Z100L / K100 (with DTK 24.04.*) | `rock-6.2.35-1.6.7d` | `5.719.001200r.710209` |
| K100-AI / Z100L / K100 (with DTK 25.04.* and later) | `rock-6.3.28-1.3.0b` and later | `6.312.002400Q.998006` and later |

The table is compiled from Hygon's Photon developer community deployment guide. **At the site, use the
combination shipped with the release package.** Before swapping a driver or firmware, confirm it matches the
DTK already installed.

## Confirm the hardware is present

Before installing the driver, confirm the cards are seated and the system sees them — so a hardware problem
is not mistaken for a driver problem:

```bash
lspci -nn | grep -e Display -e Co-processor | grep -i -E "hygon|haiguang|Chengdu"
```

| Model | Appears in `lspci` as |
| --- | --- |
| Z100 / Z100L | `Display controller` |
| K100 / K100-AI / BW series | `Co-processor` |

Also check the trailing `rev` value: `rev 01` means the device is healthy; `rev ff` means the device is
already in a bad state — **a normal reboot may not recover it**: you need a hard reset (DC) or a power cycle (AC).

:::info A BAR address beyond 44 bits will not run

A DCU's BAR register address must stay within 44 bits. Before installing the driver, inspect the `Region`
section with `lspci -vvv` (the BW series device ID is `1d94:6320`, K100-AI is `1d94:6210`). If it exceeds the
limit, lower MMIO High Base in the BIOS — the menu location differs between server vendors, so follow the
server manual.

:::

## Steps

### 1. Install the dependency packages

Run the commands for your operating system.

CentOS:

```bash
yum install -y rpm-build gcc-c++ cmake automake elfutils-libelf-devel libdrm libdrm-devel pciutils
yum install -y kernel-devel-`uname -r` kernel-modules-extra
```

Ubuntu:

```bash
apt install -y gcc g++ cmake automake libelf-dev libdrm-amdgpu1 libtinfo5 pciutils libdrm-dev
apt install -y linux-headers-`uname -r` linux-modules-extra
```

### 2. Download the driver and make it executable

Download entry points for the driver and DTK:

| Purpose | Address |
| --- | --- |
| Photon developer community (main entry) | `https://developer.sourcefind.cn/` |
| DTK and toolkits | `https://download.sourcefind.cn:65024/1/main` |
| Driver (primary) | `https://download.sourcefind.cn:65024/6/main/latest` |
| Driver (mirror) | `https://cancon.hpccube.com:65024/6/main/latest` |
| Driver image registry | `https://developer.sourcefind.cn/servicelist` |
| Model zoo | `https://developer.sourcefind.cn/modelzoo` |

After uploading to the target machine, grant the execute permission:

```bash
chmod +x rock*.run
```

### 3. Install the driver

```bash
./rock-<version>.run -A
```

You do not need to uninstall the old driver first — the installation removes it automatically. Common parameters:

| Parameter | Effect |
| --- | --- |
| `-A` | Fully automatic: handles the driver, configuration, VBIOS and interconnect firmware together. **Recommended** |
| `-D` | Developer mode: installs only the driver / HAL / configuration, leaves VBIOS alone |
| `-a` | Driver upgrade policy: `0` automatic / `1` ignore version / `2` ask |
| `-u` | VBIOS update policy: `0` automatic / `1` ask / `2` do not update |
| `-H` | Interconnect firmware (HY Switch) policy: `0` automatic / `1` ask / `2` do not update |
| `-t` | DCU interconnect type (PCIe 2-card / 4-card, OAM 2/4/8-card direct connect, etc.), supported on the BW series |
| `-s` | Enable vGPU software scheduling (one-into-four splitting) |
| `-d` | Do not load the driver during installation; it takes effect after a reboot |
| `-h` | Show every parameter the current package supports |

:::warning Parameters depend on the package

Parameters vary slightly between driver versions. Run `./rock-<version>.run -h` before you start;
the table above is for understanding what each option means, not a fixed cross-version interface.

:::

Multi-card direct-connect machines (OAM systems) usually also need `-t` to specify the interconnect topology.
It is supported on the **BW series only** — not on K100-AI — and guessing at it affects multi-card communication,
so do not fill it in unless you know the value:

| `-t` value | Interconnect type | Applies to |
| --- | --- | --- |
| `0` | PCIE_2HCU | PCIe add-in card, 2-card direct connect |
| `1` | PCIE_4HCU | PCIe add-in card, 4-card direct connect |
| `4` | OAM_2HCU | OAM 2-card direct connect |
| `5` | OAM_4HCU | OAM 4-card direct connect |
| `6` | OAM_8HCU | OAM 8-card direct connect |
| `10` | OAM_7HSW_8HCU | 8 cards interconnected through 7 HY Switches |
| `11` | OAM508_7HSW_8HCU | OAM508 form factor |
| `NONE` / `KEEPOLD` | Disable hlink / keep the old type | As needed |

### 4. Restart the driver service

```bash
systemctl restart hymgr
```

### 5. Answer the prompts during installation

Two kinds of questions come up during installation. Answer them by this table:

| Prompt | Meaning | What to choose |
| --- | --- | --- |
| `Do you want to remove legacy hymgr config file? [Y/n]:` | Whether to regenerate `/etc/hymgr.cfg` | Choose `yes` to regenerate it, or `no` to keep the existing file. If unsure, keep it (`no`) |
| `Update vbios? [y/N]:` (K100/K100-AI environments) | Whether to update the card firmware | For a first installation, choose `y` and reboot the physical machine; later you can choose `N`. If rebooting the physical machine is tightly restricted in your environment, you may skip the update |

## Uninstalling and upgrading the driver

**Upgrading does not require uninstalling first**: install the new `.run` directly and the installer removes
the old driver automatically. To uninstall by hand, follow this order:

```bash
rpm -qa | grep rock          # see which package is installed
systemctl stop hymgr         # stop the driver service
rmmod hycu                   # unload the driver module (hydcu on 6.2.x and below)
rpm -e rock-*                # remove the driver package
```

:::warning A firmware upgrade needs a physical reboot

Whenever this installation touched the **HY Switch firmware or VBIOS**, the physical machine must be rebooted
before it takes effect. If the site has strict downtime windows, plan this step in.

:::

## Updating the firmware (VBIOS / HY Switch)

After the driver is installed, the host gets a firmware directory at `/opt/hyhal/firmware/vbios`, with
subdirectories per product family (`BW3000/` for the BW series, `KM/` for K100, `ZD/` for K100-AI, `ZF/` for
Z100L, `NMZ/` for BW1100), plus the flashing tool `hyflash_*` and the automatic script `vbios_upgrade.sh`.

Flash a specified image manually (`--xhcl` also enables the interconnect):

```bash
./hyflash --index a --update ./BW3000/BW3000-<VBIOS version>.bin --xhcl
```

Or just run the automatic script:

```bash
cd /opt/hyhal/firmware
./vbios_upgrade.sh
```

:::warning Three rules for flashing firmware

(1) Confirm the VBIOS matches the hardware version first — **flashing the wrong version can brick the card**.
(2) **Do not cut power** while flashing. (3) **Reboot** afterwards for it to take effect.
Schedule firmware flashing inside a maintenance window in production.

:::

## Verify that the driver is loaded

Run:

```bash
lsmod | grep -E "hydcu|hycu"
```

Seeing the driver modules listed means the driver loaded successfully. **The module names differ by driver version.**

Drivers 6.2.x and below show `hydcu`:

```text
hydcu                1435342  0
hydcu_sched            34432  1 hydcu
hyttm                  61919  1 hydcu
hykcl                  46567  3 hydcu_sched,hydcu,hyttm
hy_extra               32140  3 hydcu_sched,hydcu,hykcl
```

Drivers 6.3.x and above show `hycu`:

```text
hycu                 3371008  2
hycu_sched             45056  1 hycu
hyttm                  86016  2 hycu,hydrm_ttm_helper
hykcl                  40960  5 hycu,hycu_sched,hyttm
hy_extra               65536  2 hycu,hycu_sched
```

## Common problems

| Symptom | Possible cause | What to do |
| --- | --- | --- |
| Installation fails, reporting missing build tools | The dependency packages are incomplete, or the `cmake` / `gcc` version is too low | Newer drivers require `cmake` later than 3.2 and `gcc` later than 7.3. Upgrade them first, then install again |
| Installation fails, reporting that kernel headers are not found | The `kernel-devel` version does not match the running kernel | Check the kernel version with `uname -r` and install the exactly matching `kernel-devel` |
| `lsmod` does not show the driver modules | The driver was not installed, or the service was not restarted afterwards | Confirm the installation output reported success, then run `systemctl restart hymgr` |
| The container cannot read DCU process information | On 6.3.* drivers the debug path is not mounted | When calling Docker, mount `/sys/kernel/debug` into the container |

:::warning Keep the versions matched

The driver, the DTK, and the kernel headers you install later must all match. **Do not pick a version number from memory** —
use the combination shipped with the release package. Otherwise the installation may fail at best, or the card may be unusable after installation at worst.

:::
