# DCU-Exporter

DCU-Exporter **periodically collects the state of every card** — temperature, power, memory usage, utilization, PCIe bandwidth, error counts, and more —
and exposes it over an HTTP interface for a monitoring system such as Prometheus to scrape. With it installed, the platform can show the cards'
running curves and raise alerts.

Think of it as **a power meter fitted on every card**: a card does not report its own temperature and power, so something has to read the meter regularly.

## When you must install it

- When you need to see DCU utilization, memory, temperature, or power on the platform, or raise alerts and capacity statistics based on card state.
- If you only need resource scheduling and no monitoring data, you can skip this page.

## Before you start

- The driver is installed on every machine that has a card (`lsmod | grep -E "hydcu|hycu"` shows the driver modules).
- The component image is already available somewhere the cluster can pull from.
- You have the deployment file `dcu-exporter-v2.yaml`.

## Deploy

In a cluster it is usually deployed as a DaemonSet, with one Pod per node that has a card:

```bash
kubectl create -f dcu-exporter-v2.yaml
```

## Verify

### 1. Check the Pods

```bash
kubectl get pod -n kube-system -owide | grep dcu-exporter
```

There should be one Pod per node that has a card, in `Running` state.

### 2. Read the metrics directly

```bash
curl localhost:16080/metrics
```

If it prints content, collection is working. The default port is `16080` and the default path is `/metrics`; the full address looks like `http://<host>:16080/metrics`.

### 3. Confirm in Prometheus

If the cluster already runs Prometheus, query the relevant metrics there. Seeing data means scraping works.

## Port and collection settings (optional)

| What you want to change | How to change it |
| --- | --- |
| Metric port | Edit `containerPort`, `prometheus.io/port`, and the Service `port` in the deployment file (all three must match) |
| Collect only some metrics | Use the environment variable `ENABLE_METRICS` to list the metric names, separated by commas |
| Collection interval | Set it with the environment variable `PULSE`, in seconds |
| Logging | Configure log levels and switches with the `LOG*` environment variables |

## Install directly on a physical machine

Besides the containerized deployment, you can install DCU-Exporter directly on a physical machine (the driver must already be installed):

### 1. Download the installer

Download `dcu-exporter.run` from the community.

### 2. Run the installation

```bash
bash dcu-exporter.run
```

The installation directory is `/opt/dcu-exporter`.

### 3. Check the usage

```bash
/opt/dcu-exporter/dcu-exporter -h
```

## Common problems

| Symptom | Possible cause | What to do |
| --- | --- | --- |
| The Kubernetes-related labels in the metrics are always empty | No workload is using a card / the kubelet working directory is wrong / the environment variables do not match the cluster | See "Troubleshoot empty Kubernetes labels" below |
| Port `16080` is not reachable | The Pod is not ready, or the port configuration was changed | Confirm the Pod state first, then check that the three port settings in the deployment file match |
| The Pod does not start | The image cannot be pulled, or the driver on the node is broken | Run `kubectl describe pod -n kube-system <dcu-exporter-pod>` and read the events, and confirm the driver modules exist on the node |

### Troubleshoot empty Kubernetes labels

1. Check whether any workload in the cluster is using a DCU:

   ```bash
   kubectl get pod -A -o wide
   ```

2. Check whether `/var/lib/kubelet` on the node is the real working directory of kubelet:

   ```bash
   ls -d /var/lib/kubelet
   ```

3. Check whether `KUBERNETES_SERVICE_HOST` and `KUBERNETES_SERVICE_PORT` inside the container match the real cluster configuration:

   ```bash
   kubectl exec -n kube-system <dcu-exporter-pod> -- env | grep KUBERNETES
   ```

:::warning Stop the Exporter before upgrading the driver

The Exporter calls driver interfaces on a regular cycle. Before upgrading the driver, stop your workloads first and then stop the Exporter;
after the upgrade, bring them back in the reverse order. Otherwise the Exporter may read a mix of old and new driver information and report abnormal metrics.

:::
