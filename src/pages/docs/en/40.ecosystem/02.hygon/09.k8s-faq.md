# FAQ

The common failures of the Hygon DCU cluster components are all in this table: find the row that matches your symptom
first, then run the commands under "What to do". Long commands that do not fit in the table are collected in
"Full commands" at the end.

## Quick troubleshooting table

:::tip Decide first whether it is a driver problem or a cluster problem

Most of the problems below **have their root cause in the host driver** — the cluster side only shows the
symptom. To tell them apart, run `lsmod | grep -E "hydcu|hycu"` and `hy-smi` on the node. **If either of those
fails, go back to [DCU driver installation](/ecosystem/hygon/driver-runtime) and leave the cluster components
alone.**

:::

| Symptom | Possible cause | What to do |
| --- | --- | --- |
| `lspci` does not show the DCU, or the device shows `rev ff` | The card is not seated properly / the device is already in a bad state | See "Confirm the hardware is present" in [DCU driver installation](/ecosystem/hygon/driver-runtime): `rev ff` needs a hard reset (DC) or a power cycle (AC) |
| The driver will not install, or the card is still unusable afterwards | The BAR address exceeds 44 bits in the BIOS | Inspect the `Region` address with `lspci -vvv`; if it exceeds the limit, lower MMIO High Base in the BIOS, following the server manual |
| After a driver upgrade the module name in `lsmod` changed from `hydcu` to `hycu` | Driver 6.3.x renamed the module | Expected behaviour — troubleshoot with the new module name (6.2.x and below use `hydcu`) |
| DCU-Label-Node fails to add labels to a DCU node | The component version is too old and is incompatible with the current driver | Upgrade to V2.2.0 or above and redeploy; check the current version first (see "Check the current component version") |
| After requesting DCU resources, the container in the Pod has no `/opt/hyhal` directory | The device plugin version is too old | Upgrade to V2.1.0 or above, which mounts `/opt/hyhal` automatically; check the current version first (see "Check the current component version") |
| The Kubernetes-related labels in the Exporter metrics are always empty | No workload is using a card / the kubelet working directory is wrong / the environment variables do not match the cluster | See "Troubleshoot empty Exporter labels" below |
| The Exporter is running, but no DCU metrics show up in Prometheus | No ServiceMonitor, so the scraper never discovers the service | See "Confirm in Prometheus" in [DCU-Exporter](/ecosystem/hygon/k8s-exporter) and add a ServiceMonitor matching the actual Service labels |
| Running `hy-smi` in a containerd container reports `Failed to connect service!` | A problem with one specific driver version (6.3.13) | Upgrade or downgrade the driver; if that is not possible, set `hostNetwork` when starting the workload as a temporary workaround |
| After upgrading a 6.2.* driver to 6.3.*, `hy-smi` in the container reports `RSMI_NOT_SUPPORTED` | The environment variables are not loaded inside the container | Run `source /opt/hyhal/env.sh && hy-smi` inside the container |
| You want an application in a Docker container to run on a specific DCU | No card number was specified | Specify it with the environment variable `HIP_VISIBLE_DEVICES` (`0,1,2...` selects a card, `-1` means CPU); see "Full commands" for the syntax |
| The vDCU Pod fails to start after deploying the components | Components not ready / node label missing / the webhook service cannot be found / leftover resources | See "Troubleshoot a failing vDCU Pod" below |
| You want to start DCU-Exporter on its own in a Docker environment | Running the container directly, without Kubernetes | Use the command in "Start DCU-Exporter in Docker" below |

## Troubleshoot empty Exporter labels

1. Check whether any workload in the cluster is using a DCU device:

   ```bash
   kubectl get pod -A -o wide
   ```

2. Check whether `/var/lib/kubelet` on the node is the real working directory of kubelet:

   ```bash
   ls -d /var/lib/kubelet
   ```

3. Check whether `KUBERNETES_SERVICE_HOST` and `KUBERNETES_SERVICE_PORT` inside the container match the real cluster configuration:

   ```bash
   kubectl exec -n kube-system <dcu-exporter-pod> -- env | grep KUBERNETES
   ```

## Troubleshoot a failing vDCU Pod

1. Check that the component Pods are healthy, and that the node running the device plugin carries the label `dcu=on`:

   ```bash
   kubectl get pod -n kube-system -owide | grep -E "dcu-device-plugin|vdcu"
   kubectl get node <node-name> --show-labels | grep dcu
   ```

2. If the error contains `service "admission-webhook-dcu-svc" not found`:
   - Check whether `vdcu-admission-webhook` shares the network with the host, and whether port `443` on the host is occupied;
   - Delete the leftover resources and redeploy:

   ```bash
   kubectl delete secrets -n kube-system admission-webhook-dcu-certs
   kubectl delete mutatingwebhookconfigurations mutating-webhook-dcu-cfg
   ```

3. On V2.1.0 and earlier, also check:
   - whether the `k8s-vdcu-scheduler` version matches the k8s cluster version;
   - whether `k8s-vdcu-scheduler` was scheduled onto a node without a DCU;
   - on older k8s versions you may need to change `kubescheduler.config.k8s.io/v1` in the scheduler deployment file to `kubescheduler.config.k8s.io/v1beta2`.

## Full commands

### Check the current component version

Look at the images the component Pods are using (the image tag is the version):

```bash
kubectl get pod -n kube-system -o jsonpath='{range .items[*]}{.metadata.name}{"  "}{.spec.containers[*].image}{"\n"}{end}' | grep -E "dcu-|vdcu"
```

### Start DCU-Exporter in Docker

```bash
docker run --name dcu-exporter-v2 -d --privileged \
  --device=/dev/kfd \
  --device=/dev/mkfd \
  --device=/dev/dri \
  -v /etc/vdev:/etc/vdev \
  -v /etc/hostname:/etc/hostname \
  -v /opt/hyhal:/opt/hyhal \
  -p 16080:16080 image.sourcefind.cn:5000/dcu/admin/base/dcu-exporter:v2.2.0
```

### Choose which DCU card an application uses

Set `HIP_VISIBLE_DEVICES` in the workload's environment variables:

```yaml
env:
  - name: HIP_VISIBLE_DEVICES
    value: "0" # 0,1,2,...,n selects a DCU; -1 means CPU
```
