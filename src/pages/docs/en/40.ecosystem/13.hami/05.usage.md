# Requesting & operating

A shared card is requested with ordinary Kubernetes resources; only the keys change. There is no
platform-specific syntax, so the difficulty lies in the per-vendor keys and units, plus a handful of rules that
hold for one vendor and not the others.

## Minimum syntax by vendor

Only the `resources.limits` block is shown; units and granularity follow each vendor.

| Vendor | Request |
| --- | --- |
| NVIDIA | `nvidia.com/gpu: 1`, `nvidia.com/gpumem: 10240` (MiB), `nvidia.com/gpucores: 50` |
| Huawei Ascend | `huawei.com/Ascend910B: 1`, `huawei.com/Ascend910B-memory: 16384` |
| Hygon | `hygon.com/dcunum: 1`, `hygon.com/dcumem: 2000`, `hygon.com/dcucores: 60` |
| Cambricon | `cambricon.com/vmlu: 1`, `cambricon.com/mlu.smlu.vmemory: 20`, `cambricon.com/mlu.smlu.vcore: 10` |
| Iluvatar | `iluvatar.ai/BI-V150-vgpu: 1`, `iluvatar.ai/BI-V150.vCore: 50`, `iluvatar.ai/BI-V150.vMem: 64` |
| Moore Threads | `mthreads.com/vgpu: 1`, `mthreads.com/sgpu-memory: 32`, `mthreads.com/sgpu-core: 8` |
| MetaX | `metax-tech.com/sgpu: 1`, `metax-tech.com/vcore: 60`, `metax-tech.com/vmemory: 4` |
| Kunlunxin | `kunlunxin.com/vxpu: 1`, `kunlunxin.com/vxpu-memory: 24576`; whole cards use `kunlunxin.com/xpu: 1` |
| Biren | `birentech.com/gpu: 1` |
| AMD | `amd.com/gpu: 1`, `amd.com/gpumem: 8192`, `amd.com/gpucores: 25` |

Cambricon, Hygon and Moore Threads share one rule: memory and compute **only apply when the card count is 1**.
Writing `2` means two whole cards and the memory and compute values are ignored. Kunlunxin is the reverse:
sliced requests go through `vxpu`, whole cards through `xpu`, as two distinct keys. Biren only accepts whole cards
or partitions already defined through SVI, so memory size cannot be specified at all.

## A complete example

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: vgpu-demo
spec:
  containers:
    - name: cuda
      image: ubuntu:22.04
      command: ["nvidia-smi"]
      resources:
        limits:
          nvidia.com/gpu: 1            # one vGPU
          nvidia.com/gpumem: 10240     # 10240 MiB of memory
          nvidia.com/gpucores: 50      # 50% of compute
```

MetaX sGPU follows the same shape with its own keys and units:

```yaml
      resources:
        limits:
          metax-tech.com/sgpu: 1       # one sGPU
          metax-tech.com/vcore: 60     # 60% of compute
          metax-tech.com/vmemory: 4    # 4 GiB of memory
```

Omitting memory or compute falls back to that vendor's default, usually the whole card. Memory can also be
requested as a percentage: on NVIDIA that is `nvidia.com/gpumem-percentage`, and the platform's built-in Volcano
vGPU offers `volcano.sh/vgpu-memory-percentage`. The two names are not interchangeable.

## Annotations

Annotations control **which card** is chosen and **how workloads are placed**. They are independent of how much
resource is requested.

| Annotation | Effect |
| --- | --- |
| `nvidia.com/use-gpuuuid` | Restrict allocation to the listed cards |
| `nvidia.com/nouse-gpuuuid` | Exclude the listed cards |
| `nvidia.com/use-gputype` | Restrict allocation to the listed models |
| `nvidia.com/nouse-gputype` | Exclude the listed models |
| `hami.io/node-scheduler-policy` | Node-level policy: `binpack` or `spread` |
| `hami.io/gpu-scheduler-policy` | Card-level policy: `binpack`, `spread` or `mutex`. `mutex` only uses completely idle cards |
| `hami.io/device-scoring-weights` | Device scoring weights, such as `slot=1,core=1,memory=3`; all three are required |
| `nvidia.com/vgpu-mode` | Whether this pod uses `hami-core` or `mig` |

Hygon and Cambricon each have their own model filters: `hygon.com/use-dcutype`, `hygon.com/nouse-dcutype`,
`cambricon.com/use-mlutype` and `cambricon.com/nouse-mlutype`. An annotation carrying a vendor prefix only
applies to that vendor.

## Priority only has two levels

`nvidia.com/priority` accepts `0` and `1`, where `0` is high and `1` is the low default. Its scope is
**runtime preemption within a single card**: a high-priority workload arriving while a low-priority one is running
pauses the low-priority workload, takes the resources, and lets it resume once finished.

It does not solve queuing. When several workloads are waiting and submission priority has to decide who goes
first, HAMi does not do it on its own; that belongs to Volcano's queues. Volcano defines queues at different
priorities and performs the preemption, while HAMi handles in-card sharing and runtime preemption. The two
mechanisms together are what produce a full multi-level priority scheme.

## Environment variables inside the container

| Variable | Values | Effect |
| --- | --- | --- |
| `GPU_CORE_UTILIZATION_POLICY` | `default` / `force` / `disable` | `force` keeps compute strictly within the requested percentage; `disable` removes the limit |
| `CUDA_DISABLE_CONTROL` | `true` / `false` | When `true`, HAMi-Core is fully inactive inside the container, so neither isolation nor limits apply. Troubleshooting only |
| `LIBCUDA_LOG_LEVEL` | `0` | Silences the `[HAMI-core ...]` lines in the container output |

`CUDA_DISABLE_CONTROL=true` deserves attention because it is often set to get past a startup error and then
forgotten, silently leaving the limits off.

## Where the metrics come from

| Source | Port | Content |
| --- | --- | --- |
| `hami-device-plugin` | `31992` | Per-container vGPU metrics; change with `devicePlugin.service.httpPort` |
| `hami-scheduler` webhook | `31998` | Scheduler webhook service port |
| The platform's `volcano-device-plugin` | `9394` | vGPU metrics when running the built-in route |

Two ports mean two sources. Do not look on `9394` for HAMi's per-container metrics. Official Grafana dashboards
cover device allocation and real-time usage.

## Notes for model serving

- Serving a single-GPU vLLM model while requesting `nvidia.com/gpumem` needs no extra configuration.
- **Multi-GPU tensor parallelism** requires HAMi `v2.9.0` or later. Older releases fail NCCL initialisation
  because several processes share one CUDA device memory state file. This only shows up on vLLM 0.18 and later.
- In a Volcano environment, set `tensor_parallel_size` per pod rather than for all pods at once.
- If startup reports a CUDA graph capture error, try adding `--enforce-eager`.

Frameworks that size themselves from the reported memory, vLLM among them, will use exactly the quota. So the
allocation for a serving workload does not need much headroom, but it still has to be enough to hold the model.
