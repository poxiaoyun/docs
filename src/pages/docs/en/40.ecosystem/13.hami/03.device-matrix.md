# Supported devices & resource keys

HAMi's coverage differs from vendor to vendor in three respects: whether memory limits actually hold, whether
compute limits hold, and whether one pod can draw sliced memory or compute from several physical cards at once.
The table below is the official v2.10.0 matrix.

## Official support matrix

| Vendor | Device type | Models | Status | Memory isolation | Compute isolation | Multi-card slicing |
| --- | --- | --- | --- | --- | --- | --- |
| NVIDIA | GPU | All | Stable | Yes | Yes | Yes |
| AMD | GPU | Instinct / ROCm | Stable | Yes | Yes | No |
| Huawei Ascend | NPU | 910B, 910B3, 910C, 310P | Stable | Yes | Yes | No |
| Hygon | DCU | All | Stable | Yes | Yes | No |
| Cambricon | MLU | 370, 590 | Stable | Yes | Yes | No |
| Iluvatar | GPU | All | Stable | Yes | Yes | No |
| Moore Threads | GPU | MTT S4000 | Stable | Yes | Yes | No |
| MetaX | GPU | MXC500 | Stable | Yes | Yes | No |
| Kunlunxin | XPU | P800 | Stable | Yes | **No** | No |
| Biren | GPU | Biren166M | Stable | **No** | **No** | No |
| Enflame | GCU | S60 | Stable | Yes | Yes | No |
| Vastai | GPU | VA16 | Stable | No | No | No |
| AWS | Neuron | Inf, Trn | Stable | No | Yes | No |
| Teco | DPU | Not listed | Under validation | No | No | No |

What the three capability columns mean:

| Column | Meaning |
| --- | --- |
| Memory isolation | A container exceeding its requested memory is rejected rather than reaching for physical memory |
| Compute isolation | A container exceeding its requested compute share is throttled |
| Multi-card slicing | One pod can draw sliced memory and compute across several physical cards |

`Multi-card slicing = No` does not mean multiple cards cannot be requested. It means that when requesting more
than one card, memory and compute must not be specified as well, because that is treated as a whole-card
allocation. This rule reappears in the per-vendor notes below.

:::info The two official tables differ slightly
The Chinese FAQ lists Ascend models as `910A`, `910B2`, `910B3` and `310P`; the English Device supported page,
which is marked as reflecting v2.10.0, lists `910B`, `910B3`, `910C` and `310P`. Go by the model reported by the
device plugin you actually installed rather than guessing from either table.
:::

## Resource keys by vendor

What a workload requests is a resource key, not a model name. Some vendors end up with two sets of keys on
different routes, so do not mix them.

### NVIDIA

| Resource key | Meaning |
| --- | --- |
| `nvidia.com/gpu` | Number of vGPUs |
| `nvidia.com/gpumem` | Requested memory, in MiB |
| `nvidia.com/gpumem-percentage` | Requested memory as a share of the whole card |
| `nvidia.com/gpucores` | Requested compute, as a percentage |
| `nvidia.com/priority` | In-card runtime preemption priority: `0` high, `1` low |

Granularity is 1 MiB of memory and 1% of compute. NVIDIA is the only vendor where multi-card slicing works.

### Huawei Ascend

| Resource key | Meaning |
| --- | --- |
| `huawei.com/Ascend910A`, `huawei.com/Ascend910B`, `huawei.com/Ascend310P` | Card count |
| `huawei.com/<same prefix>-memory` | Requested memory |

Ascend does not slice by percentage but by **card type template**. Templates are defined on the device plugin
side: 910A has `vir02`, `vir04`, `vir08` and `vir16`, while 910B3 has `vir05_1c_16g` and `vir10_3c_32g`.
A request that falls between two profiles gets the smallest one that fits. The node label is `ascend=on`.
HAMi also offers a soft slicing mode (`hami-vnpu-core`), currently limited to ARM platforms and to the HAMi scheduler.

### Hygon DCU

| Resource key | Meaning |
| --- | --- |
| `hygon.com/dcunum` | Number of vDCUs |
| `hygon.com/dcumem` | Memory per vDCU, in MiB |
| `hygon.com/dcucores` | Compute per vDCU, as a percentage |

Granularity is 1 MB of memory and 1% of compute. A container can hold only one vDCU; to mount several cards,
omit memory and compute. Inside the container, `source /opt/hygondriver/env.sh` enables vDCU, and
`hy-smi virtual -show-device-info` confirms it.

### Cambricon MLU

| Resource key | Meaning |
| --- | --- |
| `cambricon.com/vmlu` | Number of vMLUs |
| `cambricon.com/mlu.smlu.vmemory` | Memory per vMLU; the smallest unit is 256 MB |
| `cambricon.com/mlu.smlu.vcore` | Compute per vMLU, as a percentage |

Granularity is 256 MB of memory and 1% of compute. Before enabling it, run `cnmon set -c <id> -smlu on` on every
card, and configure the device plugin with `mode=dynamic-smlu` and `min-dsmlu-unit=256`. Memory and compute only
take effect when `vmlu` is `1`; anything higher is a whole-card allocation, the same rule as Hygon and Moore Threads.

### Iluvatar

| Resource key | Meaning |
| --- | --- |
| `iluvatar.ai/<card>-vgpu` | Number of vGPUs |
| `iluvatar.ai/<card>.vCore` | Compute, one unit per 1% |
| `iluvatar.ai/<card>.vMem` | Memory, one unit per 256 MB |

The card types named in the documentation are `MR-V100`, `MR-V50`, `BI-V150` and `BI-V100`. Omitting memory means
using it all. When several cards are requested the compute share is scaled by the card count.

:::warning Iluvatar has two address spaces for resource keys
Whole cards are requested through `iluvatar.com/gpu`; sliced cards use `iluvatar.ai/...`. The two domains are
different. Names such as `iluvatar.ai/vgpu`, `iluvatar.ai/vcuda-core` and `iluvatar.ai/vcuda-memory` also
circulate online but do not match the current HAMi documentation. Before defining a flavor, check which plugin is
installed on the cluster and what resource keys it reports.
:::

### Moore Threads

| Resource key | Meaning |
| --- | --- |
| `mthreads.com/vgpu` | Number of vGPUs; on its own this means an exclusive whole card |
| `mthreads.com/sgpu-memory` | Memory, one unit per 512 MB |
| `mthreads.com/sgpu-core` | Compute share |

The restrictions are tighter than elsewhere: multi-card sharing is not supported, and only one Moore Threads
device can be shared in a pod even when it holds several containers. The documentation notes that these
capabilities were tested on MTT S4000 only. Install MT CloudNative Toolkits on the nodes; afterwards
`mt-mutating-webhook` and `mt-gpu-scheduler` can be removed.

### MetaX

MetaX runs on two separate routes with different resource keys:

| Route | Resource keys | Notes |
| --- | --- | --- |
| Whole card with topology awareness | `metax-tech.com/gpu` | No sharing. Cards are chosen by MetaXLink and PCIe Switch proximity; the annotation `hami.io/node-scheduler-policy` selects `spread` or `binpack` |
| sGPU sharing | `metax-tech.com/sgpu`, `metax-tech.com/vcore`, `metax-tech.com/vmemory` | `vcore` is a percentage (`60` means 60%), `vmemory` is in GiB |

The two routes need different components: whole-card topology needs MetaX GPU Extensions ≥ 0.8.0, while sGPU needs
MetaX GPU Operator ≥ 0.10.2 and driver ≥ 2.32.0. Leaving out `vcore` or `vmemory` means using that resource in full.

### Kunlunxin

| Route | Resource keys | Notes |
| --- | --- | --- |
| Whole card with topology awareness | `kunlunxin.com/xpu` | No sharing. Only 1, 2, 4 or 8-card allocations are allowed; 1, 2 and 4-card allocations must not span NUMA nodes; fragmentation is minimised after allocation |
| vXPU sharing | `kunlunxin.com/vxpu`, `kunlunxin.com/vxpu-memory` | Memory in MiB; the example uses 24576 |

vXPU is limited to the P800-OAM card type and needs driver ≥ v5.0.21.16 plus `xpu-container-toolkit` ≥
`xpu_container_1.0.2-1`. The official matrix shows no compute isolation for Kunlunxin, so slicing by memory works
while slicing by compute does not.

### Biren

| Resource key | Meaning |
| --- | --- |
| `birentech.com/gpu` | The device request; whole cards and SVI partitions both use this key |

Biren supports neither memory nor compute isolation, which means **memory size cannot be specified**. Only whole
cards or partitions pre-defined through SVI can be requested. The node label is `biren=on`, which is not the
`birentech.com=gpu` label the vendor's own plugin uses.

### AMD

| Resource key | Meaning |
| --- | --- |
| `amd.com/gpu` | Number of vGPUs |
| `amd.com/gpumem` | Requested memory, in MiB |
| `amd.com/gpucores` | Requested compute, as a percentage |

This route requires HAMi's `amd-device-plugin`; the upstream ROCm `k8s-device-plugin` cannot stand in for it.
If the AMD GPU Operator also manages the driver, disable its bundled device plugin, otherwise the two compete
for `amd.com/gpu`.

## When each vendor arrived

| Release | Published | Vendor-related changes |
| --- | --- | --- |
| v2.6.0 | | MetaX sGPU first appears in the documentation |
| v2.7.0 | 2025-09-26 | Kunlunxin support: vXPU sharing and topology-aware scheduling |
| v2.8.0 | 2026-01-20 | Fixed vXPU occasionally not working on P800 nodes |
| v2.9.0 | 2026-05-13 | Enflame device support; fixed multi-GPU tensor parallel initialisation on vLLM 0.18 and later |
| v2.10.0 | 2026-08-21 | Biren and AMD vGPU support; DRA components moved out of the main chart |

Kunlunxin and multi-GPU vLLM correspond directly to version gates: if the cluster runs an older HAMi than the
table shows, those capabilities are simply absent.
