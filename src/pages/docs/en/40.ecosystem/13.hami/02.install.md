# Installation & parameters

HAMi itself is a single Helm command. The work is in what comes before it: the driver, the container toolchain
and the vendor device plugin all have to be in place, and each vendor sets a different bar.

## Cluster and tooling prerequisites

| Item | Requirement |
| --- | --- |
| Kubernetes | 1.23 or later, with a working container runtime |
| Helm / kubectl | Installed, with permission to install cluster-scoped resources |
| Nodes | Meeting the operating system and kernel requirements of the vendor driver |

Check one thing before installing: **whether this cluster already uses the platform's built-in NVIDIA scheduling
package**. If it does, a `volcano-vgpu-device-plugin` is already running and will compete with HAMi's device
plugin for the same `nvidia.com/gpu`. The two cannot coexist. The trade-off is described under
[Platform support](/ecosystem/hami/platform-support).

## Extra prerequisites by vendor

Driver and toolkit versions are hard gates; below them the plugin will not start.

| Vendor | Extra prerequisites |
| --- | --- |
| NVIDIA | A driver matching the card model and the workload's CUDA version; NVIDIA Container Toolkit configured for the container runtime |
| Huawei Ascend | Prepare per card model; the smallest slice size depends on the card type template |
| Hygon DCU | `dtk` driver ≥ 24.04 and `hy-smi` v1.6.0 |
| Cambricon MLU | `neuware-mlu370-driver` > 5.10 and `cntoolkit` > 2.5.3, plus SMLU mode enabled on every card |
| Iluvatar | Driver version > 3.1.0 and `gpu-manager` on the nodes (do not install `gpu-admission`) |
| Moore Threads | MT CloudNative Toolkits > 1.9.0 and driver ≥ 1.2.0 |
| MetaX | MetaX Driver ≥ 2.32.0 and MetaX GPU Operator ≥ 0.10.2 |
| Kunlunxin | Driver ≥ v5.0.21.16 and `xpu-container-toolkit` ≥ `xpu_container_1.0.2-1`, P800-OAM card type only |
| Biren | Node label `biren=on`, plus HAMi's device plugin |
| AMD | A working ROCm environment (validated with ROCm 7.0.2) where `amd-smi static --gpu 0` shows the model, VRAM and compute unit count; use HAMi's `amd-device-plugin`, not the upstream ROCm `k8s-device-plugin` |

AMD carries one extra constraint worth checking early: memory isolation loads `libamvgpu.so` through glibc's
`LD_AUDIT` and requires `GLIBC_2.34` symbols. Images built on older glibc (Ubuntu 20.04 or RHEL 8, for instance)
and musl or Alpine images cannot be used yet. Among the domestic vendors, Hygon and Cambricon are the easy ones,
because their device plugins already handle device discovery and mounting without a separate runtime component.

## Installing HAMi

```bash
# Label the nodes to manage; NVIDIA's device plugin looks for gpu=on by default
kubectl label nodes <node-name> gpu=on

# Add the repository
helm repo add hami-charts https://project-hami.github.io/HAMi/
helm repo update

# Install. NVIDIA works with the defaults; other vendors need their device switch
helm install hami hami-charts/hami -n kube-system
```

For a non-NVIDIA vendor, enable the matching switch and pin the scheduler image to your Kubernetes version:

```bash
helm install hami hami-charts/hami -n kube-system \
  --set scheduler.kubeScheduler.image.tag=<your Kubernetes version> \
  --set devices.mthreads.enabled=true
```

The chart picks a scheduler image matching the cluster's Kubernetes version automatically. To read the local version:

```bash
kubectl version -o jsonpath='{.serverVersion.gitVersion}'
```

## Parameters that decide slicing behaviour

These live in the `hami-scheduler-device` ConfigMap. They can be supplied through Helm, or edited in the
ConfigMap after installation and applied by restarting the relevant components.

| Parameter | Default | Meaning |
| --- | --- | --- |
| `nvidia.deviceSplitCount` | `10` | Maximum number of workloads sharing one card |
| `nvidia.deviceMemoryScaling` | `1` | Memory scaling ratio. Above 1 means overcommit: the reported value is physical memory multiplied by the ratio |
| `nvidia.deviceCoreScaling` | `1` | Compute scaling ratio, used the same way |
| `nvidia.memoryFactor` | `1` | The requested `nvidia.com/gpumem` value is multiplied by this. It has to be tuned on large-memory cards, see below |
| `nvidia.defaultMemory` | `0` | Memory used when none is requested; `0` means the whole card |
| `nvidia.defaultCores` | `0` | Compute share used when none is requested; `100` means exclusive |
| `nvidia.defaultGPUNum` | `1` | Card count filled in when only memory or compute was requested |
| `nvidia.migstrategy` | `none` | `none` ignores MIG; `mixed` allocates MIG devices as separate resources |
| `nvidia.disablecorelimit` | `false` | Set to `true` to turn the compute limit off |

The resource keys themselves are configurable too: `nvidia.resourceCountName`, `resourceMemoryName`,
`resourceMemoryPercentageName` and `resourceCoreName` map to the card count, memory, memory percentage and
compute keys.

:::warning memoryFactor is not optional on large-memory cards
Kubernetes caps extended resources at 32767. Resources such as `volcano.sh/vgpu-memory` are reported as integers,
so an A100 80 GB card hits that ceiling without scaling and the node's memory resource is computed wrongly. This
is exactly why the platform's built-in Volcano vGPU defaults its memory factor to 128 MiB.
:::

## Per-node configuration

When individual nodes need their own slice count or working mode, edit the `hami-device-plugin` ConfigMap and add
an entry for the node:

| Field | Meaning |
| --- | --- |
| `name` | Node name |
| `operatingmode` | `hami-core` or `mig`; defaults to `hami-core` |
| `devicememoryscaling` | Memory overcommit ratio for this node |
| `devicecorescaling` | Compute overcommit ratio for this node |
| `devicesplitcount` | How many workloads may share each card on this node |
| `filterdevices` | Device types not registered to HAMi |
| `uuid` / `index` | Device UUIDs or indices to ignore |

`operatingmode` and MIG are two descriptions of one decision: if the node's cards already carry MIG instances,
let HAMi work in MIG mode. Enabling both means the same card is allocated by two sets of logic.

## Verifying the install

```bash
# Scheduler and device plugin readiness
kubectl get pods -n kube-system | grep -E 'hami-scheduler|hami-device-plugin'

# Whether allocatable resources appeared on the node
kubectl get node <node-name> -o jsonpath='{.status.allocatable}' | tr ',' '\n' | grep -E 'nvidia.com|sh/vgpu'

# Device availability lives in a node annotation
kubectl get node <node-name> -o jsonpath='{.metadata.annotations.hami\.io/node-nvidia-register}'
```

Once all three line up, run a small pod that requests only memory and check inside the container whether
`nvidia-smi` reports the requested total. Seeing less than the host is the expected result.

## Upgrade and removal

- Upgrade with `helm upgrade hami hami-charts/hami -n kube-system`. If something fails to start, suspect the
  device plugin image version first; there is a known case of an environment variable rename breaking older images.
- Before removing, clear the pods that currently hold shared cards. Otherwise the device plugin leaves while the
  in-container library is still mounted, and restarts behave oddly.
- Kunlunxin vXPU had a known problem before v2.8.0, so do not stay on an older release on P800 nodes.
