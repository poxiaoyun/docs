# FAQ

## Quick reference

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| The node shows 10 vGPUs but one pod cannot get two on the same card | vGPU is a per-workload view, not an additive resource | By design. Raise the memory and compute share, or request two whole cards |
| `capacity` shows only `nvidia.com/gpu`, no `gpumem` | A device plugin advertises one resource per instance | Expected. Memory and compute live in the node annotations, under `hami.io/node-*-register` |
| `nvidia-smi` in the container shows less memory than the host | The control library took over the memory query | Expected. The quota is reported; the host shows the physical value |
| `nvidia.com/gpumem` is requested but not enforced | The limit is being bypassed | Work through "Why a limit does not apply" below |
| Container logs keep printing `[HAMI-core Warn(...)]` | Normal output from the control library | Ignore it, or set `LIBCUDA_LOG_LEVEL=0` to silence it |
| The card count on a node is wrong after installing HAMi | Two device plugins are registering the same resource | Disable the GPU Operator's device plugin, or stop the other slicing implementation |
| Changing the slot count has no effect on the node | The value is a device plugin startup argument | Redeploy the device plugin and confirm the pod was recreated |
| The resource key in the request cannot be found | The key came from a different vendor's documentation | Use the key the node actually reports, see [Supported devices & resource keys](/ecosystem/hami/device-matrix) |
| Whether Ascend and Hygon nodes need an extra runtime | It depends on the vendor plugin | Hygon and Cambricon plugins already handle discovery and mounting, so no |
| Containers under KubeVirt or Kata cannot get a card | Incompatible with direct device passthrough | Not supported today; a different approach is needed |
| Multi-GPU model serving will not start | HAMi version too old | Tensor parallelism needs `v2.9.0` or later |

## Ten vGPUs on a card versus two vGPUs for one pod

`deviceSplitCount: 10` means "this card can serve up to 10 workloads at once", not "this card is cut into 10
additive resources".

- A vGPU is a **view** of the same physical card inside different workloads. It changes visibility, not capacity.
- Requesting `nvidia.com/gpu: 2` asks for two **physical cards**, not two vGPUs on one card.
- The GPU UUID seen inside the container matches the physical card's UUID on the node, which confirms the point.

To give one workload more compute, raise `nvidia.com/gpucores` and `nvidia.com/gpumem` to the values it needs
rather than requesting more vGPUs.

## Why a limit does not apply

In rough order of frequency:

1. The container sets `CUDA_DISABLE_CONTROL=true`. This is the easiest one to miss, because it is commonly used
   to get past a startup error.
2. The workload runs inside Docker-in-Docker, where processes never pass through the injected layer.
3. The application calls the GPU driver API directly, bypassing the CUDA library.
4. `nvidia-container-runtime` is not the default runtime on the node, so the control library never enters the container.

The check is direct: look at the total memory `nvidia-smi` reports inside the container. Matching the quota means
the library is active; matching the physical amount means it is not.

## How HAMi, Volcano vGPU and vendor plugins relate

All three manage GPU resources, but with different keys and different use cases.

| | Resource keys | Scheduled by | Best for |
| --- | --- | --- | --- |
| HAMi main route | `nvidia.com/gpu`, `nvidia.com/gpumem`, `nvidia.com/gpucores` | HAMi's scheduler extender | Memory- and compute-precise slicing, plus card and model filtering |
| Volcano vGPU | `volcano.sh/vgpu-number`, `-memory`, `-cores` | Volcano's `deviceshare` plugin | Clusters already on Volcano, needing slot sharing only |
| Vendor plugins | The vendor's own extended resource keys | Depends on cluster configuration | Whole-card allocation with no sharing |

Coexistence rules:

- HAMi and NVIDIA's official device plugin **are not recommended together**; both register `nvidia.com/gpu` and
  will conflict.
- HAMi and Volcano vGPU **can coexist in principle**, but running only one is recommended.
- Volcano vGPU and NVIDIA's official device plugin **can coexist in principle**, because the keys do not overlap.
  The platform's built-in NVIDIA scheduling package is exactly this combination.

## Multi-node, multi-GPU distributed training

Supported, with clear boundaries:

- One pod can use **several cards on the same node**.
- One pod **cannot span nodes**.
- Crossing nodes means several pods coordinated by a distributed framework (PyTorch, TensorFlow, Horovod and so
  on), communicating over NCCL or RDMA.

So multi-node, multi-GPU means a set of pods in Kubernetes, not one large pod. Multi-GPU workloads also need gang
scheduling so that either every card is acquired or none is started. That layer belongs to Volcano's gang plugin,
not to HAMi.

## Combining with the platform's built-in route

The platform's NVIDIA scheduling package already bundles the Volcano vGPU device plugin, which uses the
`volcano.sh/vgpu-*` keys. It is a peer of the HAMi main route, not a layer beneath it. Three points:

1. For NVIDIA card sharing alone, the built-in route is enough and nothing else needs installing.
2. A full HAMi is only needed for non-NVIDIA sharing, or for memory-precise slicing on NVIDIA.
3. When installing a full HAMi, turn off GPU virtualization in the platform package and settle the ownership of
   `nvidia.com/gpu`.

The item-by-item comparison and the full sequence are under
[Platform support](/ecosystem/hami/platform-support).
