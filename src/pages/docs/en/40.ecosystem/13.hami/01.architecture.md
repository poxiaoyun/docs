# Architecture & scheduling

HAMi does not replace the Kubernetes scheduler. It inserts two stages into the existing flow: an admission webhook
that rewrites the pod's scheduler name, and a scheduler extender that adds device-level filtering and scoring.
The actual assignment is carried out by the node-side device plugin and the in-container library.

## The four components

| Component | Runs on | Responsibility |
| --- | --- | --- |
| HAMi MutatingWebhook | Control plane | Scans the pod's `resources`. If every resource entry is CPU, memory or a resource HAMi recognises, it sets the pod's `schedulerName` to `hami-scheduler` |
| HAMi Scheduler | Control plane | Acts as the scheduler extender: picks the node, then the device slot, and keeps a cluster-wide view of heterogeneous devices |
| `hami-device-plugin` | Every device node | Reads the scheduling result from the pod annotations, maps the device into the container, and periodically writes device availability back to the node |
| HAMi-Core | Inside the container | Enforces the memory and compute limits. This is the layer that makes a limit actually apply |

The webhook only touches pods that request HAMi resources. Everything else keeps using the default scheduler,
so installing HAMi does not change cluster-wide scheduling behaviour, only the pods asking for shared cards.

## How a pod reaches a device

1. The pod is submitted; the admission webhook intercepts it, inspects its resources, rewrites `schedulerName`
   and fills in defaults where needed.
2. `hami-scheduler` takes over: node policy first, then device policy to pick the card and the slot.
3. The result is written into the pod's annotations.
4. The device plugin on the target node reads the annotations, mounts the device and installs the resource
   control library during container setup.
5. The library takes effect at container start: memory allocations beyond the request are rejected, compute
   beyond the share is throttled.

Node and device policy are two independent layers, each choosing between packing and spreading:

| Setting | Values | Meaning |
| --- | --- | --- |
| `scheduler.defaultSchedulerPolicy.nodeSchedulerPolicy` | `binpack` (default) / `spread` | Pack pods onto nodes already in use, or spread them across nodes |
| `scheduler.defaultSchedulerPolicy.gpuSchedulerPolicy` | `binpack` / `spread` (default) / `mutex` | Share one card, spread across cards, or only use completely idle cards |

A single pod can override both through annotations without changing the global settings.

## How device information reaches the scheduler

The Kubernetes device plugin interface advertises one resource per plugin instance, so device memory and compute
cannot be advertised alongside the card count in `capacity`. HAMi splits the information across several channels:

| Information | Channel | Where it shows up |
| --- | --- | --- |
| Card count | Standard device plugin registration | `nvidia.com/gpu` appears in the node's `capacity` and `allocatable` |
| Memory, compute, model, NUMA, health | Node annotations | Annotation `hami.io/node-nvidia-register`, a JSON array whose entries carry `id`, `count`, `devmem`, `devcore`, `type`, `numa`, `mode` and `health` |
| Device exclusion and filtering | Annotations | `nvidia.com/use-gpuuuid`, `nvidia.com/nouse-gputype` and similar, turned into scheduling constraints by the webhook |

So seeing only `nvidia.com/gpu` in `capacity`, with no `nvidia.com/gpumem`, is by design rather than a broken
install. To find out how much memory a node has left, read the annotation, not `capacity`.

## Where the limits are enforced

On NVIDIA cards the mechanism is a library injected into the container:

- `/usr/local/vgpu/libvgpu.so` on the host enters the container through `/etc/ld.so.preload` and takes over the
  relevant CUDA calls.
- Memory: memory allocation calls are intercepted and fail once the request exceeds `nvidia.com/gpumem`, which
  the application sees as an out-of-memory condition.
- Compute: kernel launches pass through a token bucket that keeps actual usage within `nvidia.com/gpucores`.
- Monitoring: the library also takes over memory query calls, so `nvidia-smi` inside the container reports the
  quota rather than the physical amount.

Two boundaries come with this design and should be part of the selection decision:

- **Workloads that bypass the CUDA library are not managed.** Calling the driver API directly, or running inside
  Docker-in-Docker, avoids the intercepted layer.
- **Isolation is weaker than MIG.** It is user-space interception rather than hardware partitioning, so
  multi-tenant noise isolation is best-effort.

If a container sets `CUDA_DISABLE_CONTROL=true`, the library is disabled entirely. That switch exists for
troubleshooting and should not stay in a production configuration.

## Choosing between vGPU and MIG

| | HAMi vGPU | NVIDIA MIG |
| --- | --- | --- |
| Hardware requirement | Any NVIDIA card, driver v440 or later | Ampere and newer architectures, such as A100, H100, A30 |
| Isolation mechanism | User-space library interception | Hardware engine partitioning |
| Memory limit | Soft, at the CUDA API level | Hard, enforced by hardware |
| Compute limit | Soft, throttled inside the library | Hard, separate SM partitions |
| Granularity | 1 MiB of memory, 1% of compute | Fixed MIG profiles such as 1g.10gb |
| Reconfiguration | Supported, no node drain needed | Requires rewriting the MIG profile |
| Noise isolation | Best-effort | Strong |

Choose vGPU when the card does not support MIG or the workload needs a flexible memory size; choose MIG when
hard isolation is a compliance or SLA requirement. HAMi also supports dynamic MIG through `mig-parted`, and the
`hami.io/vgpu-mode` annotation lets a single pod pick `hami-core` or `mig`.

## Relationship to other schedulers

| Counterpart | Relationship |
| --- | --- |
| `kube-scheduler` | Coexists. HAMi is a scheduler extender and only takes over pods the webhook has renamed |
| Volcano | Two ways to combine. Use `volcano-vgpu-device-plugin` for Volcano's `deviceshare`; or use the HAMi main path with Volcano handling queues and preemption while HAMi handles in-card sharing |
| Koordinator | Install HAMi-Core on the nodes, request resources by HAMi's keys, and let Koordinator schedule |
| Kueue, KAI Scheduler | The other project handles queuing or scheduling and reuses HAMi-Core for isolation |

The official documentation describes four ways to reach a device: HAMi, HAMi-DRA, Volcano vGPU and KAI Scheduler.
The latter three schedule on their own but still rely on HAMi-Core for isolation.

KubeVirt and Kata Containers are not compatible today, because they rely on virtual machines for isolation while
HAMi's device plugin passes devices through directly. Do not assume container experience carries over to them.
