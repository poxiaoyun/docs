# Platform support

There is exactly one HAMi component on the platform: `volcano-vgpu-device-plugin` `v1.11.1`, bundled in the
NVIDIA scheduling package (`scheduler-nvidia`). It is not a partial HAMi. It is the complete implementation of the
Volcano vGPU route, which HAMi's own documentation lists as one of four ways to reach a device. What is missing is
not completeness within that route, but **the other routes**.

## What ships today

| Item | Value |
| --- | --- |
| Package | `plugins/system/scheduler-nvidia`, chart version `1.0.0`, appVersion `1.12.1` |
| HAMi component inside | `volcano-vgpu-device-plugin`, image tag `v1.11.1` |
| Installed alongside | NVIDIA GPU Operator `v23.6.0`, Volcano `1.12.1` |
| Hardware covered | NVIDIA only |
| Upstream | HAMi's `Project-HAMi/volcano-vgpu-device-plugin`; isolation comes from HAMi-Core |

Every setting the platform exposes in this package maps onto a per-node setting in HAMi:

| Platform setting | HAMi equivalent | Platform default |
| --- | --- | --- |
| Slots per card | `deviceSplitCount` | `10` |
| Memory conversion factor | `memoryFactor` / `gpuMemoryFactor` | `128` MiB |
| `operatingmode` in per-node config | `operatingmode` | `hami-core` |
| `devicememoryscaling` in per-node config | `deviceMemoryScaling` | `1` |
| `migstrategy` in per-node config | `migstrategy` | `none` |

Scheduling is wired up as well: the Volcano scheduler configuration enables the `deviceshare` plugin with
`deviceshare.VGPUEnable: true`, and the binpack plugin counts `volcano.sh/vgpu-number` among its resource weights.
The vGPU switch also depends on Volcano, so turning Volcano off while leaving vGPU on makes the package refuse to
install.

## What the built-in route can do

| Capability | Notes |
| --- | --- |
| Share one card among several workloads | 10 slots per card by default, adjustable |
| Request by slot, memory, memory percentage or compute | All four resource keys are available |
| Memory overcommit | `devicememoryscaling` above 1 reports more than the physical amount |
| Per-node overrides | Individual nodes can set their own slot count, conversion ratio or MIG strategy |
| Metrics | The monitor container in the device plugin exposes metrics on port `9394`; the PodMonitor is on by default with a 30-second interval |
| Queuing, binpacking and preemption by resource key and count | Handled by Volcano, so quotas and billing follow the resources |

## What the built-in route cannot do

Everything below requires a full HAMi installation.

| Missing capability | Consequence |
| --- | --- |
| In-card sharing for non-NVIDIA vendors | AMD, Cambricon, Moore Threads, MetaX, Biren, Iluvatar and Kunlunxin are whole-card only on the platform |
| The `nvidia.com/gpumem` / `gpucores` resource keys | Manifests written against HAMi's documentation cannot request resources |
| Filtering by card UUID or model | Workloads cannot be pinned to particular cards or kept off a model |
| Node-level and card-level binpack / spread / mutex policies | The platform's packing is Volcano's binpack plugin, which does not reach down to the card |
| Runtime preemption priority | There is no in-card preemption such as `nvidia.com/priority` |
| HAMi WebUI | No graphical view of slot usage per card |

## The two routes use different resource keys

On the platform, one NVIDIA card has two request paths, because two components register different keys:

| Registered by | Resource keys | Meaning |
| --- | --- | --- |
| GPU Operator's device plugin | `nvidia.com/gpu` | Whole cards; one card counts as one |
| `volcano-vgpu-device-plugin` | `volcano.sh/vgpu-number`, `-memory`, `-memory-percentage`, `-cores` | Slots |

The keys do not overlap, which is why they coexist on the same node. It is also why the platform can use whole
cards and slots at the same time out of the box.

A full HAMi behaves differently: `hami-device-plugin` registers `nvidia.com/gpu`, the same key the GPU Operator's
device plugin uses. HAMi's documented remedy is to disable that plugin:

```yaml
devicePlugin:
  enabled: false
```

So installing a full HAMi on the platform forces a choice: keep the whole-card `nvidia.com/gpu` path, in which
case HAMi's `gpumem` and `gpucores` are out; or hand the whole-card path to HAMi, in which case the GPU Operator's
device plugin is disabled. Keeping both only works when the keys do not overlap.

:::warning Do not stack two slicing implementations on one node
The platform's `vGPU.enabled` and a full HAMi are two implementations of slot-based sharing. With both active on
one node, two device plugins each maintain their own view of the cards, the slot arithmetic drifts, and
diagnosing which one allocated a device becomes guesswork. Turn the old one off before switching routes.
:::

## Manual sequence for a full HAMi

1. **Pick the route first.** For NVIDIA card sharing alone, the built-in route is enough; do not install anything else.
   A full HAMi is only needed for non-NVIDIA sharing, or for memory-precise slicing on NVIDIA.
2. **Clear the field.** Turn off GPU virtualization in the platform's NVIDIA scheduling package so it does not
   compete for the same cards.
3. **Release the resource key.** Disable the GPU Operator's device plugin and hand `nvidia.com/gpu` to HAMi.
   DCGM Exporter is unaffected and keeps reporting physical-level counters.
4. **Install the vendor device plugin.** Some come from HAMi, others from the vendor's own toolkit:

   | Vendor | Device plugin source |
   | --- | --- |
   | AMD | HAMi's `amd-device-plugin` |
   | Huawei Ascend | HAMi's `ascend-device-plugin` |
   | Kunlunxin | HAMi's `vxpu-device-plugin` (P800-OAM only) |
   | Biren | HAMi's `biren-device-plugin`, node label `biren=on` |
   | Hygon | `dcu-vgpu-device-plugin` |
   | Cambricon | The vendor's `cambricon-device-plugin`, configured with `mode=dynamic-smlu` |
   | Moore Threads | The vendor's MT CloudNative Toolkits |
   | MetaX | The vendor's MetaX GPU Operator or GPU Extensions |
   | Iluvatar | The vendor's `gpu-manager`; do not install `gpu-admission` by mistake |

5. **Install HAMi.** One Helm command, with the matching device switch enabled.
6. **Define the flavor on the platform.** Use the resource keys HAMi reports rather than the ones the platform used before.

Existing flavors do not need to be deleted. When the two sets of keys do not clash they can coexist, and workloads
pick whichever path they need.

## Checking that it is wired up correctly

```bash
# The platform's built-in device plugin
kubectl get pod -n volcano-system | grep volcano-device-plugin

# A full HAMi's scheduler and device plugin
kubectl get pod -n kube-system | grep -E 'hami-scheduler|hami-device-plugin'

# Remaining capacity under each set of keys
kubectl get node <node-name> -o jsonpath='{.status.allocatable}' | tr ',' '\n' \
  | grep -E 'nvidia.com|volcano.sh/vgpu'
```

Seeing both `nvidia.com/gpu` and `volcano.sh/vgpu-number` on a node means both paths are running, which is the
default state of the platform's built-in route. If the `nvidia.com/gpu` count does not change after installing a
full HAMi, the GPU Operator's device plugin is still enabled and HAMi's plugin has not taken over.
