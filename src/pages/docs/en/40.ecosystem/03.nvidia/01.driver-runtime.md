# Drivers & Container Runtime (NVIDIA)

Everything on this page happens on every machine that has a GPU: install the driver so the host recognises the card,
then install the container toolkit (`nvidia-container-toolkit`) so containers can see it too. The check for the first
step is simple — `nvidia-smi` prints the card and driver version.

The driver is the base software the operating system needs to use the card; without it the system only knows a piece of
hardware is plugged in. The container toolkit is the adapter between card and container: workloads run in containers, so
without this layer a container cannot reach the device.

:::info The container toolkit can be left to the GPU Operator
The platform's GPU Operator component **installs the container toolkit automatically** and by default **does
not install the host driver** (it reuses the driver already on the node). When you install from the platform,
you only need the "install the driver" part of this page; the toolkit part is for manual deployments and
troubleshooting.
:::

## Before you start

- Confirm the machine has a GPU and that the operating system is compatible with the target driver version.
- Have the **driver installer** (`.run` format) or the system package source ready on the machine.
- Have **root** access and the ability to install build tools and kernel headers (`gcc`, `make`, `kernel-devel` / `linux-headers`).
- Make sure nothing on the machine depends on a graphical desktop using the NVIDIA driver — stop the graphical session first if one exists.

## Part 1 — Install the host driver

### 1. Check whether a driver is already installed

```bash
nvidia-smi
```

- It prints the GPU list, driver version and CUDA version: the driver is installed, skip to "Verify".
- It reports `command not found`, or `couldn't communicate with the NVIDIA driver`: not installed or not loaded, continue below.

Also confirm the hardware is present:

```bash
lspci | grep -i nvidia
```

### 2. Install dependencies

CentOS / openEuler:

```bash
yum install -y gcc make dkms kernel-headers-$(uname -r) kernel-devel-$(uname -r)
```

Ubuntu / Debian:

```bash
apt install -y build-essential dkms linux-headers-$(uname -r)
```

`dkms` rebuilds the driver automatically after a kernel update. Without it you get the classic "driver works
until the kernel is upgraded, then fails to load" situation.

### 3. Blacklist the open-source nouveau driver

The `nouveau` driver shipped with most distributions competes with the official NVIDIA driver for the device
and must be blacklisted:

```bash
echo -e "blacklist nouveau\noptions nouveau modeset=0" > /etc/modprobe.d/blacklist-nouveau.conf
dracut --force          # Ubuntu / Debian use: update-initramfs -u
reboot
```

After the reboot, confirm it is gone (no output means success):

```bash
lsmod | grep nouveau
```

### 4. Install the driver

If an older driver is present, remove it with the bundled uninstaller first:

```bash
# Remove an old driver (the script exists only in the install directory)
/usr/bin/nvidia-uninstall

# Install
chmod +x NVIDIA-Linux-<arch>-<version>.run
./NVIDIA-Linux-<arch>-<version>.run --silent --dkms
```

| Flag | What it does |
| --- | --- |
| `--silent` | Non-interactive install, suitable for batch rollouts |
| `--dkms` | Register with DKMS so the driver is rebuilt after kernel upgrades |
| `--no-opengl-files` | Install compute files only, no graphics libraries. **Recommended on compute-only machines** to avoid clashing with an existing graphical environment |

### 5. Reboot as prompted

```bash
reboot
```

## Part 2 — Install the container toolkit

Skip this part when installing the GPU Operator from the platform.

```bash
# 1) Configure the repository (follow the installation notes shipped with your package)
# 2) Install
yum install -y nvidia-container-toolkit        # Ubuntu / Debian: apt install

# 3) Point the container engine at the NVIDIA runtime — containerd or Docker
nvidia-ctk runtime configure --runtime=containerd
nvidia-ctk runtime configure --runtime=docker

# 4) Restart the container engine
systemctl daemon-reload && systemctl restart containerd
```

:::warning Restarting the container engine affects running workloads
`systemctl restart containerd` restarts every container on the node. **Confirm the node can be taken out of
service**, or do it outside business hours.
:::

## Verify

### 1. The host can use the card

```bash
nvidia-smi
```

The output normally shows the **driver and CUDA version** (top right), the **card model and count**, memory
usage, utilization, and the processes currently using each card. All cards listed with no errors means the
driver loaded successfully.

### 2. A container can use the card

```bash
docker run --rm --gpus all nvidia/cuda:12.2.0-base-ubi8 nvidia-smi
```

Seeing the same card list as the host means the container toolkit is configured. On containerd clusters you do
not pass `--gpus`; the GPU Operator device plugin injects the device and driver interfaces when the Pod starts.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| `nvidia-smi` cannot communicate with the driver | Driver not installed, or not rebooted after install | Confirm the installer reported success, reboot, then retry |
| The installer says a driver is already running | An old driver or nouveau is still loaded | Run `nvidia-uninstall`, and blacklist `nouveau` per step 3 |
| The installer complains about missing kernel headers | `kernel-devel` / `linux-headers` do not match the running kernel | Check `uname -r` and install the **exact matching** header package |
| The driver stops working after a kernel upgrade | Installed without `--dkms` | Reinstall with `--dkms`, or rebuild after each kernel upgrade |
| `nvidia-smi` inside a container finds no device | Container toolkit missing, or the engine was not restarted | Check that `nvidia-ctk runtime configure` ran and the engine was restarted |
| A machine with a desktop environment goes black after installing | Graphics and compute drivers conflict | Reinstall with `--no-opengl-files` and stop the graphical session first |

:::warning Driver and CUDA versions must match
The driver version determines the highest CUDA version it supports. **A workload image must not require a CUDA
version above that limit**, or the container fails with a CUDA initialization error. Check the `CUDA Version`
shown at the top right of `nvidia-smi`, or consult the
[NVIDIA compatibility table](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html).
:::
