# Device plugin (k8s-device-plugin)

The device plugin **registers the GPUs on a node as Kubernetes resources**: it discovers the cards, runs
health checks, and tells the cluster "this machine has these many usable cards". Only after registration can a
workload request a card declaratively.

Think of it as **issuing an ID card to each GPU**: the card is just hardware plugged into a machine until
registration gives it a cluster-recognised identity, and only then does the scheduler know which machine still
has a free card.

## When it is required

- **Whole-card scheduling**: one Pod owns one card.
- **Shared scheduling**: with vGPU enabled, one card is split across Pods (see [Volcano & vGPU Splitting](/ecosystem/nvidia/volcano-vgpu)).
- **Model-based scheduling**: pinning workloads to a specific model using node labels.

It is deployed together with the GPU Operator and is **never installed on its own**.

## Platform defaults

These are already set at install time. Use the table to check whether the observed behaviour is expected:

| Setting | Default | Purpose |
| --- | --- | --- |
| `PASS_DEVICE_SPECS` | `true` | Passes device specs (model, memory) into the container so the workload can read them |
| `FAIL_ON_INIT_ERROR` | `true` | Fails the Pod on an initialisation error instead of degrading silently. **Prevents the "Pod runs but has no GPU" false positive** |
| `DEVICE_LIST_STRATEGY` | `envvar` | Passes the allocated devices to the container through environment variables; a prerequisite for working with vGPU |
| `DEVICE_ID_STRATEGY` | `uuid` | Identifies devices by GPU UUID. More stable than index-based ordering, so cards do not shift after a reboot or swap |
| `NVIDIA_VISIBLE_DEVICES` | `all` | Lets the plugin see every card on the node, then trim by scheduling result |
| `NVIDIA_DRIVER_CAPABILITIES` | `all` | Enables all driver capabilities inside the container (compute, utility, video, …) |

:::info Why UUID instead of index
Index-based allocation refers to "card 0" as enumerated by the driver at start-up. That order can change after
a reboot, a card swap or a reseat, and workloads end up on a different card. A UUID is the card's identity
number, so it stays stable across reboots.
:::

## Verify

### 1. Check the plugin Pods

```bash
kubectl get pod -n gpu-operator -o wide | grep device-plugin
```

One Pod per GPU node, status `Running`.

### 2. Check the node resources

```bash
kubectl get node <gpu-node> -o jsonpath='{.status.allocatable}' | tr ',' '\n' | grep nvidia
kubectl describe node <gpu-node> | grep nvidia.com/gpu
```

`nvidia.com/gpu: 8` under `Capacity` means this machine has eight cards available to the cluster.

### 3. Run an end-to-end smoke test

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: gpu-smoke-test
spec:
  containers:
    - name: cuda
      image: nvidia/cuda:12.2.0-base-ubi8
      command: ["nvidia-smi"]
      resources:
        limits:
          nvidia.com/gpu: 1
  restartPolicy: Never
```

```bash
kubectl apply -f gpu-smoke-test.yaml
kubectl logs gpu-smoke-test
```

Card information in the logs means the whole chain — scheduling through device injection — works.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| Pods run but no resource name appears on the node | Container toolkit not ready, or the plugin failed to initialise | Read `kubectl logs -n gpu-operator <device-plugin-pod>`; with `FAIL_ON_INIT_ERROR=true` it exits outright on failure |
| Only some nodes show the resource | Those nodes have no driver, or lack the expected labels | Run `nvidia-smi` on those nodes and check the `nvidia.com/gpu.present` label |
| Pods requesting `nvidia.com/gpu` stay Pending | No free card, or a wrong resource name / count | `kubectl describe node <gpu-node>` for the remaining count; check the resource name spelling under `limits` |
| Fewer cards than physically present | Some cards were given to MIG or vGPU | See [MIG instance partitioning](/ecosystem/nvidia/gpu-operator/mig-manager) and [Volcano & vGPU Splitting](/ecosystem/nvidia/volcano-vgpu) |
| No `nvidia-smi` inside the container | The workload image does not ship that command | Use an official base image such as `nvidia/cuda:*-base-*`, or install the driver utilities yourself |
| A multi-card Pod takes a long time to start | The cards span several NUMA nodes | Configure NUMA affinity (the platform's Volcano already enables the numa-aware plugin) |

:::warning Do not mix whole-card and shared requests
Never request the same card both as a whole `nvidia.com/gpu` and as a vGPU share. **Mixing them causes memory
over-allocation (OOM).** If you want sharing, use the vGPU resource names consistently.
:::
