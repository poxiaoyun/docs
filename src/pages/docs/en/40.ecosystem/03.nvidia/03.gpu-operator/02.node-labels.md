# Where node labels come from (NFD / GFD)

A scheduler standing in the corridor **can only read the number plate; it cannot see what is inside the room**.
Node labels are those number plates: they state whether a machine has a GPU, which model it is and how much
memory it has. The device plugin and the MIG Manager use them to decide which nodes they manage, and you can
use them to pin workloads to a specific model.

These labels are written automatically by two components inside the GPU Operator; you do not set them by hand:

| Component | Labels it writes | Where the data comes from |
| --- | --- | --- |
| **NFD** (Node Feature Discovery) | `feature.node.kubernetes.io/*` — whether the node has NVIDIA devices, the OS release, kernel features | Walks the node's PCI devices and system information |
| **GFD** (GPU Feature Discovery) | `nvidia.com/*` — GPU model, memory, driver and CUDA version, MIG capability | Reads GPU information through the driver API |

A simple way to remember it: **NFD answers "is there a device of this brand in the room", GFD answers "which
model, how much memory"**. GFD depends on NFD being ready, which is why NFD comes first in the install order.

## Common labels

### Model and capacity

| Label | Meaning | Example |
| --- | --- | --- |
| `nvidia.com/gpu.present` | Whether the node has usable GPUs | `true` |
| `nvidia.com/gpu.product` | Card model | `NVIDIA-A100-SXM4-80GB` |
| `nvidia.com/gpu.machine` | Server model | `PowerEdge-R750` |
| `nvidia.com/gpu.count` | Number of cards | `8` |
| `nvidia.com/gpu.memory` | Memory per card (MB) | `81920` |
| `nvidia.com/gpu.family` | Architecture generation | `ampere` / `hopper` |
| `nvidia.com/gpu.compute.major` / `.minor` | Compute capability | `8` / `0` |

### Driver and runtime versions

| Label | Meaning |
| --- | --- |
| `nvidia.com/cuda.driver.major` / `.minor` | Host driver version |
| `nvidia.com/cuda.runtime.major` / `.minor` | Highest CUDA runtime version the driver supports |

These two are handy for bulk-checking whether workload images match the driver's CUDA support.

### MIG related

| Label | Meaning |
| --- | --- |
| `nvidia.com/mig.capable` | Whether this card supports MIG partitioning |
| `nvidia.com/mig.config` | The profile **you declare** (for example `all-1g.10gb`); see [MIG instance partitioning](/ecosystem/nvidia/gpu-operator/mig-manager) |
| `nvidia.com/mig.config.state` | Progress of that profile as executed by the MIG Manager; `success` means it is partitioned |

### Generic node features

| Label | Meaning |
| --- | --- |
| `feature.node.kubernetes.io/pci-10de.present` | Whether the node has NVIDIA PCI devices (`10de` is NVIDIA's vendor ID) |
| `feature.node.kubernetes.io/system-os_release.ID` | Operating system identifier (for example `ubuntu`, `centos`) |

## Using the labels

### 1. Inspect the GPU labels of a node

```bash
kubectl get node <gpu-node> --show-labels | tr ',' '\n' | grep -E "nvidia|feature"
```

### 2. Pin workloads to a specific model

Set the model label in the resource pool or workload node selector, for example A100 only:

```yaml
spec:
  nodeSelector:
    nvidia.com/gpu.product: NVIDIA-A100-SXM4-80GB
```

### 3. Confirm the device plugin really found the cards

The device plugin filters nodes by labels such as `nvidia.com/gpu.present`. If the labels exist but the
resource name does not, the problem is usually the container toolkit rather than the labels — follow
[Device plugin](/ecosystem/nvidia/gpu-operator/device-plugin) for the check order.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| No `nvidia.com/*` labels at all on the node | GFD is not running, or the host driver is broken | Check `kubectl get pod -n gpu-operator \| grep gpu-feature-discovery`, then run `nvidia-smi` on the node |
| `feature.node.*` labels exist but no `nvidia.com/*` labels | NFD is fine, GFD is not | Read the GFD Pod logs; usually a driver/GDF version mismatch |
| The model in the label differs from the installed card | Cards were swapped, or the label was edited by hand | Restart GFD to re-detect; do not edit these labels by hand, they are overwritten |
| Changed `nvidia.com/mig.config` but the state is not `success` | The card does not support that profile, or jobs are still using the cards | Verify the supported geometries; test on an idle node first |

:::warning Labels are detection results, not settings
Except for MIG's `nvidia.com/mig.config`, which **you write and the component reads**, all labels are detected
by the components. Editing them with `kubectl label` achieves nothing — the next detection pass overwrites them.
:::
