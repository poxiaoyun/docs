# MIG instance partitioning

MIG (Multi-Instance GPU) is NVIDIA's **hardware-level partitioning** method: it splits one card into several
**fully isolated** instances, each with its own memory and compute slices, so they cannot disturb each other.
It fits the case "several small jobs must coexist and require strong isolation".

Think of it as **rebuilding one large office into several rooms with real walls**: the walls physically exist,
so noise from next door never reaches you.

:::info MIG is off by default on the platform
The MIG Manager only acts when you **put a declaration label on a node**. By default every card is used as a
whole card. Follow this page when you actually need partitioning.
:::

## MIG or vGPU?

| | MIG (this page) | [vGPU](/ecosystem/nvidia/volcano-vgpu) |
| --- | --- | --- |
| Level of splitting | Hardware | Software (injected shared library plus memory isolation) |
| Isolation | Strong, hardware-isolated instances | Moderate, compute and memory limits enforced in software |
| Sizing | Fixed geometries (for example 1g.10gb, 2g.20gb) | Requested per job by share count or memory amount |
| Manual preparation | Yes, declare a profile first | No, the plugin splits on demand |
| Best for | Strong isolation, multi-tenant coexistence | Varying sizes, high utilization |

:::warning Pick one per environment
Running MIG and vGPU at the same time conflicts (the available geometries and memory accounting no longer line
up). **Choose one route before installing.**
:::

## Hardware support

MIG is only available on some models. The profiles bundled with the platform cover:

| Model | Available geometries (name → memory / instances) |
| --- | --- |
| A30 | `1g.6gb` → 6144MB × 4; `2g.12gb` → 12288MB × 2; `4g.24gb` → 24576MB × 1 |
| A100 40GB | `1g.5gb` → 5120MB × 7; `2g.10gb` → 10240MB × 3; `3g.20gb` → 20480MB × 2; `7g.40gb` → 40960MB × 1 |
| A100 80GB | `1g.10gb` → 10240MB × 7; `2g.20gb` → 20480MB × 3; `3g.40gb` → 40960MB × 2; `7g.79gb` → 80896MB × 1 |

Whether other models are supported, and with which geometries, depends on the card itself — the node advertises
this through the `nvidia.com/mig.capable` label.

## Steps

### 1. Confirm the card supports MIG

```bash
kubectl get node <gpu-node> -L nvidia.com/mig.capable
```

Nodes showing `true` can be partitioned.

### 2. Declare the profile

Label the node with the profile you want:

```bash
# Split everything into 1g.10gb (A100 80GB)
kubectl label node <gpu-node> nvidia.com/mig.config=all-1g.10gb --overwrite
```

Frequently used values:

| Value | Meaning |
| --- | --- |
| `all-<geometry>` | Partition **every** card on the node with that geometry (for example `all-2g.20gb`) |
| `all-balanced` | Let the component pick a balanced profile among the supported ones |
| `all-disabled` | Stop partitioning and return to whole cards |

### 3. Wait for partitioning to finish

```bash
kubectl get node <gpu-node> -L nvidia.com/mig.config,nvidia.com/mig.config.state
```

When `state` becomes `success` the cards are partitioned. The process **resets those cards**, which interrupts
any job currently using them, so do it while the node is idle.

### 4. Confirm the resources are registered

```bash
kubectl get node <gpu-node> -o jsonpath='{.status.allocatable}' | tr ',' '\n' | grep mig
```

Resource names such as `nvidia.com/mig-1g.10gb: 7` appear on the node. A workload requests one like this:

```yaml
resources:
  limits:
    nvidia.com/mig-1g.10gb: 1
```

## Reverting to whole cards

```bash
kubectl label node <gpu-node> nvidia.com/mig.config=all-disabled --overwrite
```

Once `state` returns to `success`, the `nvidia.com/mig-*` resources disappear and `nvidia.com/gpu` comes back.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| Label set but `state` stays `pending` | The card does not support that geometry, or jobs are still using the cards | Verify the profile name; make sure no Pod on the node is using a GPU |
| `nvidia.com/gpu` disappears after labelling | Expected: the cards now belong to MIG instances | Request `nvidia.com/mig-*` resources; revert with `all-disabled` to go back |
| A job reports "out of memory" although the instance size looks sufficient | The job's request exceeds that geometry | Use a larger geometry, or switch to [vGPU](/ecosystem/nvidia/volcano-vgpu) for on-demand sizing |
| Only some cards should be partitioned | The label applies to the whole node | Move the cards to be partitioned onto their own node; the granularity is the node |
| Monitoring shows more cards after partitioning | Expected: each MIG instance reports its own metrics | Read the metrics per instance |

:::warning Partitioning resets the cards
After labelling, every card on the node is reset and re-partitioned, so **running jobs are interrupted**.
Validate the profile on an idle node first in production.
:::
