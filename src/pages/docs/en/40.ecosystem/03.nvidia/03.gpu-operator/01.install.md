# Install & Verify

Installing the components is only the first step; confirming they are correct is the real work. "Deployed" in System
Apps does not mean the cards can be scheduled. The real proof is that an allocatable resource name appears on the node.

## Before you start

- Every GPU node has the driver installed and `nvidia-smi` shows the cards.
- The cluster's Kubernetes and container runtime versions are supported; note the runtime type (the default install assumes `containerd`).
- If you want monitoring, the Prometheus Operator is present; otherwise disable the ServiceMonitor option during install.
- **Air-gapped clusters**: sync the images below to a registry the cluster can pull from first.

### Images to prepare

| Purpose | Image |
| --- | --- |
| GPU Operator itself | `nvcr.io/nvidia/gpu-operator:v23.6.0` |
| Node feature discovery | `registry.k8s.io/nfd/node-feature-discovery:v0.13.1` |
| Container toolkit | `nvcr.io/nvidia/k8s/container-toolkit:v1.13.4-ubuntu20.04` |
| Device plugin | `nvcr.io/nvidia/k8s-device-plugin:v0.14.1-ubi8` |
| Node GPU labels | `nvcr.io/nvidia/gpu-feature-discovery:v0.8.1-ubi8` |
| Monitoring | `nvcr.io/nvidia/k8s/dcgm-exporter:3.1.8-3.1.5-ubuntu20.04` |
| MIG partitioning | `nvcr.io/nvidia/cloud-native/k8s-mig-manager:v0.5.3-ubuntu20.04` |
| Volcano scheduler and controller | `vc-scheduler` / `vc-controller-manager` / `vc-webhook-manager` / `vc-agent`, all tagged `v1.12.1` |
| Volcano vGPU device plugin | `volcano-vgpu-device-plugin:v1.11.1` |

## Steps

### 1. Choose the install entry point

Go to **Cluster Management → select the target cluster → Operations → System Apps**, click **Create system app**
and pick the **NVIDIA scheduling component** template (the GPU Operator + Volcano + Volcano vGPU bundle
described in this section).

If the cluster already has the Ascend scheduling components installed, **do not install a second scheduler**:
one cluster keeps a single set of scheduling components.

### 2. Check the key settings

| Setting | Suggested value | Notes |
| --- | --- | --- |
| Cluster hardware type | NVIDIA | Decides which scheduling component bundle is installed |
| Container runtime | Match the node (default `containerd`) | A mismatch makes the device plugin fail to find the runtime |
| Install driver via GPU Operator | Leave off | Keep it off when nodes already have a driver, so host kernel modules are untouched |
| DCGM Exporter | On | The platform's accelerator dashboards depend on its metrics |
| Create ServiceMonitor | On when a Prometheus Operator exists | Otherwise the install blocks on the missing CRD |
| GPU virtualisation (vGPU) | On when several jobs must share a card | Details in [Volcano & vGPU Splitting](/ecosystem/nvidia/volcano-vgpu) |
| Image registry | Company registry for air-gapped clusters | The platform rewrites the image prefix for all components; no need to set them one by one |

### 3. Wait for the components to become ready

The install creates two namespaces and brings up the components:

```bash
kubectl get pod -n gpu-operator
kubectl get pod -n volcano-system
```

`gpu-operator` holds the operator itself, node feature discovery, the container toolkit, the device plugin and
the monitoring exporter; `volcano-system` holds the scheduler, the controller and — when vGPU is enabled — the
vGPU device plugin. They are DaemonSets and Deployments, so **each GPU node gets its own device plugin Pod**.

## What changes once it is installed

This is the part that proves "the cards really joined the cluster". Check each row:

| What to look at | Command | Expected result |
| --- | --- | --- |
| Device plugin Pod | `kubectl get pod -n gpu-operator -o wide \| grep device-plugin` | One per GPU node, status `Running` |
| New node resource | `kubectl get node <gpu-node> -o jsonpath='{.status.allocatable}'` | The output contains `nvidia.com/gpu` |
| Card count | `kubectl describe node <gpu-node> \| grep nvidia.com/gpu` | Matches the number of usable cards on the node |
| Node GPU labels | `kubectl describe node <gpu-node> \| grep nvidia.com/gpu.product` | Shows the specific model |

Once the resource name appears, a workload can request a card like this:

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

If the node still has a free card, such a Pod schedules successfully — that is the final proof.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| Device plugin Pod stuck in `CrashLoopBackOff` | Container toolkit not ready, or wrong runtime type | Check `kubectl logs -n gpu-operator <device-plugin-pod>`; make sure the runtime type matches the node |
| `nvidia.com/gpu` never appears on the node | Host driver missing, or `nouveau` still holds the device | Run `nvidia-smi` and `lsmod \| grep nouveau` on the node |
| Resource name exists but Pods fail to start on that node | The image's CUDA version exceeds what the driver supports | Lower the image's CUDA version, or upgrade the host driver |
| Validator Pod reports failure | A sub-component is not ready | `kubectl logs -n gpu-operator <validator-pod>` shows which step failed |
| Accelerator dashboards show no GPU data | DCGM Exporter disabled, or no ServiceMonitor | Check `kubectl get svc -n gpu-operator \| grep dcgm` and whether a Prometheus Operator exists |
| After uninstall and reinstall the device plugin will not start | Leftover `nvidia` mounts and directories on the node | Clean up the node leftovers per NVIDIA's uninstall guide, then reinstall |

:::warning Shutdown order when upgrading the driver
Before upgrading the host driver, stop workloads and **stop the components in reverse order**: the device
plugin and vGPU device plugin first, then the monitoring exporter, and only then the driver. Leaving them
running tends to produce "half-read old driver" problems.
:::
