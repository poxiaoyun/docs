# Volcano & vGPU Splitting

Volcano handles multi-card scheduling; vGPU handles sharing one card among several jobs. On the platform, multi-card
jobs are not placed by the default Kubernetes scheduler but handed to Volcano, and sharing a card among jobs goes
through Volcano's vGPU capability.

A way to picture it: Volcano is the building manager handing out offices, and vGPU is a movable partition that divides
one large office into workstations. The partition can be adjusted at any time, and the desk goes back into the pool
when the job leaves.

## What Volcano solves

The default Kubernetes scheduler looks at one job at a time, so it stalls on requests like "all four cards or
nothing". Volcano adds:

| Capability | What it solves |
| --- | --- |
| Gang scheduling | A multi-card job either gets all its cards or does not start, so it never holds half and waits |
| Queues and fair share | Quotas per queue when teams share a cluster, so nobody starves |
| Preemption | A higher-priority job can make a lower-priority one step aside |
| Bin packing | Packs jobs onto fewer nodes, leaving whole machines free for large jobs |
| NUMA awareness | Keeps multi-card jobs inside one NUMA domain to avoid cross-socket memory traffic |
| Device sharing | Supports vGPU resources so one card can serve several jobs |

## How vGPU splits a card

vGPU works through **the scheduler side (the deviceshare plugin) together with the node-side device plugin**:
the node advertises a number of shares per card, and the scheduler allocates by share. By default each card is
split into **10 shares**, and memory is accounted in units of **128 MiB**.

| Resource name | Meaning |
| --- | --- |
| `volcano.sh/vgpu-number` | Number of vGPU shares to request |
| `volcano.sh/vgpu-memory` | Memory quota to request (MiB) |
| `volcano.sh/vgpu-memory-percentage` | Memory requested as a percentage of the whole card |
| `volcano.sh/vgpu-cores` | Compute to request (percentage) |

## Platform defaults

| Setting | Default | Notes |
| --- | --- | --- |
| Volcano version | `1.12.1` | Namespace `volcano-system` |
| Shares per card | `10` | One card can serve up to ten jobs at once |
| Memory factor | `128` | Unit in MiB |
| Per-node overrides | Empty | Add entries only when individual nodes need a different share count or MIG policy |
| vGPU monitoring | On | The device plugin exposes metrics on `9394`, scrape interval `30s` |
| Scheduler actions | Enqueue, allocate, backfill, reclaim, preempt | Active as soon as the scheduler starts |

The device plugin runs as a DaemonSet on GPU nodes and receives the split parameters as start-up arguments
(`--device-split-count` and `--gpu-memory-factor`), so **changing the share count means redeploying the
DaemonSet**.

## Requesting a shared card

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: vgpu-demo
spec:
  containers:
    - name: cuda
      image: nvidia/cuda:12.2.0-base-ubi8
      command: ["nvidia-smi"]
      resources:
        limits:
          volcano.sh/vgpu-number: 1      # one share
          volcano.sh/vgpu-memory: 3000   # 3000 MiB of memory
          volcano.sh/vgpu-cores: 50      # 50% of compute
```

Requesting only `volcano.sh/vgpu-number` also works; memory and compute fall back to their defaults. Add all
three when you need finer control.

## Per-node overrides

When some nodes need their own share count, memory scaling or MIG policy, add entries under the node-specific
configuration of the install:

```yaml
nodeConfig:
  - name: gpu-node-01
    operatingmode: hami-core      # sharing mode
    devicememoryscaling: 1.8      # memory scaling: reported = actual × factor
    devicesplitcount: 10          # shares per card on this node
    migstrategy: none             # MIG policy for this node
```

- A `devicememoryscaling` above 1 **over-commits memory** (it reports more than physically exists). Useful for
  jobs with low memory footprints, but be aware of what happens when several jobs really do fill the card.
- `migstrategy` covers the same ground as [MIG instance partitioning](/ecosystem/nvidia/gpu-operator/mig-manager).
  **Enable it in one place only.**

## Verify

```bash
# device plugin and its monitor
kubectl get pod -n volcano-system -o wide | grep volcano-device-plugin
# vGPU resources on the node
kubectl get node <gpu-node> -o jsonpath='{.status.allocatable}' | tr ',' '\n' | grep vgpu
```

`volcano.sh/vgpu-number` appearing on the node means the split was advertised successfully.

## Troubleshooting

| Symptom | Likely cause | What to do |
| --- | --- | --- |
| The node shows `nvidia.com/gpu` but no `volcano.sh/vgpu-*` | vGPU not enabled, or the device plugin is not running | Enable GPU virtualisation in the scheduling component; check the device plugin Pod in `volcano-system` |
| Pods requesting `volcano.sh/vgpu-number` stay Pending | All shares are taken, or the request exceeds one share's limits | `kubectl describe node <gpu-node>` for remaining shares; lower `vgpu-memory` / `vgpu-cores` |
| `nvidia-smi` inside a job shows more memory than requested | Inherent to software-level isolation: the limit is enforced by the injected shared library | Expected; switch to [MIG](/ecosystem/nvidia/gpu-operator/mig-manager) when hardware isolation is required |
| Changed the share count but the node did not change | The value lives in the DaemonSet and must be re-deployed | Re-deploy the component and confirm the device plugin Pod was recreated |
| The scheduler version differs from the Ascend cluster's | Each component bundle carries its own Volcano version | Keep a single set of scheduling components per cluster; do not mix |
| Multi-card jobs run slower with low CPU utilization | Cards spread across NUMA nodes | Keep the numa-aware plugin enabled (the platform enables it by default) |

:::warning Shares are not hard isolation
vGPU enforces compute and memory limits **in software**, so isolation is weaker than MIG. For production jobs
sensitive to interference, prefer [MIG instance partitioning](/ecosystem/nvidia/gpu-operator/mig-manager).
:::
