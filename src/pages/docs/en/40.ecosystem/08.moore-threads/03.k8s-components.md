# Kubernetes Components

The cluster-side pieces ship as one bundle called **MT GPU Operator**, currently v2.1.0, with the Helm chart file named `mt-gpu-operator-2.1.0.tgz`. It supports Kubernetes 1.19 through 1.32 and offers full and core install modes. After installing, the cluster gains two CRDs: `ClusterConfig` (`mthreads.com/v1alpha4`) and `ClusterPolicy` (`mthreads.com/v1beta2`). Component switches and settings such as the resource name live on those two objects.

| Component | Purpose | What breaks without it |
| --- | --- | --- |
| `mt-device-plugin` | Registers cards as Kubernetes resources | No `mthreads.com/gpu` on the node, so jobs cannot request a card |
| `mt-universal-gpu-device-controller` | Device allocation and admission control | Scenarios that allocate devices by policy do not work |
| `mt-gpu-feature-discovery` | Labels nodes with card model, driver version and similar | Nothing to select nodes by when you want a specific model |
| `mt-container-toolkit-daemonset` | Rolls the container toolkit out to nodes | Containers cannot see the card |
| `mt-operator-validator` | Post-install self check | You end up checking every item by hand when something fails |
| `mt-gpu-webhook` | Admission and device injection for sGPU | sGPU split resources cannot get through |
| `mt-gpushare-scheduler` | In-card shared scheduling | Sharing one card across several jobs is unavailable |

## Where to get the packages

The components are not open source. The MooreThreads GitHub organisation has no device-plugin or operator repository, the packages ship with the KUAE cloud native suite, and **there is no public Helm repo**.

:::warning Ask the vendor for the package first
`helm repo add` does not apply here. The component package and chart come from the vendor, and you should ask for the matching notes for your driver and Kubernetes version at the same time. Do not take a same-named chart from a third-party mirror; a version mismatch is hard to diagnose.
:::

## Resource names the device plugin reports

By default there is one whole-card resource:

```
mthreads.com/gpu
```

Ask for as many cards as you need:

```yaml
resources:
  limits:
    mthreads.com/gpu: 2
```

To rename it, change the `gpuResourceName` field on `ClusterPolicy`, for example to `example.com/MTT-S5000-80G`. The resource name the node reports changes with it, so specs and quotas on the platform must be rebuilt under the new name; existing specs do not follow automatically.

## Monitoring

| Component | Port / path | Notes |
| --- | --- | --- |
| `mt-dcgm` | hostPort 5555 | hostengine, the collection service |
| `mt-dcgm-exporter` | `/metrics` on port 9400 | Exposes the metrics, default collection interval 10s |

Metric names keep the `DCGM_FI_*` prefix, and there are additional MTLink-specific metrics. Port 9400 is the same default as the NVIDIA DCGM Exporter, so when both vendors are present in one cluster, change one of them, otherwise the data gets mixed up in dashboards downstream.

:::warning mt-gpu-exporter in older documents
`mt-gpu-exporter` is no longer supported as a product. New clusters should go straight to `mt-dcgm` plus `mt-dcgm-exporter`.
:::

## Sharing one card

Two routes exist and they hand out different things, so do not plan them together:

| Route | How it splits | Resource name / form | When to use |
| --- | --- | --- | --- |
| sGPU | In-cluster split, compute by time-slice weight, memory in 512MiB units | `mthreads.com/sgpu-core`, `mthreads.com/sgpu-memory` | Several jobs in the cluster sharing one card |
| MT vGPU | Host-side hardware split, mdev / SR-IOV, type name `mtgpu-1101` | Device nodes, **not Kubernetes resource names** | Cases needing hardware-level isolation; stated as supported on S4000 and S5000 |

sGPU needs the GPU scheduler and webhook enabled (`mt-gpushare-scheduler` and `mt-gpu-webhook` from the table above), and both resources must be requested together:

```yaml
resources:
  limits:
    mthreads.com/sgpu-core: <time-slice weight>
    mthreads.com/sgpu-memory: <in 512MiB units>
```

sGPU gives exclusive memory and weighted time sharing, **not strong isolation**, so do not plan requirements for independent memory and fault isolation on top of it.

Separately, the resource name `mthreads.com/vgpu` appears in HAMi setups. HAMi's official documentation lists
`mthreads.com/sgpu-memory` (one unit per 512 MB) and `mthreads.com/sgpu-core` alongside it, and notes that these
capabilities have only been validated on MTT S4000, so do not carry them over to other models. That route also
disallows multi-card sharing: only one card can be shared in a pod. See [HAMi](/ecosystem/hami).

## Relationship to Volcano

No official Volcano plugin for Moore Threads was found. `mt-gpu-scheduler` and `mt-gpushare-scheduler` are the vendor's own scheduling components, and **their relationship to Volcano is unconfirmed**.

:::info This one goes to the vendor
If you want Volcano and the Moore Threads scheduling components in one cluster, ask the vendor whether the two conflict and which one owns in-card splitting. There is no conclusion to give here, and it is not safe to assume the generic path where the device plugin reports a standard extended resource and Volcano schedules on the resource name.
:::

## Verify after install

```bash
# The node reports a schedulable Moore Threads resource
kubectl describe node <gpu-node> | grep -A 5 "Allocatable" | grep mthreads.com

# The component pods are running
kubectl get pods -A | grep -i mt-

# The monitoring components are running
kubectl get pods -A | grep -i dcgm

# Both CRDs are present
kubectl get crd | grep mthreads.com
```

Then submit a minimal job requesting 1 card and run `mthreads-gmi` inside the container. If it prints the card, the whole chain works.
