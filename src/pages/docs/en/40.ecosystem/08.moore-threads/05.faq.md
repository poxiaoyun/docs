# FAQ

## Quick reference

| Symptom | Check first | Action |
| --- | --- | --- |
| `mthreads-gmi` is not found | Whether the driver package is installed | Install `sgpu-dkms`, then confirm the `mtgpu` kernel module is loaded |
| `mthreads-gmi` runs but lists no card | Kernel module and device nodes | Check the kernel version against the official docs, reinstall the driver |
| The host sees the card, containers do not | Container toolkit on the node | Check the status and logs of `mt-container-toolkit-daemonset` |
| No `mthreads.com/gpu` on the node | Whether `mt-device-plugin` is running | Confirm driver and toolkit are fine first, then restart the plugin |
| Cannot find a download for the cluster components | Whether the components are open source | They are not; get the package from the KUAE cloud native suite through the vendor |
| sGPU resource requests never satisfy | Scheduler and webhook switches | Enable the GPU scheduler and webhook, i.e. `mt-gpushare-scheduler` and `mt-gpu-webhook` |
| No card metrics in platform monitoring | Whether the collectors are installed | Install `mt-dcgm` and `mt-dcgm-exporter` and scrape `/metrics` on port 9400 |
| The metrics port clashes with NVIDIA | The listening port of both exporters | Both default to 9400, so change one in a shared cluster |
| The spec name carries a long prefix | The model string inside the resource name | The platform does not strip Moore Threads prefixes, this is expected |
| Multi-card jobs queue for a long time | Whether whole cards are held by someone | The platform has no in-card split template, so jobs queue by whole cards |

## Why is there nowhere to install Moore Threads components

System Apps bundles only the NVIDIA and Ascend hardware scheduling sets. Moore Threads cluster components come from a vendor package and are installed by hand. This is not a configuration problem but the current product boundary, and the item-by-item comparison is on [Platform support](/ecosystem/moore-threads/platform-support).

## Why can the package not be downloaded

The MooreThreads GitHub organisation has no device-plugin or operator repository. The packages ship with the KUAE cloud native suite and there is no public Helm repo, so `helm repo add` goes nowhere and the vendor is the only source.

:::warning Do not substitute a same-named chart
Do not use a same-named chart from a third-party mirror. The version pairing with driver and Kubernetes will not match, and problems become very hard to trace.
:::

## Which route splits one card across jobs

The two routes hand out different things:

- **sGPU**: split inside Kubernetes, with resource names `mthreads.com/sgpu-core` and `mthreads.com/sgpu-memory`. Compute follows time-slice weight and memory is counted in 512MiB units. Memory is exclusive, compute is time-shared, and it is not strong isolation.
- **MT vGPU**: the hardware route, mdev / SR-IOV on the host, type name `mtgpu-1101`, stated as supported on S4000 and S5000. It produces device nodes rather than Kubernetes resource names, so no resource spec can be built against it on the platform.

The `mthreads.com/vgpu` name seen in HAMi setups is a third thing again, with `mthreads.com/sgpu-memory` and
`mthreads.com/sgpu-core` alongside it. HAMi's documentation notes it has only been validated on MTT S4000, and
multi-card sharing is not supported on that route. See [HAMi](/ecosystem/hami).

## Can Volcano schedule Moore Threads cards

Short answer: this one is not confirmed. No official Volcano plugin for Moore Threads was found, and `mt-gpu-scheduler` and `mt-gpushare-scheduler` are the vendor's own scheduling components whose relationship to Volcano is not documented either.

So do not reason from the generic path where the device plugin reports a standard extended resource and Volcano schedules on the resource name. Ask the vendor whether the two conflict and which owns in-card splitting. Since multi-card scheduling on the platform depends on Volcano, until that is settled, build specs and quotas around whole cards.
