# Platform Support

Recognising a card on the platform runs through four places in the code, each responsible for one thing. This page lists the actual state of each for Moore Threads, so that when something is missing from the UI you know whether it is misconfigured or simply not there yet.

## Layer-by-layer check

| Layer | Location | Current state for Moore Threads |
| --- | --- | --- |
| Image accelerator type | The accelerator option when registering an image | **Registered**: `Musa(摩尔线程)` |
| Model metadata backend enum | `hardware_backends` in the model metadata | **Present**: `musa` |
| Model metadata model names | The accelerator model picker on a model card | **No Moore Threads model is registered** |
| Accelerator label on specs | The wording shown on the spec label | **Generic path**: shows `GPU`, with no dedicated label |
| Model name on specs | Spec name composition | **The prefix is not stripped**. The platform only strips prefixes for nvidia / amd / intel / huawei |
| Vendor icon on specs | The small icon on the spec label | **Missing**. There is no Moore Threads icon |
| Cluster scheduling components | Cluster Management → Operations → System Apps | **Missing**. Only the NVIDIA and Ascend sets ship with the platform |

## What works today

- **Image metadata**: an image can be registered as `Musa(摩尔线程)`, and search and filtering pick it up.
- **Model metadata**: `musa` is present in `hardware_backends`, so filtering models by backend finds them; the model picker has no MTT models, so a specific card cannot be selected.
- **Resource specs**: build specs against the `mthreads.com/gpu` resource name the node reports. Quotas and job requests both go through that name.
- **Compute scheduling**: once the device plugin is installed on a node and reports the resource name, quotas, specs and job requests work on the platform side without further changes.

## What does not work yet

| Missing capability | Impact | How to fill the gap |
| --- | --- | --- |
| One-click install of cluster components | Nothing to install from System Apps, so the package is a manual job | Get the package from the vendor as described in [Kubernetes components](/ecosystem/moore-threads/k8s-components) |
| Model names in model metadata | Model cards cannot select something like MTT S5000 | Spell it out in the model description for now, until the platform adds the model table |
| Prefix stripping for model names | The model string inside the resource name shows up verbatim in the spec name | Keep custom resource names short, or check the display name by hand |
| Vendor icon | No Moore Threads icon on the spec label | A display-layer matter, scheduling is unaffected |
| Dedicated accelerator label | The label only says the generic `GPU`, not MTT | Same |

## Full manual onboarding sequence

System Apps has no Moore Threads entry, so the early steps all happen outside the platform:

1. Get the MT GPU Operator package from the vendor: `mt-gpu-operator-2.1.0.tgz` plus the matching notes. There is no public Helm repo, so this step cannot be skipped.
2. On every machine with a card, install MT Linux Driver (`sgpu-dkms`) and MT Container Toolkit (`mt-container-toolkit`). `mthreads-gmi` must list the card.
3. Install the Operator in the cluster, choosing full or core mode as needed, and confirm `mthreads.com/gpu` appears on the node.
4. If you want monitoring, install `mt-dcgm` and `mt-dcgm-exporter` and wire the `/metrics` endpoint on port 9400 into Prometheus.
5. Back on the platform, build resource specs and quotas against the resource name, then submit a job requesting 1 card to prove it works.

Step 5 is the only place the platform UI is touched; the first four steps are all on machines and in the cluster.
