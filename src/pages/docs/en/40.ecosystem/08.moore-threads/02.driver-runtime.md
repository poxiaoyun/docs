# Drivers & Container Runtime

This page covers the host layer only, not Kubernetes. The cluster-side components are on [Kubernetes components](/ecosystem/moore-threads/k8s-components).

The install is done when `mthreads-gmi` lists the card. Until that passes, every cluster component above it is wasted effort.

## Prerequisites

| Item | Requirement |
| --- | --- |
| Operating system | A distribution matching the target driver version; use the official compatibility list |
| Kernel driver | MT Linux Driver, kernel module `mtgpu`, package `sgpu-dkms` |
| Hardware | Card seated, power and cooling within spec. S4000 is rated 450 W and PCIe 5.0 |
| Privileges | Driver install, toolkit install and module loading need root or sudo |

## Install the driver

The driver ships in the same release set as the MUSA SDK. What you install is the DKMS package `sgpu-dkms`, after which the `mtgpu` kernel module builds against your kernel. Four steps:

1. On the official docs site, find the driver version that matches your operating system and kernel version. Driver and MUSA SDK are a matched pair, so do not upgrade one alone.
2. Add the software source or download the offline package as the docs describe, then install `sgpu-dkms`.
3. Load the `mtgpu` kernel module and confirm it loads at boot.
4. Run `mthreads-gmi`. If it lists the card, the host layer is done.

:::warning Commands follow the current official version
The exact install commands for the driver and the MUSA SDK are not reproduced here, because everything beyond the package name (source URL, version string, kernel header dependency) changes between releases and distributions. Check the install chapter at `https://docs.mthreads.com` and substitute current values.
:::

## Container toolkit

Workloads in the cluster run in containers, so the host seeing the card is not enough. On the Moore Threads side this layer is **MT Container Toolkit**, package `mt-container-toolkit`. After installing it, two environment variables control what a container sees:

| Variable | Purpose |
| --- | --- |
| `MTHREADS_VISIBLE_DEVICES` | Selects which cards are visible in the container |
| `MTHREADS_DRIVER_CAPABILITIES` | Selects which driver capabilities are injected into the container |

How the device is injected is up to the toolkit, and a node running containerd takes different configuration from one running Docker. Follow the container toolkit chapter in the official cloud native docs.

:::tip Pinning a job to specific cards
Do not reconfigure the whole host for one job. Check first whether `MTHREADS_VISIBLE_DEVICES` can narrow the range, and use the official container chapter for the exact way to pass it in.
:::

## Verify

```bash
mthreads-gmi
```

The output carries the card model, driver version and memory usage. Keep the whole block when troubleshooting; the first question you will be asked is the driver version.

Verifying the container layer depends on whether the image carries MUSA user space. Pick an image with the toolkit, run the example from the official docs once, and if the card shows up inside the container this layer is done too.

## Upgrade and uninstall

- Stop workloads first, then stop `mt-device-plugin` and the monitoring components on the cluster side. The device plugin polls the driver interface, so upgrading the driver underneath a running plugin tends to leave it reporting the wrong card count, recoverable only by restarting the plugin.
- Driver and MUSA SDK move together. When the MUSA version in a workload image is too far from the host driver, you get missing library errors at runtime.
- Uninstalling means removing the `sgpu-dkms` package. Before installing a new version, confirm no old kernel module is left behind, otherwise the new module may fail to load.
