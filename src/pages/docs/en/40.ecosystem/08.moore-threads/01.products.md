# Products & Software Stack

## Product line

The data centre line runs from MTT S2000 up to MTT S5000. The workstation and consumer line is MTT S80 / S70 / S50 plus X300.

| Model | Segment | Notes |
| --- | --- | --- |
| MTT S5000 | Data centre | Current flagship |
| MTT S4000 | Data centre | 48 GB GDDR6, 768 GB/s, 450 W, PCIe 5.0; stated to support hardware virtualisation and SR-IOV isolation |
| MTT S3000 | Data centre | |
| MTT S2000 | Data centre | Previous generation |
| MTT S80 | Workstation & consumer | Desktop and graphics workstations, not part of data centre selection |
| MTT S70 | Workstation & consumer | Same |
| MTT S50 | Workstation & consumer | Same |
| X300 | Workstation & consumer | Same |

The vendor does not split the line into training cards and inference cards, and calls the whole range full-function GPUs. Do not ask whether a card is for training or for inference; the question lands on the memory, interconnect and virtualisation capability of a specific model instead. Full specifications are at `https://mthreads.com/product/category/gpu`.

## Software stack layers

MUSA is one name covering several layers. Install them in order, because a missing layer breaks everything above it:

| Layer | Components | Installed on | Purpose |
| --- | --- | --- | --- |
| Kernel driver | MT Linux Driver (kernel module `mtgpu`, package `sgpu-dkms`) | Host | Lets the operating system see the card |
| Management library and CLI | MTML (`libmtml.so`), `mthreads-gmi` | Host | Inspect cards, topology and memory usage |
| Container toolkit | MT Container Toolkit (package `mt-container-toolkit`) | Host | Hands the device to containers |
| Compilers and migration | MUSA SDK: compiler `mcc`, migration tools `musify` and `musify-text`, `muPTI` | Host or image | Compile MUSA code, move CUDA code over |
| Operator and math libraries | muDNN, muBLAS, muFFT, muSOLVER, muSPARSE, muRAND, muPP, MUSA-X | Host or image | Operator dependencies for workload images |
| Communication library | MCCL | Host or image | Collective communication between cards |
| Framework ports | torch_musa, torchada, vllm-musa, SGLang-MUSA, TensorFlow-MUSA | Workload image | Run frameworks on MUSA |
| Cluster components | MT GPU Operator v2.1.0 and its components, see [Kubernetes components](/ecosystem/moore-threads/k8s-components) | Kubernetes cluster | Registers the card as a schedulable resource |

Names fall into two families: `mu` prefixes the operator and math libraries, `mt` prefixes the management tools and cluster components. `musify` and `musify-text` move CUDA code to MUSA, so when an image fails to build, check whether that step was done first.

## Version policy

This chapter pins no versions. Driver, MUSA SDK, container toolkit and cluster components ship as a matched set, and the official docs give the combinations, so follow those. Working backwards from a model number to a driver version does not work, so use the docs site for compatibility.

| What you need | Where to look |
| --- | --- |
| Products and models | `https://mthreads.com/product/category/gpu` |
| Documentation home | `https://docs.mthreads.com` |
| Cloud native and cluster components | `https://docs.mthreads.com/cloud-native/cloud-native-doc-online/` |
| Developer community and SDK | `https://developer.mthreads.com` |
| Corporate site | `https://www.mthreads.com` |

:::tip Confirm the model before planning any splitting
Hardware virtualisation is not on every model. S4000 and S5000 are stated to support hardware virtualisation, flexible GPU partitioning and SR-IOV isolation. Do not plan an MT vGPU layout around any other model; ask the vendor for the virtualisation support list first.
:::
