# Kubernetes Components

The cluster side is essentially one device plugin plus node labels. Monitoring and split scheduling both have gaps, described plainly below.

## Component overview

| Component | Role | Status |
| --- | --- | --- |
| Device plugin `k8s-device-plugin` | Registers cards as Kubernetes resources | Official repository archived; image is `ghcr.io/birentechnology/k8s-device-plugin:v0.7.1` |
| Node labels | Mark nodes that carry Biren cards | Official plugin uses `birentech.com=gpu`, the HAMi route uses `biren=on` |
| Monitoring exporter | Exposes card metrics to Prometheus | Official exporter name and port unconfirmed |
| In-card splitting | Cut one card into several instances | Uses official SVI, which must be configured on the card beforehand |

## Device plugin repository and archive status

The repository is `https://github.com/BirenTechnology/k8s-device-plugin`. It is archived: the last commit was on 2024-10-17 and the latest tag is v0.7.3. Archived means upstream takes no more updates and will not fix anything for a new kernel or a new container runtime.

Current distribution appears to have moved to a vendor delivery package, and third-party material mentions a component named `op-adrm-device-plugin` inside it. That is third-party evidence only and has not been verified officially, so confirm the actual component name in your delivery package before installing.

:::warning Treat the archived repository image as a reference only
The repository is archived, and the `v0.7.1` image is the community form. Which version production clusters use comes from the delivery manifest. Do not mix the community example image with the components in the delivery package either, since their node labels differ.
:::

## Reported resource names

| Resource name | Meaning |
| --- | --- |
| `birentech.com/gpu` | Whole card |
| `birentech.com/1-2-gpu` | One share after splitting into 2 |
| `birentech.com/1-4-gpu` | One share after splitting into 4 |

To request whole cards, put the count in the value:

```yaml
resources:
  limits:
    birentech.com/gpu: 1
```

To request a split share, change the resource name to the matching suffix:

```yaml
resources:
  limits:
    birentech.com/1-2-gpu: 1
```

To see which resource names a node actually offers, read its Allocatable:

```bash
kubectl describe node <NODE_NAME> | grep -A 5 "Allocatable" | grep birentech.com
```

## Node labels

```bash
kubectl label node <NODE_NAME> birentech.com=gpu
```

The HAMi route uses `biren=on`, which is not the same set. Pick the label that matches the plugin actually installed; label it wrongly and the plugin will not treat the node as a Biren node.

## Monitoring status

`brsmi` is a confirmed command line tool, but it is not a metrics exporter. It offers command line queries on the node and does not expose Prometheus-format metrics.

| Item | Status |
| --- | --- |
| Prometheus exporter name | Not published officially |
| Default port | Not published officially |
| Command line tool | `brsmi`, confirmed to exist, not an exporter |
| Third-party lead | suDCGM, described in third-party material as a `br-dcgmd` server plus a `br-dcgmi` client on default port 8182, not verified officially |

The conclusion: there are no Biren card metrics in platform monitoring for now. To connect them you first have to confirm where the exporter actually comes from. If you cannot find it, do not connect one, and do not guess an address from a third-party port and paste it into a ServiceMonitor.

## SVI splitting

The official name for sharing one card is **SVI (Secure Virtual Instance)**, and a BR106 supports up to 4 independent secure virtual instances. The result maps to the two resource name suffixes: split into 2 uses `birentech.com/1-2-gpu`, split into 4 uses `birentech.com/1-4-gpu`.

SVI is like a cinema box: it has to be partitioned on the card before the audience arrives. Instances must be configured on the card in advance, and the device plugin only reports resources for instances that already exist; it does not create them at scheduling time. A node without pre-configured SVI reports whole cards only.

The third-party HAMi route is more restrictive: it cannot specify memory size, and can only split a card into 2 or 4 shares.

## Relation to Volcano

The platform hands multi-card jobs to Volcano, but Biren has no official Volcano plugin. Volcano's built-in vGPU capability supports only HAMi-core (CUDA interception) and NVIDIA MIG, and neither covers Biren.

The practical route is HAMi: `Project-HAMi/biren-device-plugin` (image `projecthami/biren-device-plugin`).
HAMi only gained Biren support in v2.10.0, so check the cluster's HAMi version first. On that route the node label
is `biren=on`. Its matrix ticks neither memory nor compute isolation for Biren, so it can schedule shares that
were defined up front but cannot specify a memory size. Resource keys for the other vendors are compared under
[HAMi](/ecosystem/hami).

Without HAMi, a Biren card in the cluster is just a standard extended resource, and Volcano schedules by resource name and count. Multi-card jobs schedule fine; scheduling split jobs by share does not.

## Verifying the install

```bash
# the node label is present
kubectl get nodes -l birentech.com=gpu

# the node offers allocatable resources
kubectl describe node <NODE_NAME> | grep -A 5 "Allocatable" | grep birentech.com

# the device plugin pod is up
kubectl get pods -A | grep -i biren
```

Then submit one minimal job requesting 1 `birentech.com/gpu`; if `brsmi` prints the card inside the container, the path works.
