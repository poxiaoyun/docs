# Platform Support

The platform has several places that decide whether it recognises an accelerator, each responsible for one thing. The table below lists the actual state of each for Biren, so that a missing item in the UI does not have to be guessed at as a misconfiguration or as something that simply was never there.

## Layer-by-layer check

| Layer | Location | Current state for Biren |
| --- | --- | --- |
| Image accelerator type | The accelerator option when registering an image | No Biren entry; the options are CUDA / ROCm / CANN / DKT / MACA / CoreX / Musa / Neuware / CPU |
| Model metadata model | The accelerator model selectable on a model card | No Biren model registered |
| Model metadata backend enum | `hardware_backends` in model metadata | Not present; the list is cpu / cuda / rocm / ascend / mlu / musa / metal |
| Flavour accelerator label | The wording on a flavour label | Takes the generic path and shows `GPU` |
| Flavour model name | Flavour name assembly | The prefix is not stripped; the platform's prefix-stripping list covers only nvidia / amd / intel / huawei |
| Flavour vendor icon | The small icon on a flavour label | Not present |
| Cluster scheduling component | Cluster Management → Operations → System Apps | Not present; the platform bundles only NVIDIA and Ascend |

Nothing in this table is a misconfiguration. All seven are the current product state.

## What works today

- **Scheduling by resource name**: once a node reports `birentech.com/gpu`, platform quotas, flavours and job requests can all use that resource name.
- **Split cards schedule too**: define flavours for `birentech.com/1-2-gpu` and `birentech.com/1-4-gpu` and the platform will submit jobs against the matching resource name.
- **Multi-card jobs**: nodes report a standard extended resource, so the platform's multi-card jobs queue in Volcano as usual.
- **Container images**: register Biren images as generic images. The workload image carries the BIRENSUPA runtime itself, and the platform does not take part inside the image.

## What still does not work

| Missing capability | Impact | How to cover it |
| --- | --- | --- |
| Image accelerator type | No Biren choice when registering an image, and no such category in filtering or search | No platform-side entry today, so register as a generic image |
| Model metadata model | No Biren model selectable on a model card | The model is not in metadata, which does not affect actual scheduling |
| Backend enum | No Biren value in `hardware_backends` | Same as above |
| Flavour model name | The flavour name is not rendered as a short name such as `106M`; the prefix stays | The platform's prefix-stripping list does not include Biren, and this is a display-layer design choice |
| Flavour vendor icon | The flavour label carries a generic icon rather than a Biren one | Display-layer design, does not affect scheduling |
| Dedicated accelerator label | The label shows `GPU` and does not name Biren | Display-layer design, does not affect scheduling |
| One-click cluster component install | No Biren entry in System Apps, so it cannot be clicked | Install the device plugin by hand as described in [Kubernetes components](/ecosystem/biren/k8s-components) |
| Platform-side monitoring dashboard | Biren card metrics do not reach platform monitoring | The official exporter is unpublished, so nothing can be preset for now |

## Full manual connection sequence

The platform's System Apps has no Biren entry, so every step happens on the cluster side plus the platform resource layer:

1. Install the driver on every machine with a card until `brsmi` lists them all, with driver version ≥ 1.2.2.
2. Install the container runtime toolkit and confirm cards are visible inside containers; the CDI route requires kubelet ≥ 1.28 and containerd ≥ 1.7.
3. Install the device plugin in the cluster, label nodes with `birentech.com=gpu`, and confirm `birentech.com/gpu` appears.
4. If in-card splitting is needed, configure SVI on the card first, then confirm `birentech.com/1-2-gpu` or `birentech.com/1-4-gpu` appears.
5. If split scheduling by share is needed, switch to `Project-HAMi/biren-device-plugin` and change node labels to `biren=on`.
6. Back on the platform, define flavours and quotas against the resource names, then submit one job requesting 1 `birentech.com/gpu` to prove it.

Step 6 is the only one that touches the platform UI; the first five are all cluster-side.
