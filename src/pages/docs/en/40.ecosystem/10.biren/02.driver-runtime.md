# Drivers and Container Runtime

The host layer has one goal: get `brsmi` to list every card. Until that passes, no amount of work on the cluster-side device plugin will help.

## Prerequisites

| Item | Requirement |
| --- | --- |
| Driver version | ≥ 1.2.2, the minimum stated by the device plugin repository |
| Kubernetes | ≥ 1.13, required by the device plugin on the cluster side |
| CDI route | kubelet ≥ 1.28 and containerd ≥ 1.7, both needed when injecting devices through CDI |
| Operating system and firmware | No public support matrix from the vendor; take the delivery documentation as the source |

The first two come from the device plugin repository and are the hardest requirements that can be verified today. No public list covers operating system and firmware pairing, so do not extrapolate from another vendor's experience.

## Installing the driver

The driver install commands for Biren have not been verified in public official documentation, so this section describes the flow only. Take the actual commands from the current install guide in the developer community.

1. **Fix the baseline**: in the developer community, check which operating systems, cards and firmware versions the current driver supports, and line the three up before touching anything.
2. **Install the driver package on every machine with a card**: driver and firmware may ship separately; follow the order in the delivery package and do not skip steps.
3. **Load the kernel module**: after install, confirm the Biren device nodes appear and the kernel module is loaded.
4. **Reboot and re-check**: a driver install usually needs a reboot to take full effect; run `brsmi` again afterwards.

:::warning Take commands from the official developer community
The list above is a flow, not commands you can paste. Biren driver package names, install scripts and kernel module names change between versions, and this section does not copy commands from elsewhere. Open `https://developer.birentech.com/` and work through the install guide for the current version before starting.
Cluster nodes need one extra check: the driver may need rebuilding or reinstalling after a kernel upgrade, so never do a kernel upgrade and a driver upgrade in the same change window.
:::

## Container runtime toolkit

The device plugin supports injecting devices through CDI, and that route requires kubelet ≥ 1.28 and containerd ≥ 1.7. The name, package name and configuration paths of Biren's container runtime toolkit are not given directly in public official material, so they are unpublished; follow the delivery documentation.

Making cards visible inside containers normally takes two steps: install the vendor's container toolkit and generate the device specification, then have the container runtime reference it. Take the generation command and the specification file path from the delivery package, and do not reuse another vendor's paths.

## Verification

```bash
brsmi
```

`brsmi` (BR-SMI) is a confirmed command line tool that lists cards and basic status. Take the specific subcommands and output fields from the tool documentation in the developer community; this page does not list unverified flags.

Two checks decide whether the driver is in place: `brsmi` lists every card, and the number of cards listed matches the number installed. A missing card is usually not a driver problem, so check firmware and slots first.

## Upgrade and removal

Stop workloads first, then stop the cluster-side device plugin, and only then touch the driver. The device plugin polls the driver interface on a timer, and upgrading the driver with the plugin running tends to leave a state where the process is alive but reports the wrong card count, recoverable only by restarting the plugin.

The order between driver and firmware upgrades comes from the delivery documentation. Biren publishes no removal commands or package names, so remove according to the delivery guide, and do not delete kernel modules or device nodes by hand: deleting the wrong one makes the next load fail.
