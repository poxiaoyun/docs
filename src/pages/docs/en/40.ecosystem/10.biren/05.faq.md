# FAQ

## Quick reference

| Symptom | Check first | What to do |
| --- | --- | --- |
| `brsmi` cannot find the card | Whether the driver is installed, whether the device node exists | Reinstall the driver per the developer community docs and re-check after a reboot |
| Cards are listed but the count is wrong | Firmware and slots | Verify firmware against the delivery guide; a missing card is usually hardware |
| Cards not visible in a container | Container runtime toolkit and the CDI specification | Confirm kubelet ≥ 1.28 and containerd ≥ 1.7, then generate the device specification per the delivery guide |
| No `birentech.com/gpu` on the node | Device plugin pod and node label | Confirm the node carries `birentech.com=gpu`, then restart the plugin |
| Device plugin pod will not start | Image source | The community repository is archived; confirm the version in the delivery package |
| `birentech.com/1-2-gpu` requests stay Pending | Whether SVI is configured on the card | SVI must be configured in advance; the plugin does not create it |
| Splitting by memory size does not work | Which splitting route is in use | Official SVI splits only into 2 or 4; HAMi cannot specify memory either |
| Multi-card jobs queue for a long time | Whether whole cards are being held | Without SVI or HAMi, cards are scheduled whole |
| No Biren card metrics visible on the platform | Whether an exporter exists | `brsmi` is not an exporter, and the official exporter name and port are unpublished |
| Flavour label shows `GPU` rather than Biren | Platform display logic | Expected behaviour, does not affect scheduling |

## Why there is no Biren option on the platform

Biren is absent from the platform's current accelerator list: image accelerator types, model metadata models and the backend enum, and flavour vendor icons all lack it. This is not a missing configuration, it is the current product coverage.

What does work is the resource layer: whatever resource name a node reports, the platform can build flavours, quotas and jobs against it. So the whole Biren connection effort sits cluster-side, and the platform side only needs flavours keyed on resource names such as `birentech.com/gpu`. For the item-by-item comparison see [Platform support](/ecosystem/biren/platform-support).

## Can an archived device plugin repository still be used

Yes, but know the consequences. `https://github.com/BirenTechnology/k8s-device-plugin` had its last commit on 2024-10-17 and its latest tag is v0.7.3, and upstream no longer maintains it. An archived repository receives no updates, so there will be no fixed release for a new kernel or a new containerd version.

Current distribution appears to have moved to a vendor delivery package, and third-party material mentions a component named `op-adrm-device-plugin` inside it. That has not been verified officially. In practice: confirm the component name and version against the delivery manifest rather than copying the community example, and treat the community image `ghcr.io/birentechnology/k8s-device-plugin:v0.7.1` as a reference only.

## How does in-card splitting work, and can memory be specified

The official splitting mechanism is SVI (Secure Virtual Instance), and a BR106 supports up to 4 independent secure virtual instances. After splitting, nodes report `birentech.com/1-2-gpu` and `birentech.com/1-4-gpu`, corresponding to 2 and 4 shares.

Two things need saying up front:

- SVI instances must be configured on the card in advance; the device plugin does not create them at scheduling time. A node without them reports whole cards only, and requests for split resources stay Pending.
- The third-party HAMi route cannot specify memory size and can only split a card into 2 or 4 shares. Scenarios that need fine splitting by memory ratio are not supported on the current Biren path.

## How do Biren cards schedule in Volcano

Biren has no official Volcano plugin, so there are two cases:

- Without HAMi, the card is a standard extended resource and Volcano schedules by resource name and count. Multi-card jobs queue normally; in-card split scheduling is absent.
- To schedule split jobs by share, use third-party HAMi: `Project-HAMi/biren-device-plugin` together with HAMi's built-in biren device support. On that route the node label is `biren=on`, which is not the same set as the official plugin's `birentech.com=gpu`.

Volcano's built-in vGPU capability supports only HAMi-core (CUDA interception) and NVIDIA MIG, and neither covers Biren. Do not carry NVIDIA assumptions over here.
