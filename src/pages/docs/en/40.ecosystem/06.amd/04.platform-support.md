# Platform Support

Four places in the platform code take part in "recognising a card", each responsible for one thing. This page lists what
each of the four actually does with AMD today, so that a missing item in the UI is not mistaken for a misconfiguration
when it was never there.

## Layer by layer

| Layer | Where it lives | Current state for AMD |
| --- | --- | --- |
| Image accelerator type | The framework / accelerator option when registering an image | **Registered**: `ROCm(AMD)` |
| Model metadata card model | Accelerator card models selectable on a model card | **Registered**: MI210 / MI250 / MI250X / MI300A / MI300X / MI325X / MI350X / MI355X, 8 in total |
| Model name inside a spec | The spec name assembled from the resource name and model | **Supported**: when the model name starts with `amd` the prefix is stripped, so `amd-mi300x` displays as `MI300X` |
| Vendor icon inside a spec | The small icon on the spec label | **Supported**: maps to the AMD icon |
| Accelerator card label inside a spec | The GPU / NPU / DCU wording on the label | **Generic path**: no AMD-specific label, it displays as `GPU` |
| Vendor dropdown on a spec | Choosing the vendor when creating a spec | **Registered**: `AMD` appears in the dropdown |
| Cluster scheduling component | Cluster Management → Operations → System Apps | **Missing**: the platform bundles only the NVIDIA and Ascend sets |

## What works today

- **Image metadata**: tag an image as ROCm when uploading or registering it, and search and filtering pick it up.
- **Model metadata**: select a specific MI model on a model card, next to the models from other vendors.
- **Resource specs**: create specs against the resource name an AMD node reports. The spec name renders in the form `MI300X*1 . 8CPU . 64Gi` and carries the AMD icon.
- **Compute scheduling**: as long as the AMD device plugin is installed on the node and reports `amd.com/gpu`, platform-side quotas, specs and job requests all work against that resource name.

## What does not work yet

| Missing capability | Impact | How to fill the gap |
| --- | --- | --- |
| One-click install of cluster components | The components cannot be installed from System Apps | Install the official GPU Operator by hand, as described in [Kubernetes components](/ecosystem/amd/k8s-components) |
| Vendor-specific accelerator card label | The spec label shows the generic `GPU` instead of `AMD` | A platform display-layer decision, scheduling is unaffected |
| Partitioning templates | The platform only has slicing templates for Huawei NPUs, none for GPUs | Partitioning is pushed down by the GPU Operator's DCM and does not go through the platform |
| Pre-built monitoring dashboards | GPU metrics have to be wired into Prometheus by hand | Create a ServiceMonitor to scrape port 5000 |

## Full manual onboarding sequence

There is no AMD entry in the platform's System Apps, so all four steps happen outside the cluster:

1. Install the `amdgpu` driver and ROCm on every machine that has a card, until `rocminfo` lists them.
2. Install `amd-container-toolkit` on the same machines. If the cluster runs containerd, generate the device spec through CDI.
3. Install the AMD GPU Operator in the cluster from the official Helm chart, and confirm `amd.com/gpu` appears on the nodes.
4. Back on the platform, create resource specs and quotas against that resource name, then submit a job asking for one card to check the whole path.

Step 4 is the only one that touches the platform UI; the first three all happen on the cluster side.
