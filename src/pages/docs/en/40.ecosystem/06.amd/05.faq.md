# FAQ

## Quick reference

| Symptom | Check first | What to do |
| --- | --- | --- |
| `rocminfo` reports no devices | Whether the current account is in the `render` and `video` groups | Add the groups or switch to udev rules, then reboot |
| `rocminfo` reports the module not loaded | Whether the kernel driver is installed | Reinstall following the Instinct data centre driver documentation |
| The host sees the card, the container does not | Which container toolkit route is in use | With containerd in the cluster, generate `/etc/cdi/amd.json` through CDI |
| `--runtime=amd` is set but the container will not start | Whether the container runtime is Docker | That runtime is valid under Docker only; containerd takes CDI |
| No `amd.com/gpu` on the node | Device plugin Pod status and logs | Confirm the driver and container toolkit are both fine, then restart the plugin |
| A job gets a card but fails immediately on a missing library | The ROCm version inside the image | Switch to an image matched to the host driver |
| Several `amd.com/...` resource names on the node | The device plugin naming strategy | The `mixed` strategy is in use, so specs and quotas have to be created against the matching names |
| The spec label reads `GPU` instead of AMD | Platform display logic | Expected behaviour, scheduling is unaffected |
| Multi-card jobs queue for a long time | Whether resources are held by whole-card allocations | The platform has no in-card splitting, so jobs are queued by card count |
| Wanting to split a card by memory | Whether HAMi has been introduced | Go through [HAMi](/ecosystem/hami): the keys are `amd.com/gpumem` and `amd.com/gpucores`, with HAMi's `amd-device-plugin` as the device plugin |
| Wanting to select nodes by model | Whether node labels are present | Install the Node Labeller and schedule by model label |

## Why is there no place on the platform to install AMD components?

System Apps on the platform bundles only the NVIDIA and Ascend hardware scheduling component sets. AMD cluster
components have to be installed by hand from the official GPU Operator. This is not a configuration problem but the
current product boundary; see [Platform support](/ecosystem/amd/platform-support).

## Containers cannot see the cards, but the host is fine

Nine times out of ten the container toolkit route was chosen wrongly. AMD offers two:

- **CDI**: `amd-ctk cdi generate` writes a device spec file that the runtime reads. Docker, Podman and containerd all support it.
- **AMD container runtime**: registers `--runtime=amd`, and **only Docker accepts that argument**.

Cluster nodes usually run containerd, so the CDI route is mandatory there. The check is simple: look at whether the
default runtime in `docker info` is `runc`, and whether the cluster's `RuntimeClass` objects mention AMD. If neither
does, go with CDI.

Once the spec exists, the official command validates it:

```bash
sudo amd-ctk cdi validate --path=/etc/cdi/amd.json
```

## How do I read the driver version and the ROCm version?

```bash
amd-smi version
```

This prints three lines at once: tool version, ROCm version and `amdgpu` driver version. From ROCm 7.0 the driver and
the user space are two independent version sequences, **so the ROCm version cannot be used to work out the driver
version**; check compatibility against AMD's official Compatibility matrix.

## Do components have to be stopped before upgrading the driver?

Yes. Stop the workloads first, then the cluster-side device plugin and metrics exporter, and only then touch the driver.
The device plugin calls driver interfaces on a timer, and upgrading underneath it tends to leave a state where the
plugin runs but reports the wrong device count, recoverable only by restarting the plugin.

## Is in-card splitting the same thing as MIG?

No. AMD compute partitioning splits one card into physical partitions used in parallel, and the granularity and mode
names (SPX / DPX / QPX / CPX) depend on the card model; NVIDIA MIG is a different implementation. Neither provides fault
isolation across partitions. Where fine-grained splitting by memory proportion is needed and a shared fault domain is
acceptable, go through [HAMi](/ecosystem/hami): since v2.10.0 it lists AMD Instinct / ROCm as stable, slicing memory
in 1 MiB units and compute in 1% units. That requires switching to HAMi's device plugin and disabling the AMD GPU
Operator's own device plugin. The shared fault domain applies on HAMi as well.
