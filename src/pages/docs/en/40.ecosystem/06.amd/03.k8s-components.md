# Kubernetes Components

The cluster side ships as one bundle called the **AMD GPU Operator**. It belongs to the same family as the GPU Operator
on the NVIDIA side: device plugin, node labeller, metrics exporter and driver management packaged together and
installed from a single Helm chart.

| Component | Purpose | What breaks without it |
| --- | --- | --- |
| Device Plugin | Registers the cards as Kubernetes resources | A node without `amd.com/gpu`, and jobs that cannot request a card |
| Node Labeller | Puts card model, memory and similar labels on nodes | Nothing to select nodes by when scheduling on card model |
| Metrics Exporter | Exposes GPU metrics | Card utilisation and temperature missing from platform monitoring |
| DCM (device-config-manager) | Applies compute partitioning profiles | Cards stay on their factory partitioning mode |
| NFD / KMM | Node feature discovery and kernel module management | The base the components above sit on, normally installed alongside them |

## Installation

The official repository carries the Helm chart, and the CRD is `DeviceConfig` (`amd.com/v1alpha1`):

```bash
helm repo add rocm https://rocm.github.io/gpu-operator
helm repo update
```

:::warning Chart name and configurable fields follow the repository README
The AMD GPU Operator chart name appears in abbreviated form in the repository README, and the namespace and values
structure are adjusted between versions. Open the repository page and check before installing rather than copying an
example from somewhere else.
:::

## Resource names reported by the device plugin

By default it reports one whole-card resource:

```
amd.com/gpu
```

This is the same scheme as `nvidia.com/gpu` on the NVIDIA side: **ask for as many cards as the value says**:

```yaml
resources:
  limits:
    amd.com/gpu: 2
```

The device plugin has a `--resource_naming_strategy` switch, and different values report different resource names:

| Value | Resource names reported | When to use it |
| --- | --- | --- |
| `single` (default) | Only `amd.com/gpu` | Whole-card scheduling only, the simplest case |
| `mixed` | One per partitioning mode, for example `amd.com/spx_nps1`, `amd.com/cpx_nps4` | One cluster has to schedule jobs under different partitioning modes |

After switching to `mixed`, several resource names appear on the node, and **specs and quotas have to be created
against the matching names**, otherwise jobs cannot be admitted.

## Monitoring

Metrics come from the **AMD Device Metrics Exporter** in Prometheus format:

| Item | Value |
| --- | --- |
| Exporter listen port | 5000 |
| Metrics path | `/metrics` |
| GPU Agent port | 50061 |
| How it joins platform monitoring | Create a ServiceMonitor and let the Prometheus Operator scrape it |

This port differs from the 9400 used on the NVIDIA side, so a shared monitoring dashboard cannot use one port for both.

## Compute partitioning

Partitioning on this generation of AMD cards is **Compute Partitioning** combined with **Memory Partitioning (NPS)**,
and the two together form several modes:

| Mode | Meaning |
| --- | --- |
| SPX | One whole card, no split |
| DPX | Split in two |
| QPX | Split in four |
| CPX | Split in eight (model dependent) |

MI300A is an APU, so its mode set is different: SPX / TPX / CPX.

Applying a mode is not a matter of changing the card by hand. **The GPU Operator's DCM pushes the profile down**, and
the node carries the matching label:

```bash
kubectl label node <gpu-node> dcm.amd.com/gpu-config-profile=<profile>
```

:::warning Partitioning is not hard isolation
AMD compute partitioning lets the partitions of one card run different jobs in parallel. **It is not an instance with
its own memory and fault isolation in the way NVIDIA MIG is.** Where strong isolation is required, confirm first that
the workload accepts a shared fault domain.
:::

## Relationship to the scheduler

Multi-card jobs on the platform are scheduled by Volcano. AMD **ships no official Volcano plugin**, so the generic path
applies: the device plugin reports the cards as standard extended resources, and Volcano schedules by resource name and
count. That means:

- Multi-card jobs schedule because of the standard extended resource mechanism.
- Scheduling by card partition and allocating memory proportionally **is outside the official support range of the
  Volcano plugin** and requires HAMi. Since v2.10.0 HAMi lists AMD Instinct / ROCm as stable, using the resource
  keys `amd.com/gpumem` (MiB) and `amd.com/gpucores` (a percentage) with HAMi's `amd-device-plugin` as the device
  plugin. This is a separate route running alongside the platform's built-in Volcano vGPU, see
  [HAMi](/ecosystem/hami) for the detail.

## Verifying the install

```bash
# allocatable AMD resources now exist on the node
kubectl describe node <gpu-node> | grep -A 5 "Allocatable" | grep amd.com

# the device plugin Pod is up
kubectl get pods -A | grep -i amd

# the monitoring port answers
kubectl get svc -A | grep -i metrics-exporter
```

Then submit a minimal job that asks for one card; if `amd-smi` prints the card inside the container, the path works.
