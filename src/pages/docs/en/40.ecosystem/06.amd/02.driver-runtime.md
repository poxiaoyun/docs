# Drivers & Container Runtime

This page stays on the host layer and does not involve Kubernetes. Cluster-side components are covered in
[Kubernetes components](/ecosystem/amd/k8s-components).

Two checks mark the end of this work: `rocminfo` lists the cards, and `amd-smi` reports the driver and ROCm versions.
Fail either one and every cluster component installed afterwards is wasted effort.

## Prerequisites

| Item | Requirement |
| --- | --- |
| Operating system | A distribution matched to the target ROCm version, commonly Ubuntu 22.04 / 24.04 / 26.04, RHEL or CentOS 9, SLES |
| Kernel driver | `amdgpu`. Instinct driver installation follows different documentation from Radeon; use the Instinct data centre docs |
| Extra libraries | Some ROCm tools depend on `libatomic1` and `libquadmath0` |

```bash
sudo apt install libatomic1 libquadmath0
```

## Device permissions

By default, only members of the `video` and `render` groups can reach the GPU device nodes. The account that runs
workloads and the account that runs containers both have to be added:

```bash
sudo usermod -a -G render,video $LOGNAME
```

If group-based management is not wanted, udev rules open the nodes directly instead:

```bash
sudo tee /etc/udev/rules.d/70-amdgpu.rules << EOF
KERNEL=="kfd", GROUP="render", MODE="0666"
SUBSYSTEM=="drm", KERNEL=="renderD*", GROUP="render", MODE="0666"
EOF

sudo udevadm control --reload-rules
sudo udevadm trigger
```

Pick one of the two. Permission changes need a reboot before they take effect. **With permissions misconfigured, the
symptom is `rocminfo` running but reporting no devices**, which is easily mistaken for a driver that was never
installed.

## Install ROCm

On Ubuntu through apt, register the repository first and then install a meta package:

```bash
sudo mkdir --parents --mode=0755 /etc/apt/keyrings
wget https://stable.repo.amd.com/rocm/gpg/packages.gpg -O - | \
    gpg --dearmor | sudo tee /etc/apt/keyrings/amdrocm.gpg > /dev/null

sudo tee /etc/apt/sources.list.d/amdrocm-stable.sources << EOF
X-Repo-Id: amdrocm-stable
Types: deb
URIs: https://stable.repo.amd.com/rocm/core/packages/ubuntu2604/
Suites: stable
Components: main
Architectures: amd64
Signed-By: /etc/apt/keyrings/amdrocm.gpg
Enabled: yes
EOF

sudo apt update
sudo apt install amdrocm10.0
```

The `ubuntu2604` in the repository URL is a distribution codename, and that segment changes with the operating system.

ROCm is split into several meta packages. Which one to install depends on what the machine is for:

| Meta package | Purpose | Contents |
| --- | --- | --- |
| `amdrocm<version>` | Running applications only | Runtime, libraries, system monitoring tools |
| `amdrocm-core-dev<version>` | Building applications | The above plus compilers, headers, CMake configuration |
| `amdrocm-developer-tools<version>` | Performance profiling | Profilers and related tools |
| `amdrocm-opencl<version>` | Running OpenCL applications | OpenCL components |
| `amdrocm-core-sdk<version>` | Everything | The complete SDK |

:::warning Follow the official install guide for commands
ROCm package names carry a version (`amdrocm10.0`), so a version change means a package name change, and the repository
path moves with the distribution. The commands above are here to show the shape of the process. Before running them on
a real machine, open the official Install on Linux page and replace the package names and repository URLs with the
current ones.
:::

## Verify the driver

```bash
rocminfo
```

Seeing `ROCk module version ... is loaded` plus the cards listed under HSA Agents means the driver is in place.

```bash
amd-smi version
```

This prints `AMDSMI Tool`, `ROCm version` and `amdgpu version` on three lines. **Keep all three when troubleshooting**:
the first question anyone asks about a problem report is the driver version.

## Container runtime toolkit

Workloads in the cluster run in containers, so the host recognising the card is not enough; the containers have to get
the device as well. On the AMD side this layer is the **AMD Container Toolkit**, and installing it brings two things:
`amd-container-runtime` (an OCI runtime) and `amd-ctk` (the command line used for configuration).

```bash
sudo apt update && sudo apt install -y wget gnupg2
wget https://repo.radeon.com/rocm/rocm.gpg.key -O - | gpg --dearmor | sudo tee /etc/apt/keyrings/rocm.gpg > /dev/null
echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/rocm.gpg] https://repo.radeon.com/amd-container-toolkit/apt/ $(. /etc/os-release && echo $VERSION_CODENAME) main" | sudo tee /etc/apt/sources.list.d/amd-container-toolkit.list
sudo apt update && sudo apt install amd-container-toolkit
```

Two configuration routes follow, and **the choice follows whichever container runtime the cluster uses**; pick the
wrong one and containers never see the cards:

| Route | How it is configured | Container runtimes it suits |
| --- | --- | --- |
| CDI | `amd-ctk cdi generate` writes the device spec, and the runtime reads it | Docker, Podman and containerd all work |
| AMD runtime | `amd-ctk runtime configure` registers `--runtime=amd` | **Docker only** |

Platform clusters run containerd, so **take the CDI route**:

```bash
sudo amd-ctk cdi generate --output=/etc/cdi/amd.json
sudo amd-ctk cdi validate --path=/etc/cdi/amd.json
```

A Docker environment registers the runtime and restarts instead:

```bash
sudo amd-ctk runtime configure --runtime=docker --set-as-default
sudo systemctl restart docker
```

## Verify that containers can see the cards

```bash
docker run --rm --device amd.com/gpu=all rocm/rocm-terminal rocm-smi
```

A card list printed inside the container means this layer is working. To select a card by index, list them first and
then name one:

```bash
amd-ctk gpu list
docker run --rm --device amd.com/gpu=0 rocm/rocm-terminal rocm-smi
```

:::info Environment requirements of the container toolkit
AMD Container Toolkit officially requires Ubuntu 22.04 / 24.04 / 26.04 or RHEL/CentOS 9, and Docker 25 or later.
`amd-ctk runtime configure` has to run as root or through sudo. Docker Desktop on Linux is outside the supported range.
:::

## Removal and upgrade

```bash
sudo apt autoremove amdrocm10.0
sudo rm -f /etc/apt/sources.list.d/amdrocm-stable.sources
```

Stop the workloads before upgrading, and stop the cluster-side device plugin before touching the driver. The device
plugin reads driver interfaces on a timer, and upgrading underneath it tends to leave a state where the plugin is
running but reporting the wrong device count.
